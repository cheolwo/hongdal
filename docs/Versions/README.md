# Version Configuration Management

Ssalddel은 소스 프로젝트를 버전별 폴더로 복제하지 않습니다. 실행 코드는 앱/도메인 경계에 따라 유지하고, 버전별 형상은 문서, 브랜치, 태그, 마이그레이션, 노출 정책으로 관리합니다.

## 현재 릴리즈와 통합 구축

공개 운영 기반은 커뮤니티 `0.0`입니다. 첫 공개 릴리즈 판단은 운송 모듈 없이도 `글쓰기 → 참여 의사 → 가원장 → 역할 슬롯 → 당사자 합의 → 완료 사례` 흐름을 완성하는지에 둡니다.

구축 순서는 `0.0`을 모두 끝낸 뒤 다음 버전으로 이동하는 직렬 방식으로 제한하지 않습니다. [통합 구축 로드맵](./integrated-build-roadmap.md)에 따라 전체 페이지를 하나의 제품 지도로 관리하고, 아홉 워크플로우에서 조회·영속 작성·상태 전이·인계를 한 단계씩 순환해 완성합니다. 버전별 체크리스트와 [릴리즈 게이트](./release-gates.md)는 실제 운영 노출과 외부 효과를 허용하는 기준으로 계속 사용합니다.

`0.0` 커뮤니티 기반에 직접 도움이 되지 않는 기능은 다음 원칙을 따릅니다.

- 구현되어 있어도 기본 노출하지 않습니다.
- 운영 플래그 기본값은 `false`로 둡니다.
- 대화, 참여, 원장, 개인정보 동의, 신고와 신뢰 기록의 흐름을 깨면 안 됩니다.
- 새 작업은 먼저 [v0.0 체크리스트](./v0.0/checklist.md)에 영향을 주는지 확인합니다.

## 원칙

| 원칙 | 설명 |
| --- | --- |
| 소스는 역할별로 유지 | `DriverApp`, `SsalddelApp`, `WarehouseManagerApp`, `Ssalddel`, `Ssalddel.Domain` 같은 프로젝트 구조를 버전 때문에 나누지 않습니다. |
| 버전은 관리 단위로 사용 | 각 버전 폴더는 목표, 포함 범위, 보류 범위, 관련 앱/모듈, DB 변경, 릴리스 체크리스트를 기록합니다. |
| 브랜치로 안정화 | 실제 코드 안정화는 `release/0.0`, `release/1.0`, `release/1.5`, `release/2.0`, `release/2.5`, `release/3.0`, `release/3.5` 브랜치에서 관리합니다. |
| 태그로 기준점 고정 | 배포 또는 검증 가능한 기준점은 `v0.0.0`, `v1.0.0`, `v1.5.0`, `v2.0.0`, `v2.5.0`, `v3.0.0`, `v3.5.0` 태그로 남깁니다. |
| 기능 노출은 버전 정책을 따름 | 구현되어 있어도 해당 버전 범위가 아니면 기본 UI 노출이나 운영 플래그를 끕니다. |
| 마이그레이션은 역방향 영향을 점검 | 다음 버전의 DB 테이블이나 설정이 이전 버전 운영 흐름을 깨지 않게 관리합니다. |
| 설정도 버전별로 묶음 | Admin/User 기능 설정은 버전 그룹을 함께 표시해 현재 릴리즈 기능과 확장 기능을 분리해서 관리합니다. |

## 폴더 사용법

각 버전 폴더는 다음 내용을 유지합니다.

- `README.md`: 버전 목표와 포함/보류 범위
- `checklist.md`: 릴리스 전 확인 목록
- `migration-notes.md`: DB, 설정, 운영 데이터 변경 기록
- `scope.md`: 기능별 포함 여부와 관련 앱/모듈

새 기능을 추가할 때는 먼저 이 기능이 어느 워크플로우와 페이지 capability 단계에 속하는지 판단하고, 도입 버전 폴더의 `scope.md` 또는 `checklist.md`와 통합 구축 로드맵에 미치는 영향을 확인한 뒤 구현합니다.
