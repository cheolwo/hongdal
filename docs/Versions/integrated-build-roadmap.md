# 통합 구축 로드맵

이 문서는 이미 존재하는 여러 버전과 역할별 앱을 한 제품으로 확장하는 실제 개발 순서를 정한다. `0.0`부터 `1.5`까지의 제품군 이름은 문화교통이며, `0.0`은 공개 운영 기반이고 현재 제품 집중 버전은 `문화교통 1.5 공급·가격·무역 준비`다. 제품 인계 순서는 `문화교통 1.0 공동구매 → 문화교통 1.5 공급·무역 준비 → 2.0 운송 → 2.5 창고·판매 이행`으로 유지한다. 구현은 한 버전을 모두 끝낸 뒤 이동하는 방식이 아니라, 이 순서를 침범하지 않는 범위에서 아홉 워크플로우의 최소 작동 루프를 차례로 닫는다.

## 두 개의 독립 축

| 축 | 판단 기준 |
| --- | --- |
| 제품 버전 | 기능이 처음 도입된 시점, 선행 의존성, 릴리즈 게이트 |
| 페이지 capability | 현재 환경에서 조회·저장·상태 전이·외부 실행 중 어디까지 가능한지 |

기능 플래그는 페이지와 API의 노출 가능성을 정한다. 실제 외부 효과는 전역 `SsalddelExecution:Mode`가 정한다. 기능 플래그가 켜져 있어도 `Simulation`에서는 자동 배차, 계약 확정, 실결제, 실정산, 실제 보관과 외부 신고를 실행하지 않는다.

## 공통 완성 단계

| 단계 | 최소 조건 |
| --- | --- |
| 준비 중 | 라우트와 책임은 식별되지만 실제 업무 입력을 받지 않는다. |
| 체험 | 교체 가능한 샘플 또는 세션 데이터로 화면과 연결 구조를 확인한다. |
| 베타 | Controller API를 통해 조회·저장하고, 새로고침과 서버 재시작 뒤에도 같은 원장을 읽는다. 인증, 빈 상태, 오류, 재시도를 제공한다. |
| 운영 | 권한, 개인정보, 감사, 복구, 멱등성, 브라우저 E2E와 운영 절차를 통과한다. 외부 효과는 별도 승인과 `Operational` 모드가 필요하다. |

단계 표시는 임의의 화면 문구가 아니라 `SsalddelPageCapabilityCatalog`와 `GET /api/v1/version-feature-flags`의 `PageCapabilities`를 기준으로 한다.

## 우선순위

### P0. 페이지 기준 원장

다른 기능을 넓히기 전에 화면과 운영 경계를 추적할 기반을 만든다.

1. 전체 Razor 페이지와 `@page` 라우트를 앱별로 자동 발견한다.
2. `(AppCode, RouteTemplate)`을 페이지 소유 식별자로 사용하고 중복 소유를 테스트한다.
3. 대표 라우트 계열에 단계, 도입 버전, 워크플로우, 기능 플래그, 인증, 외부 효과 여부를 부여한다.
4. 통합 WebApp과 서버 메타데이터가 같은 capability catalog를 사용한다.
5. 관리자 검토 상태를 프로세스 메모리가 아닌 서버 영속 저장소로 옮긴다.
6. 전문 앱의 모든 라우트를 같은 catalog로 확장한다.

현재 기준선은 10개 UI 프로젝트, 233개 Razor 페이지 파일, 260개 라우트다. 이 수치는 기능을 제한하는 상한이 아니라 의도하지 않은 누락을 발견하는 회귀 기준이다.

### P1. 각 워크플로우의 실제 조회

각 워크플로우에서 대표 허브·목록·상세 하나를 샘플 fallback 없이 서버에 연결한다.

1. 커뮤니티 신뢰: 음식·재료와 게시글 → 참여 동의·공동 원장
2. 공동구매: 모집·비구속 수요 → 서버 집단화 → 같은 공동 원장
3. 공급·무역 준비: 공급자·견적·HS 검토 목록 → 검토 상세
4. 국내 화물 운송: 확인된 원장 → 운송 의뢰 상세 → 화주·관리자 동일 ID 조회
5. 창고 입출고: 입고 예정 → 작업 보드
6. 판매채널 출고: 채널·주문 목록 → 출고 후보
7. 참여 인력 관리: 역할 지원 → 검토 목록
8. 음식 배달: 음식점·메뉴 → 주문 상세
9. 알뜰살뜰 마트: 상품·주문 → 피킹 작업

### P2. 각 워크플로우의 영속 작성

P1과 같은 순서로 업무마다 작성 하나를 완성한다. 서버 검증, 멱등성, 저장 후 재조회, 실패 시 샘플 성공으로 위장하지 않는 것이 공통 조건이다.

### P3. 서버 검증 상태 전이

업무마다 한 개의 상태 전이를 완성한다. 클라이언트는 서버 성공 응답 뒤 원장을 다시 조회한다. 상태 변경 Event, 감사와 필요한 Outbox를 함께 검증한다.

### P4. 워크플로우 인계

1. 음식·재료 탐색 → 비구속 공동구매 수요
2. 공동구매 원장 → 공급·가격·HS 준비 원장
3. 확정된 구매·출고 필요 → 운송 의뢰 초안
4. 운송 완료 → 창고 입고 또는 주문자 배분 인계
5. 판매 주문 → 창고 출고 → 운송 인계
6. 음식·마트 준비 완료 → 기사 배송 Simulation
7. 완료 활동 → 공개 동의를 받은 커뮤니티 신뢰 신호

자동 전환은 하지 않는다. 관심, 참여, 연락처 공개, 원장 전환과 실행은 각각 명시적인 동의 상태를 가진다.

### P5. 운영 강화

권한, 개인정보 최소화, 속도 제한, 감사, 백업·복구, Outbox 재처리, 모바일·데스크톱 검증을 완료한다. 외부 결제·계약·배차·정산은 관련 릴리즈 게이트와 별도 운영 승인을 통과할 때까지 비활성으로 유지한다.

## 작업 방식

- 동시에 진행하는 세로 흐름은 하나로 제한한다.
- 한 흐름은 `Contract → Controller API → UseCase/Command → DB/Event → 공용 UI → 브라우저 검증`까지 닫는다.
- 한 워크플로우를 운영 단계까지 몰아서 개발하지 않고, P1 조회를 전체에 한 바퀴 적용한 뒤 P2 작성으로 이동한다.
- `Ssalddel.WebApp`은 통합 브라우저 셸로 사용하고 공용 화면·ViewModel은 `Ssalddel.Ui.Common`에 둔다. 역할별 앱은 삭제하지 않고 장치·역할 adapter로 유지한다.
- 검증 환경에서는 `ClientDataMode.AllowSampleFallback=false`로 실제 서버 실패가 드러나게 한다.

## 바로 이어갈 세로 흐름

현재 세로 흐름은 `한국 음식·재료 탐색 → 비구속 수요 등록 → 서버 집단화 → 사람 인계 승인 → 공급자·견적·원가·HSK/HTS·국가별 검토 원장 → 원천 OS 대상원장 연결`이다. 이를 `1.5`의 기술 완성 단위로 두고 결제·계약·통관 신고·운송 실행은 넘지 않는다.

아래의 2026-07-20 운송 수직 흐름 기록은 이미 구현된 기술 자산의 완료 이력이다. 제품 우선순위를 뜻하지 않으며 해당 기능은 이제 `2.0` 운송 단계로 분류한다.

2026-07-20 기준으로 첫 단계인 `커뮤니티 화물 글 → /shipper/request 초안`을 완료했다. 사용자가 화물 글 상세에서 직접 가져오기를 선택해야 하며, 제목·본문만 비파괴적으로 합치고 주소·연락처·수량·운임은 자동 추출하지 않는다. 초안은 새로고침 뒤 복구되고 같은 글을 중복 반영하지 않는다. `DomesticTransportWorkflow`가 비활성인 환경에서는 서버 등록 버튼을 잠그고 초안 작성·저장만 허용한다.

2026-07-20 기준으로 두 번째 단계인 `/shipper/request/{id}` 재조회를 완료했다. 서버 등록이 성공하면 생성 응답의 같은 의뢰 ID 상세로 이동해 다시 조회하고, 직접 ID를 입력하는 `/shipper/request/detail` 진입점도 제공한다. 예시 ID fallback은 제거했으며 로그인, 소유자·관리자 조회 권한, 기능 플래그 비활성, 조회 실패와 재시도 상태를 화면에 분리했다. 상세 조회만으로 자동 배차·계약 확정·실결제가 실행되지 않는다는 경계도 표시한다.

2026-07-20 기준으로 세 번째 단계인 관리자 `/requests` 목록 연결을 완료했다. 서버관리자 권한과 `DomesticTransportWorkflow`를 확인한 뒤 최근 의뢰를 조회하고, 의뢰 ID 부분 검색과 결제·배차 상태 조건, 오류·재시도·빈 상태를 제공한다. 목록의 상·하차지는 전체 도로명·번지 대신 권역만 표시하며, 같은 의뢰 ID의 관리자 상세와 관제 화면으로 이동한다. 개발 메모리 데이터는 명시적인 샘플 경계로 구분한다.

2026-07-20 기준으로 네 번째 단계인 관리자 `/requests/{RequestId}` 상세 보완을 완료했다. 서버관리자 권한과 `DomesticTransportWorkflow`를 상세 진입 시 다시 확인하고, 기본 화면에는 상·하차 권역만 표시하며 상세 주소와 정밀 좌표는 관리자가 업무상 필요할 때 직접 펼쳐 확인한다. 취소·환불은 운송 시작 전 상태에서만 허용하고 사유와 의뢰 ID 재입력을 클라이언트와 서버에서 모두 검증한다. 서버 성공 뒤 같은 의뢰를 다시 조회하며, `Simulation`에서 의뢰·결제·정산·배차 투영과 감사 이벤트를 한 번에 기록한다. 외부 PG를 호출하지 않으며 `Operational` 모드에서는 실제 환불 연동이 준비되기 전 실행을 거부한다.

이로써 첫 통합 인계인 `커뮤니티 화물 글 → 운송 의뢰 초안 → 화주 동일 ID 재조회 → 관리자 목록·상세 확인`을 닫았다.

2026-07-20 기준으로 P1 창고 흐름의 첫 페이지인 창고관리자 `/warehouse/inbounds/expected` 입고 예정 조회를 완료했다. 토큰 세션 저장·만료·갱신, 로그인 API, 창고 역할 판단, 페이지 capability 확인, 입고 예정 조건 고정과 표시 문구를 각각 분리하고 PageViewModel은 인증 후 창고 조회·선택·목록 갱신만 조정한다. 샘플 fallback 없이 보호 API의 서버 페이징 목록을 사용하며, 기능 비활성·로그인·역할 거부·로딩·창고 없음·목록 없음·오류·재시도 상태를 제공한다. 행을 선택하면 같은 `inboundId`를 `/work-board?inboundId={id}`로 전달한다. 개발용 `shipper1`에는 기존 보안 역할과 일치하는 전역 `Warehouse.Manager` HR 세부 역할을 멱등 시드한다. 이 페이지는 capability catalog에서 인증이 필요한 `Beta/ReadOnly`로 기록하며, 조회만으로 실제 보관·계약·정산 효과는 발생하지 않는다.

2026-07-20 기준으로 P1 창고 흐름의 두 번째 페이지인 창고관리자 `/work-board`를 완료했다. `inboundId` query를 받아 `GET /api/v1/warehouse-operations/inbounds/{inboundId}`로 같은 입고 요청을 다시 조회하며, 서버는 요청자·창고 소유자·배정 사용자 범위 밖의 ID를 존재하지 않는 ID와 동일하게 404로 처리한다. 정적 작업 카드와 샘플 피킹 조회를 제거하고 페이지 조정, 단건 조회, 서버 상태 해석을 각각 PageViewModel·공용 상세 ViewModel·순수 정책으로 분리했다. 기능 비활성·로그인·HR 역할 거부·선택 없음·로딩·대상 없음·API 오류·재시도 상태를 제공하고, 입고 예정·운송 중·완료·취소 상태별 다음 행동을 안내한다. 이 페이지는 인증이 필요한 `Beta/ReadOnly` capability이며 검수·적재·실제 보관·정산 상태 전이는 실행하지 않는다.
