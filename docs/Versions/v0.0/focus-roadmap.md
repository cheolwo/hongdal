# Ssalddel 1.0 집중 로드맵

이 경로는 기존 작업 링크와 `AGENTS.md` 호환을 위해 유지합니다. `0.0` 커뮤니티·공공데이터 기반은 계속 운영 기반으로 보존하되, 현재 제품 개발 집중 버전은 **`1.0 공동구매·주문자 집단화`**입니다.

## 제품 순서

```text
0.0 커뮤니티·공공데이터 기반
  → 1.0 공동구매·주문자 집단화 ← 현재 집중
  → 1.5 공급·가격·무역 준비
  → 2.0 국내 화물·운송 이행
  → 2.5 창고·판매 이행
```

운송 능력을 먼저 확장하지 않습니다. 실제 수요 집단과 구매·출고 조건이 확인된 뒤에만 운송 단계로 인계합니다.

## 한 줄 목표

> 사용자가 여러 나라의 음식과 재료를 탐색하다 구매 의향을 남기면, 서버가 품목·지역·수령 조건별로 주문자를 안전하게 모아 비구속 공동구매 모집으로 보여 줍니다.

## 현재 세로 흐름

```mermaid
flowchart LR
    A["음식 탐색"] --> B["재료·기업·HS 참고"]
    B --> C["비구속 수요 등록"]
    C --> D["집단화 미리보기"]
    D --> E["주문자 집단·모집 원장"]
    E --> F["공급 조건 협의"]
    F --> G["1.5 준비 원장 인계"]
```

사용자는 탐색 문맥을 잃지 않고 한 여정 안에서 이동해야 합니다. 단일 페이지 원칙은 모든 기능을 한 컴포넌트에 넣는다는 뜻이 아니라, 음식 → 재료 → 수요 → 집단 상태가 하나의 주 화면과 stable ID로 이어지고 세부 책임은 독립 컴포넌트·ViewModel·API로 나뉜다는 뜻입니다.

## 서버 집단화 책임

서버는 다음을 담당합니다.

1. 사용자가 명시적으로 제출한 비구속 수요를 사용자 소유 범위로 저장합니다.
2. 상품·재료 키, 희망 수량, 지역·수령 범위, 온도·시간창 같은 이행 조건을 정규화합니다.
3. 같은 입력에 같은 결과가 나오도록 결정적 집단화 규칙과 미리보기를 제공합니다.
4. 기존 집단 참여, 새 집단 후보, 조건 불일치와 보류 이유를 설명합니다.
5. 중복 요청을 멱등 처리하고 수요 변경·철회를 집계에 반영합니다.
6. 공개 응답에는 참여자 수와 합계만 제공하고 개인 주소·연락처·결제 정보를 숨깁니다.
7. 목표 수량과 검토 조건을 충족한 집단만 `1.5` 준비 원장 후보로 넘깁니다.

서버가 하지 않는 일은 다음과 같습니다.

- 국적, 언어, 인종, 성별 등 비관련 속성에 따른 배제·순위·가격 차별
- 사용자의 명시적 참여 없이 자동 가입
- 주문·결제·매매 계약·수입 신고 확정
- 공급자·수입자·관세사·운송사·창고 자동 선정
- 자동 배차, 운임 수취, 대금 보관과 정산

## 집단화 최소 키

| 구분 | 예시 | 공개 여부 |
| --- | --- | --- |
| 상품 문맥 | 음식·재료·상품 stable key, 규격 | 공개 가능 |
| 수요 | 희망 수량, 허용 가격 범위, 참여 상태 | 집계 공개, 개인값 보호 |
| 지역 | 국가, 우편번호 권역, 생활권·수령 지점 후보 | 권역만 공개 |
| 이행 조건 | 상온·냉장·냉동, 수령 방식, 희망 시간창 | 공개 가능 |
| 출처 | MFDS 등 원자료, 기업 조사 출처, 확인 시각 | 공개 가능 |
| 식별 정보 | 사용자 ID, 상세 주소, 연락처 | 서버 보호 |

HS·HTS는 `1.0`에서 탐색 참고값으로 연결할 수 있지만, 분류 후보 검토와 수입 준비 상태는 `1.5`가 소유합니다.

## 기준 실행 설정

개발 검증 환경:

```text
CommunityTrustWorkflow=true
GroupPurchaseDemandWorkflow=true
CustomsAndTradeDataWorkflow=false
DomesticTransportWorkflow=false
WarehouseFulfillmentWorkflow=false
SalesChannelFulfillmentWorkflow=false
FoodDeliveryWorkflow=false
SsalddelMartWorkflow=false
SsalddelExecution:Mode=Simulation
```

운영 환경은 별도 승인 전 `GroupPurchaseDemandWorkflow=false`를 기본으로 유지할 수 있습니다. 기능 플래그가 켜져도 `Simulation`에서는 결제·계약·신고·배차·정산을 실행하지 않습니다.

## 현재 진행 순서

| 순서 | 단계 | 목표 | 완료 판단 |
| --- | --- | --- | --- |
| 1 | `1.0-A` 탐색 연결 | 음식·재료 상세에서 공동구매 진입 | 원출처와 선택한 재료 문맥이 보존됨 |
| 2 | `1.0-B` 비구속 수요 | 등록·변경·철회와 본인 조회 | 멱등 저장, 소유권, 오류·재시도 검증 |
| 3 | `1.0-C` 서버 집단화 | 미리보기와 배치 규칙 | 같은 입력은 같은 배치와 이유를 반환 |
| 4 | `1.0-D` 모집 원장 | 공개 집계·목표·상태·협의 | 개인정보 없이 같은 campaign ID 재조회 |
| 5 | `1.0-E` 준비 인계 | 공급 조건과 미확인 항목 정리 | `1.5` 입력 원장이 명시적으로 생성됨 |

## 1.0 릴리즈 게이트

- [x] 음식·재료 탐색에서 수요 등록까지 한 흐름으로 이어집니다.
- [ ] 수요 등록·변경·철회가 인증, 소유권과 멱등성을 검증합니다.
- [ ] 집단화 미리보기와 저장 결과가 같은 규칙을 사용합니다.
- [ ] 공개 집계에서 개인 주소·연락처·결제 정보가 노출되지 않습니다.
- [ ] 집단화 기준과 배치·보류 이유를 사용자가 이해할 수 있습니다.
- [ ] 보호되거나 비관련 속성을 집단화·가격 차별 기준으로 사용하지 않습니다.
- [ ] 결제·계약·신고·자동 배차·운임 수취·정산이 비활성입니다.
- [ ] Web과 미국 사용자 페이지가 같은 서버 계약과 stable ID를 사용합니다.
- [ ] 관련 Controller·페이지 capability가 제품 버전 `1.0`으로 표시됩니다.

## 후속 버전 처리

| 버전 | 현재 처리 |
| --- | --- |
| `1.5` | 공급자·기업 근거, 견적, 예상 총원가, HS·HTS와 수입 준비 계약을 설계하되 실제 신고·계약은 비활성 |
| `2.0` | 운송 의뢰·기사 앱·배차·증빙·정산 코드를 보존하되 현재 공동구매 흐름에서 자동 호출하지 않음 |
| `2.5` | 창고·판매채널·최종 배분 코드를 보존하되 운송·입고 조건이 확인되기 전 자동 실행하지 않음 |
| `3.0`·`3.5` | 음식 배달과 마트 즉시배송을 별도 후속 제품 경계로 유지 |

## 다음 작업을 고르는 규칙

1. 음식·재료 탐색에서 공동구매 수요까지의 끊김을 줄이는가?
2. 서버 집단화의 결정성, 멱등성, 설명 가능성과 개인정보 보호를 높이는가?
3. 참여·철회와 공개 집계를 같은 원장으로 닫는가?
4. 공급·무역·운송·창고를 자동 실행하지 않고 명시적으로 인계하는가?
5. 위 네 가지가 아니면 현재 백로그로 보냅니다.
