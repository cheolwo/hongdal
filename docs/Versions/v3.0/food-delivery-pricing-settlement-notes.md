# Ssalddel 3.0 Food Delivery Pricing and Settlement Notes

작성일: 2026-07-10

이 문서는 음식점 일반 음식 배달, RestaurantDeskApp, FDriverApp, FoodDeliveryDispatchEngine에 대한 요금과 정산 논의를 보류 메모로 남긴다. 현재 릴리즈 집중 대상은 1.0 국내 화물/용달 운송 안정화이므로, 아래 내용은 바로 운영 정책이나 코드 상수로 고정하지 않는다.

## 현재 판단

음식점 일반 배달은 주문자, 음식점, 배달 기사, 플랫폼 사이의 부담 구조가 동시에 얽힌다. 우천, 피크 시간, 심야, 장거리, 조리 지연, 묶음 배달, 월말 환급까지 함께 고려해야 하므로 1.0 용달 흐름을 닫기 전에는 실운영 정책으로 확정하지 않는다.

다만 기본 방향은 정률 중개수수료보다 정액 배달료 모델이 적합하다. 음식 주문 금액에 비례해 사장님 부담이 늘어나는 구조를 피하고, 주문자와 음식점이 배달 수행 비용을 나누어 부담하는 단순한 모델로 시작한다.

## 임시 요금 기준

| 항목 | 임시 기준 | 메모 |
| --- | ---: | --- |
| 주문자 부담 배달료 | 2,500원 | 기본 고정값 |
| 음식점 부담 배달료 | 2,500원 | 기본 고정값 |
| 주문 1건 배달료 풀 | 5,000원 | 정률 중개수수료 없음 |
| 기사 최소 지급액 | 3,500원 | 이 금액 아래로는 지급하지 않는 하한 |
| 기사 목표 지급액 | 4,500원 전후 | 평균적으로 맞추고 싶은 기준 |
| 플랫폼 목표 마진 | 500원/건 | 운영 안정 기준 |
| 플랫폼 최소 허용 마진 | 100원/건 | 손실 방어 하한 |

주문 금액이 커져도 플랫폼 수수료가 자동으로 늘어나지 않는 구조를 기본으로 둔다. 초기 설명은 "주문자 2,500원, 음식점 2,500원, 정률 수수료 없음"이 가장 명확하다.

## 기사 지급 산식

기사 지급액은 수취 배달료와 분리된 정책으로 계산한다. 최종 금액만 남기지 말고 항목별 산출 내역을 기록해야 기사 앱, 사장님 정산서, 관리자 정산 화면에서 설명 가능하다.

```text
기사 지급액 =
  max(
    기사 최소 지급액,
    기본 배달료
  + 거리 할증
  + 피크 시간 할증
  + 우천/악천후 할증
  + 심야 할증
  + 조리 지연/대기 보상
  + 멀티배차 보정
  )
```

할증 항목은 금액뿐 아니라 부담 주체를 함께 기록한다.

| 할증 항목 | 예시 | 부담 주체 후보 |
| --- | --- | --- |
| 거리 할증 | 기준 거리 초과 | 주문자, 음식점, 플랫폼 |
| 피크 시간 할증 | 점심/저녁 피크 | 주문자, 플랫폼 |
| 우천/악천후 할증 | 비, 눈, 강풍 | 주문자, 플랫폼 |
| 심야 할증 | 늦은 시간대 | 주문자 |
| 대기 보상 | 조리 완료 지연 | 음식점, 플랫폼 |
| 멀티배차 보정 | 묶음 배달 효율 반영 | 플랫폼 |

## 플랫폼 마진 방어

플랫폼 목표는 수익 극대화보다 손실 통제다. 건별 판단과 월간 평균 판단을 함께 둔다.

```text
예상 플랫폼 마진 =
  주문자 부담 배달료
+ 음식점 부담 배달료
+ 별도 할증 수취액
- 기사 지급 예정액
- 플랫폼 부담 쿠폰/보상
- 취소/환불/오류 보정
```

| 마진 구간 | 판단 |
| --- | --- |
| 500원 이상 | 정상 배차 |
| 100원 이상 500원 미만 | 제한 허용. 월 평균 마진이 안정적일 때만 적극 허용 |
| 100원 미만 | 원칙적으로 비추천. 멀티배차 전체 평균이 회복될 때만 예외 |

월간으로는 평균 마진이 100원 아래로 내려가지 않게 방어한다. 월 평균이 낮아지면 플랫폼 부담 쿠폰, 장거리 단건, 플랫폼 부담 할증을 줄이고 멀티배차 또는 추가 수취 할증을 우선한다.

## 멀티배차 판단

음식 배달 멀티배차는 최대 2건을 1차 기준으로 둔다. 한 주문의 픽업을 완료해야 그 주문의 하차가 가능하다는 선행 조건은 반드시 지킨다.

```text
허용 방문 순서 예시:
  P1 -> D1 -> P2 -> D2
  P1 -> P2 -> D1 -> D2
  P1 -> P2 -> D2 -> D1
  P2 -> D2 -> P1 -> D1
  P2 -> P1 -> D1 -> D2
  P2 -> P1 -> D2 -> D1
```

1차 필터는 위경도 기반 근사 거리와 선행 조건으로 빠르게 판단하고, 2차 검증은 Naver Directions5 같은 실제 경로 API로 한다.

| 조건 | 임시 기준 |
| --- | --- |
| 묶음 건수 | 최대 2건 |
| 배달권 | 같은 배달권 우선, 인접 배달권 허용, 비인접 배달권 기본 제외 |
| 묶음 내부 총 이동거리 | 가능하면 6km 이하 |
| 조리 완료 후 배달 완료 시간 | 주문 안내 최대시간 이내 |
| 기본 최대 배달 시간 예시 | 42분 |
| 피크 시간 허용 초과 | 15~20분까지 유연 허용 후보 |

멀티배차의 정산 판단은 주문별이 아니라 묶음 단위로 한 번 더 봐야 한다.

```text
2건 멀티배차 수취액 = 10,000원
목표 플랫폼 마진 = 1,000원
최소 허용 플랫폼 마진 = 200원
```

기사 지급 총액이 10,000원을 넘는 묶음은 기본적으로 추천하지 않는다. 다만 서비스 품질, 피크 대응, 전략 운영이 필요한 경우에는 관리자 정책으로 예외를 열 수 있다.

## 월말 상생 크레딧

음식점 부담 2,500원이 장기적으로 부담될 수 있으므로, 월말에 플랫폼이 목표 이상으로 남긴 금액을 음식점 혜택으로 돌리는 구조를 후보로 둔다. 명칭은 세무 검토 전까지 환급보다 크레딧으로 둔다.

```text
월 플랫폼 실현마진 =
  총 배달료 수취액
- 기사 지급 총액
- 플랫폼 부담 쿠폰/보상
- 취소/환불 보정
- 기타 직접 배달비용

월 크레딧 가능액 =
  max(0, 월 플랫폼 실현마진 - 월 운영비 - 목표 영업이익 - 안전준비금)
```

크레딧 배분은 단순 매출액보다 완료 배달 건수와 품질 기준을 함께 본다.

| 기준 | 반영 방식 |
| --- | --- |
| 완료 배달 건수 | 기본 기여도 |
| 조리 지연 | 감점 |
| 취소율 | 감점 |
| 고객 클레임 | 감점 |
| 픽업 준비 안정성 | 가점 |
| 재주문율 | 가점 |
| 월 배달 건수 구간 | 많이 판 음식점 가산 |

음식점별 크레딧 상한은 해당 음식점이 낸 월 음식점 부담 배달료의 일정 비율로 둔다. 예를 들어 상한 30%라면 월 400건을 처리한 음식점은 음식점 부담금 1,000,000원 중 최대 300,000원까지 크레딧 후보가 된다.

## 장부 분리

실제 구현 시에는 금액을 한 필드로 합치지 말고 장부를 분리한다.

| 장부 | 책임 |
| --- | --- |
| 주문 수취 장부 | 주문자/음식점으로부터 받은 배달료와 할증 수취액 |
| 기사 지급 장부 | 기본료, 할증, 보상, 멀티배차 보정 |
| 플랫폼 마진 장부 | 주문별 예상/실현 마진 |
| 월간 마진 풀 장부 | 월 운영비, 목표 영업이익, 안전준비금, 초과분 |
| 상생 크레딧 장부 | 음식점별 다음달 차감 또는 크레딧 후보 |

부가가치세, 세금계산서, 크레딧 처리 방식은 거래 구조가 중개인지 직접 배달서비스인지에 따라 달라질 수 있다. 세무 검토 전에는 "환급 확정" 같은 표현을 피하고, 시스템 내부 정책 후보로 관리한다.

## 보류 사유와 다음 우선순위

음식점/FDriverApp 요금 정책은 위 기준으로 보류한다. 지금 먼저 닫아야 하는 대상은 1.0 화물/용달 흐름이다.

다음 우선순위는 다음과 같다.

| 순서 | 대상 | 이유 |
| ---: | --- | --- |
| 1 | 화주 운송비 구조 | 1.0의 실제 수취 금액 기준 |
| 2 | 용달기사 지급 운임 구조 | 추천 수락과 기사 정산의 핵심 |
| 3 | 플랫폼 수수료/마진 구조 | 운영 지속 가능성 판단 |
| 4 | 선결제, 하차 후 정산, 월말 정산 | 결제/정산 상태 전이 안정화 |
| 5 | 배차 추천과 운임 조건 연결 | 낮은 운임, 재알선, 공개배차 판단 |
| 6 | 상차/하차 증빙 후 지급 확정 | 1.0 운송 완료 기준 |
