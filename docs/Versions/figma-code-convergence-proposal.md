# 서버·클라이언트 변화의 Figma 수렴 제안

## 제안 목적

2026-07-26 이후 서버 원장, 역할별 클라이언트와 운영 화면이 빠르게 확장되면서
Figma `ssalddle` 파일과 실제 코드 사이에 차이가 생겼다. 이 문서는 Figma 화면을
바로 늘리기 전에 다음 세 가지를 먼저 고정한다.

1. 이미 Figma에 반영된 기능은 새로 만들지 않고 현재 코드에 맞게 수정한다.
2. 코드에는 있지만 Figma에 없는 사용자 화면만 실제 여정 단위로 추가한다.
3. 버튼, route, stable ID와 원장 상태가 화면 이동 화살표와 일치하게 만든다.

이 문서는 설계·작업 순서를 정하는 제안서다. Figma node를 생성·이동·수정하거나
애플리케이션 코드를 변경하지 않는다.

> 실행 상태 — 2026-07-28에 P0 범위인 `02M`, `08 Seller`,
> `09 Admin Mobile`과 역할 계층도, 음식·화물 버튼-화면 흐름을 Figma에
> 반영했다. 실제 node와 시각 검증 결과는
> [Figma 서버·클라이언트 수렴](../Changes/2026-07-28-figma-code-convergence.md)에
> 기록한다. 후속 P1까지 반영된 화면을 실제 client·server 코드와 맞추는 순서는
> [Figma·클라이언트·서버 코드 정렬 실행 계획](figma-client-server-alignment-implementation-plan.md)을
> 따른다. 아래 내용은 실행 전 차이 분석과 후속 P1 범위를 함께 보존한다.

## 조사 기준선

### 코드 기준

- 기준 브랜치: `codex/rename-ssalddel`
- 검토 범위:
  - 2026-07-27 이후 역할 앱·서버 변경
  - 현재 미커밋된 주문자 통관·3PL 및 물류대행 계약 검토 변경
- 동작 기준:
  - 실제 Razor `@page`
  - route 상수
  - Controller와 공용 contract
  - `docs/Changes`의 구현·간접 검증 기록
- Figma보다 코드가 우선하는 항목:
  - 인증과 역할 권한
  - stable ID
  - 상태 전이
  - loading, empty, error, retry, offline
  - `Simulation`과 `Operational` 실행 경계

## 제안하는 Figma 정보구조

### `00 Overview` 수정

- 역할 앱 트리를 `01~09` 기준으로 갱신한다.
- `06 Global`은 공개 공급자 탐색으로 유지한다.
- `07 Restaurant`, `08 Seller`, `09 Admin Mobile`을 독립 역할로 표시한다.
- 각 역할에 `운영`, `베타`, `검토`, `설계` 상태를 실제 코드와 맞춰 표시한다.
- 화면 개수보다 다음 공통 원장 관계를 먼저 보여 준다.

```text
네 주문 원장
  → 플랫폼 배달권
  → 운송 실행 원장
  → 주문자·음식점·판매자·화주·기사·창고·관리자 투영
```

### `02 Orderer` 보완

현재 `02A2`, `02A3`, `02B~G`, `02L`, `02T`는 유지한다. 숨김 참고본
`2101:64`, `2026:66`도 삭제하거나 이동하지 않는다.

신규 활성 구역은 `02M · 같이 수입 통관·3PL 검토`로 제안한다.

| 화면 코드 | 화면 | 실제 route 또는 상태 |
| --- | --- | --- |
| `02M.01` | 같이 수입 준비 개요와 7단계 지도 | `/group-purchase/imports/{LedgerId}` |
| `02M.02` | 공급자·비용·HS 분류 요약 | suppliers, costs, classification |
| `02M.03` | 구매 목적·물품가격·식품·보관온도 입력 | logistics-review 입력 |
| `02M.04` | 통관·세금·식품요건 판단 | logistics-review 결과 |
| `02M.05` | 상온·냉장·냉동 3PL 후보 필터 | exact capability와 restriction 적용 |
| `02M.06` | 비교 후보 선택과 시설 재확인 | 운영 배정이 아닌 검토 후보 |
| `02M.07` | 포워더·3PL 인계 조건과 동의 | handoff, consent |

기존 화면 수정:

- `02L` 원장 상세에 `통관·3PL 검토` 버튼을 추가한다.
- `02L-DOC`에는 문서 생성 실패, 누락 정보, 다운로드 만료 상태를 추가한다.
- `02T`에는 같이 수입 국내 인계 전 `통관 반출 가능`과 `3PL 입고 가능`
  상태를 분리한다.
- 냉장과 냉동을 하나의 checkbox로 합치지 않고 별도 선택값으로 표시한다.
- 현재 공개 후보가 미국 시장에만 있는 경우 `US 공개자료 후보`로 표시하고,
  대한민국 후보가 없는 배포에서는 빈 상태를 보여 준다.
- 3PL 후보는 플랫폼 제휴·추천·자동 배정으로 표현하지 않는다.

### `03 Shipper` 보완

`03 Shipper`에서는 판매자 화면을 더 확장하지 않고 화주·물류 의뢰 책임에
집중한다.

신규 구역 `03C · 물류대행 계약 검토`:

1. 업무 범위 선택
2. 입고·검수·적재·보관·피킹·포장·출고 요율표
3. 예상 물량과 예상 비용
4. 냉장·냉동·식품 취급 조건
5. 화주·3PL 책임 분담
6. 초안 확인과 양측 서명 전 실행 금지

기존 운송 의뢰 화면에는 다음 이동을 명시한다.

```text
운송 의뢰 제출
  → 기사 추천 대기
  → 배정 기사·위치 신선도
  → 상차
  → 운송
  → 하차·POD
  → 완료 원장 재조회
```

### `04 Driver` 보완

새 화면보다 기존 `04.21`, `04.22` 수정이 우선이다.

- 실시간 수신과 30초 보완 조회를 별도 상태로 표시
- 추천 만료와 서버 재확인 중 버튼 비활성
- 수락 전 축약 위치, 수락 후 수행 주소 공개
- 다건 배차 배너와 선택된 한 건의 상세
- 네트워크 단절, 토큰 갱신, 재연결
- 수락·거절·픽업·전달 뒤 같은 운송 원장 재조회
- 음식 배달과 일반 화물의 실행 프로필 차이를 같은 카드 골격 안에서 표현

### `05 Warehouse` 보완

`05T`와 작업 보드에 다음을 추가한다.

- 상온·냉장·냉동 보관 가능 범위
- 식품 취급과 lot·유통기한 추적
- 물류대행 계약의 작업별 과금 단위
- 포장 완료 → 운송 인계 초안 → 기사 수락 → 반출 인계
- 마트·같이 주문·같이 수입 원천 원장 구분
- 실제 배송 주소가 준비되지 않은 오류 상태

### `06 Global` 유지

`06 Global`은 해외 공급자나 상품을 발견하고 신청하는 공개·체험 영역으로

## 교차 앱 흐름 페이지

비어 있는 `Flow · Food Order` 페이지를 다음 한 건 폐쇄 루프의 기준으로
사용한다.

```text
Orderer 주문 제출
  → Restaurant 수락·조리시간
  → Restaurant 준비 완료
  → FDriver 추천·수락
  → FDriver 픽업·전달
  → Orderer 수령 상태
  → Admin 주문번호 추적
```

각 화살표에는 실제 누르는 버튼과 다음 route를 함께 표시한다.

예:

```text
[주문하기]
/food/restaurants → 주문 상세
```

```text

  → Admin 관제
```

## 화면 배치와 상호작용 규칙

1. 화면은 번호순보다 실제 사용자 이동순으로 좌→우, 상→하 배치한다.
2. 한 section 안의 화면은 393×852 모바일 frame과 Auto Layout을 사용한다.
3. 화면 사이 화살표에는 `버튼명`, `route`, `전달되는 stable ID`를 적는다.
4. 분기점은 한 화면에 모두 펼치지 않고 결정 화면 뒤에 별도 열로 둔다.
5. loading, empty, error, retry, disabled, expired, offline은 대표 상태 frame을
   최소 한 개씩 둔다.
6. 구현 화면, 설계 화면, 참고 화면을 같은 색으로 표시하지 않는다.
7. 주문자 역할 화면은 기존 파란색 계열을 유지한다.
8. 숨김 참고본을 삭제하지 않고 활성 여정 밖의 오른쪽 참고 구역에 둔다.
9. 실제 개인정보, 주소, API key, 토큰, 계좌와 문서 원문을 샘플에 넣지 않는다.
10. `가까운 음식점`처럼 거리 수치를 확정하지 않는 표현을 유지한다.

## 실행 순서

### 1단계 · 대응표와 Figma 골격

- `00 Overview` 역할 트리 갱신
- `08 Seller`, `09 Admin Mobile` 페이지 생성
- 기존 page의 활성·참고 구역 경계 확인
- route와 Figma screen code 대응표를 canvas에 배치

완료 기준: 모든 실제 route가 `화면 있음`, `상태로 포함`, `Figma 제외`
중 하나로 분류된다.

### 2단계 · 주문자 최신 변경 수렴

- `02M.01~07` 작성
- `02L`, `02L-DOC`, `02T` 수정
- 구매 목적·통관·세금·식품·상온/냉장/냉동·3PL 후보를 한 여정으로 연결
- 현재 앱 버튼과 화살표를 대조

완료 기준: 원장 상세에서 통관·3PL 검토를 거쳐 인계·동의로 가는 경로를
버튼명과 route만 보고 따라갈 수 있다.

### 3단계 · 판매자와 관리자 신규 페이지

- `08.01~08.08`
- `09.01~09.07`
- standalone 앱 shell, 목록·상세·상태 화면을 기존 역할 앱 디자인과 조화

완료 기준: `SellerApp`과 `SsalddelAdminApp`의 핵심 route가 Figma에서
독립 역할 여정으로 확인된다.

### 4단계 · 음식점·화주·창고 보완

- `07 Restaurant` 복구·예외·인계 상태

- `05T` 냉장·냉동과 계약 작업 단가

완료 기준: 상태 변경 주체와 다음 앱이 같은 stable ID를 다시 조회하는 관계가
보인다.

### 5단계 · 검증과 정리

- 각 대상 frame metadata 확인
- screenshot으로 텍스트 잘림, 겹침, 빈 frame 확인
- route·버튼·stable ID 표기 재검토
- 대표 PNG와 node ID를 `docs/Changes`에 기록
- 코드 미구현 화면은 `설계` 또는 `준비 중`으로 표시

## 승인 전 확인할 결정

제안 기준으로는 다음 방향을 권장한다.

1. `SellerApp`은 `03 Shipper` 안에 다시 넣지 않고 `08 Seller`로 분리한다.
2. 모바일 관리자는 `00 Overview`의 변형이 아니라 `09 Admin Mobile`로 분리한다.
3. `06 Global`은 공개 공급자 탐색, `08 Seller`은 인증된 판매 운영으로 구분한다.
4. 주문자 통관·3PL은 `02D~G`를 대체하지 않고 `02M` 활성 여정으로 연결한다.
5. 교차 앱 화살표는 각 역할 page에 중복해서 흩뿌리지 않고 전용 flow page에서
   전체 흐름을 보여 주고, 역할 page에는 앞·뒤 한 단계만 표시한다.

이 다섯 결정을 기준으로 승인되면 `1단계 → 2단계`부터 Figma를 실제로
수정하고, 단계별 screenshot과 node ID를 남긴다.
