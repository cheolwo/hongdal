## 첫 진단과 구현 범위

1. 개발이 기존 LH 창 계산·셀 공급·배치 검증·Coordinator·Unity 표현의 경계를 대조한다. 카메라 far clip/컬링·LOD, 상세/활성/선행 준비 범위, 셀 누락·해제 시점, 지면 Mesh/법선/재질 연결, 식생 경계 간격을 원인 후보로 구분한다. 원인 없이 모든 표시 거리를 늘리지 않는다.
2. 기존 승인 셀·배치·자산의 누락된 연결이나 수명 관리 결함은 소유 경로·회귀·기획 및 연구 hash를 작업 명세에 결속한 후 좁게 수정한다. 카메라를 돌리거나 경계를 왕복할 때 필요한 이웃 셀이 준비되는지, 불필요한 셀은 정상 해제되는지 검사한다.
3. 표시 반경·LOD·시각 연결의 기술 조정은 원복 가능한 프로젝트 설정/복사본에서 비교한다. 월드 seed·권위 지형·자원량·H 계보·생산 면적·저장 규칙을 바꾸지 않는다. 기존 상세≤활성≤선행 계약과 예산을 유지한다.
4. 원경 전용 장식·안개·새 숲 패턴이 필요하면 먼저 기존 자산과 실제 지원 기능을 확인한 전문 연구 후보로 분리한다. 기존 고정 후보/연구를 조용히 수정하거나 안개만으로 누락된 지형을 감추고 해결로 보고하지 않는다. 상호작용·충돌 없는 원경을 실제 탐험 가능 공간으로 표시하지 않는다. 신규 공간 구성이나 플레이 의미 변경이 필요한 부분만 추가 기획 결속 대상으로 남긴다.

## 담당·실행 순서

- 개발은 현행 명세/Goal의 추가 승인·비중첩 경로를 등록하고 통합·회귀·공유 코드 변경을 소유한다. 별도 대형 엔진 신설이나 LH/배치 엔진 강제 합병은 하지 않는다.
- 공간 담당은 다음 안전한 Editor 슬롯에서 재현 경로·상태·실제 Game View·성능을 조사하고 전후 비교한다. 현재 벌목 연결을 중단시키거나 중복 Editor 점유를 만들지 않는다. 코드·파일 조사는 비중첩이면 병행 가능하다.
- 필요한 Required 연구는 현재 원문을 보존한 추가/후속 판본으로 작성하고 개발 검토·Accepted 결속 뒤 해당 구현만 진행한다. 게임 규칙 선택이 필요 없는 기술 결함은 불필요하게 새 문답 대기로 돌리지 않는다.
- 기존 D363 배치와 D359 벌목의 작은 실제 연결 목표를 유지하되, 화면 경계 결함은 같은 야간 우선 작업으로 배분한다.

## 수용 기준과 아침 반환

- 같은 위치·카메라·시야각·시간대에서 UI 포함 실제 Game View 전후 PNG를 남긴다. 주간 진단을 추가하면 주간끼리 비교하고, 야간→주간 차이를 수정 효과로 계산하지 않는다.
- 정지 화면뿐 아니라 경계 접근/통과·회전·뒤로 돌아오기·해제/재적용 시 갑작스러운 지면 구멍·수목 소실·중복 객체·통행 문제를 확인한다. 개선되지 않은 항목도 기록한다.
- 같은 조건의 프레임 시간·메모리·활성 셀/객체 수를 가능한 도구로 측정한다. 수치가 없으면 성능 미검증으로 표시하고 무제한 셀 상주로 성공을 만들지 않는다.

- 개발이 캡처를 직접 열어 실제 변화·원인·검증·미완료·다음 작업을 기획에 반환한다. 장면 저장은 본인 변경만 분리 가능할 때 기존 승인 경계 안에서 수행한다. 외부 효과·강제 복구·원본 덮어쓰기·commit/push·E 자동 승격 금지는 D375와 동일하다.
