# 기존 서버 개체·KAMIS 코드와 Synty 표현 대응 재검증

- 판본: `entity-kamis-visual-audit.plan.r1` / D430 / 2026-08-31.
- 상태: `ApprovedScopedWork` — 기존 데이터의 대응 실태를 먼저 감사하고, 검증된 범위부터 기존 전산화 경로에 축적한다. 조사 지시가 개별 자산의 적합성 승인이나 실제 배치 완료는 아니다.
- 사용자 우선순위: 오크 수종 조사나 통신 점검보다 기존 서버 DbSet의 개체 종류·개별 기록 및 KAMIS 농수산물 코드가 보유 Synty 자산과 적절히 대응하는지 먼저 확인한다.
- 의미 식별자: `existing-entity-kamis-visual-audit-first` / `Confirmed`.

## 1. 기존 체계를 다시 검증한다

[D425 품목 대응](농수산품목-시각자산대응-기획과개발인계-2026-08-31.md)·[D426 개체/레코드 확장](개체레코드-시각자산대응-확장과개발인계-2026-08-31.md)과 [자료조사 운영 D429](../Architecture/게임자료조사전문운영.md)를 재사용한다. 새 상품·자산 대장이나 별도 DB를 만들지 않는다. D426 동결 원문/hash는 보존하고 후속 감사·실행 결과는 별도 보고로 연결한다.

이번 기획의 파일 읽기에서 [D426 구현 보고](../Reports/개체시각대응-D426-서버구현-2026-08-31.md)와 현재 Reader/Catalog를 대조했다. 등록된 원천 종류는 `farm`, `farm.plot`, `farm.cultivation`, `warehouse.inventory`, `mart.product`, `food.product` 여섯이다. 코드의 기본 자산 목록은 비어 있으며 명시적 검토 사본을 요구한다. 실제 실행 설정과 MySQL의 행 존재/선택 결과는 개발이 별도로 조회해야 한다. 과거 133개 시험·8개 자산 키 파일 대조는 실제 DB 대응·적합성 승인 근거가 아니다.

## 2. 두 축의 대응을 분리한다

| 축 | 확인할 연결 | 오인하지 않을 것 |
| --- | --- | --- |
| 개체 종류/기록 | DbSet·개체 의미 → 기존 권한별 조회 → 종류 기본 또는 특정 레코드 대응 → 상태/목적에 맞는 표현 키 | 재고 행은 창고 건물이 아니며 마트 상품은 매장 건물이 아니다. 모든 테이블을 물리 객체로 만들지 않는다. |
| 농수산물 코드 | KAMIS 출처/분류·품목 → 검토된 공통 품목 ID → 생육/수확/포장 등 표현 문맥 → 표현 키 | 가격 관측 행마다 새 품목/객체를 만들지 않는다. 코드 대응 확정과 Prefab 적합성 확정은 서로 다른 사실이다. |
| 자산 실체 | 표현 키 → 현재 자산 대장 판본 → GUID/Prefab/meta → 기존 외형 근거 | 이름 일치·파일 존재는 품종/어종·품질/산지·크기·사용 장면의 일치를 증명하지 않는다. |

KAMIS 분류·품목·품종/종류·등급·단위 및 시점을 구분한다. 어떤 수준까지 표현이 구별되는지 기록하고, 범용 채소/물고기/상자는 명시적인 범주 대체로만 검토한다. 원천 필드나 확정 코드 관계를 시각 모델에 맞춰 바꾸지 않는다. 동일 숫자 ID가 다른 원천/종류/권한에서 충돌하지 않는지 확인한다.

## 3. 첫 감사 순서와 완료 기준

1. 기존 Context/DbSet 목록과 D426 등록 조회를 대조하여 지원·미지원·정보창/내부 전용을 목록화한다. 코드 정의, 실제 테이블 존재, 실제 레코드 존재를 별도 표시한다. 전수 목록화와 표본의 적합성 검토를 혼동하지 않는다.
2. 현재 Compose·서버 연결 대상과 스키마를 비밀값 없이 확인한다. 기존 로컬 Docker MySQL만 읽기 감사하며 원격 운영 DB로 대체하지 않는다. 테이블 부재/접근 거부를 0건으로 보고하지 않는다.
3. 여섯 등록 종류별 존재하는 대표 기록과, D425의 농산물 최대3·수산물 최대3 범위에서 저장된 품목을 우선 대조한다. 감자 외에도 실제 존재하는 품목을 포함하되 자료를 만들거나 어종을 추정해서 수를 채우지 않는다. 나머지는 미검토 목록에 남긴다.
4. 기존 개별/기본 승인·미검토/제외·누락·판본변경·중복·권한/원천 실패의 선택 결과를 확인한다. 검증용 합성 자료는 실제 DB 표본과 분리하고 실제 원천 행은 수정하지 않는다.
5. 자료 담당은 코드/개체 의미, 공간 담당은 기존 자산/이미지와 역할 적합성, 개발은 조회·선택·저장 및 판본을 검토한다. 원본/Scene 수정 없이 기존 근거부터 재사용한다. 추가 미리보기가 필요하면 정확 후보·보호 기준·기존 사용조건·단독 슬롯을 후속 결속하며 파일 검색을 시각 검증으로 대체하지 않는다.
6. 결과는 기존 상태를 보존한 대응표로 반환한다. 최소 열은 원천 종류/기록 식별·코드/공통 품목·상태/목적·개별/기본 구분·표현 키/GUID·판본·기존 승인 상태·의미 검토·외형 검토·현재 선택 결과·필요 후속이다. 원천 없음, 대응 없음, 미검토, 부적합, 승인된 범주 대체, 정확 문맥 적합을 구별한다.

실제 테이블/고유 품목/표본/검토 후보/유효 대응/선택 성공의 수를 따로 보고한다. 한 품목의 가격 행 수나 같은 Prefab 참조 수로 대응률을 부풀리지 않는다. 감자 상자 하나를 모든 농수산물의 승인 기본값으로 사용하지 않는다. `urban.building.logistics`의 역 건물 참조 등 기존 후보는 잘못된 대응으로 단정하지 말고 실제 목적 적합성의 열린 항목으로 검토한다.

## 4. 감사 다음 전산화

감사에서 안전하게 확인한 범위는 D426의 기존 대응·검토/이력 저장과 D429의 정확 로컬 DB 경계를 이용한다. 필요한 좁은 결함 수정/연결·제한 테이블 추가는 개발이 정확 경로·근거·시험 범위를 선언한 뒤 기존 승인 안에서 수행한다. 감사 결과나 후보의 저장은 가능하지만 근거가 부족한 행을 `ApprovedForContext`로 만들거나 기본 활성화를 켜서 성공시키지 않는다.

실제 저장 → 별도 조회 문맥 재조회 → 동일 입력 중복 방지 → 같은 판본 선택을 검증한다. 품목 코드, 원천 관측·가격·재고·거래/권한은 불변이다. 후보 보관과 실제 승인 선택·Unity 소비는 각각 미완료 여부를 보고한다. 기존 서버 계약에는 표현 키/근거를 저장하며 Prefab/텍스처 원본이나 로컬 절대 경로를 업무 데이터로 업로드하지 않는다.

새 외부 수집·전량 데이터 승격·사용조건 변경·원격 운영 쓰기·전체 마이그레이션·원본/Scene 변경·게임 규칙/E·r129/야간·commit/push는 이번 감사로 재개하지 않는다. 기존 D428 제출 자료는 보존하되 대응 재검증을 우선하고, 감사 중 불필요한 양조/오크 추가 조사를 늘리지 않는다.

## 5. 역할과 인계

기획은 이 원문과 DECISIONS만 소유한다. 개발은 `docs/Reports/DbSet-KAMIS-Synty대응-D430-읽기감사-2026-08-31.md`, `artifacts/local/validation/entity-visual-audit-d430/`, 기존 CURRENT_WORK/개발통합상태판과 정확 선언한 감사 도구/근거를 소유하며 자료·공간 담당을 배분한다. 공통 코드/DB 쓰기는 조사 결과와 기존 D426 승인 범위에 결속한 후 개발이 통합한다.

첫 반환은 실DB 조회 가능 여부·정확 대상·기존 구현과 실데이터의 차이·대표 표본 결과다. 모든 분야를 기다리지 않되 부분 결과를 전체 대응 완료로 표현하지 않는다. 사용자에게는 소통 성공이 아니라 어떤 개체/품목이 무엇으로 보이고, 어디가 아직 미연결인지 보고한다.
