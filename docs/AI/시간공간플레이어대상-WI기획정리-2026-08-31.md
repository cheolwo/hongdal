## 1. 바뀌는 것과 유지하는 것

기존의 질문별·기능별 문서에 **같은 플레이를 네 관점으로 읽는 연결 구조**를 추가한다. 파일을 전부 옮기거나 질문을 새 번호로 다시 쓰는 방식은 사용하지 않는다.

| 바뀌는 읽기 방식 | 유지할 원본·경계 |
| --- | --- |
| 질문에서 시간·공간·플레이어·대상을 함께 확인 | 기존 Q/의미 후속 ID, 답변 상태·판본·근거 |
| WI에서 행동 전 조건과 행동 후 변화를 확인 | 기존 WI ID와 Preview/Confirm·권위 결과 계약 |
| H1/H2에서 어떤 행동과 상황을 지원하는지 역조회 | 기존 H 정의·고유 식별자·후보 상태·상위 포함 관계 |
| 자산·이미지에서 어떤 조건과 결과를 보여주는지 확인 | Prefab 후보와 실제 조립·Game View 증거의 구분 |
| 미정과 미검토를 관점별로 찾아 다음 문답 선정 | 현재 Logic/Presentation E·실행 승인·기존 중지 상태 |

## 2. 사람이 읽는 한 행동의 정리 형식

기존 문답 또는 기획의 해당 절에 아래 항목을 연결한다. 새로운 필수 JSON 스키마나 모든 WI에 같은 비용·시간을 요구하는 규칙은 아니다.

대화 출력은 이 표를 한꺼번에 펼치지 않고 **게임 안의** `지금·여기·나·너·이렇게`, 관련된 오행 관계, Codex 추천·이유·대가의 세 층으로 요약한다. `나`는 게임의 플레이어 또는 관점 Actor, `너`는 그 Actor가 대하는 NPC·사물·환경·조직이다. 현재 대화 참여자, 문서 편집 상황이나 Codex 작업 절차를 이 칸에 넣지 않는다. 확정·미정·다음 질문 하나는 세 번째 추천 층의 끝에 둔다. 문서 본문에는 아래 상세 필드를 유지하여 대화 요약이 원문 계보와 결과·다음 선택을 잃지 않게 한다.

### `이렇게`는 상황에 적중하도록 고른 행위다

`이렇게`는 가능한 행동을 중구난방으로 나열하는 칸이 아니다. **지금의 시간·진행 상태, 여기의 공간·접근 조건, 나의 목적·역량·자원·권한, 너의 상태·필요·반응을 함께 고려해 플레이어가 현재 목적에 가장 적절하다고 판단하여 고른 행위 방식**이다. 기획은 왜 그 행동이 현재 상황에 적중하는지와 어떤 대가·위험·미확인을 감수하는지를 함께 보여 준다.

여기서 `가장 적절함`은 시스템이 하나의 효율 최적해·도덕적 정답·자동 추천을 정한다는 뜻이 아니다. 구조, 탐험, 관계, 성장처럼 플레이어가 둔 목적이 다르면 복수의 적절한 선택이 공존할 수 있다. 하지 않기·관찰하기·보류·위임·후퇴도 현재 목적과 조건에 맞으면 `이렇게`의 후보가 된다. 기획은 대표 추천 하나와 이유를 제시하되 다른 유효한 선택을 지우지 않는다.

`적중`은 전투 명중률이나 결과 성공 보장이 아니다. 선택 시점에는 확인 가능한 근거에 비추어 상황에 맞는지를 판독하고, 실제 성공·부분 성공·실패와 대상 변화는 WI의 권위 결과로 확인한다. 이 구분은 새 점수·추천 엔진·WI·상태 권위를 만들지 않는다.

| 항목 | 적는 내용 |
| --- | --- |
| 원문 | 질문/의미 ID, 기획·연구 경로와 실제 위치, 판본, 결정 상태 |
| 시간 | 언제·얼마나·어떤 진행 단위, 중단/재개·기한·결과 지속과 미정 |
| 공간 | 필요한 H 역할, 장소 조건·접근·통행·차폐·지지, 상위 조립 후보 또는 해당 없음 |
| 플레이어 | 목표·판독 가능한 정보·권한·능력·도구·자원, 직접/위임 선택 |
| 대상 | 상대/사물/환경의 식별과 상태·성질, 상대의 수요·반응 등 해당되는 조건 |
| 이렇게 / WI | 현재 목적에 적중하는 기존 행위·후보, 시간·공간·나·너에서 가져온 적합 근거, 열어 둘 대안, 허용·거부 조건, 명시 선택과 대가 |
| 결과·다음 선택 | 권위 변화와 표현을 분리, 실패·중단·회복·귀환·이어지는 선택 |
| 연결과 공백 | H/WI/자산/이미지/구현 근거, 확정·미정·제안·해당 없음·근거 미확인 |

## 3. 첫 재정리 예시 — 새 규칙이 아니라 원문 대응

### 약초차 재가열

원문: [약초 제작 문답 Q363·Q371](../Architecture/PlayableLoops/PlanningSessions/약초Recipe제작/herbal-recipe-crafting.inquiry.r1.md). 개발이 원문 위치·최신 판본과 연결을 검증한다.

- 시간: 재가열에는 시간·연료가 들며 구체 시험값은 이 표에서 정하지 않는다.
- 공간: 기존 거점의 제작 역할 재사용을 우선한다. 냄비·열원 지지와 접근의 실제 적합성은 별도 준비다.
- 플레이어: 새 약초를 필수 투입하는 재제작 대신, 준비된 차를 데우는 선택을 한다.
- 대상: 내용물·냄비·열원은 서로 다른 대상이다. 물 보관 능력과 가열 능력도 구분하며 휴대병을 직접 가열하지 않는다.
- WI: 보편 데우기의 대상별 적용으로 읽는다. 열원 상태 변경이나 약초 배합·달이기 완료와 합치지 않는다. 새 WI ID는 발급하지 않는다.
- 결과·다음 선택: 기존 내용물을 데운 결과와 음용 선택을 연결하되 자동 음용·자동 약효·정수 효과를 추가하지 않는다.

### 농작물 수확과 집하

원문: [농장 문답 Q378~380·Q383~384](../Architecture/PlayableLoops/PlanningSessions/건물공간배치/building-spatial-placement.inquiry.r1.md).

- 시간: 성숙 후 수확 지연은 효율·수량 저하 또는 수확 불가로 이어질 수 있으나 작물별 시점·곡선은 미정이다.
- 공간: 기존 생산구획과 작은 집하 지점·용량 있는 보관처를 연결한다. 물류 창고 건설을 첫 수확의 필수 조건으로 만들지 않는다.
- 플레이어: 소지 여유와 승인 보관처를 고려하여 수확하거나 옮긴 뒤 재개한다.
- 대상: 남은 작물, 완료 단위 수확물, 보관처의 용량·권한은 별도 상태다.
- WI: 현재 소지 가능한 완료 단위까지 수확하고 나머지는 식물에 남긴다는 기존 결정을 참조한다. 기획 대응표를 실제 부분수확 구현 완료로 읽지 않는다.
- 결과·다음 선택: 보관→수확 재개 또는 다음 파종 준비로 잇는다. 씨앗 자동 생산·전역 자동 구매를 추가하지 않는다.

### 농사 NPC의 위협 대응

원문: [지역 위협 Q385](../Architecture/PlayableLoops/PlanningSessions/지역오행몬스터/region-five-elements-monster.inquiry.r1.md), [초소 Q228·Q239](../Architecture/PlayableLoops/PlanningSessions/Farm병영방위/farm-barracks-defense.inquiry.r1.md).

- 시간: 작업 중 위협에 대응하고 후퇴·무장·복귀의 순서와 실제 상태를 구분한다. 별도 응답 시간이나 자동 성공 시간은 만들지 않는다.
- 공간: 접근 가능한 안전 지점과 무기고/장비 준비 지점·이동 경로가 필요하다. 후보 존재만으로 통행 가능을 가정하지 않는다.
- 플레이어: 직접 참여 여부와 업무·방위 배정은 기존 결정대로 둔다. 이 행동의 실제 수행자는 NPC이므로 플레이어와 실행 Actor를 혼동하지 않는다.
- 대상: 위협, NPC의 훈련·장비 상태, 무기 보관처를 구분한다. 다른 Actor는 플레이어와 독립된 상태를 가진다.
- WI: 미훈련 NPC에게 전투를 강제하지 않는다. 훈련 NPC도 무기·훈련·접근 경로가 없으면 무장 복귀를 성립시킬 수 없다.
- 결과·다음 선택: 생존·회복·업무 복귀를 기존 근거로 연결한다. Q239가 장비 반납 절차까지 확정했다는 해석은 하지 않는다.

위 세 사례만 첫 대응 예시다. 전체 437개 색인 항목의 의미 이관이나 모든 주제 검토 완료를 뜻하지 않는다.

## 4. 기존 자료를 옮기는 순서

1. **기존 자료 보존**: 승인된 문답·연구·명세는 읽기 원본으로 유지하고, 현재 원문 위치·판본을 찾는다. 과거의 완료 기록은 소급 수정하지 않는다.
2. **연결표 우선**: 개발이 진행 중인 문답↔공간 색인에서 재사용할 관계와 조회 방식을 검토한다. 네 관점은 같은 원문을 묶어 읽는 방식이며 별도 병렬 DB나 새 수기 원본을 만들지 않는다.
3. **작은 대표 적용**: 위 세 사례의 원문·관계부터 확인하고 방문자/거래·상환 등 다른 주제로 넓힌다. 기존 H1 전목록은 유지하되 미검토는 미검토로 둔다.
4. **기획 부족분 선별**: 관점에 빈 곳이 있어도 사유 있는 해당 없음일 수 있다. 이미 답한 내용은 연결하고, 기술 공백은 개발에, 새 플레이 선택만 기획 문답으로 돌린다.
5. **원문 재편집은 후속**: 실제 문서 재배치가 유익할 때만 주제별로 수행한다. 의미 변경 없는 재편집과 새 결정을 분리하고 승인 hash/참조 이관을 개발과 조율한다. 이번에는 승인 원문 전체를 일괄 수정하지 않는다.

## 5. 개발 인계와 검증 책임

- 기획 소유: 공통 관점, 이 적용 계획, 문답 진행 안내, D391 결정. 원문 의미와 사용자 미정을 유지한다.
- 개발 소유: 기존 색인·문서 생성·조회 계약의 최소 보완 여부 판단과 구현, 원문 위치/판본/관계 검증, 회귀·문서 검증, CURRENT_WORK/통합판 갱신 및 결과 반환.
- 공간/애니메이션: 기존 승인된 H1 시각조사 안에서 지정된 자료만 제공한다. 이 정리 방식만으로 새 촬영·조립·Blender 가공 범위를 넓히지 않는다.
- 개발은 변경 경로를 먼저 고정한다. 필드 추가가 불필요하면 기존 관계와 생성 문서로 표현하고, 기계 판독 지원이 필요하면 선택적 확장을 검토한다. 과거 자료의 새 형식 미기입을 실행 차단으로 만들지 않는다.
- 확인할 항목: 기존 질문 검색 호환, 원문·결정과 해석 제안 구분, 네 관점 다대다 관계, 비공간/복수 대상/NPC 위임, 시간 단위 혼동 방지, 누락·오래된 근거 표시, 기존 H/표현 이미지/실제 E의 분리.
- 이번은 기획 구조와 조회 준비다. 새 생산 규칙·시간 수치·보상·Save·Scene·E 승격·운영 DB·외부 게시·commit/push를 승인하지 않는다. r129/야간/다른 기능 중지를 유지한다.

## 6. 완료와 남은 작업

기획의 공통 관점과 기존 문답 절차 연결, 세 대표 사례의 재정리 틀을 작성했다. 코드·색인 반영과 기술 검증은 개발 인계 대상이며 이 문서 작성만으로 완료되지 않는다. 개발 반환에서 실제 이관 범위·기존 원문 보존·조회 예시·미검토 수와 다음 기획 선택을 구분한다.
