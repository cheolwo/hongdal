# D441 — Synty 분류를 DB 검색·자동 할당에 연결

- 판본: `synty-taxonomy-assisted-assignment.plan.r1` / 2026-08-31.
- 상태: `ApprovedScopedWork` — 기존 D440 자동 할당의 후보 검색·분류 보완.
- 의미 식별자: `synty-taxonomy-assisted-assignment` / `Confirmed`.
- 사용자 의도: 프리팹/Synty 자산을 종류별로 관리하여 Codex가 용도를 추론하고 더 정확하게 할당하도록 돕는다.
- 책임: 기획은 이 원문·DECISIONS, 개발은 구현·시험·MySQL·현재 상태판과 전문 배분을 맡는다. 기획에서 자산 전수 검증·코드·DB 작업은 하지 않는다.

## 1. 발견한 기존 기반과 연결 공백

분류를 처음부터 만들지 않는다. [기존 표현 모듈 기준](../Architecture/플레이폐루프Synty표현모듈체계.md)의 사람이 읽는 분류와 [단일 분류 원본](../../eng/execution-ledgers/synty-asset-human-taxonomy.json)을 재사용한다.

현재 파일 파싱 결과는 실외/실내/공통 **3범위·12기능군·152개 말단 경로**다. 이는 자산 수나 유일 종류 152개의 뜻이 아니다. `box`, `door`, `stairs`, `storage-rack`, `wall`, `workbench` 같은 말단 코드는 여러 경로에 반복된다.

기존 순서는 **범위 → 기능군 → 세부 기능군 → 자산 종류 → 자산 계열 → 실제 Prefab**이다. [13팩 기능 모듈 기준](../../eng/execution-ledgers/synty-asset-functional-modules.json)과 Unity의 `Synty전체자산ModuleCatalog.asset`에는 `moduleCodes`, `assetFamilyId`, Prefab GUID, 원천 fingerprint, 수명주기/보류 정보가 있다. 이 대장을 읽어 활용하되 원래 `needs-review` 등을 적합성 통과로 바꾸지 않는다.

[현재 DB 목록 계약](../../Ssalddel.Contracts/Admin/Content/보유시각자산목록Contracts.cs)과 [목록 조회](../../Ssalddel/Services/Content/보유시각자산목록UseCase.cs)는 원천/팩·파일 종류·이름·기존 VisualKey·조사판본 검색을 제공한다. 위 기능 분류·세부 형태·할당 역할로 검색하는 매개변수는 현재 조회에 없다. `EvidenceJson`에 보존된 조사 내용 전체가 분류되지 않았다고 단정하지 않고 실제 산출물과 함께 대조한다.

기존 기능 대장 기준은 Prefab4,211, D437 저장 보고는 보조 원천을 포함한4,221이다. 서로 다른 모집단을 같은 것으로 덮어쓰거나 10개 누락으로 단정하지 않는다. 개발이 정확 GUID/판본 집합으로 연결·차이·보류를 설명한다. 14,461개는 모든 종류의 파일 메타데이터이며 전부 Prefab이 아니다.

## 2. 분류 방법

한 축에 용도·파일 종류·형태·사용 상태를 모두 섞지 않는다.

| 구분 | 관리할 정보 | 자동 할당에서의 사용 |
| --- | --- | --- |
| 기술 종류 | 기존 Prefab, ModelFile, Clip, Controller, Material, Texture 등 | 외형 슬롯에 텍스처나 동작을 넣는 잘못된 후보 차단 |
| 기능 분류 | 기존 실내/실외/공통과 기능군·세부종류·자산계열 | 개체/WI의 역할에서 후보 집합 조회 |
| 보조 특성 | 근거가 있는 실내/실외 활용, 열린 입구, 손잡이, 외관/실내 부품, 색/형상, 측정 크기 | 같은 기능 후보 사이 적합성을 비교 |
| 기술·근거 상태 | 원본 판본, 실제 이미지 여부, Collider/Rig/Avatar 확인, 누락/미검사 | D440의 해당 역할 필수 조건 판정에 사용 |
| 사용 문맥 | 관련 기존 개체·WI·역할, 참고 영역 | 검색 방향을 돕되 새 게임 기능/영역을 자동 생성하지 않음 |

표현 예시는 다음과 같다. 아직 특정 자산에 확정한 분류나 실제 할당은 아니다.

- 헛간: 실외 구조물 → 건물 → 헛간. 지붕 부재와 완성 건물을 구분한다.
- 선반: 실내 설비 → 보관 설비 → 선반. 실외에서도 쓸 수 있는지는 별도 근거로 판단한다.
- 냄비: 기존 조리/용기 분류에서 후보를 찾고 열린 입구·내부·손잡이 여부를 확인한다. 기존 말단에 정확 종류가 없으면 근거 있는 세부 분류를 같은 원본에 최소 추가한다. 이름의 `Pot`만으로 병을 냄비로 확정하지 않는다.
- NPC: 캐릭터 외형과 대기/걷기/작업 Clip을 별도 자산 종류·역할로 관리한다. 상인 복장이 실제 거래 능력이나 NPC 역할 권한을 증명하지 않는다.

팩은 출처다. Farm 팩을 Farm에서만 쓰게 하거나 City 팩이 새로운 City를 생성하는 것으로 해석하지 않는다. 한 자산에 복수 분류·역할이 가능하며 원본 자산 행을 복제하지 않는다. 같은 `stairs` 말단이라도 전체 분류 경로를 식별하여 실외/실내 등의 의미 충돌을 막는다.

## 3. 분류 근거와 오분류 방지

1. 기존 승인된 문맥/검증 근거와 동일판본 대응을 우선하고 기존 대장·원본/meta·이미지 근거를 재사용한다. 이름·폴더 규칙은 초기 추정이며 시각 검증을 대신하지 않는다.
2. 분류와 보조 특성마다 어떤 근거로 판단했는지 남긴다. 이름/폴더 추정, 기존 대장 대응, 파일/이미지 확인을 구분하고 확인한 성질까지만 표시한다. 모르는 크기·Rig·재질/용량·가열 능력은 미확인으로 둔다.
3. ‘미분류’와 ‘부적합/제외’를 구별한다. 미분류 후보는 조회 가능하게 남기고 전체 모집단에서 없애지 않는다. 알려진 분류에서 충분한 후보를 못 찾으면 미분류·추정 후보도 추가 조사 대상으로 조회하되 자동 할당하지 않는다.
4. 기술 종류처럼 명확한 불일치는 먼저 제외한다. 의미 분류가 추정 단계인 것만으로 후보를 영구 차단하지 않으며 분류 일치만으로 자동 선정하지 않는다. 실제 선정은 D440의 용도·형상·필수 기술 근거를 다시 만족해야 한다.
5. 기존 정정·사용자 고정/선택은 보호한다. 규칙 판본 변경이나 원본 변경은 재확인 필요로 표시하고 과거 검증 결과를 조용히 현재 사실로 재사용하지 않는다.
6. 범용 분류에 맞추기 위해 WI·게임 객체·H/AreaSet·Prefab GUID·VisualKey를 새로 만들지 않는다. 그림의 외형과 게임 규칙상 기능·실제 능력을 분리한다.

## 4. 개발 보완 범위

- 기존 분류 JSON과 기능 모듈 대장을 의미 원본으로 유지한다. MySQL의 검색용 분류는 그 판본화된 투영/연결로 관리하며 별도 경쟁 분류 사전을 만들지 않는다. 새 세부 분류·보조 특성이 필요할 때만 같은 체계에 추가하고 기존 코드/경로는 보존한다.
- D437의 불변 조사 사본/MetadataJson·MetadataHash를 수정하여 분류를 끼워 넣지 않는다. 사본/내용 판본에 연결한 별도 분류 주석·관계와 근거/분류판본을 최소 추가한다. 분류 노드와 자산은 다대다이며 자산 GUID만 아니라 실제 판본까지 결속한다.
- 현행 `EvidenceJson`·Unity 대장과 관계를 먼저 읽고 재사용 가능한 것을 인수한다. 원천 fingerprint의 산식이 다르면 값이 비슷하다는 이유로 동일판본이라고 주장하지 않고 생성 기준을 확인한다. 기존4,211 ↔ 저장4,221 대응/미대응을 전수 계수하되 추정으로 채우지 않는다.
- 기존 목록 조회에 기능군/분류 경로·분류 상태·필요한 보조 특성의 선택적 필터를 추가한다. 기존 팩/종류/이름 조회·페이지 제한을 보존하고 분류가 없어도 목록 조회가 가능해야 한다. 응답은 분류 경로·근거 상태·판본을 함께 반환한다.
- Codex는 기존 개체/WI 역할 → 관련 분류/필수 조건 → 후보 조회 → D440 근거 판정 → 자동 초안 저장 순으로 사용한다. 서버에 별도 LLM을 두거나 매번 외부 유료 호출하는 분류기를 만들지 않는다.
- 현재 등록 목록 전체는 기술 종류별 조회를 유지한다. 기능 분류 연결은 기존 대장 재사용분부터 인수하고 D440 첫 최대10역할이 요구하는 종류를 우선 보완한다. 14,461개 전부의 새 이미지·세부 의미 확정을 첫 자동 할당의 선행조건으로 삼지 않는다.
- 실제 코드/계약/시험/분류 대장·조회·최소 로컬 DDL 소유 경로를 개발이 먼저 선언한 뒤 반영한다. 기존 자산·개체·할당과 원천 업무 테이블을 보존하고 제한된 추가 관계/검색 데이터만 저장·독립 재조회한다.

## 5. 시험·반환

필수 회귀는 중복 말단 경로 식별, 복수 분류와 단일 자산 정체성, 팩과 사용 영역 분리, 건물/부재·병/냄비·Prefab/Clip 구별, 추정/확인 근거 구분, 미분류 조회·보류, 기존 분류 정정 보호, 판본 변경·충돌/재처리, 구형 목록 조회·D440 선정 조건 불변을 포함한다.

분류별 합계는 다중 분류로 중복될 수 있으므로 전체 고유 자산 수와 구분한다. 분류 연결·추정·확인·미분류/충돌 수, D440 후보 축소 전후 수와 올바른 후보를 누락하지 않는 대표 사례, 실제 DB 저장/재조회·시험을 보고한다. ‘분류됨’을 이미지 검증·실제 할당·Scene 적용/E 완료로 세지 않는다.
