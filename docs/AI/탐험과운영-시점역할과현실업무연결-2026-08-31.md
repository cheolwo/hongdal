## 3. 플레이어에게 설명할 시점의 역할

새 숫자 단계나 별도 게임 모드를 만들지 않고 기존 시점에 다음 역할을 부여한다.

| 역할 | 지금·여기·나·너·이렇게 | 결과와 다음 선택 |
| --- | --- | --- |
| 직접 탐험 — 1인칭 | 춘분의 봄 같은 현재 문맥에서, 숲·길·마을 현장에 있는 내가, 풍경·NPC·식물과 사물을 가까이 보고 이동·관찰·허용된 채집을 한다. | 실제 발견 정보/획득 결과를 확인하고 대화·탐색·돌아가기 등을 선택한다. 단순 시야 이동을 지식/보상 획득으로 바꾸지 않는다. |
| 현장 운영 — 높은 사선의 전술 3인칭 | 업무가 있는 현재, 해당 농장·공방·시설 주변에서, 내가 작업자·시설·재고를 비교하고 허용된 선택·작업 초안·지시를 준비한다. | 확정된 작업/변화와 차단 사유를 보고 조정하거나 다시 직접 탐험한다. 카메라 이동이 인력/물품 이동·명령 성공은 아니다. |
| 광역 관찰 — 기존 전략 시점 | 여러 활동의 상황을 확인할 때, 서로 다른 영역을 보는 내가, 알려진 장소·진행 중 작업·요구와 위험을 비교하고 살펴볼 현장을 고른다. | 접근 가능한 장소/업무 상세로 초점을 옮긴다. 카메라로 볼 수 있음, 지도에서 알고 있음, 실제 방문 가능, 업무 명령 권한은 구별한다. |

운영이 늘어난다는 말은 지역 개수에 따른 강제 카메라 전환 규칙이 아니다. 기존 D134의 허용된 수동 전환을 유지하고 운영 화면을 언제 소개/추천할지, 첫 선택을 기억할지, 기존 Save에서 어떤 시점을 복원할지는 후속 설계에서 결정한다. 멀미·입력 접근성 때문에 필요한 기존 대체 시점을 막지 않는다.

일반 3인칭 추적 카메라와 RTS형 지휘 카메라의 역할도 구별한다. 사용자 의도의 핵심은 캐릭터 등을 보는 것 자체보다 **여러 대상의 상태를 읽고 운영할 수 있는 도구**다. 기존 전략/전술 시점의 범위·전환·상태 공급을 먼저 조사하고 네 번째 독립 카메라 시스템을 기본 해법으로 만들지 않는다.

## 4. 시간·자동 행동·자기 Actor의 경계

카메라가 넓어져도 같은 세계의 시간·플레이어·재고·작업은 이어진다. [시간 경계](../Architecture/WorldTick과실시간실행경계.md)의 게임 시간/WorldTick·BattleTick·표현 시간을 구분하고 시점 전환을 세계 일시정지/가속·자동 완료·순간이동의 근거로 쓰지 않는다. 기존 전투 감속/일시정지 등 명시적 규칙은 그 범위대로 유지한다.

자동사냥은 최소한 다음을 나누어 후속 기획한다.

- 이미 시작된 전투에서 자동 행동하는 것: D237 관찰 운영의 재사용 대상.
- 사냥 대상 탐색→이동→전투 시작→전리품 회수→귀환/반복: 별도 미정의 연속 업무. 기존 관찰 전투가 있다는 이유로 완성/자동 승인하지 않는다.
- 플레이어 자기 Actor의 자동 수행과 NPC 위임: 서로 다른 주체·권한·소모·중단 조건.
- 앱을 켜 둔 동안과 종료/부재 중의 수행: 기존 Solo/Hosted 시계·저장 원칙을 따르며 새 오프라인 보상/자동 진행을 추가하지 않는다.

광역 화면을 보는 동안 자기 Actor가 어디에 남는지, 이미 확정된 일을 계속하는지, 위험을 어떻게 알리고 복귀하는지는 개발에서 기존 계약을 확인한 뒤 미정만 문답한다. 이번 방향으로 자동 타겟/지역 반복·자동 회복약·자동 전리품 판매·무한 실행을 확정하지 않는다.

## 5. 게임과 실제 업무 보조를 함께 제공하되 실행은 구별한다

Mirror의 장기 방향을 게임 안의 현실 자료 참고에만 한정하지 않는다. 실제 권한을 가진 사용자가 실제 업무를 조회·검토하고 적절한 도구로 이어 갈 가능성도 포함한다. 단순 참고와 실제 업무 실행은 서로 다른 경계다.

1. **게임:** 가상 세계에서 탐험·제조·상업·운영을 즐긴다. 실제 계정·구매·업무 계약을 진행 조건으로 만들지 않는다.
2. **현실 참고:** 관심 있을 때 상품·거래 상세에서 기존 선택형 현실 자료를 살펴본다. 게임 가격/성과에서 현실 수익을 역산하지 않는다.
3. **실제 업무 보조:** 별도 인증·조직/역할·동의·공개 범위와 운영 준비가 성립한 업무를 조회/검토하고, 실행이 필요한 경우 실제 효과와 대상 원장을 알아볼 수 있게 한 뒤 기존 서버 절차를 따른다. 게임의 자동 행동과 실제 발주/배차/결제 자동화를 합치지 않는다.

세 가지는 기획상 목적 구분이며 새 실행 모드 세 개를 만드는 뜻이 아니다. 기존 `Simulation`/`Operational` 경계와 `Preview → 명시적 Confirm → 서버 권한·개정 검사 → 저장/행위 → 재조회`를 재사용한다. UI 표지·확인 위치·사용할 실제 업무 하나는 미정이다.

글로벌 지향은 현재 모든 국가/언어/통화·법률·물류를 지원한다는 주장이 아니다. 실제 서비스를 선정할 때 지역·언어·시간대·통화·단위·자료 출처/갱신·권리·운영 제공 범위를 확인하도록 남긴다. 이번에 API·DB·개인정보·계정·유료 호출·실거래·외부 게시를 연결하지 않는다.

## 7. 시점을 스케일로 보고 WI와 대응한다 (D418)

### 7.1 보는 범위와 행동 단위를 설명하는 스펙트럼

사용자는 시점마다 더 특수하게 작용하는 WI와 그 시점에서만 사용할 수 있는 WI를 구별하고, 시점 자체도 스케일의 스펙트럼으로 독립 발전시키기를 원한다. 이는 **가까이 체험하기 ↔ 현장 운영하기 ↔ 여러 영역을 관찰하기**의 범위이며 우열이나 개발 Evidence 단계가 아니다.

- 시각 범위: 손앞 대상·주변 현장·영역/여러 영역 중 무엇을 읽는가.
- 조작 단위: 개별 대상 직접 입력·여러 대상 비교/초안·작업/영역 요약 중 무엇을 다루는가.
- 실제 명령 범위: 어떤 주체와 대상에게 지시할 권한·접근/통신·자원·시간 조건이 있는가는 별도로 확인한다.

이 세 항목은 설명상의 관점이지 신규 필수 schema나 점수 세 개가 아니다. 카메라를 확대/축소했다고 명령 권한·NPC 통제·숨은 정보가 함께 확대되지 않는다. 넓은 화면이 정밀 조작에 항상 유리한 것도 아니다. H1~H5는 공간 포함/의미, 시점은 이를 어떻게 보고 조작하는가이며 서로 같은 번호로 대응시키지 않는다.

### 7.2 WI는 하나를 유지하고 허용과 특화를 나눠 기록한다

| 사람이 읽는 구분 | 의미 | 판정할 근거 |
| --- | --- | --- |
| 시점 공통 | 여러 시점의 입력이 같은 WI 의미·권위 결과로 이어질 수 있다. | 각각의 입력/대상 선택과 같은 Command·조건·결과 연결. 한쪽 구현만으로 전 시점 통과하지 않는다. |
| 시점 특화 | 여러 시점에서 가능하더라도 한 시점에 정밀 조작·상태 비교·초안 도구 등 알맞은 표현/입력 방식이 있다. | 어떤 편의가 달라지는지와 실제 입력 근거. 특화만으로 다른 시점 금지나 보상 증가를 뜻하지 않는다. |
| 특정 시점 전용 | 승인된 조작 의미나 참여 조건 때문에 특정 시점의 상호작용으로만 제공한다. | 전용인 이유·기존 승인/계약·다른 시점 안내/전환·실패/복귀. 임의 UI 숨김만으로 권위 조건을 보장하지 않는다. |
| 미검토 / 해당 없음 | 아직 대응을 대조하지 않았거나 시점에 의미 있게 의존하지 않는다. | 이유와 원문/구현 공백. 비공간 WI를 억지로 1인칭이나 광역 전용으로 배정하지 않는다. |

공통과 특화는 동시에 성립할 수 있다. 따라서 코드에서 상호 배타적인 enum 하나를 새로 만들기보다 **허용되는 시점과 특화되는 시점/기능**을 구분해 기존 정책을 재사용할 수 있는지 먼저 조사한다. 활동 단위의 `AllowedViewModeCodes`, `AdvantageCapabilityCodes`, `AllowsManualOverride`는 조사 출발점이며 아직 WI별 대응 원장은 아니다. 현재 `AdvantageCapabilityCodes`는 기본 시점으로 판정됐을 때만 반환되는 표시능력 목록이지 그 WI의 실행 권한/유일한 능력 보유 여부가 아니다. 목록에 시점이 없거나 UI 소비가 미구현인 상태를 기획상 금지로 오해하지 않는다.

같은 WI를 `1P 수확 WI`·`RTS 수확 WI`처럼 복제하지 않는다. 기존 WI ID·주체·대상·상태/행위 기록을 기준으로 시점별 입력과 표시를 연결한다. 직접 수확과 NPC 위임처럼 주체·업무 의미가 다르면 기존 별도 명령/역할을 보존하며 카메라 차이만으로 합치지도 않는다.

시점 전용 **입력**과 권위상 **참여 방식**도 구분한다. D237 전투 참여 잠금처럼 이미 권위 계약이 있는 범위는 서버가 계속 판정한다. 과거 시점 전환 구상이나 이번 분류 방향을 근거로 전투 잠금·보상·피해·자율 행동을 변경하지 않는다.

### 7.4 독립 발전은 두 종류를 구별한다

**제품 기획의 발전:** 1인칭의 대상 판독·정밀 조작, 전술의 선택·작업 비교/지시, 광역의 알려진 지역·업무 요약은 각각 개선할 수 있다. [발전 군집/테크트리](문답기반-발전군집과테크트리-2026-08-31.md)의 필수 선행·선택 대안·병행 보완 구분을 재사용한다. 구체 해금이 필요하면 해당 지식·시설·권한 원문을 연결하며, 시점 자체를 유료/경험치 기술이나 1P→3P→광역의 강제 순서로 확정하지 않는다.

**개발 준비의 발전:** 기존 WI/명세 아래 시점별 E4 입력·자산/판독 준비, E5 실제 대상/상태/입력 연결, E6 품질·간섭, E7 결과/복귀 근거를 구분한다. 같은 WI의 논리를 공통으로 재사용하되 어느 시점을 검증했는지 적는다. 전술 화면 미완료를 이유로 이미 검증한 1인칭 근거를 없애지 않고, 1인칭 성공을 전술·광역 성공으로 복사하지도 않는다. 통합 E 판정 자체는 기존 규칙과 현재 승인 범위를 그대로 사용한다.

각 시점은 독립적으로 개선할 수 있지만 전환 경계는 공동 검증 대상이다. 같은 Session/Actor·선택 대상·진행 중 작업, 입력/커서·모달·전투 잠금, 중단/반환·재집중을 서로 다른 판본으로 이어 붙이지 않는다. 시점별 새 E축·중복 Goal/원장·복제 상태 저장소를 만들지 않는다.

### 7.5 기존 기획/조회에 남길 최소 대응과 인계

기존 WI/명세의 표현 준비와 원문 관계에 아래 내용을 담을 수 있는지 개발이 조사한다. 먼저 기존 필드·보고를 사용하고, 부족한 경우에만 선택적 확장을 별도 제안한다. 필수 schema·새 관리자를 이번에 구현하는 승인은 아니다.

- 기존 WI/관련 활동과 지금·여기·나·너·이렇게의 문맥.
