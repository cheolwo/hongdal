# 배치 구조·제약과 계획·검증·표현 책임 리팩토링

- 날짜: 2026-08-31
- 기획 판본: `placement-responsibility-refactor.plan.r1`
- 결정 식별: D423
- 상태: `ApprovedScopedWork`. 책임 구분의 문서 반영과 기존 구현의 좁은 리팩토링 승인이다. 코드·시험·실제 배치 완료 보고가 아니다.
- 기획 원문 소유: 기획. 구현·시험·명세·상태판·생성물 통합: 개발. Editor가 필요한 검증과 실제 공간 작업은 개발이 단독 점유를 조율한다.
- D419~421 검증 중인 공통/DECISIONS 등 동결 4파일과 D422 승인 원문은 변경하지 않는다. 동결 해제 후 공통 결정·조회 연결은 개발과 조율한다. 이번 원문 자체는 추가 승인 근거로 인수할 수 있다.

## 1. 사용자 승인

사용자는 ‘배치 엔진’과 ‘배치 계층’의 구분을 명확히 한 뒤 ‘배치 구조·제약 체계’ 등으로 책임이 드러나도록 리팩토링하기를 요청했다.

| 의미 식별자 | 상태 | 승인 범위 |
| --- | --- | --- |
| `placement-responsibility-separation-refactor` | `Confirmed` | 기존 배치 구조·제약, 계획 계산, 범위별 검증, 월드 조립·표현을 구별하고 기존 구현을 호환 보존 방식으로 정리한다. |

이는 네 개의 새 관리자·엔진, 새 H/E 축, 새 배치 규칙을 만드는 승인이 아니다. 이미 분리된 책임은 재사용하고, 이름·설명 또는 구현이 실제로 혼합된 지점만 좁게 정리한다.

## 3. 개발이 정리할 경계

| 구분 | 최소 산출물 | 완료로 확대하지 않을 것 |
| --- | --- | --- |
| 구조·제약 | 기존 H/외곽/기준점/규칙 선언과 이를 확인하는 코드의 책임 설명·호출 대응 | 선언이 존재한다는 이유로 실제 배치 적합성 통과 |
| 계획 계산 | 같은 입력·규칙에서 동일 배치 계획을 반환하는 기존 엔진의 책임 명료화 | 후보 계산을 Unity 실제 생성으로 표현 |
| 검증 | 구조·참조, 계획 기하·지지·접근, 실제 적용 대조의 범위와 호출자 구별 | 한 검사 이름 아래 모든 공간 조건을 통과한 것으로 표시 |
| 조립·표현 | 기존 Coordinator/Runtime/LH의 계획 소비·소유·해제 경계 명료화 | LH에 권위 계산 또는 모든 자산 수명을 흡수 |

우선 확인할 혼동은 `배치통제계층Root.Validate`의 선언·참조 검사와 실제 배치 검사다. 기존 공통 검증·계획 서비스·조립 경로를 재사용한다. 긴 메서드 안에 책임이 섞였다면 동작을 보존하는 내부 분리와 호출 설명을 적용할 수 있다. 이미 명확히 분리되어 있으면 재사용 대조와 필요한 명칭·주석·보고 수정으로 남긴다. 불필요한 새 인터페이스나 빈 모듈은 만들지 않는다.

현재 `Configure`·`ConfigureInterior`·`ConfigureCompositionV3`·`ConfigureSensoryPresentationV4` 및 v1~v4는 호환 경로다. v3 상수만 보고 v4가 없는 것으로 판단하거나 일괄 판본 변경하지 않는다. 특정 H 배치 모판의 합성 지면·여러 영역 조건과 작은 실제 Farm 적용 조건도 구분한다.

## 4. 변경 방식과 소유권

1. 개발이 현행 원문/hash·관련 소스·호출자·기존 시험을 읽고 정확한 코드/시험/보고 경로를 선언한다. D422와 겹치는 공용 Root·Coordinator·Runtime은 개발 한 소유자가 통합한다.
2. 사람이 읽는 설명·주석·검사 결과/보고 범위를 위 책임에 맞춘다. 기술 식별자를 바꾸지 않고도 구별되는 곳은 유지한다.
3. 실재하는 책임 혼합만 내부적으로 분리한다. 공개 메서드·직렬화 필드·클래스/파일 경로·Prefab/meta GUID·저장 값·규칙 판본·기존 계획 hash 의미는 보존한다.
4. 기존 정상/거부 입력의 결과·진단·검사 순서와 소유권을 비교한다. 판정 변경이나 버그 수정이 필요하면 순수 리팩토링과 분리해 원인·영향·기존 승인 근거를 기록한다. 범위를 벗어난 새 규칙은 기획으로 반환한다.
5. 기존 LS01/D406 개발 보고와 현재 상태판에 반영한다. 새로운 보고 묶음이 꼭 필요한 경우만 추가하며 동일 사실을 여러 대장으로 복제하지 않는다.

이번 기획 소유 경로는 이 승인 원문과 위 Architecture 2문서다. 개발은 이 세 원문을 임의 수정하지 않고 기술 발견을 반환한다. CURRENT_WORK·개발통합상태판·작업 명세·필요 생성물과 기술 검증은 개발이 소유한다.

## 5. 검증·수용 조건

- 같은 상태/지도/자산/규칙 입력의 배치 결과·정렬·판본/hash가 전후 동일하다. 기존 거부 입력을 완화하거나 입력을 변경하지 않는다.
- v1~v4의 실제 사용 경로와 기존 호출자가 보존된다. 선언 검사와 실제 지지·통행 검사의 차이를 관련 회귀와 설명에서 확인한다.
- 특정 모판의 조건은 그 모판에 유지한다. Farm 작은 적용을 위해 전체 영역 모판을 먼저 완성하도록 강제하거나, 반대로 그 모판의 검사를 완화하지 않는다.
- 조립 코드가 변경되면 대상의 소유·취소·낡은 판본 거부·해제·재적용에 영향이 있는지 검증한다. 공개 반환값이 같은 이유만으로 실제 누락 객체를 정상 처리한 것으로 설명하지 않는다.
- 개발이 관련 집중 시험·소비자 빌드와 범위 지정 Fast/필요 Task를 수행한다. Unity 소스를 바꾸면 해당 컴파일·관련 검증을 개발이 조율한다. 문서/구조 리팩토링만으로 새 Play·캡처·Scene 저장을 요구하거나 허용하지 않는다.
- 실제 화면 동작이 달라지거나 D422 실제 적용 단계에 도달하면 그 명세의 단독 Editor·전후 화면·통행·보존 기준으로 검증한다. 이번 코드 회귀는 그 실제 증거를 대신하지 않는다.

최종 반환에는 변경 경로, 재사용한 기존 책임, 동작 보존 확인, 실패/미검증, D422와의 연결을 분리한다. 기획 반영·코드 리팩토링·실제 Farm 적용·E 성숙도는 각각 보고한다.

## 6. 유지하는 제한

Simulation의 시간·WI·공간 성립·Save 권위, 기존 E/WI/H 상태·연구 기준선·동결 후보는 그대로다. 자동 위치 보정이나 누락 건너뛰기와 동결 계획의 충돌을 이름 변경으로 숨기지 않으며 실제 연결 수정은 D422의 정확 범위로 별도 추적한다.

진행 중인 Farm 작업과 비중첩 준비는 계속한다. r129/야간/다른 중지 작업, 새 게임 선택·새 H/WI·패키지 확장·가공 권리·운영 DB/API·외부 게시·commit/push는 재개하거나 승인하지 않는다. Scene·원본·미소유 dirty를 일괄 저장·정리하지 않는다.
