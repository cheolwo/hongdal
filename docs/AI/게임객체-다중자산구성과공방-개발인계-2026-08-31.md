# 게임 객체와 다중 자산 구성 — NPC 공방부터

- 판본: `game-object-multi-asset-composition.plan.r1` / D434 / 2026-08-31.
- 상태: `ApprovedScopedWork` — 기존 서버/MySQL 관계를 재사용한 게임 객체 정의·역할별 자산 구성의 제한 저장·조회. 실제 World 생성/배치는 별도다.
- 사용자 의도: Town NPC 공방을 게임 객체로 관리하고 한 공방에 여러 Synty 자산을 연결한다. 특정 테이블 이름이나 전체 일대일 관계 강제보다 이 다중 연결 의도를 따른다.
- 의미 식별자: `game-object-role-based-multi-asset-composition` / `Confirmed`.

## 1. 기존 결정과 현재 확인

[D426 종류/개별 대응](개체레코드-시각자산대응-확장과개발인계-2026-08-31.md), [D431 MySQL 목록](Synty자산-MySQL목록과개체관계-구현승인-2026-08-31.md), [D432 이미지 검토](개체자산-이미지비교와할당검토-2026-08-31.md), [D433 이미지 보관](프리팹이미지-전담조사와Azure보관-2026-08-31.md)을 확장한다. 과거 승인 원문/hash·기존 단일 대응·현재 DB 기록은 보존한다.

현재 파일을 읽어 확인한 범위:

- [개체시각대응](../../Ssalddel.Domain/Content/개체시각대응.cs)은 한 대응 기록에 선택적인 `AssetVersionId` 하나를 둔다.
- [DbContext](../../Ssalddel.Infrastructure/Persistence/WorldProjection/개체시각대응DbContext.cs)는 `world_visual_asset_versions`, `world_entity_visual_bindings`, 이력 테이블을 정의하고 대응 문맥의 중복을 제한한다.
- [기존 선택 정책](../../Ssalddel/Services/Content/개체시각선택Policy.cs)은 같은 문맥의 여러 대응을 `BindingConflict`로 거부한다. 이 검사를 제거하고 여러 행을 넣는 방식으로 공방 구성을 구현하지 않는다.
- [대상 Reader](../../Ssalddel/Services/Content/개체시각대상Reader.cs)의 지원 목록에는 `farm`, `farm.plot`, `farm.cultivation`, `warehouse.inventory`, `mart.product`, `food.product`가 있으며 공방 전용 종류는 없다. 이 좁은 파일 대조로 저장소 전체에 게임 객체/구성 계약이 없다고 단정하지 않는다.

개발이 보고한 D431 실제 자산8/초안3 저장은 기존 범위의 결과다. 이번 기획은 공방 레코드/여러 부품 구성의 DB 구현 완료가 아니다. 개발은 최신 코드·스키마와 기존 Blueprint/배치 구성 계약을 먼저 조사한다.

## 2. 관계의 의미

`게임 객체 정의 → 표현 구성의 역할별 항목 → 기존 자산판본`으로 연결한다. 객체 하나는 여러 구성 항목을 가지며 항목 하나는 정확한 자산판본 하나를 참조할 수 있다. 동일 자산을 여러 객체/항목에서 재사용하므로 전체 객체↔자산 관계는 다대다다. 한 행이 객체 하나와 자산 하나를 잇는다는 뜻이지 객체 전체에 자산 하나만 허용하는 일대일 제약이 아니다.

| 구분 | 예시·역할 | 경계 |
| --- | --- | --- |
| 게임 객체 정의 | NPC 양조 공방이라는 설계 대상/종류 | 영속 정의와 검토 초안이며 Unity GameObject 자체나 실제 운영 시설이 아님 |
| 게임 내 개별 객체 | 특정 세계·지역에 실제 성립한 공방 | 기존 World/Session/고유 식별자를 참조. 이번 저장만으로 생성하지 않음 |
| 표현 구성 | 공방의 외관·내부 설비를 이루는 역할별 항목 | 기존 구성 계약을 우선 재사용. 자산 목록을 새로 복제하지 않음 |
| 자산판본·이미지 | Synty Prefab과 그 외형 근거 | D431 판본/D433 이미지 참조 재사용. 등록은 적합성 승인 아님 |

공방의 설명용 역할 예시는 건물 외형, 작업대, 통, 진열대, 간판이다. 정확한 자산·수량·배치나 전부 필수라는 결정은 아니다. NPC는 별도 Actor로서 공방과 관계를 맺으며, 캐릭터 Prefab을 공방 부품으로 넣었다고 소유자·교사·작업자가 생성된 것으로 처리하지 않는다.

자료 항목의 최소 의미는 객체/구성 판본, 구성 항목 고유 식별자, 역할, 선택된 자산판본 또는 미선정, 검토 상태·근거다. 같은 자산의 반복 사용은 서로 다른 항목으로 식별할 수 있어야 한다. 순서·수량·연결 기준점이 필요하면 기존 계약을 재사용하고, 미정 위치를 `(0,0,0)`으로 채워 배치 준비로 표시하지 않는다. 정확 DB 이름/정규화/추가 열은 개발이 현재 구조에 맞춰 선언한다.

## 3. 후보 목록과 조합은 다르다

- 건물 후보 A/B는 둘 중 무엇을 쓸지 검토하는 대안이고, 건물+작업대+통은 함께 구성하는 역할이다. 후보 전부를 동시에 배치하거나 승인하지 않는다.
- 공방 종류 기본형과 특정 공방의 개별형은 구분한다. 기존 개별 우선/같은 문맥의 승인 기본형/미연결 원칙을 유지하고 새 구성도 어느 판본을 사용했는지 반환한다.
- 검토 중인 구성·미선정 역할도 저장/조회할 수 있다. 실제 사용은 필요한 구성의 승인·정합성·현재 자산판본을 확인해야 하며 일부 후보 조회 성공을 전체 구성 Ready로 올리지 않는다.
- 기존 단일 자산 대응을 파괴적으로 변환하지 않는다. 독립된 여러 역할을 표현하기 위해 기존 문맥/충돌 검사를 약화하거나 Purpose에 임의 문자열을 붙이는 편법을 쓰지 않는다.
- 논리적인 기능·작업 가능 여부·재고/용량은 Simulation/기존 업무 상태가 정한다. 통 모델의 존재로 발효/저장 기능·오크 수종·용량이 확정되지 않는다.

## 4. 개발이 수행할 첫 묶음

1. 기존 게임 객체 정의/Blueprint/구성 계약과 D431의 DB·권한·검토 구조를 대조하고 정확 코드/테이블 소유 경로·최소안을 반환한 뒤 구현한다. 새 범용 게임 엔진·별도 자산 대장을 만들지 않는다.
2. 재사용할 정의가 없을 때만 **NPC 양조 공방의 편집용 정의 초안**과 필요한 구성 저장을 최소 추가한다. 이것은 사용자 요청의 설계 자료이며 가짜 실제 공방/운영 사업자/게임 Session을 만드는 일이 아니다. 종류/템플릿·실제 개체 구분을 조회에 표시한다.
3. 역할이 다른 항목을 두 개 이상 가진 구성과 동일 자산 재사용을 시험하고, 실제 저장은 확인된 자산판본만 참조한다. 공방 적합 후보가 아직 없으면 정의/미선정 역할까지 저장·재조회하고 자산 결속은 미완료로 보고한다. 임의의 감자상자/상점/창고 모델로 수를 채우지 않는다.
4. 기존 승인 대상인 로컬 `hongdal-mysql-1/hongdal_dev`를 재확인하고 필요한 제한 DDL·서버 저장·독립 재조회·멱등 검증을 수행한다. 원천9테이블·D431 기록·다른 앱 DB 설정은 보존한다. 전체 마이그레이션/초기화·원격 운영 DB 쓰기는 하지 않는다.
5. 기존 관리자 API/조회에서 객체→역할별 구성→자산판본·이미지 준비 상태를 확인할 수 있게 한다. D432/D433 비교 화면에서 이를 소비할 수 있도록 기존 계약을 최소 확장하며 이미지 미확보를 명시한다. 공개/실제 할당 자동 승인은 없다.
6. 검증은 한 객체의 여러 역할·동일 자산 여러 객체/항목 재사용·역할/항목 중복·고아 참조/삭제 제한·잘못된 판본·권한 거부·개정 경합·재전송/이력·단일 대응 호환을 포함한다. 구성 변경과 이력은 같은 저장 경계에서 처리하며 준비 중 변경으로 사용 중 판본이 부분 갱신되지 않도록 한다.

자산 조사·이미지는 새 `프리팹 조사` 작업의 기존 D433 범위를 우선 재사용한다. 개발이 공방 후보 조사 필요를 정확히 추가 배분하며 전체팩 재조사·Editor 촬영을 중복 시작하지 않는다. 이번에는 직접 Scene 배치하지 않고 [배치 책임 기준](배치책임구분-리팩토링승인-2026-08-31.md)의 구조·제약→계획→검사→조립을 후속으로 유지한다.
