# 농수산물 품목 코드와 시각 자산의 대응 체계

- 날짜: 2026-08-31
- 기획 판본: `product-visual-correspondence.plan.r1`
- 결정 식별: D425
- 상태: `ApprovedScopedWork`. 기존 품목/자산 체계를 잇는 자료 구조·소수 후보 조사·개발/시험용 연결 구현 승인이다. 실제 품목별 Prefab 선정·운영 DB 반영·Unity 배치 완료가 아니다.
- 소유: 기획은 이 원문과 [Synty 표현 기준의 D425 절](../Architecture/플레이폐루프Synty표현모듈체계.md#현실-품목과-시각-자산의-대응--d425-2026-08-31). 개발은 계약·저장/조회·검증·통합, 자료조사는 품목 의미/출처, 공간은 자산 외형/표현 적합성을 맡는다.
- 기존 D424 원문/운영r3, D419~421 동결 입력, D422/D423 원문은 수정하지 않는다. 기존 결정/조회 입력의 추가 연결은 개발의 동결 검증 경계와 조율한다.

## 1. 사용자 요청과 범위

사용자는 운영 서버의 농수산물 품목 코드와 보유 Synty 농수산물 관련 Prefab·이미지가 적절히 연결되도록 자료 구조를 마련하기를 원한다. 외부 코드가 존재한다는 이유만으로 같은 이름의 Prefab을 즉시 배치하지 않고, 어느 정도 외형이 맞는지를 관리한다.

| 의미 식별자 | 상태 | 승인 내용 |
| --- | --- | --- |
| `agri-fishery-product-visual-correspondence` | `Confirmed` | 기존 공통 품목을 중심으로 이미지/Prefab 대응과 외형 적합성·대체·미검토 상태를 기록하고 조회 가능한 연결 구조를 마련한다. |

[D424 자료 축적](현실자료-서버MySQL축적-기획과개발인계-2026-08-31.md)의 후속이다. 새 공통 상품 원장을 만들지 않으며, 코드 대응과 표현 대응을 분리한다. 모든 농수산물의 자산 제작이나 전량 조사·신규 품목 등록·운영 스키마 적용·Scene 배치를 이번 방향 승인으로 실행하지 않는다.

## 2. 재사용할 구조와 연결 관계

현행 파일에서 다음 기반을 확인했다. 이는 현재 운영 DB나 실제 자산 적합성 검증이 아니다.

- [공통 품목 계약](../../Ssalddel.Contracts/Common/PublicData/공통식품품목IdentityDtos.cs): `CanonicalProductStableId`, 출처/코드체계/상위코드, `Confirmed / Candidate / Unlinked`와 검토 이력.
- [기존 품목 저장 설정](../../Ssalddel.Infrastructure/Persistence/AgriculturalFisheries/공통식품품목IdentityConfigurations.cs): `agri_common_food_product_identities`, 코드 관계/이력 및 감자 초기 자료. 기존 외부 코드 간 관계 상태는 보존한다.
- [폐루프 자산 연결 대장](../../eng/execution-ledgers/playable-loop-synty-expression-modules.json), [자산 기능 대장](../../eng/execution-ledgers/synty-asset-functional-modules.json): WI 순간·역할·자산 계열의 기존 연결.
- 별도 Unity 저장소의 `Assets/Ssalddel/Presentation/World/WorldVisualCatalog.cs`: 알려진 표현 키와 실제 Prefab 참조를 연결하고 누락/중복 키를 거부한다. 해당 키를 풀어 임의 자산 경로를 허용하지 않는다.

사람이 읽는 연결은 다음과 같다. 새 단계 번호나 새 관리자 다섯 개를 뜻하지 않는다.

```text
출처별 농수산물 코드
  → 기존 공통 품목 ID와 코드 대응 근거
  → 품목별 표현 대응: 역할·상태·외형 적합성·후보 판본
  → 기존 표현 키/자산 계열
  → Unity 자산 목록의 Prefab 또는 UI 이미지
```

게임 품목 ID가 현실 공통 품목 ID와 다르면 기존 게임↔현실 대응을 명시적으로 참조한다. 두 ID를 같다고 가정하거나, 이미지 선택을 위해 재고/Recipe의 품목 식별자를 바꾸지 않는다. 현실 자료를 보지 않는 플레이에도 기존 게임 품목 표현은 독립적으로 동작할 수 있어야 한다.

품목 한 개에 여러 표현이 필요할 수 있고, 한 범용 자산이 여러 품목의 대체 표현일 수도 있다. 외부 코드마다 1:1 Prefab을 요구하지 않는다. 한 품목/역할/상태/문맥에 충돌하는 활성 대응이 있으면 임의로 첫 행을 고르지 않고 명시적 우선순위·선택 규칙 또는 충돌 결과를 적용한다.

서버/MySQL에는 품목과 표현 참조·대응/검토 이력을 보관할 수 있다. Unity `GameObject`·절대 로컬 경로를 서버 업무 계약으로 만들지 않는다. 정확 자산 정보는 기존 표현 목록/검증된 목록 사본으로 참조하며, 클라이언트는 자신이 지원하는 목록 판본에서만 해결한다. 관리용 GUID/hash 기록과 게임 의미 식별자는 서로 다르다.

## 4. 외형 매칭의 판단 기준

- **품목 외형 적합:** 해당 사용 장면에서 품목을 알아볼 수 있다는 시각 근거가 있다. 특정 종·품종·등급·산지를 정확히 묘사한다는 의미는 별도 확인이 필요하다.
- **범주 대체:** 일반 채소·일반 물고기·상자 등의 형상이다. 어떤 품목의 어느 장면에 대체로 쓰는지 명시한다. 특정 생물 종이나 상품 동일성의 증거가 아니다.
- **부적합:** 품목 또는 표시 상태를 오해하게 만든다. 후보 이력은 남기고 실제 선택에서는 제외한다.
- **미검토/미확보:** 파일 이름/목록만 찾았거나 후보가 없다. 존재를 적합성으로 올리지 않는다.

감자라면 밭의 식물·수확한 덩이줄기·상자에 든 상품·인벤토리 아이콘은 서로 다른 역할이다. 이는 설명 예시이며 해당 보유 Prefab을 확인/선정한 결과가 아니다. 일반 물고기 모델도 특정 어종의 정확 표현으로 자동 채택하지 않는다. 포장 모형의 개수·크기와 실제 수량/중량·가격 단위를 서로 환산하지 않는다.

명칭 검색은 후보 찾기에만 사용한다. 외부 코드 대응이 `Candidate/Unlinked`이면 자산이 닮았다는 이유로 `Confirmed`로 올리지 않는다. 이미 알려진 내부 품목의 게임 표현을 이 미확인 외부 코드 때문에 전부 차단하지도 않는다. UI에서는 실제 이름·수량·상태는 권위 데이터를 읽고 범용 외형 사용 여부를 구별할 수 있게 한다.

미리보기는 공급자 이미지/프로젝트의 격리 자산 렌더/실제 Game View를 구분한다. 식물/상품 실물 사진과 3D 자산 미리보기를 같은 종류의 증거로 취급하지 않는다. 원본 Prefab/텍스처를 운영 서버나 외부에 업로드·재배포하지 않는다.

## 5. 첫 소수 품목 조사와 구현

### 자료조사·공간 담당

개발을 통해 기존 전문 담당에게 분리 배분한다. 첫 묶음은 기존 공통 품목과 자료가 있는 농산물 최대 3개·수산물 최대 3개 이내다. 감자는 기존 ID를 우선 대조하되 수를 채우기 위한 신규 품목 생성·어종 추정은 하지 않는다.

- 자료조사 담당은 기존 코드·품목 의미·자료가 설명하는 종/상태/단위와 미확정을 대조한다. 새 외부 수집이 필요하면 D424의 출처/표본/접근 범위 안에서 조율하며 이번 요청만으로 분량을 늘리지 않는다.
- 공간 담당은 기존 13팩 기능/Prefab 목록과 과거 이미지부터 소수 후보를 찾고 해당 이름·GUID/원본/meta 판본·형태·역할을 기록한다. 자산 목록 존재와 시각 판독을 분리한다.
- 첫 조사에서 새 Editor/렌더는 실행하지 않는다. 기존 근거가 없으면 미검토로 반환하고, 실제 미리보기가 필요한 정확 자산·보호 기준·단독 슬롯은 개발이 후속으로 결속한다. Farm D422의 실행 슬롯을 빼앗거나 전문이 중복 점유하지 않는다.

### 개발 담당

1. 기존 공통 품목/코드 관계·D424 자료 저장·Synty 기능/표현 대장·WorldVisualCatalog/Resolver를 대조해 중복이 없는 최소 연결 위치를 고른다. 정확 계약·저장/조회·시험 파일 소유를 먼저 반환한다.
2. 품목/역할/상태/문맥으로 검토된 표현 후보와 적합성·대체/누락 사유를 조회하는 작은 계약과 선택 검증을 구현한다. 등록된 키·목록 판본을 검증하고 자산 이름에서 권위 품목 ID를 자동 생성하지 않는다.
3. 기존 자료 저장 경계에 대응 이력의 저장·재조회/개정을 연결한다. D424와 같은 공용 DbContext/마이그레이션/API 변경은 개발 단일 소유로 묶는다. 자료가 미확정이면 후보/보류 상태로 보관하고 테스트 Fixture와 실재 자료를 구분한다.
4. 동일 입력/판본의 동일 선택, 중복 대응/미등록 키·누락 후보·오래된 근거, 부적합 후보 배제, 정확/범주 대체의 역할 제한, 여러 상태별 후보, 외부 코드 미확정의 비승격, 품목/재고 불변을 관련 회귀로 확인한다. 여러 동등 후보의 선택은 기존 결정적 선택 계약을 재사용한다.
5. DB 검증은 분리된 개발/시험 환경에서만 한다. 실제 MySQL 저장·재조회 여부와 메모리 시험을 분리한다. 운영 DB 접속/스키마 적용·권한 부여·외부 게시·새 수집기 실행은 하지 않는다.

기존 감자 대응 한 건과 다른 상태/범주 대체·미확보 Fixture를 먼저 검증해 구조를 실제로 소비한다. 실제 적합 자산이 없는데 임의 GUID/VisualKey를 등록하여 통과시키지 않는다. 필요한 새 표현 키는 정확 근거/후속 명세로 등록하며 `IsKnown` 검사를 완화하지 않는다. 이 구현을 전체 품목 매칭/실제 Unity 적용 완료라고 하지 않는다.

## 6. 배치 파이프라인과 증거 수준

[D423 책임 구분](배치책임구분-리팩토링승인-2026-08-31.md)에서 이 대응은 계획 엔진이 참조할 수 있는 **표현 후보 입력**이다. 대응 승인만으로 지지·통행·Collider/Bounds·상호작용 또는 실제 배치 검증을 통과하지 않는다. [D422 Farm 월드맵](Farm월드맵-배치계층경유-점진구성-2026-08-31.md)의 구조·제약 → 계획 → 검증 → 조립·표현 경로를 그대로 통과한다.

Presentation E4에는 후보/판본·역할·판독 순간·조건·근거를 연결한다. E5는 실제 상태 사본과 배치·입력의 기존 기준으로 별도 판정한다. 코드/표현 대응표·격리 미리보기·Game View·상품/생물 동일성·권리 승인 중 어느 하나로 다른 것을 대신하지 않는다.

## 7. 소유·반환

기획 소유는 이 원문과 Synty 기준의 연결 절 두 파일이다. 개발은 D424와 공용 소유를 조율하고 기존 코드/대장 재사용·정확 변경/검증, CURRENT_WORK·통합상태판 및 기술 보고를 갱신한다. 자료 전문/공간 전문은 개발이 지정한 비중첩 전용 경로로 반환한다.

반환 목록에는 품목·출처 코드 상태·표현 역할·후보/미확보·외형 대응 수준·미리보기 종류·개발 구현·실제 DB/Unity 연결·남은 조건을 구분한다. 전체 코드를 강제로 채우는 매칭률을 목표로 삼지 않는다. 기존 게임 규칙·원본 자산·H/WI/E·Save·Scene·r129/야간/다른 중지 작업·commit/push는 변경하거나 재개하지 않는다.
