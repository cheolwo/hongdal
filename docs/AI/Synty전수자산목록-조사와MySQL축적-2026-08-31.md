# 보유 Synty 전수 자산 목록 조사와 MySQL 축적

- 판본: `synty-full-inventory-mysql.plan.r1` / D437 / 2026-08-31.
- 상태: `ApprovedScopedWork`.
- 의미 식별자: `owned-synty-full-inventory-mysql` / `Confirmed`.
- 사용자 요청: City·Town·Farm 등 보유 팩 전부를 조사하여 자산 목록을 DB화한다. 기존 Synty/프리팹 조사 담당이 이를 맡는다.

## 1. 범위 확장과 담당

[D431 목록/관계](Synty자산-MySQL목록과개체관계-구현승인-2026-08-31.md)의 첫8키 제한을 **현재 로컬 프로젝트에서 확인할 수 있는 보유 Synty 팩 전체의 목록 조사·메타데이터 DB 등록**까지 확장한다. [D433 이미지 조사](프리팹이미지-전담조사와Azure보관-2026-08-31.md)의 이미지8키/제한 촬영·업로드 범위는 자동 확대하지 않는다. 목록 등록과 이미지·외형 검토·실제 배치는 별도다.

주관은 기존 `프리팹 조사` 작업 `01a05775-33d3-7182-a7b4-8b35764498e4`다. 새 작업을 만들지 않는다. 전담은 전체 팩/자산 재고, 기계 판독 가능한 가져오기 입력, 누락/충돌/판본·근거, 진행·완료 수량을 책임진다. 개발 `01a02198-8b2a-7491-ac93-366b30ff474c`은 기존 ASP.NET Core 가져오기·조회, 정확 DB/스키마와 코드 변경, 실제 저장·독립 재조회 및 통합 검증을 책임진다. 전담이 목록 파일만 제출한 것을 사용자 요청 전체 완료로 보지 않는다.

전담 첫 쓰기는 자신의 worktree `docs/Research/PrefabImages/D437/`의 README.md·inventory.json·manifest.json 및 `artifacts/local/prefab-inventory/d437/`의 추출 입력/검증 기록으로 한정한다. 공유 Hongdal/Unity 원본은 읽기 전용이다. DB 저장은 개발이 정확 경로/대상과 검증된 가져오기 방식으로 실행하며 전담의 별도 SQL·공유 코드/DDL 수정을 병행하지 않는다.

## 2. 전수의 모집단을 먼저 확정한다

현재 Unity 프로젝트 `C:/Users/user/ssalddel`의 Synty로 식별되는 실제 팩 경로를 기존 [기능 대장](../../eng/execution-ledgers/synty-asset-functional-modules.json), [분류](../../eng/execution-ledgers/synty-asset-human-taxonomy.json), [상향식 재고](../../eng/world-seedbeds/synty-bottom-up-inventory/catalog.v3.json)와 대조한다. 이 파일들의 과거 선언 수량/팩 수를 오늘 실측 결과로 사용하지 않는다.

- City·Town·Farm뿐 아니라 실제 발견된 Nature·Construction·캐릭터/애니메이션 등 Synty 팩을 빠짐없이 목록화한다. 팩 이름만으로 Farm 등 게임 영역을 확정하지 않는다.
- 설치/임포트된 팩, 기존 목록에만 있는 팩, 원본 경로 부재·미확인 팩을 구분한다. 계정/구매함 전체를 조사했다고 주장하지 않으며 새 다운로드/구매/임포트는 하지 않는다.
- 실행 전에 정확 포함 경로와 제외 경로·대상 파일 종류를 기록한다. Library/Temp/bin/obj·복구 사본·검증 결과·다른 worktree 복제본을 새 보유 자산으로 중복 집계하지 않는다. 애매한 경로나 공급자는 미확인으로 반환한다.
- 주 대상은 모든 Prefab 파일이다. 캐릭터·환경·건물·소품·식물·FX 등은 유형/하위 분류로 구분한다. 메시/FBX·재질·텍스처·AnimationClip·Controller·데모 Scene 등 보조 자산도 종류별 메타데이터 재고로 구분하며, Prefab 행이나 배치 가능한 객체로 위장하지 않는다. FBX 안의 하위 자산처럼 파일 읽기만으로 세부 식별이 불가능한 것은 파일 단위 등록/하위 미확인으로 표시한다.

## 3. 저장할 최소 정보와 식별

팩/공급자, 실제 상대 경로, 자산명·종류, meta GUID, 확인 가능한 팩 판본과 근거, 원본/meta hash, 조사 시점/입력 판본, 기존 자산 키/계열과의 관계, 분류·미확인 상태를 저장한다. 이미지가 있으면 출처 종류/참조를 연결하되 없으면 미확보로 둔다. 바이너리·텍스처 원문·GameObject를 MySQL에 넣지 않는다.

기존 GUID/판본과 D431 등록8개를 우선 대조한다. 같은 자산의 여러 표현 키는 자산 실체 중복과 구별한다. 이름이 같다는 이유로 다른 팩 자산을 합치지 않고, 경로 이동/같은 GUID·다른 내용/다른 GUID·같은 이름/누락 meta/읽기 실패/변경 중 파일을 구분한다. Prefab 변형의 원본 관계는 확인 가능한 근거만 기록한다.

아직 게임 표현 키가 없는 자산도 목록 등록 대상이다. 기존8키 전용 검사를 통과시키려고 가짜 게임 키·승인 상태를 만들지 않는다. 개발은 기존 자산 목록/판본 계약을 먼저 재사용하고, 전수 목록에 꼭 필요한 식별·유형·팩 검색 필드나 관계가 없을 때만 좁게 확장한다. 정확 기술 경로·추가 테이블/열과 보존 조건을 먼저 선언한다. 새 독립 자산 권위/대장을 병렬로 만들지 않는다.

파일 존재/판본 확인, 의미 분류, 외형 적합성, 실제 사용 승인은 별도 상태다. 파일 이름만으로 식물 종·품종·음식 코드·건물 용도·사용조건/구매 증빙을 확정하지 않는다. DB 등록 기본은 미검토/미선정이며 D426·D434 개체 대응/구성을 자동 변경하지 않는다.

## 4. 팩별로 저장하고 재개 가능한 방식으로 마무리한다

개발은 기존 로컬 Docker `hongdal-mysql-1/hongdal_dev`를 재확인하고 기존 ASP.NET Core 가져오기/관리 권한·개정/이력을 재사용한다. 원격 운영 DB나 다른 앱의 연결 설정을 바꾸지 않는다. 비밀값은 대화·소스·기록에 남기지 않는다.

1. 전담이 포함 팩/파일 목록과 조사 입력 판본을 고정하고 중복/충돌을 분리한다.
2. 기존 등록분과 차이를 대조해 추가·동일·판본 변경·검토 필요를 나눈다.
3. 개발이 승인된 목록 메타데이터를 팩별/적정 크기의 묶음으로 저장한다. 일부 실패 때 처음부터 전체를 반복하거나 기록을 삭제해 맞추지 않는다.
4. 같은 입력 재처리 시 중복이 없고, 다른 판본은 과거 근거를 보존하는지 확인한다. 저장 중 파일이 바뀌면 영향을 받은 묶음만 다시 조사한다.
5. 별도 조회 문맥에서 실제 DB의 식별자 집합·판본/수량을 입력과 대조한다. 팩·자산 종류·이름/기존 키로 조회할 수 있게 하며 기존 페이지 크기/제한을 전수 누락으로 오인하지 않는다.
6. 전담 조사 결과와 개발 DB 결과를 합쳐 팩별 완료/차단·누락을 기획에 반환한다. 모집단을 임의로 줄여 전수 완료로 표시하지 않는다.

마지막 재고에서 발견되지 않은 자산은 과거 기록을 삭제하지 않고 현재 미확인/재검토로 남긴다. 기존 자산8/대응·구성/WI 관계와 원천 자료/재고/가격·개인정보는 보존한다. 전체 마이그레이션/초기화·제품 자동 활성화·Scene/Save/E 변경·공개 게시·commit/push는 없다.

## 5. 완료 판정과 현재 우선순위

반환 수량은 **확인 팩 수, 발견 파일 수/고유 자산 수, 종류별 수, 기존/신규/판본 추가 수, 실제 DB 저장·조회 확인 수, 중복·충돌·부재/읽기 실패 수, 이미지 미확보 수**로 나눈다. 목록 전체를 검사하되 외형/리깅/Collider 실측·실제 Unity 사용까지 전수 완료했다고 하지 않는다.

완료는 명시한 현재 로컬 팩 모집단의 모든 발견 항목이 DB 등록 또는 근거 있는 미등록 상태로 설명되고 입력↔DB 대조·중복 방지가 끝난 상태다. 미등록이 남으면 ‘조사 전수 대조 완료/DB 등록 일부 미완료’로 구분하고 필요한 조치를 남긴다. 게임 객체별 프리팹 적합성/할당은 후속이다.

[D436 우선순위](기존요청-우선순위와완료기준-2026-08-31.md)의 DB/자산 기반 보완으로 진행한다. 현재 D435 공용 Context/계약 쓰기를 중단·충돌시키지 않고 전담 전수 파일 조사는 즉시 병행한다. 개발은 현재 작은 묶음의 안전한 경계에서 전수 가져오기/DB 확대를 결속하며 이미지 전수 촬영을 기다리지 않는다. D433 기존 소수 이미지·웹 완결을 전수 메타데이터 조사 전체에 무조건 종속시키지 않는다.

기획은 이 원문과 DECISIONS만 편집한다. 개발은 상태판/현재 목록의 D437 담당·진행/다음·차단을 갱신하고 `docs/Reports/Synty전수목록-D437-개발통합-2026-08-31.md`와 `artifacts/local/validation/synty-full-inventory-d437/`에 저장/조회·검증 결과를 반환한다. 전담은 개발과 기획에 조사 결과를 보고하며 DB 완료 여부도 구분한다. 새로운 작업 생성/자동화·r129/야간·무관한 중지 작업은 재개하지 않는다.
