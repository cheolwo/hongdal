# 기존 요청의 우선순위와 사용자 확인 가능한 완료 기준

- 판본: `approved-work-closeout-priorities.plan.r1` / D436 / 2026-08-31.
- 상태: `ApprovedScopedWork` — 기존 승인 작업의 마무리 순서와 통합 책임 확정.
- 의미 식별자: `approved-work-closeout-priority` / `Confirmed`.
- 사용자 승인: 새 문답보다 이미 요청한 일의 완결에 집중한다는 제안에 대해 “그렇게 우선순위대로 진행”을 요청했다.

## 1. 목적과 기존 범위

새 기능 문답과 조사 주제 확대는 잠시 뒤로 두고 **WI 근거 → 객체 정의 → 실제 자산 이미지 → 선택 저장·재조회 → 작은 실제 배치**를 연결한다. 전체 WI·자산 조사를 첫 사용 가능한 결과의 선행 조건으로 만들지 않는다. 아래 순서는 결과 반환의 우선순위이지 모든 담당을 직렬 대기시키는 제한이 아니다.

기존 [D435 WI 객체 추출](WI문서-게임객체추출과MySQL연결-2026-08-31.md), [D434 다중 자산 구성](게임객체-다중자산구성과공방-개발인계-2026-08-31.md), [D431 자산 목록](Synty자산-MySQL목록과개체관계-구현승인-2026-08-31.md), [D432 이미지 비교](개체자산-이미지비교와할당검토-2026-08-31.md), [D433 이미지 보관·웹 열람](프리팹이미지-전담조사와Azure보관-2026-08-31.md)을 재사용한다. 원문/명세를 복제하거나 새로운 객체·WI·작업 관리 시스템을 만들지 않는다.

## 2. 첫 마무리 순서

| 순서 | 기존 요청과 이번 집중 범위 | 사용자 관점의 완료 기준 | 완료로 대체할 수 없는 근거 |
| --- | --- | --- | --- |
| 0 | 진행 중 D434 묶음의 검증·보고 마감 | 실제 저장·독립 재조회, 관련 회귀와 범위 밖 실패, 남은 연결이 보고에 구분됨 | 시험 개수나 초안 저장을 자산 선정/공방 기능 완료로 표시 |

| 2 | D432/D433 프리팹 이미지와 객체별 비교 | 기존8키의 준비된 소수부터 실제 이미지·판본·대상/역할·미선정 상태를 함께 볼 수 있음 | 텍스처/혼합 Showcase를 개별 미리보기로 사용, URL만 반환 |

| 4 | D422/D427 Farm 한 구역 배치 | 배치 구조·제약 검사를 거쳐 건물·밭·통로 관계가 정돈된 실제 Game View와 접근·해제/재적용 검증을 반환 | 준비 코드/격리 Prefab/과거 Showcase를 현재 World 배치로 표시 |

순서1의 전량 확장은 첫 작은 저장·조회 결과 이후 분야별로 이어간다. 순서2의 이미지 준비는 순서1과 독립적으로 병행할 수 있으며, 촬영·전담 인계는 기존 담당과 정확 판본을 재사용한다. 다른 순서가 일시 차단되면 실제 선행 조건이 없는 승인 작업을 진행하되 우선순위 변경 사유를 상태판에 남긴다.

순서3은 선택 조작과 영속화의 완결이다. 정확 자산이 아직 선택되지 않은 공방에는 미선정 역할을 유지하며 임의 대안을 채우지 않는다. 필요한 승인 상태 전이는 기존 검토 계약을 재사용하고, 시험용 선택 성공을 사용자의 실제 적합성 승인으로 기록하지 않는다. 새 게임 규칙/구성 의미가 필요한 부분은 별도 판단으로 남긴다.

순서4는 [D422 Farm 배치 경유](Farm월드맵-배치계층경유-점진구성-2026-08-31.md)와 [D427 배치 정돈](농장정돈-상점실내진열-시각배치보완-2026-08-31.md)의 기존 승인 범위다. 승인된 주제/연구·현재 명세·정확 대상과 소유·보호 조건을 다시 결속한 뒤 진행한다. DB 이미지 관리가 전체 맵의 새 필수 의존성은 아니다. 이 순서로 상점 실내 배치 요청을 취소하거나 모든 Farm 객체의 수정/삭제를 승인하지 않는다.

## 3. 대기열은 기존 관리 문서에서 최신 상태로 유지한다

[CURRENT_WORK](CURRENT_WORK.md)와 [개발 통합 상태판](개발통합상태판.md)에 개발이 기존 요청을 기준으로 한 최신 실행 목록을 유지한다. PlayableLoop 작업은 기존 Goal·명세를 참조하고, 서버/자료/이미지 작업을 억지로 게임 Goal이나 새 WI로 등록하지 않는다. 별도 DB 큐나 범용 자동 실행 프레임워크를 이번에 만들지 않는다.

최소 조회 항목은 **요청 ID/승인 원문, 결과물, 담당·소유 경로, 대기/진행/차단/완료, 실제 선행 조건, 완료 근거, 다음 작업**이다. 기존 값과 의미를 대응하여 표시하며 기존 원장 상태 코드를 임의 변경하지 않는다. 순서0~4 외의 이미 맡긴 요청도 소실되지 않도록 기존 항목을 연결해 보류 이유/후속 위치를 표시한다.

- 새 묶음을 시작할 때 승인 원문·현재 상태·명세/경로·선행 조건을 확인한다. 대기열 제목만으로 구현하지 않는다.
- 작은 묶음이 끝나면 개발은 결과를 인수·검증하고 다음 승인 작업으로 이어간다. 전문 제출 완료와 개발 통합 완료는 구분한다.
- 기술 결손은 개발이 처리한다. 범위 밖 회귀 실패는 영향과 격리 근거를 남기고 전체 성공으로 보고하지 않는다.
- 새 게임 선택, 권리·접근 권한 또는 파괴적 변경 승인이 필요한 부분만 보류한다. 같은 실패를 같은 방식으로 반복하지 않는다.
- 새 사용자 중지/변경 지시가 항상 우선이다. 작업 목록 갱신은 예약 실행 설정이 아니며, 앱 종료/idle 이후 자동 재기동이나 상시 실행을 보장하지 않는다. 기존 야간 자동화는 재개하지 않는다.

## 4. 자료·이미지·배치의 별도 완료 경계

공공자료는 이미 맡긴 제한 표본부터 [D429 기본 수집·저장 절차](../Architecture/게임자료조사전문운영.md)의 실제 MySQL 저장·독립 재조회까지 닫는다. 이번 순서 변경으로 새 출처/대량·정기 수집을 배분하지 않는다. 앞선 우선순위로 보류된 자료 요청도 현재 상태를 명시하며 긴급한 게임 선행으로 만들지 않는다.

이미지는 파일 확보, Azure 비공개 업로드·재읽기, DB 연결, 인증된 웹 열람을 구분한다. 정확 대상/접근/사용조건이 미확인일 때는 그 단계만 보류한다. 안전한 로컬 조회를 먼저 반환할 수 있지만 이를 Azure/원격 웹·모바일 접근 완료라고 하지 않는다.

실제 Farm 배치는 담당의 현재 Editor 상태·미소유 변경을 먼저 확인한다. 배치 구조/계획/검사/조립/해제·재적용을 통과시키고, 필요한 실제 화면·보행/접근 결과를 개발이 검토한다. 기존 r129·야간·무관한 중지 작업, 새 Scene/원본 덮어쓰기·전체 Root 해제/강제 복구는 일괄 재개하지 않는다. Logic/Save/E 자동 변경, 운영 원천 변경·공개 게시·commit/push도 승인하지 않는다.

## 5. 역할과 반환

기획은 이 승인 원문과 DECISIONS를 소유하며 새 놀이 문답보다 기존 요청의 완료 여부·사용자 확인 결과를 우선한다. 개발은 현재 D434의 안전한 마감을 유지하고 D435부터 위 순서에 맞게 정확 구현·시험·DB/웹 연결과 전문 배분을 담당한다. 프리팹 조사·자료 조사·공간·애니 담당을 중복 생성하지 않고 공통 코드/Editor 쓰기 소유를 조율한다.

개발은 수신 후 현재 목록과 다음 항목을 기존 상태판에 반영하고 기획에 반환한다. 사용자 보고는 **이번에 실제로 볼/쓸 수 있는 결과, 남은 미완료, 차단과 필요한 사용자 조치, 다음 결과** 위주로 한다. 별도 시험/문서 해시 검증은 개발이 수행하며 기획 문서의 승인·인계만으로 제품 완료를 선언하지 않는다.

기존 미답변 `town-workshop-component-interaction` 등은 그대로 보존한다. 이번 승인은 마무리 순서와 기존 기능 연결의 승인이지 그 미답변이나 모든 자산·개체의 일괄 승인이 아니다.
