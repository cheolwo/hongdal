## 1. 이번에 정한 플레이의 출발점

플레이어는 3인칭 시점으로 수풀 주변을 돌아다니다 허브에 도달한다. 허브는 화물차와 기사 NPC가 드나드는 물류센터 성격의 장소다. 플레이어는 바로 운영 책임이나 과제를 부여받기보다 그곳에서 무슨 일이 일어나는지 알아차릴 시간을 갖고 기사와 대화할 수 있다. 현장 3인칭과 광역 시점으로 살펴볼 수 있으며, 광역 화면의 허브 노드를 클릭하면 입구 내역·접점 내역·출구 내역을 확인할 수 있게 한다. 두 시점 어디에서든 창고를 선택하면 같은 입고·출고·적재 내용을 볼 수 있다. 돌아다니다 NPC에게 퀘스트를 받아 자유롭게 수행하는 흐름을 함께 둔다.

양조장은 이 시작의 필수 장소가 아니라 이후 관심에 따라 선택할 Town 활동으로 남긴다. 기존 농장·숲·공방 사례와 다른 영역의 독립 기능을 삭제하지 않는다. 이번 문답의 허브 도입에서는 D417의 최초 권장 1인칭 대신 3인칭을 사용한다. 기존 저장 복원·전투 잠금·접근성 대체 시점·1인칭 집중 기능을 전역 변경하거나 금지하는 뜻은 아니다. D417/r3 원문과 과거 실행 근거는 그대로 보존한다.

## 3. 입구·접점·출구 — 명칭과 내용은 구분한다

세 내역의 구분은 채택했지만 구체 표시 항목은 아직 정하지 않았다. 특히 ‘입구/출구’를 입고/출고 원장과 자동으로 동일시하지 않고, ‘접점’을 도로 교차점이나 NPC 상호작용으로 임의 확정하지 않는다.

후속 질문의 추천은 **접점을 사람·물품·업무가 만나는 활동 지점으로 묶는 것**이다. 예를 들어 인수대·보관 장소·분류 장소·NPC 의뢰 지점을 후보로 검토할 수 있다. 이는 기존 Hub 인수/보관/할당/출고 준비를 재사용하기 위한 설명안이며 구체 시설·노드·WI·자산 할당 승인이 아니다. 통행상의 교차점과 업무 접점은 구별해서 표시한다.

- 입구: 진입 위치·들어오는 연결·들어오는 물품 정보 중 무엇을 보여줄지 미정.
- 접점: 활동 지점 중심의 해석을 추천하며 사용자 답변 전 `Asked`.
- 출구: 나가는 위치·연결된 장소·출고 관련 정보 중 무엇을 보여줄지 미정.
- 공개 범위: 알려진 장소/단서, 현재 관찰 가능한 내용, 권한이 필요한 운영 내역을 구별한다. 허브 노드 선택을 숨은 전체 재고·모든 경로·NPC 사정의 자동 공개로 확대하지 않는다.
- 세부 조작: 전환 키·카메라 종류/높이·자동 전환·일시정지·발견 판정·실시간 갱신 범위는 미정. 광역 카메라 이동은 캐릭터 이동·순간이동이 아니다.

### 창고는 현장과 광역에서 같은 상태를 읽는다 — D451

- 3인칭에서는 가까운 창고 배치 객체를 선택하고, 광역에서는 해당 창고 노드를 선택한다. 두 진입점은 같은 창고 고유 식별자와 같은 상태 사본을 읽는다.
- 공통 상세에는 `입고`, `출고`, `적재`의 세 묶음을 둔다. 정확 행·수량·예정/완료 구분·시간 범위·정렬과 `적재`가 보관 위치/점유와 차량 상차 상태 중 어디까지 포함하는지는 후속 설계다.
- 시점마다 별도 재고 사본이나 서로 다른 수량을 만들지 않는다. 광역에서 바뀐 것처럼 보인다는 이유로 현장 원장을 수정하거나, 현장에서 선택했다는 이유로 운영 명령을 자동 실행하지 않는다.
- 처음 방문한 플레이어에게 세 묶음의 어느 필드까지 공개할지는 계속 미정이다. 관찰 가능한 요약과 역할·권한이 필요한 상세를 나누며 자료 없음·지연·갱신 실패도 표시한다.
- 창고를 선택할 수 있다는 것은 접근·업무 권한, 문 열림, 내부 이동이나 실제 적재/출고 가능을 자동 증명하지 않는다.

화물차의 출입은 물류센터가 작동함을 보여 주는 생활 표현이다. 실제 도착·대기·하역·출발 상태와 연결할 때에는 같은 권위 상태/행위 기록을 읽고, 단순 반복 애니메이션을 실제 입출고 완료로 표현하지 않는다. 기사 NPC의 대화 가능 여부와 기사에게서 퀘스트를 받을 수 있다는 방향은 채택했지만 대화 내용·업무 역할·퀘스트 종류·보상/실패는 후속 질문으로 남긴다.

### 설명과 도움 요청은 사용자가 선택할 때만 연다 — D455

기사 NPC·창고 등 설명 가능한 대상에는 자동 대화나 강제 팝업 대신 작은 `?` 또는 `!` 표시만 둔다. 플레이어가 현장 3인칭에서 대상을 선택하거나 광역 화면에서 같은 노드를 선택했을 때에만 설명을 연다. 대상 근처에 왔다는 이유만으로 말을 시작하거나 화면을 멈추지 않는다.

- `?`는 상황·시설·현실 자료 대응처럼 읽기 전용 설명이 있음을 알리는 기본 의미로 추천한다.
- `!`는 공개된 도움 요청이나 선택 가능한 퀘스트 후보가 있음을 알리는 기본 의미로 추천한다. 표시를 보는 것과 대화 열기, 퀘스트 미리보기, 수락은 각각 분리한다.
- 두 표시는 같은 대상 고유 식별자·관찰자 공개 범위·상태 판본에서 파생한다. 현장과 광역에서 서로 다른 설명이나 완료 상태를 만들지 않는다.
- 표시가 없더라도 기본 창고 선택·이동·관찰을 막지 않는다. 표시가 있다고 해서 역할 권한·숨은 재고·NPC 사정이 공개되거나 업무가 자동 실행되지 않는다.
- 접근성 대체는 아이콘에만 의존하지 않고 형태/텍스트·화면 읽기용 이름·색상 이외 구분을 함께 준비한다. 정확 크기·거리·겹침·표시 우선순위·컨트롤러/키 입력은 후속 표현 설계다.

D456은 처음에 `?`를 읽기 전용 설명, `!`를 도움 요청·퀘스트 후보로 구분했고 D457은 `?`를 정보/퀘스트 획득 색으로 나눴으나, D462가 `?`의 의미를 일반/메인 퀘스트 위계로 다시 대체한다. `!`가 이미 수락한 퀘스트의 목표가 권위 상태에서 충족되어 완료 확인·보고가 가능한 경우에만 표시된다는 규칙은 유지한다.

- 파란 `?+일반 표식`=일반 퀘스트 후보, 금색 `?+메인 표식`=메인 퀘스트 후보, 초록 `!+완료 표식`=목표 충족 후 완료 확인/보고 가능이다. 순수 상황·시설·현실 자료 설명은 퀘스트 `?`와 충돌하지 않는 중립 정보 표식/기본 대화 항목으로 분리하는 방향이며 정확 도형은 후속 질문이다.
- 색만으로 의미를 전달하지 않는다. 아이콘 내부 작은 문자/모양, 대상 이름 옆 상태 텍스트, 화면 읽기용 이름을 함께 사용한다.
- `!`는 진행 중·실패·단순히 가까이 온 상태에는 나타나지 않는다. 같은 퀘스트 ID·목표 판본·권위 결과에서 완료 가능 상태를 확인한 뒤 표시한다.
- `!` 선택은 완료 내역·결과·보상/다음 선택의 미리보기를 연다. 결과 확인이나 보상 수령이 별도 Confirm이면 선택만으로 정산하지 않는다.
- 최종 완료·정산 뒤 World의 `!`는 사라지고 퀘스트 기록에는 완료 체크와 결과 판본을 남기는 방식을 추천한다. 영구 반복 퀘스트·후속 연쇄의 표시 규칙은 별도다.
- 한 대상에 일반 `?`, 메인 `?`, 완료 `!`가 함께 있을 때는 겹쳐 띄우지 않고 통합 표시 하나를 선택한 뒤 `일반 퀘스트`, `메인 퀘스트`, `완료 보고` 항목으로 나눈다. 중립 정보 설명도 있다면 내부 `정보` 항목으로 함께 정리할 수 있다.

D458은 완료 확인과 보상/결과 정산이 끝난 뒤 World의 `!`를 제거하고 퀘스트 기록에 완료 체크·결과 판본을 남기는 방식을 확정한다. 후속 의뢰는 기존 `!`를 금색 `?`로 바꾸는 화면 연출만으로 만들지 않고, 실제 후속 퀘스트 후보가 생성되고 공개 조건을 충족한 경우에만 새 금색 `?`를 표시한다. 일반 대화·과거 설명은 별도 기본 상호작용이나 기록에서 다시 볼 수 있게 하되 완료 표식을 영구 유지하지 않는다.

### 일반 퀘스트 경험이 메인 퀘스트의 준비 조건이 된다 — D462

- 파란 `?`는 허브의 생활·물류·사람을 폭넓게 경험하는 일반 퀘스트, 금색 `?`는 허브의 핵심 변화와 다음 큰 선택을 다루는 메인 퀘스트다.
- 메인 퀘스트는 관련 일반 퀘스트를 적절히 완료해 필요한 사람·시설·문제 원인을 알고 준비 조건을 갖춘 뒤 열린다. 단순 총 완료 횟수만 채우거나 무관한 반복 퀘스트로 해금하지 않는다.
- 추천은 `물류 흐름 이해`, `구성원과의 신뢰/접촉`, `공공 문제 기여`처럼 서로 다른 준비 범주에서 최소 조건을 만족하는 방식이다. 같은 목적에 여러 일반 퀘스트 대안을 두어 특정 직업·전투·제작만 강제하지 않는다.
- 잠긴 메인 퀘스트는 미발견 내용을 누설하지 않는 범위에서 `준비가 더 필요함`과 공개 가능한 부족 범주를 보여준다. 정확 퀘스트·정답·숨은 보상은 자동 공개하지 않는다.
- 일반/메인 등급 자체가 회복 기여량을 자동 결정하지 않는다. 개인 회복은 의미 있는 완료 품질, 공동체 공공 기여는 실제 문제 완화 효과를 기준으로 하며 작은 메인 퀘스트가 큰 일반 퀘스트보다 항상 높은 보상을 주지는 않는다.
- 메인 퀘스트의 해금과 수락은 분리한다. 조건을 갖춰 금색 `?`가 나타나도 사용자가 선택·미리보기·수락하기 전에는 시작하지 않는다.

### 퀘스트는 게임 문제와 현실 자료의 관계를 함께 이해하게 한다 — D463

일반·메인 퀘스트는 게임 세계의 입고·출고·적재·차량·사람 문제를 다루면서, 그 게임 상태가 어떤 승인 현실 물류 자료와 변환 판본에서 영향을 받았는지 살펴볼 수 있게 한다. 목표는 현실 수치를 맞히는 시험이 아니라 게임에서 한 선택의 원인과 현실의 유사 문제를 함께 이해하는 것이다.

| 층 | 플레이어가 보는 것 | 완료/권위 경계 |
| --- | --- | --- |
| 게임 해결층 | 허브의 현재 물류 상태, NPC 설명, 선택 가능한 조사·운반·정비·조정과 결과 | 게임 상태만으로 퀘스트를 이해하고 완료할 수 있으며 Simulation이 결과를 판정 |
| 현실 이해층 | 출처·지역/기간·원 단위·추세/불균형/품목 비중·게임 변환 요약·한계 | 선택형 참고이며 열람 자체를 완료·회복·보상 조건으로 삼지 않음 |
| 관계 설명층 | 현실 신호가 게임 상황의 어느 부분에 영향을 주었고 어디부터는 시나리오/Simulation 규칙인지 | 현실 자료와 게임 결과를 동일 사실로 표현하지 않고 대응 근거·판본 보존 |

- 퀘스트 설명에는 `게임에서 확인할 일`과 `관심이 있으면 살펴볼 현실 자료`를 분리해 표시한다. 외부 자료를 읽지 않아도 기본 해결 경로는 닫혀야 한다.
- 현실 자료를 살펴보면 원인 이해, 대체 해결책 후보, 결과 보고서의 설명이 풍부해질 수 있으나 정답·최적 수익·실제 구매/계약을 보장하지 않는다.
- 자료 없음·갱신 지연·대응 미검토 상태에서도 게임 Fixture/시나리오의 출처를 명시해 플레이할 수 있어야 한다. 이를 최신 현실 자료인 것처럼 꾸미지 않는다.
- 현실 자료를 열었다는 사실만으로 개인/공동체 회복을 지급하지 않는다. 실제 게임 행위 완료와 공공 문제 완화가 회복 원인이다.
- 완료 뒤에는 `게임에서 일어난 결과`, `참고한 현실 자료`, `서로 다른 점과 한계`, `다음에 알아볼 선택`을 결과 카드와 선택형 보고서 후보에 남긴다. 현실 전문 자격·업무 숙련 인증으로 표현하지 않는다.

### 동적 퀘스트는 그래프 호환 뼈대만 남긴다 — D464

장기적으로 퀘스트는 현재 허브 상태·플레이어가 이미 안 사실·완료 결과·미해결 문제를 읽어 다음 후보를 단계적으로 구성하는 그래프로 발전시킨다. 이번에는 전체 동적 생성 알고리즘과 콘텐츠를 만들지 않고 후속 호환 구조만 남긴다.

- 노드: 일반/메인 퀘스트 후보, 목표, 상태 사본 요구, NPC/시설/품목 대상, 완료 결과, 회복/공공 기여, 현실 자료 참고 후보.
- 엣지: 선행, 해금, 대체 경로, 실패/회복, 완료 후속, 배타/병행, 현실 자료 대응.
- 입력: 같은 Session/WorldRevision의 권위 상태, 플레이어 공개/발견·역할/권한, 기존 완료 ActionRecord, 승인된 퀘스트 Template/Profile과 동결 현실 의미 신호.
- 출력: 자동 수락이나 결과가 아니라 `후보 그래프 + 해금/차단 이유 + 판본`이다. Preview·명시 Confirm 전에는 시작하지 않는다.
- 결정성: 같은 입력과 판본은 같은 후보 그래프를 만들고 Save/Replay·Local/Remote에서 재현 가능해야 한다. LLM 대사는 선행·보상·완료·회복을 결정하지 않는다.
- 기존 WI/Graph/Goal과 별개의 두 번째 권위 원장을 만들지 않는다. 정확 schema·생성 규칙·첫 그래프·UI는 후속 승인이다.

사용자 요청에 따라 퀘스트 문답은 이 판본에서 일단 마감한다. 남은 Asked 항목은 승인으로 간주하지 않고 후속 재개 목록으로 보존한다. 개발은 Confirmed/ConfirmedDirection 중 기존 승인 계약에 결속할 수 있는 가장 작은 범위만 구현하고 `FutureExtension`·`FutureExtensionSkeleton`·Asked를 자동 구현하지 않는다.

### 금색 의뢰의 의미 있는 완료는 개인을 거쳐 공동체 회복에 기여한다 — D459

금색 `?`로 받은 의뢰를 권위 결과까지 적절히 완료하면 플레이어 개인의 NatureMind 회복 축에 작은 기여를 남기는 방향을 채택한다. 이 값은 체력·상처 치료나 즉시 행동력 충전과 구별한다. 기존 `ActionRecordAppend → PlayerProgressionApply/NotApplicable → MeditationProgressionApply/NotApplicable` 순서와 Q122의 의미 있는 행위 완료 회복 원칙을 재사용한다.

개인 회복의 상승은 공동체 회복 관점에도 기본적으로 영향을 준다. 다만 사람 수가 많을수록 무조건 커지는 원시 합계가 아니라, 현재 구성원 범위·개인별 회복/위협·최근성·참여 상태를 정규화한 기본층으로 드러낸다. 공동체에 실제 도움이 된 퀘스트 결과는 이 기본층과 구분된 공공 기여층으로 더 크게 반영한다. 결과, 참여자, 영향 대상·범위, 결과 판본과 반복/멱등 여부를 원인으로 기록하고 기존 Q196~198처럼 개인·공동체 기간 상태의 독립 판정은 유지한다.

- Preview·취소·실패·자동 완료·NPC 대행·같은 결과의 멱등 재요청·보상만 노린 무의미 반복은 개인/공동체 회복 입력이 아니다.
- 개인 회복은 의미 있게 완료했다는 기본 기여이며, 집중 품질·계획 진척·숙련 수행의 추가 기여와 중복 지급 규칙을 명시해야 한다.
- 공동체 회복의 기본층은 구성원 개인 회복의 정규화된 분포를 읽는다. 한 개인의 회복도 작게 영향을 주지만 소수 플레이어의 반복 퀘스트나 인구 수 원시 합계로 급상승하지 않도록 구성원 범위·최근성·상한을 판본화한다.
- 공공 기여층은 물류 적체·식량 부족·시설 고장·안전 위험 등 공동 문제의 실제 완화 정도·영향 범위·참여 분산·지속성을 읽어 기본층보다 큰 변화를 줄 수 있다.
- 같은 퀘스트 완료에서 개인 회복이 기본층으로 반영되는 경로와 공공 문제 해결이 공공 기여층으로 반영되는 경로를 서로 다른 원인 코드로 기록한다. 하나의 수치를 두 번 복제해 더하지 않는다.
- 개인 광복기와 공동체 광복기는 계속 독립적으로 판정한다. 개인 회복 상승이 공동체 광복기를 자동 확정하거나 공동체 상태가 개인 기간을 덮어쓰지 않는다.
- 표시 피드백은 작은 개인 회복과 공동체 기여를 구분하여 보여주고, 정확 수치/문턱/Profile·Save/Replay·UI·음향은 후속 작업 명세에서 정한다.

D461은 공동체 기본층의 구성원을 해당 허브에 실제 소속되고 현재 또는 최근 체류하며 개인 상태가 권위에서 관측되는 플레이어와 NPC로 한정한다. 잠시 지나가는 방문자·통과 차량 기사·상태가 없는 배경 Actor, 관계가 끝났거나 장기간 체류하지 않은 명목상 소속자는 제외한다. 정확 최근성 시간창과 휴가·원정·입원·오프라인 구성원의 처리 규칙은 후속 Profile로 남긴다. 공개 UI는 개인별 내면 상태를 노출하지 않고 공동체 집계와 공개 가능한 주요 원인만 보여준다.

### 현실 물류 자료는 서버에서 게임용 의미 신호로 변환한다 — D452

온라인 쇼핑·택배·창고 입출고 등 현실 물류 자료는 기존 ASP.NET Core 수집 경계와 로컬 Docker MySQL의 비공개 검토 저장을 재사용한다. 원문 행을 Unity나 창고 UI가 직접 읽지 않고, 출처·자료셋·지역·기간·단위·수집 시각·판본·품질·제약과 원자료 해시를 보존한 승인 사본만 게임 변환 후보가 된다.

```text
공식/허용된 현실 물류 자료
  → ASP.NET Core 수집·정규화·검토보류 저장·중복 방지
  → 승인된 현실 자료 사본
  → 세션 시작 시 동결된 물류 의미 신호
  → 게임 세계의 입고·출고·적재 후보/분주함/병목
  → 현장·광역 창고의 동일 게임 상태
  → 사용자가 선택한 현실 자료 상세
```

- 현실 수치와 게임 수치는 같은 값이 아니다. 국가·산업 단위 물동량을 창고 한 곳의 상자 수로 복사하거나 현실 증가율을 게임 보상·수익으로 바로 환산하지 않는다.
- 변환에는 대상 지역/기간, 품목 분류, 게임 시간 배율, 허브 규모, 시나리오 계수와 변환 판본을 기록한다. 대응할 수 없거나 낡은 자료는 `자료 없음`·`갱신 지연`·`대응 미검토`로 표시하며 임의 값으로 메우지 않는다.
- 게임의 실제 입고·출고·적재 상태는 Simulation 권위가 소유한다. 현실 자료는 승인된 의미 신호 또는 초기 후보를 제공할 수 있지만 입출고 완료·재고 변경·차량 도착을 직접 확정하지 않는다.
- 현실 자료 상세는 창고/거래 상세에서 관심이 생긴 사용자가 선택해 연다. 출처, 기준 기간/지역, 원 단위, 게임 변환 요약과 한계를 보여주되 열람을 퀘스트 완료·성장·보상의 조건으로 만들지 않는다.
- API 이용조건·재배포·보관기간·인증 정보가 확인되지 않은 자료는 게임 노출 후보로 승격하지 않는다. 원격 운영 DB·정기/대량/유료 수집과 게시도 별도 승인 범위다.

첫 데이터셋·정확 공급처·수집 주기·품목 대응·현실→게임 변환식·사용자에게 보여줄 원문 범위는 아직 미정이다. 기존 `ExternalDataSourceCatalog`·수집 Runtime·`SimulationRealityContext` 경계를 우선 재사용하고 병렬 수집기나 두 번째 현실 원장을 먼저 만들지 않는다.

D453은 첫 게임 변환 신호를 `입고량·출고량 추세`, `입출고 불균형`, `품목군 비중`으로 확정한다. 이 값은 원자료와 변환 판본을 가진 상대 단계이며, 창고의 분주함·적재 압력과 기사 대화의 공개 단서가 같은 동결 사본을 읽는다. 정확 구간 수·임계값·시간창·품목군 분류는 실제 후보 자료의 분포와 품질을 조사한 뒤 정하며, 기획만으로 임의 수치를 고정하지 않는다.

### 접촉한 게임 데이터를 선택형 현실 대응 보고로 다시 본다 — D454

플레이어가 원할 때 자신이 실제로 접촉한 게임 객체·품목·허브 사건·선택 기록 가운데 현실 자료 대응이 검토된 항목만 모아 보고서를 만들 수 있는 장기 확장 방향을 둔다. 이는 게임 기록을 현실 사실로 단순 치환하는 기능이 아니다. 각 항목은 `게임에서 본 것`, `대응하는 현실 자료`, `왜 연결했는지`, `출처·지역/기간·단위·최신성`, `해석 한계`를 나란히 보여준다.

- 기본값은 생성·발송 모두 꺼짐이다. 플레이어가 대상 기간·포함 항목·전달 수단을 선택하고 보고서 미리보기를 확인한 뒤 별도로 발송을 확정한다.
- 이메일·다른 연락 수단은 게임 계정 공개 범위와 분리된 연락처 동의·검증·철회·발송 기록·실패 상태를 요구한다. NPC 대화, 창고 열람이나 퀘스트 수행만으로 구독시키지 않는다.
- 대응 미검토·자료 없음·낡음·권리상 재노출 불가 항목은 이유를 표시하고 제외한다. 게임 가격·수량·성과를 현실 수익·구매·계약·투자 추천으로 변환하지 않는다.
- 보고서는 플레이 기록 요약과 선택형 현실 참고이며, 실제 업무 실행·상품 구매·보험/계약·자동 연락·광고 발송을 포함하지 않는다.
- 보고서 판본은 접촉 기록 범위와 현실 자료 사본/변환 판본을 보존하여 같은 입력의 재생성 근거를 남긴다. 원자료가 갱신되면 과거 보고서를 조용히 다시 쓰지 않고 새 판본 후보로 구분한다.

첫 보고서의 정확 형식·주기·보존기간·전달 채널·수신자·연락처 처리·구독 해지·비용은 미정이다. 이번에는 미래 확장으로만 기록하며 이메일 서비스·메시징 Provider·계정/연락처 DB·스케줄러를 만들거나 연결하지 않는다.

## 4. 기존 WI·그래프·자산과 E6 준비 연결

새 WI를 바로 등록하지 않고 기존 이동·관찰/조회·NPC 대화·수락/수행의 실제 범위부터 대조한다. 패널 열기나 시점 전환은 그 자체로 새 권위 변화 WI가 아닐 수 있다. 기존 Hub Q240~249의 운영 의미와 Q250의 미완료 대응 보류는 보존한다. 자유로운 퀘스트 선택이 수락 이후의 기한·약속·실패·회복 규칙을 없애는 뜻은 아니며 구체 퀘스트 조건은 후속 문답이다.

| 공식 절차의 검토 | 이 사례에 필요한 준비 |
| --- | --- |
| 그래프 레벨 1 | 수풀 접근·허브·선택한 활동 지점과 필요한 접근/복귀 관계. 허브 노드의 H1/H2/H3 대응은 크기만 보고 확정하지 않는다. 업무 인과와 통행 엣지를 분리한다. |
| 그래프 레벨 2 | 선정된 활동의 출입·지지·통로·간섭·시야와 자산 후보/판본. 기존 수풀·건물·물품·NPC 자산 목록을 조사하되 실제 장소에 미리 배치하지 않는다. |
| E4 준비 | 기존 시점·노드 조회·허브 상태/권한 공급·NPC 참여 계약과 후보 대응, 표현 소유·적용/해제·회복의 결손을 명시한다. |
| E5 실제 성립 | 승인된 상태 사본과 같은 대상의 노드 선택·내역 표시·필요한 현장 접근/입력 결과를 연결한다. 이번 문서로 입증한 것은 없다. |
| E6 정제 | 현장과 광역 내역이 같은 허브를 설명하는지, 어떤 일을 할 수 있는지 이해되는지, 열람 후 현장에 돌아올 수 있는지, 미발견/권한 정보가 새지 않는지 정제한다. 현실 물류 자료가 쓰이면 출처·지역/기간·단위·품질·변환 판본·한계와 선택형 상세를 결속하되, 자료 수집만으로 E6를 선언하지 않는다. |

개별 기능의 실제 E는 기존 검증 그대로 유지한다. E6 공식 절차 사용과 실행 권한·완료는 별개이며 전체 월드맵이나 모든 영역을 완성해야 이 도입을 검토할 수 있는 구조로 만들지 않는다.

## 5. 허브를 데이터 통합과 개발 정밀화의 중심 사례로 쓴다 — D450

허브에는 여러 영역에서 온 요청·물품·사람·업무 진행 정보가 모인다. 그래서 허브를 **모든 상태의 최종 소유자**가 아니라 **여러 영역의 판본화된 상태 사본을 비교하고 허브 내부 결정을 내리는 통합 지점**으로 사용한다. 이 구조는 한 화면에 데이터를 많이 쌓는 것이 목적이 아니라, 동일한 작은 허브 사례로 아래 경계를 반복 검증하여 개발 효율을 높이는 데 목적이 있다.

```text
영역별 상태 사본
  → 허브가 읽을 수 있는 요약
  → 현장 3인칭 관찰
  → 광역 노드의 입구·접점·출구 내역
  → 플레이어가 선택한 Preview·Confirm 또는 퀘스트 참여
  → 허브 내부 결과와 각 원천의 후속 상태 재조회
```

| 허브에서 함께 읽을 층위 | 책임과 개발 효율 | 섞지 않을 것 |
| --- | --- | --- |
| 원천 상태 | Nature·Farm·Town·City 또는 독립 Fixture가 발행한 요청·공급·위험·시간창의 판본화된 사본 | 허브가 다른 영역의 생산·욕구·계약을 임의 생성하거나 수정하지 않음 |
| 허브 내부 상태 | 실제로 도착한 물품, 보관·예약·분류·피킹·출고 준비, 허브 NPC/시설의 현재 업무 | 화면 카드 표시와 실제 예약·할당·완료를 구별 |
| 플레이어 관점 | 현재 위치·발견/지식·공개 범위·역할/권한에 맞는 현장과 광역 요약 | 미발견 장소·숨은 재고·다른 NPC의 사정을 자동 공개하지 않음 |
| 선택 가능한 일 | NPC 대화·퀘스트 후보·미리보기·거부/수락·중단/복귀 | 목록 생성과 퀘스트 자동 수락·보상 확정을 구별 |
| 근거·최신성 | 원천·기준 시각·상태 버전·마지막 성공·지연/결손·Simulation/실운영 구분 | 오래된 값이나 자료 없음 상태를 현재 사실로 메우지 않음 |

### 허브 중심으로 개발하되 전역 의존점으로 만들지 않는다

- 첫 검증은 다른 네 영역의 완성을 요구하지 않고 판본화된 입력 Fixture와 허브 내부 상태로 독립 완결할 수 있어야 한다. 각 영역이 준비되면 같은 입력 계약의 Adapter만 실제 상태 사본으로 교체한다.
- 허브 화면·그래프 노드·UI가 원장을 대신하지 않는다. 상태 변경은 기존 Simulation 또는 서버 권위의 Preview·명시적 Confirm·재조회 경계를 따른다.
- 허브에서 공통으로 발견한 상태 사본·최신성·권한·표현 모듈은 실제 의미가 같은 다른 영역에서 재사용한다. 허브 전용 용어를 억지로 전역 추상화하지 않는다.
- 많은 데이터는 기본 요약·선택한 노드 상세·출처/판본 상세로 점진적으로 펼친다. 처음부터 모든 원장 필드를 한 화면에 노출하지 않는다.
- 한 허브 사례의 Logic·Presentation·실제 화면 근거를 각각 쌓으며 자동시험 성공을 실제 광역 시점·노드 클릭 완료로 확대하지 않는다.

이 방향은 개발 우선순위를 허브 하나에만 고정하거나 Farm·Town·City를 허브의 하위 기능으로 만드는 결정이 아니다. 독립 영역 개발 정책을 유지하면서, 공통 경계를 검증하기 좋은 대표 사례로 허브를 적극 활용한다. 기존 D437~D440의 게임 객체·시각 자산·자동 할당 자료는 표현 후보 조사에 재사용할 수 있지만 DB에 있다는 이유만으로 E4/E5 자산 결속이나 적합성 승인을 완료한 것으로 보지 않는다.

### 기존 계약 읽기 인수와 가장 이른 공백

개발의 읽기 검토에서 D450은 기존 Q240~250의 `DemandSignal 상태 사본 → Hub 카드 → 할당 Preview → 명시적 Confirm → 피킹·출고 준비 → 결과 귀환` 경계와 정합하고, 실제 네 영역 Runtime 없이 독립 Fixture로 시작한 뒤 Adapter를 바꾸는 구조도 재사용 가능하다고 판정했다. 기존 NPC 루틴에는 재고 개정 번호·원천 식별자·갱신 Tick·행위 촉발 출처와 Local/HTTP 공통 조회 근거가 있다. 파일·시험·DB·Editor를 다시 실행한 결과가 아니라 현행 코드·문답의 읽기 대조다.

다만 현재 근거의 실제 범위는 **Hub 내부 재고 하나를 NPC 루틴이 처리하는 Logic E3 / Presentation·통합 E1**이며, 네 영역 수요 카드나 플레이어 희소 재고 할당·광역 노드 UI가 아니다. 특히 아래 공백은 E4/E5 전에 분리한다.

- 기존 NPC 루틴은 시스템 계획자/NPC 정책이 작업을 만들며 플레이어 직접 Confirm을 허용하는 퀘스트 계약이 아니다. 자유로운 NPC 퀘스트는 별도 Preview·수락/약속 계약이 필요하다.
- 기존 조회 결과에는 발견 여부·관찰자 역할·권한별 필드 공개가 없다. 내부 재고·Task/NPC 식별자와 차단 사유를 광역 UI에 그대로 노출하지 않는다.
- 세계 Tick/개정 번호는 세션 최신성 근거지만, 영역별 원천 사본의 기준 시각·마지막 성공·지연·결손을 각각 설명하지는 못한다.
- Hub 입지/건설 Preview와 광역 노드 상세 열람은 다른 기능이다. 클릭을 건설 Confirm·캐릭터 이동·순간이동으로 연결하지 않는다.
- 입구·접점·출구의 실제 노드/H·카메라/UI·현장↔광역 판독과 E5 대상 결속은 아직 근거가 없다. Q250의 부분 납품·대체품·협상·실패/보상도 `Deferred`를 유지한다.

따라서 나중에 구현이 승인되면 기존 Hub Fixture는 그대로 두고 **원천 사본 식별/개정·기준 시각/상태 → 관찰자 공개 범위 → 읽기 전용 Hub 요약 → 선택 노드 상세 → 기존 Preview/Confirm로 가는 명시적 링크** 순으로 작은 계약을 검토한다. 기존 NPC 루틴 조회나 Command를 광역 UI 모델로 겸용하지 않는 방향을 우선한다.

## 6. 다음 핵심 질문과 인계

창고·현실 물류·일반/메인/완료 표시·개인/공동체 회복·게임/현실 이중 이해까지 기획했다. 동적 퀘스트는 후보 그래프 뼈대만 남겼으며 사용자 요청에 따라 퀘스트 문답을 일시중지하고 개발 인계로 전환한다.
