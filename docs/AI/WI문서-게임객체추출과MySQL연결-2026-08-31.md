# WI 문서에서 게임 객체를 추출하여 MySQL에 연결한다

- 판본: `wi-document-game-object-extraction.plan.r1` / D435 / 2026-08-31.
- 상태: `ApprovedScopedWork` — 기존 WI/문답을 근거로 한 편집용 게임 객체·WI 사용 관계의 추출, 제한 서버/MySQL 저장·재조회.
- 의미 식별자: `wi-document-derived-game-object-registration` / `Confirmed`.
- 사용자 요청: 기존 WI와 ‘나·너’ 등으로 정리한 기획에서 드러나는 게임 객체를 찾아 지금 마련하는 게임 객체 테이블에 저장한다.

## 1. 기존 체계를 연결한다

[공통 플레이 관점](../Architecture/플레이어중심게임개발업무구조.md), [WI 전체 준비](WI전체-E4문서코드자산준비-2026-08-31.md), [D434 객체/다중 자산 구성](게임객체-다중자산구성과공방-개발인계-2026-08-31.md)을 따른다. 별도 게임 객체 대장·새 검색기나 WI 체계를 만들지 않는다.

이번 기획에서 직접 읽은 [공식 WI 목록](../../eng/execution-ledgers/world-interactions.json)은 `simulation-world-interactions.r43`/105항목이다. [기존 관계 입력](../../eng/planning-inquiries/spatial-relations.json)은 WI 목록과 [문답 검색기](../../eng/planning-inquiries/manage-inquiry-search.ps1)를 연결하고 시간/공간/player/target/choice/result/nextChoices 및 원문 근거를 가진다. [WI 생성 조회](generated/planning-inquiry-wi-preparation.md)와 [순환 생성 조회](generated/planning-inquiry-circulation.md)는 탐색 출발점이지 독립 승인 원문이 아니다. 새 추출 실행 전 개발이 현재 원문·색인의 판본/신선도를 확인하며 이번 읽기를 전량 의미 재검증으로 보고하지 않는다.

개발이 작성 중인 [게임객체시각구성](../../Ssalddel.Domain/Content/게임객체시각구성.cs)과 [계약](../../Ssalddel.Contracts/Admin/Content/게임객체시각구성Contracts.cs)은 편집용 정의/구성 판본·역할항목을 관리한다. 아직 작성 중인 코드의 존재를 시험/DB 저장 완료로 표현하지 않는다. D434의 정의 저장을 재사용하고, WI 참여 관계/원문 근거를 담는 데 꼭 필요한 최소 확장만 개발이 선언한다.

## 2. 무엇을 추출하고 무엇을 구분하는가

**WI·기획 원문 → 객체/비객체 구분 → 기존 정의와 대조 → 객체 정의와 WI 참여 관계 저장 → 역할별 자산 후보·이미지 검토** 순서로 진행한다. 문장을 명사 단위로 잘라 전부 GameObject로 만들거나 이름이 같다는 이유만으로 합치지 않는다.

| 문서에서 읽는 것 | 저장 의미 | 자동 생성하지 않는 것 |
| --- | --- | --- |
| 나 | 플레이어/실행 Actor 정의와 해당 WI에서의 행위자 역할 | WI마다 다른 플레이어 정의, 실제 사용자/Session 인물 |
| 너 | 상대 NPC·대상 사물·자원·환경 객체와 WI의 대상 역할 | NPC를 단순 장식 부품으로 취급하거나 숨은 정보 공개 |
| 도구·투입물·결과물 | 도구/재료/예상 결과물 정의와 사용·소모·생성 결과 역할 | 실제 장비 지급·수량 차감·재고/결과물 인스턴스 |
| 여기 | 기존 H/AreaSet/공간과 장소 역할 참조; 근거가 있는 시설 정의 | 모든 H를 새 물체로 복제하거나 포함 관계를 물리 배치로 확정 |
| 지금·대상 상태·능력 | 시간/상태/능력 조건을 관계 문맥으로 참조 | 춘분·낮·숙련도·접근 가능 등을 각각 프리팹 객체로 생성 |
| 지식·허가·UI·금융 등 비물리 대상 | 정보/상태/표현 방식 분류와 기존 원천 참조 | 장부 행·채무·정책마다 실물 객체나 프리팹 할당 |

‘나/너’는 WI 안의 역할이다. 같은 NPC/플레이어가 다른 WI에서는 행위자나 대상이 될 수 있으므로 정의의 고정 두 분류로 사용하지 않는다. 자기 대상·복수 대상도 표현하고 가짜 외부 대상을 만들지 않는다.

서 있는 나무/벌목된 나무, 생육/수확 가능 작물은 기존 상태 모델을 먼저 재사용한다. 별도 결과물(예: 통나무)은 원문이 별도 대상을 정의할 때 구분한다. 상태 변화인지 새 정의인지 모호하면 검토 필요로 남긴다. 지식 출처가 책인지 NPC인지 미정이면 임의 책 프리팹으로 확정하지 않는다.

## 3. 객체 정의와 WI 사용 관계

한 WI에 여러 객체가 참여하고 한 객체를 여러 WI가 사용하므로 WI↔객체 정의는 다대다다. D434의 객체↔자산 구성 관계와 다르다. WI 참여 관계를 공방의 건물/통 같은 시각 부품 항목에 억지로 넣지 않는다.

최소 보존 의미:

- 기존 WI ID, 객체 정의 ID, 문맥별 역할(행위자/대상/도구/투입물/결과/장소 등), 대상 상태·참조 조건.
- 원문 경로/절 또는 Q·의미 ID, 원문/대장 판본과 hash, 연결된 주제/명세 근거. 같은 객체에 여러 WI/여러 출처를 연결한다.
- 원문의 결정 상태, 추출/검토 상태, 정의/자산 선정 상태를 분리한다. `ConfirmedDirection`, `Asked`, `FutureExtension`을 현재 구현 승인으로 바꾸지 않는다.
- 직접 명시·기존 정의 재사용·해석 후보·근거 누락을 구분한다. 기술 해시 일치가 객체 의미/동일성 검토를 대신하지 않는다.

원문은 계속 기획 의미의 권위이고 MySQL은 추적 가능한 편집용 정의·조회 자료다. DB 편집이나 프리팹 선정으로 WI 규칙을 역으로 덮어쓰지 않는다. 기존 정식 ID를 우선 재사용하고 신규 정의 ID는 중복/동의어/종류·개별 차이를 대조한 뒤 안정적으로 발급한다. 최초 이름만으로 공방·작업대·현실 시설을 합치지 않는다. 기존 실세계 사업자/사용자 개인정보를 추출 표본으로 복제하지 않는다.

## 4. 첫 검증 묶음과 전량 확장

개발은 현행 공식 WI 전체를 **조회·분류 대상 목록**으로 확보한다. 모든105개를 의미 승인/자산 배치 완료로 약속하거나 한꺼번에 DB에 강제 등록하지 않는다. 기존 자료에서 명시된 객체는 작은 묶음으로 계속 저장하고 미검토·모호/누락·비객체도 빠짐없이 구분한다.

첫 적용은 서로 다른 성격의 다음 세 WI를 우선한다. 아래는 기획 대조 출발점이며 자산/수량·완료 규칙의 신규 승인표가 아니다.

| WI | 읽은 원문에서의 추출 출발점 | 구분할 것 |
| --- | --- | --- |
| WI-NATURE-06 나무 벌목 작업 시작 | 플레이어, 장착한 벌목 도구, 나무; 후속 Task의 통나무 결과 참조 | 시작 WI를 즉시 벌목 완료로 만들지 않음. 능력/상태/점유는 별도 객체가 아님 |
| WI-FARM-04 익은 농작물 수확 | 실행 Actor, 수확 대상 재배 단위/작물, 수확 Lot 결과 | PlayerOrNpc와 위임 문맥·품목 정의/재배 단위/화물 상태 구분; 기존 수치/규칙 불변 |
| WI-ACTOR-03 지식 습득 | Player, 승인 지식 출처, 처방 지식 참조 | 비물리 지식과 실제 책/기록지/교사 표현 구분; 출처 미정이면 미선정 |

D434의 Town NPC 공방도 기존 정의 재사용 대상으로 포함한다. 정식 대응 WI가 아직 없으면 기획 근거만 연결하여 `WI 미연결`로 반환하고 새 양조 WI ID를 만들거나 `WI-CRAFT-BREW`(배합물 달이기)를 이름만 보고 발효 양조로 전용하지 않는다.

첫 묶음 후 농장·Town·Hub·City·자연 등 기존 분야별로 확장하되 전체 조사를 첫 저장의 선행으로 두지 않는다. 새 놀이 의미를 정해야 하는 항목만 기획에 돌려보내고 다른 명시 항목은 진행한다. 전체 WI 수/검토 WI 수/객체 정의 수/참여 관계 수/미검토·제외 수/실제 DB 저장 수를 나누어 보고한다.

## 5. 구현·저장·검증

기획 원문을 임의 문자열/URL 입력으로 서버가 읽는 API나 별도 LLM/외부 유료 추출 서비스를 만들지 않는다. 기존 조회/검토 관계와 등록된 원천 범위로 제한한 가져오기를 사용한다. 초안 추출은 허용하되 모호한 연결은 검토 필요로 저장하고 승인된 실제 게임 객체로 소비하지 않는다.

개발이 D434의 정확 소유 경로와 합쳐 최소 관계/근거 필드·서버 조회/가져오기·시험을 선언한다. 기존 검토·관리자 권한/개정/멱등/이력·자산판본 경계를 재사용하고 필요하면 기존 Context에 좁은 관계 저장을 추가한다. D434 작성 중 계약을 다른 담당이 동시 수정하지 않는다. 원문/공식 WI/공통 방법론은 읽기 전용이다.

실제 저장은 재확인한 기존 로컬 `hongdal-mysql-1/hongdal_dev`의 편집용 자료 범위다. D431/D434 기록을 삭제하거나 전체 마이그레이션·운영 원천/별도 앱 연결 설정 변경을 하지 않는다. 실제 Session/Actor/재고·World 생성, WI 활성화, 게임 Save/Scene·E 승격은 없다.

필수 확인:

1. 같은 입력 재처리 시 정의/관계 중복 없음; 여러 WI가 같은 객체를 재사용하며 같은 객체의 복수 역할은 보존.
2. 잘못된 WI/원문·객체 참조, 오래된 hash/판본, 중복/충돌·타 권한·임의 경로를 거부하거나 명확한 검토 상태로 분리.
3. 해석 후보·비객체/정보형·WI 미연결, 부정문/가정/미채택·미래 방향의 오인 방지.
4. 원문 변경 시 이전 추출 근거를 보존하고 영향 관계를 재검토 대상으로 표시; 원문에서 사라진 항목을 자동 삭제하거나 현재 승인으로 유지하지 않음.
5. 정의 저장·WI 관계·이력의 일관성/실패 재시도, 독립 조회 문맥에서 실제 MySQL 재확인, D426/D431/D434 기존 호환 회귀.

미선정 프리팹이 있어도 객체·관계 저장은 진행한다. [D433](프리팹이미지-전담조사와Azure보관-2026-08-31.md)의 전담 이미지 조사와 [D434](게임객체-다중자산구성과공방-개발인계-2026-08-31.md)의 역할별 자산 구성은 후속으로 연결하며 보유 자산에 맞춰 객체 의미를 바꾸지 않는다.

## 6. 소유·인계와 미답변

기획은 이 원문과 DECISIONS만 작성한다. 개발은 추출/가져오기·DB·회귀·기존 조회 연결/문서 검증·CURRENT_WORK/통합판을 소유하고 필요한 전문 조사만 조율한다. 보고는 `docs/Reports/WI문서-게임객체-D435-개발통합-2026-08-31.md`, 임시 결과는 `artifacts/local/validation/wi-game-object-extraction-d435/`다. 정확 기술 파일 경로는 착수 전에 개발이 반환한다.

D434 구현 중인 묶음은 안전한 통합 경계까지 유지하며 이번 요청으로 재시작/폐기하지 않는다. 독립 원문 조사는 병행 가능하다. D433 이미지 저장/웹과 이 추출을 서로의 전체 완료 조건으로 삼지 않는다. 기존 r129/야간·Editor·Scene·commit/push 중지는 유지한다.

이번 답변은 객체 추출/DB 연결 승인이다. 이전 `town-workshop-component-interaction`의 설비 직접 선택/장식 비조작은 여전히 `Asked`이며 자동 승인하지 않는다. 다음 새 놀이 질문은 추출에서 발견한 실제 의미 공백 하나를 근거로 이어간다.
