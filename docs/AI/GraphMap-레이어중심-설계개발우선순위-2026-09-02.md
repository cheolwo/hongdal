# Graph Map 레이어 중심 설계·개발 우선순위

- 기획 ID: `PLAN-GRAPH-LAYER-FIRST-WORKFLOW-001`
- 기획 분야: `Graph Map / 설계 운영`
- 기획 판본: `graph-map-layer-first-workflow.r1`
- 상태: `ActivePlanningPriority`
- 상위 기획: `PLAN-GRAPH-NORTHERN-LIFE-001`
- 관련 하위 기획: `PLAN-GRAPH-LONG-ROUTE-ENCOUNTER-001`, `PLAN-GRAPH-HUB-LOGISTICS-CIRCULATION-001`
- 관련 결정·기준: [Graph Map 기획 인계 순환](../Architecture/GraphMap기획인계순환체계.md), [Graph Map 개발 인계](../Architecture/GraphMap개발인계체계.md)
- 관련 WI·PlayableLoop: 레이어별 닫힌 작은 부분 그래프에서만 기존 WI·Goal·작업 명세 후보를 대조
- Graph Map 영향: 기준 공간·기상·시간·운송·위협·경비·물류·보급·플레이어 선택 레이어의 설계 순환
- 다음 질문 또는 인계 상태: 이 문서의 제품 설계 우선은 유지하되, 기존 기획 현행화는 별도 전수 목록에서 분야 우선순위 없이 진행
- 적용 기간: 사용자가 다른 우선순위를 정하기 전까지
- 기준 절차: [Graph Map 기획 인계 순환](../Architecture/GraphMap기획인계순환체계.md), [Graph Map 개발 인계](../Architecture/GraphMap개발인계체계.md)

## 방향

당분간 게임 기획은 새로운 기능과 이야기를 계속 넓히는 것보다, 현행 Graph Map의 안정 노드·엣지와 레이어를 중심으로 정밀화한다. 기획 하나는 최소한 `어느 레이어에서`, `어떤 노드·엣지의`, `어떤 입력·비용·상태·선택·결과가 달라지는가`를 설명해야 Graph Map 인계 후보가 된다.

Graph Map은 기획을 줄이는 도구가 아니라 구현 가능한 구조로 바꾸는 중간 기준이다. 모든 기획을 즉시 코드로 만들지는 않지만, Graph Map에서 닫힌 작은 부분 그래프는 기존 Goal·WI·E7 작업 명세와 결속해 개발 후보로 넘길 수 있다.

## 당분간 우선하는 레이어

1. 기준 공간 topology
2. 기상·시간
3. 운송
4. 위협·경비
5. 물류·보급
6. 플레이어 선택·조회

새 레이어는 기존 레이어로 책임을 표현할 수 없는 경우에만 제안한다. 화면 탭이나 색상을 늘리기 위해 업무 레이어를 새로 만들지 않는다.

## 기획 한 건의 최소 산출물

| 항목 | 필요한 내용 |
| --- | --- |
| 기획 근거 | 현재 승인 문서·판본·SHA-256 |
| 대상 레이어 | 한 개의 주 레이어와 필요한 보조 레이어 |
| 기준 topology | 재사용할 안정 노드·엣지·하위 맵·port |
| 입력 | 권위 상태, 관측, 자료 출처, 신선도 |
| 파생값 | 비용, 용량, 위험, 상태, 후보와 계산 근거 |
| 플레이어 선택 | 보고 비교하며 Confirm·중단·우회·귀환하는 지점 |
| 결과 | 권위 결과, ActionRecord, 다음 선택과 복구 |
| 미정 | 임의로 채우지 않을 수치·자산·코드·실행 증거 |

이 표를 채우지 못한 아이디어는 폐기하지 않고 `PlanningReference`로 보존하되 Graph Map 개발 인계는 하지 않는다.

## 설계에서 개발까지의 순환

```text
기획 질문·승인
  → 주 레이어와 영향 노드·엣지 지정
  → 기존 Graph Map 안정 ID 대조
  → 레벨 1 플레이 관계 반영
  → 레벨 2 비용·배치·통행·회복 제약 반영
  → 레벨 3 기존 코드·계약·시험 결속 조사
  → Integrated / Blocked / NoImpact
  → 닫힌 작은 부분 그래프 추출
  → 기존 Goal·WI·E7 재사용 또는 새 관문 필요 판정
  → ReadyForDevelopment
  → 개발의 AcceptedByDevelopment / Blocked / Deferred
  → 코드·시험·Runtime·Game View 증거를 분리해 반환
  → Graph Map과 기획 판본 재결속
```

기획 스레드는 Graph Map 원본이나 생성물을 직접 수정하지 않고 승인 판본과 영향만 인계한다. Graph Map 담당은 중간 진행을 반복 보고하지 않고 최종 상태를 반환한다. 개발은 `ReadyForDevelopment`만으로 자동 시작하지 않으며 현재 파일 소유와 검증 상한을 다시 확인한다.

## 확장 억제 규칙

- 새 아이디어가 기존 노드·엣지·레이어에 미치는 영향이 없다면 현재 Graph Map 개발 범위로 확대하지 않는다.
- 한 번에 전체 World를 구현하지 않고 진입·결과·복구가 닫힌 부분 그래프 하나만 고른다.
- 기상·운송·위협·물류가 같은 비용을 중복 계산하지 않도록 원인 계보를 유지한다.
- 수치·자산·Scene·실제 입력이 미정이면 문서 후보와 실행 증거를 구분한다.
- 알고리즘 선택보다 입력 의미·비용 단위·차단·복구·플레이어 Confirm을 먼저 안정화한다.
- 영역 간 경로를 다루더라도 Farm·Hub·Town·City의 독립 플레이 폐루프를 시작 선행 조건으로 바꾸지 않는다.

## 첫 개발 후보 묶음

### 후보 A — 레이어 대장과 구조 검사

- 기존 `graph-map-overlays.v1.json`을 단일 기준으로 재사용한다.
- 기상·시간뿐 아니라 운송·위협·물류·선택 레이어의 공통 필드와 대상 안정 엣지 참조를 표현할 수 있는지 검토한다.
- topology 변경 금지, 권위 변경 금지, 판본·근거·신선도·비용 중복 금지 검사를 기존 Graph Map 도구에 추가할 수 있는지 평가한다.
- 이것은 문서·구조 검사이며 실제 게임 경로 계산이나 E5가 아니다.

### 후보 B — 작은 다중 경로 Fixture

- 실제 World 배치 전에 거점 3개와 병렬 경로 3~4개인 결정적 Fixture를 사용한다.
- 기상 보정 전후, 한 엣지 `Degraded`·`Blocked`, 대체 경로, 용량 부족을 구분한다.
- 빠름·안전·저렴·대량 후보의 구성 요소와 선택 이유를 사본으로 반환한다.
- Dijkstra·Yen·Pareto·최대 유량 가운데 필요한 최소 조합은 정확 입력 계약과 E7 관문 뒤 개발이 결정한다.

### 후보 C — 실제 PlayableLoop 결속

- 후보 A·B가 통과하고 승인된 Goal·WI·E7이 있을 때만 실제 운송·보급 부분 그래프 하나를 고른다.
- Simulation 상태, ActionRecord, 중단·우회·복구와 Unity 조회 표현을 같은 revision으로 검증한다.
- 실제 Scene·입력·Game View는 월드·공간·배치 담당이 반환하고 개발이 통합한다.

## 현재 완료 의미

이 문서로 레이어 중심 우선순위와 설계·개발 순환을 정했다. 아직 Graph Map 레이어 대장 확장, 알고리즘 구현, 실제 운송, 보급로 차단, Unity 표현, E 승격은 완료되지 않았다.
