사용자 시각 판단에 따라 PolygonFarm `SM_Bld_WaterTower_01`은 공급사 이름과 무관하게 급수탑보다 곡물 사일로·식량 저장탑으로 먼저 읽히므로 급수점 발전형에서 제외한다. 해당 렌더는 삭제하지 않고 식량 저장 시설의 시각 후보로 재분류 대기한다. 급수점의 기능 발전은 `수동 우물 → 동력 펌프가 붙은 우물 또는 펌프장 → 압력 상수관·상수도 급수망`으로 다시 제안한다. 사용한 물을 내보내는 배수관·하수도는 급수점의 상위 상태가 아니라 별도 배수·오수 처리 노드와 Edge로 분리한다. 보유 자산에는 City 배관 조각·소화전, Construction 물탱크·배관, Town 배수구·배수관 후보가 있으나 실제 조합과 기본형 채택은 다음 시각 검토 전 `Asked`다.

사용자 확인으로 우물 이후 발전 방향의 의미를 `상수도`로 확정한다. 보유 팩에는 배관 조각·소화전·물탱크가 있지만 생활농장에서 호스를 연결해 사용하는 완성 급수점은 없으므로 프로젝트 소유 `농장 상수도 급수점 H1` r1 후보를 Blender로 제작했다. 약 1.25×1.02×1.11m 기초 위에 급수함, 지하 상수관 유입, 전면 차단 밸브와 압력계, 파란 호스 출수구를 두고 `WaterMainIn`, `HoseOut`, `Service` 세 기준점을 기록했다. Synty 배관과 호스 릴은 형식 참고만 했고 공급사 메시를 파생 FBX에 포함하지 않았다. 이 후보는 사용자 외형 검토 전이며 Unity Import·Prefab/Scene·실제 유량·E5는 열지 않는다.

사용자는 r1 급수함 외형을 `농장 상수도 급수점 H1` 시안으로 채택하고 파란 호스 연결구를 실제 소켓처럼 열어 달라고 정했다. r2는 막힌 마개를 제거하고 청색 결속 링 안쪽에 어두운 관내 공간이 보이는 개방형 소켓으로 바꾸며, `Anchor_HoseOut`을 소켓 중심에 다시 맞춘다. 급수함 자체에는 호스를 고정 포함하지 않고 `급수점 H1 → 호스 H1 → 경작 구획 H1`의 Graph 연결로 사용한다. 후속 E4 시안은 `미연결 → 호스 연결 → 고랑 관수 중`을 구분하되, 실제 호스 길이·변형·물 효과·유량·Unity E5는 별도 검증한다.

사용자 검토에서 급수원과 세척점 사이의 호스 연결 및 같은 물을 고랑 관수에 사용하는 의미가 빠졌음이 확인되어 위 H2 확정을 보류한다. 보유 자산에서 농장 호스·스프링클러·호스 릴을 추가로 찾아 Blender 렌더했다. 호스 선은 `WaterSupplyHose` Graph Map Edge, 호스 릴·밸브·손잡이는 `급수 연결점 H1`, 스프링클러와 세척 수조는 서로 다른 소비점 H1으로 제안한다. 급수원에서 연결점을 거쳐 소비점으로 이어지는 Anchor·길이·유량·압력·개폐·누수·통행 방해 규칙이 정해지기 전에는 세척 공간 H2를 확정하지 않는다.

후속 사용자 의견에 따라 바닥 배치 호스와 호스 릴·손잡이를 각각 H1으로 보고, 두 H1을 `급수 호스 세트`라는 재사용 조립 구성으로 묶는 안으로 정밀화한다. 조립 세트는 H2 번호를 소비하지 않는다. `급수 호스 세트 + 세척 작업점 + 배수 처리점`은 농산물 세척 공간 H2를, `급수 호스 세트 + 경작 구획`은 수동 고랑 관수 공간 H2를 구성한다. H1 사이의 실제 연결·급수·통행 점유는 Graph Map Edge로 별도 표현한다. 한 세트가 세척과 관수를 동시에 공급할 수 있는지는 아직 정하지 않는다.

사용자 승인에 따라 `호스 H1 + 호스 릴·손잡이 H1`의 급수 호스 세트를 기본 구성으로 확정한다. 수동 관수에는 호스 끝을 직접 사용할 수 있으므로 스프링클러 H1은 필수가 아닌 선택 설치물이다. 스프링클러를 추가했을 때만 자동·반자동 살수 구성이 생긴다. 한 급수 호스 세트의 세척·관수 동시 사용 여부는 계속 미정이다.

H1 개별 후보와 별도로 연결·설치된 H2 조립 시안을 Blender 자료함에 둔다. 첫 시안은 압력 급수원인 급수탑에서 호스 릴·호스를 거쳐 세척 수조와 배수점으로 이어지는 농산물 세척 공간, 두 번째는 같은 기본 세트가 2.5×2.5m 경작 구획과 선택 스프링클러로 이어지는 고랑 관수 공간이다. 우물 변형은 펌프 없이 압력 공급이 성립하지 않으므로 이번 연결 완료 시안에서 제외한다. 이 이미지는 E4 조립 검토 자료이며 canonical 배치·Unity Scene·E5가 아니다.

H2 Blender 시안은 `연결해서 사용한다`는 위상 관계만 확정하며 그림 속 거리·각도·호스 곡률을 고정하지 않는다. 실제 World에서는 급수원·호스 릴·세척점·관수점의 간격이 달라질 수 있으므로 E5에서 World Anchor 양끝, 필요·최대 길이, 지면 추종, 장애물 회피 또는 차단, Collider·통행 간섭과 물 공급·도달 상태에 맞춰 호스 표현이 동적으로 변하는지를 검증한다. E4 시안만으로 해당 구현이나 E5 성립을 주장하지 않는다.

일곱 번째 시각 검토 대상은 `h1-stock:farm-work-yard` 수확·집하 작업마당이다. 자동 배당의 `SM_Bld_ProduceStand_01`을 차양형 농산물 작업대 주 후보 A로 Blender에서 렌더했다. 차양과 넓은 작업면은 수확 직후 정리·포장·인계 전 취급점의 고정 골격 후보로 보고, 상자·농산물·도구·작업자는 `EmptyOrAvailable → HandlingOrOccupied → LoadedStoredOrTransferred → ClearedOrReturned` 상태에 따라 붙는 가변 표현으로 분리한다. 아직 사용자 승인 전이며 H2 작업·출하 블록 조립, Unity 배치와 E5는 성립하지 않는다.

작물별로 작업대 전체를 새로 모델링하지 않는 원칙을 첫 감자 표본으로 구체화했다. 같은 차양형 작업대 골격 위에 보유 Synty `SM_Prop_Box_Potato_01` 세 개를 독립된 `crop-payload:potato-box.v1` 모듈로 얹었다. 이후 작물은 외형 유형별 대표 내용물·용기 모듈을 교체하고 수량·밀도·색·라벨을 변형하며, 실루엣이 뚜렷이 다른 경우에만 새 모델을 연다. 이 Blender 결과는 E4 작물 적재 상태 검토이며 실제 Anchor·점유·수량 권위·Unity E5는 별도다.

사용자 결정으로 감자 상자 적재 모듈을 E4 조립 후보로 채택했다. 두 번째 유형은 보유 자산에 완성된 잎채소 상자가 없어 프로젝트 소유의 재사용 가능한 단순 목재 수확 상자와 Synty `SM_Prop_Cabbage_01_L`을 결합했다. 같은 작업대 골격에 배추형 잎채소 상자 세 개를 배치해 큰 잎 실루엣이 감자와 구별되도록 했으며 현재는 사용자 검토 대기다. 공급사 배추 메시와 프로젝트 소유 상자의 소유권을 분리하고, Unity Prefab·작물 수량 상태·E5는 열지 않는다.

사용자 결정으로 배추형 잎채소 적재 모듈도 E4 조립 후보로 채택했다. 세 번째 외형 유형은 길쭉한 채소이며, 보유 Synty 완성 상자인 `SM_Prop_Box_Carrot_01`과 `SM_Prop_Box_Cucumber_01`을 같은 작업대에 각각 교체해 렌더했다. 두 모듈은 상위 유형을 공유하지만 당근의 주황색 뿌리·돌출 잎과 오이의 짙은 녹색 장형 실루엣이 명확히 달라 개별 작물 모듈로 유지하며 현재 사용자 검토 대기다.

사용자 결정으로 당근·오이 모듈을 모두 E4 조립 후보로 채택했다. 네 번째 유형은 둥근 과실이며 사과와 배를 각각 렌더했다. 사과는 보유 Synty 완성 상자 `SM_Prop_Box_Apple_01`을 그대로 쓰고, 배는 완성 상자가 없어 프로젝트 소유 재사용 목재 상자와 개별 `SM_Prop_Pear_01` 여섯 개를 조합한다. 두 후보는 색·꼭지·몸통 윤곽으로 구분하며 현재 사용자 검토 대기다.

사용자 결정으로 사과·배 모듈을 모두 E4 조립 후보로 채택했다. 다섯 번째 유형은 곡물·종자 포대이며 같은 작업대에 밀봉 `SM_Prop_GrainBag_01`과 개봉 `SM_Prop_GrainBag_Open_01`을 각각 렌더했다. 둘은 별도 품종보다 `보관·출고 대기`와 `계량·분배·종자 준비 중`의 상태 차이를 표현하는 후보로 두며 현재 사용자 검토 대기다.

후속 검토의 우선순위는 H2 조립이나 한 H1의 세부 상태 확장보다 **H1 자체를 하나씩 확립하는 것**으로 고정한다. 각 H1은 먼저 역할·대표 외형·대략적 크기·필수 연결점·주/대체 후보를 사람 검토로 정하고, 그 뒤에만 필요한 전·중·후 상태와 Blender 파생형을 연다. 작업마당 상태 흐름 비교 렌더는 참고 초안으로 보존하지만 현재 승인 대상에서 제외한다. 다음 H1이 확립되기 전에는 작업마당의 작물 유형이나 상태 변형을 더 늘리지 않는다. H2는 구성 H1의 기준선이 충분히 모인 뒤 연결·통행·배치 제약만 조립한다.

여덟 번째 H1 검토 대상은 `h1-stock:farm-loading-gate` 농장 상차·출입 공간이다. 현행 자동 배당 후보인 Farm 팔레트 상자, City 빈 팔레트, Farm 나무 상자를 각각 렌더했다. 세 후보는 상차 대기 화물·적재 기반·소형 회수 용기 역할로는 쓸 수 있지만 차량 진입로·경계 표지·정차 Anchor·회전 및 보행 여유를 표현하지 못하므로 H1 전체 골격 후보로는 불충분하다. City 팔레트의 공급사 단위 차이는 Blender 검토 사본 표시 배율로만 보정했으며 원본은 불변이다. 현재는 소품 후보의 사람 검토 대기이고 Unity 배치·E5는 열지 않는다.

PolygonFarm 위주로 후보가 좁아지지 않도록 PolygonConstruction을 보충 대조한다. Construction 팔레트와 대형 운송 상자는 `적재 기반`과 `대형 화물 용기` 후보로 유지한다. 이름이 `Driveway`인 지형은 단독 시각 검토에서 차량 진입면으로 판독하기 어려워 지형 전이 보조로만 제한하고, `Barrier`는 돌망태 방호물에 가까워 출입 제어 표지로 쓰지 않는다. 파일 이름보다 실제 형상과 H1 역할 판독을 우선하며, 이 조사만으로 차량 진입로·정차 Anchor·회전·보행 골격 결손이나 E5 차단은 해소되지 않는다.

사용자 결정으로 Farm 팔레트 상자, City 빈 팔레트, Construction 팔레트와 대형 운송 상자를 농장 상차·출입 공간의 가변 화물층 후보로 채택한다. Farm 소형 나무 상자는 이번 결정에서 명시적으로 확정하지 않았으므로 검토 대기를 유지한다. 진입 골격은 화물층과 분리해 PolygonTown의 넓은 진입로·정차선 도로, PolygonCity의 기본 도로면까지 조사한다. Town 정차선 도로는 정차·상차 구획을 가장 직접적으로 읽히게 하고, Town 넓은 진입로와 City 기본 도로면은 각각 농장·타운 인접형과 시티 인접형 표면 후보로 둔다. City `Entrance` 표지는 실제로 지하철 입구 표지이므로 이 H1에서 제외한다. H1 전체는 `진입면 + 정차·상차 구획 + 회전·보행 여유 + 가변 화물층`의 결속 전까지 미정이며 Unity 배치·E5는 열지 않는다.

후속 사용자 판단에 따라 Town의 넓은 진입로와 정차선 도로는 아스팔트 인상이 강하므로 농장 기본형에서 제외한다. 두 후보는 도로 정비·승격 이후의 `발전된 타운 인접형` 상태 변형으로 보류하고, 농장 기본형은 흙길·자갈길처럼 농장 외곽과 자연스럽게 이어지는 비포장 진입면을 우선 조사한다. 동일 H1 안에서 기본 농장형과 발전형의 역할은 공유하되 표면 후보와 통행 성능은 상태에 따라 분리한다.

농장 기본형 보충 조사로 Farm 자갈 직선로·T 접속로와 Construction 흙길 직선로를 렌더한다. Construction 흙길 직선로는 바퀴 자국이 있는 비포장 진입면으로 단독 판독성이 가장 높다. Farm 자갈 직선로는 외부 경로, T 접속로는 상차 작업마당으로 갈라지는 내부 접속 후보가 될 수 있지만 현재 Blender Atlas 검토색이 옅으므로 원 재질 대조가 필요하다. 세 후보는 아직 사용자 검토 전이며 기본 농장형으로 확정하거나 E5로 승격하지 않는다.

후속 사용자 결정으로 자산과 상대 배치를 더 고르기 전에 **독립적으로 성립하는 H1 주체·객체 노드부터 확립**하는 순서를 우선한다. 각 노드는 안정 식별자, 플레이어가 알아보는 역할, 상태 소유 범위, 상호작용 기준점, 대략적 점유 범위와 필수 표현 역할까지 먼저 정한다. 노드 사이의 연결·거리·방향·경로 비용·통행·상대 배치는 해당 노드들이 확립된 뒤 Graph Map Edge와 배치 맵에서 정한다. 자산 후보는 확립된 노드의 표현 역할에 배당하며 파일 이름이나 도로 조각에서 노드 의미를 거꾸로 만들지 않는다.

이 원칙에 따라 현행 `농장 상차·출입 공간 H1`은 계층 재검토 대상으로 둔다. `상차 지점`은 팔레트·팔레트 상자·대형 운송 상자와 작업 상태를 가지는 노드 후보이고, `차량 진입 경로`는 두 노드 사이의 이동·운송 Graph Map Edge 및 배치 표면 후보다. 둘을 결합한 상차·출입 공간은 정차·회전·보행 제약까지 포함하는 상위 조립 후보로 본다. 기존 안정 식별자와 H 정의는 정확한 분할·호환 계획이 승인되기 전까지 변경하지 않으며, 지금까지 조사한 도로 자산은 후속 엣지·배치 검토 자료로 보존한다.

첫 노드 표본은 작업 명칭 `농장 상차 지점`으로 시작하고 기존 `h1-stock:farm-loading-gate`는 호환 참조로 유지한다. 이 노드는 수확물 또는 포장 화물을 입력받아 팔레트·운송 상자 단위로 임시 적치하고 운송 주체에게 출력·인계하는 작업 지점이다. 입력 후보는 수확물 묶음, 포장 완료 화물, 빈 팔레트·회수 용기이며, 적치 작업 인력은 화물 입력과 구별되는 수행 주체다. 출력 후보는 인계 가능한 화물 단위, 실제 인계 화물, 반환 빈 용기와 입출력 기록이다.

최소 상태 흐름 초안은 `Available → ReceivingOrStacking → ReadyForPickup → HandedOffOrCleared`로 둔다. 입력이 들어오면 비어 있는 작업면에 화물이 누적되고, 출력이 성립하면 화물이 빠지며 빈 팔레트·회수 용기 또는 빈 작업면이 남는다. `CapacityBlocked`, `AccessBlocked`, `DamagedCargo`는 예외 상태 후보로만 기록한다. 입력 승인 시점과 출력 인계 조건이 확정되기 전에는 상태 코드를 구현 계약이나 E5 근거로 사용하지 않는다.

사용자 정정에 따라 여러 H1 또는 여러 상태를 한 Blender 장면에 합친 통합 검토 시안을 만들지 않는다. 기본 출력은 `H1 하나 = 독립 .blend 하나 = 대표 PNG 하나`로 고정한다. 같은 H1의 상태 변화가 실제 WI 판독에 필요하면 시작·진행·결과·회복 상태도 각각 별도 파일과 이미지로 분리하고, 목록과 문서에서만 순서를 연결한다. H1 사이의 조합은 개별 H1 기준선이 확정된 뒤 H2 조립 또는 배치 맵에서 다루며, 통합 장면을 개별 H1 승인 근거로 사용하지 않는다.

첫 독립 시각 후보로 `농장 상차 지점` 작업 식별자 `h1-node-candidate:farm-loading-point`를 연다. 기존 `h1-stock:farm-loading-gate`는 호환 참조로 유지하며 아직 대체하지 않는다. PolygonFarm `SM_Bld_ConcreteBase_01`만 사용해 화물·팔레트·상자·작업자·차량·도로가 없는 약 4.5×4.5m 빈 작업 기반을 독립 `.blend`와 PNG로 렌더한다. 넓은 작업면은 역할 후보에 맞지만 약 0.99m 높이와 콘크리트 기초 인상이 강하므로 사용자 검토 전에는 대표 외형으로 확정하지 않는다. 이 후보는 H1 단독 E4 시각 자료이며 Unity 배치나 E5가 아니다.

## H1·AreaSet 쌍 검토 운영

H1을 하나씩 확립하는 순서는 유지하되, 매 검토는 다음 두 이미지를 한 쌍으로 제시한다.

1. `H1 개별 이미지`는 형태·크기·재질 인상·상태 판독성을 검토하는 근거다. 다른 H1과 도로를 배제하고 해당 H1만 본다.
2. `AreaSet 전체 조감도`는 동일 H1이 주변 노드·이동 경로·작업 흐름과 어떻게 읽히는지 검토하는 문맥 자료다. 노란색 둘레는 현재 검토 중인 H1만 표시한다.
3. 조감도는 개별 H1 승인 근거를 대신하지 않고, 개별 이미지는 배치·통행·인접 적합성을 대신하지 않는다.
4. 노드 검토 순서가 끝나기 전의 조감도는 대화형 `LocalReviewDraft`다. Graph Map·배치 맵·canonical AreaSet·Unity Scene을 변경하지 않으며 E5 근거가 아니다.

첫 맥락 검토 모판은 기존 `placement-map-profile:forest-edge-farm:hans-living-farm`을 참고한 `area-set-review:forest-edge-farm:hans-living-farm.r1`이다. 농장 생활주택·경작 구획·울타리와 출입구·헛간 작업마당·숲 완충·비포장 진입로를 문맥으로 두고 `농장 상차 지점`을 첫 포커스 H1로 배치한다. 이 모판의 위치·거리·크기는 질문을 위한 초안이며 기존 배치 프로필의 미확정 제약을 해소하지 않는다.

첫 r1 조감도는 각 FBX를 수동 목표 크기로 정규화하고 중심점 기준으로 배치해 원본 축척·pivot·접지·경계·도로 접속이 일관되지 않았다. 따라서 r1은 `RejectedPlacementDraft`로 남기고 배치 근거로 쓰지 않는다. r2에서 지면·비포장 진입로·출입구·상차 작업면의 접속과 AreaSet 경계를 먼저 맞추었지만, 이도 여전히 시각 보정본이다. 후속 조감도는 Blender 수동 눈대중 배치를 정본으로 삼지 않고 `Graph Map 노드·엣지 → 배치 맵 Anchor·footprint·clearance·snap → Blender 조감도 생성`의 읽기 방향을 따른다. Blender는 배치 권위가 아니라 판독을 위한 표현기로만 쓴다.

r3에서는 위 원칙을 실행 가능한 저작 순환으로 고정했다. Unity가 canonical 지형 Mesh의 삼각 격자와 대상 Synty Prefab의 실제 Renderer Bounds·GUID·dependency hash를 사본으로 내보내고, Blender는 `ScenarioLocalMeters / XRightYUpZForward / 1 unit = 1 m` 계약에서 수평 위치·Y축 회전·균일 축척만 편집한다. 높이는 `지표면 중심 높이 - Prefab Bounds 최소 Y × 축척`으로 Unity 검사기가 다시 계산하며, 자산 대장이 허용하고 사유가 기록된 `SurfaceOffset`만 예외다. 지형·자산 fingerprint 불일치, 범위 이탈, 경사·높이 편차 초과, 객체 중첩과 통행 여유 위반은 자동 이동이나 지형 평탄화 없이 staging을 차단한다.

첫 `area-set-placement-draft:forest-edge-farm:hans-living-farm.r3`은 31개 배치 객체를 같은 지형·자산 사본으로 Blender 왕복한 뒤 변환값 무변경과 Unity 검사 오류 0·경고 0을 확인했고, 별도 staging Prefab과 동일 구도 비교 PNG를 생성했다. 이는 격리된 Editor 저작 검증과 E4 문맥 자료이며 canonical `SimulationWorldShell` Scene 저장, Play Mode·Game View, 플레이어 입력, 서버 revision 결속 또는 Presentation E5 증거가 아니다. 현행 전체 Unity 프로젝트 컴파일은 별도 진행 중인 `SimulationPlayerLearningFocusService` 패키지 결손 때문에 차단되어 이 범위를 임의 수정하지 않았다.

## 숲 경계 생활농장 방어 H4 r4

한스 농장을 고유 H4로 고정하지 않고 재사용 가능한 `h4-blueprint:forest-edge-living-farm-defense-region`의 첫 AreaSet 인스턴스로 둔다. 새 H3를 중복 생성하지 않고 기존 `h3-candidate:highland-farm`, `h3-candidate:nature-home-encounter-defense`, `h3-candidate:nature-threat-recovery`를 각각 생활·생산 / 접근·방어 / 피해·회복·복귀 역할로 재사용한다.

r4 Blender 마스터는 r3의 실제 배치 31개와 자산 fingerprint를 유지하고, 미승인 방어 집결점·울타리 돌파점·회복점은 파란 반투명 자리표시자로 구별한다. Graph 경로는 적 주 진입, 울타리 손상 때만 열리는 조건부 돌파, 플레이어·한스, 보급·수리, 후퇴·회복 다섯 종류로 분리하며 `Normal`, `Defense`, `BreachRecovery` View Layer에서 따로 검토한다. Blender 재개방 구조 검사는 배치 31개·자리표시자 3개·경로 5개·View Layer 3개를 통과했다.

이 결과는 Presentation E4 저작·검토 자료다. H4 공식 공간 대장 등록, 실제 울타리 상태와 조건부 경로 실행, canonical Unity Scene, 지면 재접지, Renderer·Collider·Bounds·입력·결과 결속 전에는 E5로 승격하지 않는다.

첫 방어 H1 독립 시안으로 `h1-node-candidate:farm-fence-defense-chokepoint`를 열었다. r2는 중앙 4m 통과부와 좌우 각 2.5m 울타리 연장을 하나의 배치 가능 H1 후보로 묶고, 문을 농장 안쪽으로 82° 연 상태와 통과부 안쪽의 플레이어·한스 공동 방어 위치를 Blender에서 표현한다. 표식 없는 깨끗한 이미지와 설명용 이미지를 분리했으며 빨강은 적 주 접근선, 파랑은 플레이어 위치·내부 복귀선, 초록은 한스 위치다. 기존 PolygonFarm 나무 울타리와 출입문 원본은 수정하지 않았다. r2 외형은 현재 `PendingUserReview`이며 이 이미지로 후보 채택, Graph 연결, 실제 이동 감속, 전투, Collider나 E5를 확정하지 않는다.

## 농장 상수도 급수점과 수동 관수 r1

사용자 결정으로 프로젝트 소유 `농장 상수도 급수점 H1`의 개방형 호스 소켓 r2를 H1 시각 기준선으로 채택한다. 급수점의 파란 출력 소켓에는 호스를 연결하고, 전면의 빨간 차단 밸브가 수동 개폐 행위를 나타낸다.

연결 판독용 E4 조립 시안은 `급수점 H1 → 호스 릴·손잡이 H1 → 호스 H1 → 2.5m×2.5m 경작 구획 H1` 순서로 구성한다. 닫힘 상태에서는 호스가 연결되어 있어도 물줄기가 없고, 열림 상태에서는 빨간 밸브 살이 45도 회전하며 손잡이 끝에서 고랑 쪽으로 물줄기가 나타난다. 두 상태는 각각 독립 PNG와 `.blend`로 저장하고 재개방 검사에서 닫힘 물줄기 0개, 열림 물줄기 5개, 동일 `Anchor_HoseOut`을 확인했다.

이 시안은 H1들을 하나로 합쳐 새 canonical H2를 확정하는 근거가 아니다. 실제 거리·장애물에 따른 호스 변형, 수압·유량·급수 권위, 물 효과, 플레이어 밸브 입력, Collider, Unity Scene과 E5는 후속 구현·검증 범위로 남긴다.

r2에서는 호스가 출수구 중심에 가늘게 꽂혀 보이던 r1 연결을 대체한다. 회색 연결구 외경 `0.108m`보다 큰 외경 `0.126m`의 파란 체결 슬리브가 파이프 바깥 둘레를 완전히 감싸고, 앞쪽 감속 연결부에서 유연한 호스로 좁아진다. 닫힘 상태에는 체결부와 호스만 있고, 열림 상태에는 밸브 45도 회전·물줄기 5개와 함께 고랑 중앙의 젖은 흙 상태 2개가 나타난다.

재개방 검사에서 두 파일 모두 체결 슬리브·감속 연결부를 보유했고, 닫힘은 물줄기 0·젖은 흙 0, 열림은 물줄기 5·젖은 흙 2로 확인했다. 실제 체결 규격, 클램프·나사, 젖음 확산, 수압·유량과 Unity 입력·E5는 아직 검증하지 않는다.

사용자 검토 결과 r2는 체결 슬리브가 다소 두껍다는 시각적 한계를 인정하되 현 단계 E4 조립 시안으로 채택한다. 이를 최종 제작 규격이나 Unity E5 외형으로 고정하지 않으며, 후속 정밀화가 필요할 때만 체결부 외경과 형상을 다시 연다. 관수 지속 시 젖은 영역이 고랑 길이 방향으로 퍼지는 것이 자연스럽다는 방향은 보존하되 이번 시안에 추가 상태를 더 만들지 않는다.

다음 독립 H1 검토는 `농산물 세척 작업점`으로 이동한다. 이미 렌더한 긴 세척 수조와 반통 세척조를 각각 대용량 공동 작업형과 소량 개별 작업형 후보로 다시 제시하고, 사용자 선택 전에는 어느 쪽도 대표 외형으로 확정하지 않는다.

후속 결정으로 긴 세척 수조와 반통 세척조를 모두 `농산물 세척 작업점 H1`의 형태 후보로 보존한다. 먼저 긴 수조를 `빈 수조 → 물 채움 → 농산물 세척 중 → 오염수 배출 대기` 네 상태로 나누며, 각 상태는 독립 PNG와 독립 `.blend`를 가진다. 상태 간 순서는 목록과 기획 문서에서만 연결하고 한 장면을 다른 상태의 증거로 재사용하지 않는다.

긴 수조 r1 재개방 검사 결과는 `빈 수조: 물0·농산물0·침전물0`, `물 채움: 물1·농산물0·침전물0`, `세척 중: 물1·농산물5·침전물0`, `오염수 배출 대기: 물1·농산물0·침전물3`이다. 이는 상태 판독용 E4 표본이며 실제 세척 애니메이션, 수질 판정, 급수·배수 연결, 저장 상태, Unity Scene과 E5는 포함하지 않는다.

사용자 검토로 긴 수조의 네 상태를 E4 상태군으로 채택하고, 반통 세척조에도 같은 네 상태를 독립 파일로 적용한다. 반통 공급사 원본은 중앙 내부 면이 솟아 수면을 관통하므로 원본 FBX를 바꾸지 않고 상태 표본 안에서만 해당 내부 정점 13개를 낮춘 세척조 파생형을 사용한다.

반통 r1 재개방 검사 결과는 `빈 반통: 물0·농산물0·침전물0`, `물 채움: 물1·농산물0·침전물0`, `세척 중: 물1·농산물4·침전물0`, `오염수 배출 대기: 물1·농산물0·침전물2`다. 네 상태 모두 동일한 평탄화 파생 기준을 보유한다. 사용자 검토로 이 네 상태를 긴 수조와 함께 E4 상태군으로 채택한다. 실제 세척·수질·급배수·Unity Scene·E5는 여전히 별도다.

다음 독립 검토 대상을 `농장 배수·오수 처리점`으로 전환하고 보유 Synty 자산 세 가지를 Blender에서 분리 렌더했다. Town 바닥 배수구 A는 세척점의 배수 입구 H1 후보, Construction 콘크리트 관 C는 두 지점을 잇는 `WastewaterDrainRoute` Edge의 표현 후보, City 수변 관 B는 지형 가장자리의 방류구 H1 후보로 읽힌다. 따라서 세 후보를 한 H1의 외형 대안으로 섞지 않고 `배수 입구 → 배수 경로 → 방류구`의 방향성 있는 Graph 관계로 관리한다. B는 공급사 단위가 작게 읽혀 실제 사용 전 축척 재검증이 필요하다. 후보 선정 전에는 방류 권한·수리 계산·canonical H 등록·Unity 배치·E5를 열지 않는다.

배수 입구가 공간에서 어떻게 읽히는지 확인하기 위해 `세척 작업 바닥의 완만한 경사 → 바닥 배수구 → 짧은 낙차 연결관 → 절개로 보이는 콘크리트 배수관 → 지형 가장자리 방류관`의 E4 연결 시안을 만들었다. 청색 표식은 흐름 방향을 설명하는 도식이며 실제 유체가 아니다. 조감도와 절개 측면도는 동일한 `.blend`에서 분리 렌더했다. 실제 구배 또는 펌프 조건, 관경, 막힘·역류, 방류 허가·수질, World Anchor와 Unity 배치는 E5 이전 별도 조건이다.

벌목 표현은 기존 `WI-NATURE-06`의 의미를 재사용한다. 최초 r1은 공급사 도끼·나무와 프로젝트 소유 저폴리 모형으로 `도끼 휴대·준비`와 `나무 타격 접촉`을 블로킹했으나, 사용자 검토에서 하체·허리의 연쇄가 약하고 초보자처럼 보인다는 결손이 확인됐다. r1은 삭제하지 않고 초기 자세 이력으로만 보존하며 시각 채택 후보에서는 제외한다.

같은 `AnimationSwordCombat` 팩의 캐릭터와 동작 리그는 골격 자세값을 직접 이전할 때 메시가 정상 유지되는 것을 다시 확인했다. 이에 실제 53-bone Armature·스킨 캐릭터를 사용해 `골반 회전 백스윙`과 `보폭·무릎 굽힘·몸통 추종이 있는 타격` 두 독립 PNG·`.blend`를 r3로 만들었다. 검토 기준은 넓은 지지면, 무릎 굽힘, 고관절 접기, 골반 선행 회전, 몸통 추종, 두 손 그립이다. 다만 원천은 검술 동작을 벌목 자세 검토에 전용한 것이므로 최종 벌목 AnimationClip으로 승인하지 않는다. r3도 Presentation E4 자세 연구일 뿐 최종 접촉·감속 곡선, 손 미끄러짐, 실제 Synty 도끼 결속, Unity 재생과 E5가 아니다.
