# 게임 개체·Synty 자산 로컬 검토 웹 제안

- 작성일: 2026-08-31
- 상태: **ReadyForReview — 제안서, 구현·DB 변경·배포 승인 아님**
- 목적: 보유 자산을 이미지로 비교하고, 게임 개체의 외형·설비·동작에 무엇을 사용할지 역할별로 정한다.
- 사용자 요청: 추가 VM 운영보다 로컬 PC/Codex에서 확인하는 방식을 우선하며, 게임 개체에 여러 자산을 할당할 수 있게 설계한다.
- 이번 조사: 저장소 문서·계약·구현을 읽었다. DB 수치는 통합 보고의 검증 시점 값이며 이번 DB 재조회 결과는 아니다. 웹 실행·이미지 표시·로그인은 미검증이다.

> 후속 승인: [D440 자동 할당 원문](개체자산-자동할당-D440-개발인계-2026-08-31.md)에 따라 아래의 매번 사용자 선택 중심 흐름은 Codex 자동 할당 결과·근거·보류 사유를 확인하고 필요할 때 교체하는 흐름으로 대체한다. 기존 제안 본문은 당시안으로 보존한다. 첫 실제 개발은 최대10역할의 자동 초안 저장·재조회이며, 아래 전체 웹·전수 이미지·동작 비교 완료를 선행조건으로 삼지 않는다. 로컬 우선·다중 역할·판본/권리·실제 배치 분리 경계는 유지한다.

## 1. 권장안

**기존 ASP.NET Core 관리자 앱에 ‘개체·자산 검토실’을 추가하고, 로컬 MySQL과 로컬 비공개 이미지 저장소를 사용한다.** 페이지는 같은 PC의 Codex 내장 브라우저 또는 일반 브라우저에서 연다. 검토실 때문에 Azure VM을 켜거나 Blob에 새로 올리지 않는다.

게임 개체와 자산을 일대일로 제한하지 않는다. 이미 있는 **개체 → 구성 판본 → 역할별 할당 항목**을 재사용한다. 캐릭터 하나가 외형·대기·걷기·작업 동작을 각각 가질 수 있고, 같은 자산을 여러 개체가 재사용할 수도 있다.

첫 목표는 전수 사진 완성이 아니다. 전체 목록은 검색하고, 이미지가 확보된 작은 묶음부터 비교·초안 저장이 가능한 도구를 먼저 만든다. 검토상 선택과 실제 Unity 배치·게임 기능 완료는 구분한다.

## 3. 사용자가 보는 화면

기본은 ‘개체를 먼저 고르고, 그 개체에 필요한 역할별 후보를 비교’하는 방식이다.

| 화면 영역 | 보여줄 내용 | 할 수 있는 일 |
| --- | --- | --- |
| 개체 목록 | 이름·분야·관련 WI·이미지/할당 준비 상태 | 농장, 공방, 창고, NPC 등 검색·선택 |
| 역할 목록 | 외형, 설비, 용기, 대기, 걷기, 작업 동작 등 | 지금 검토할 역할 하나 선택 |
| 후보 비교 | 후보 2~3개, 이미지, 팩, 실제 크기 정보의 유무, 근거 종류 | 확대·나란히 비교·선택 또는 보류 |
| 구성 요약 | 역할별 선택, 미선정 역할, 미검증 사항, 이전 판본 | 초안 저장·다시 조회·이전 구성과 비교 |

상세에서는 **지금·여기·나·너·이렇게(WI)·결과·다음 선택**을 펼쳐 본다. 자산 이름만 보고 고르는 대신 어떤 플레이에 쓰이는지 확인한다. WI 관계가 없는 개체는 ‘미연결’로 표시하고 임의로 채우지 않는다.

‘전체 자산’ 보기에서는 팩·종류·이름을 기본 필터로 제공하고, 이미지 유무·검토 상태·역할 후보 필터를 보완한다. 뒤의 필터들은 제안 기능이며 현재 API의 지원 완료를 뜻하지 않는다. 기본은 Prefab이고, 애니메이션·재질·텍스처는 종류를 바꿔 확인한다.

한 번에 24~48장씩 보여주고 페이지·지연 로딩을 사용한다. 모든 원본 이미지나 14,461건 상세를 처음부터 내려받지 않는다. 좁은 화면에서는 목록 → 후보 → 구성 요약 순으로 쌓는다.

### 첫 검토 묶음

약 10개 역할에 후보 2~3개씩을 모으는 것을 제안한다. 이는 목표이며 현재 사진 확보 수량은 아니다.

- Farm: 헛간, 밭 외형, 울타리, 수확물 보관함.
- Nature·공통: 침엽수, 바위, NPC 외형.
- Town: 공방 설비, 실내 진열대.
- Hub: 화물 보관 설비.

City 등 다른 분야도 독립적으로 검색한다. 순서는 선행 의존성이 아니며 준비된 다른 분야의 이미지를 먼저 검토해도 된다. ‘진열대 후보’ 선택만으로 실내 배치가 완료되지는 않고, 헛간·밭의 간격도 별도 배치 검토로 남긴다.

## 4. 할당 관계: 기존 구조와 역할별 슬롯 재사용

| 관계 | 기존 구조 | 의미 |
| --- | --- | --- |
| 개체 1 : 구성 판본 여러 개 | `world_visual_object_definitions` → `world_visual_object_compositions` | 개체 정체성을 유지하면서 선택 이력 보관 |
| 구성 판본 1 : 할당 항목 여러 개 | `world_visual_object_composition_items` | 역할(`Role`)·슬롯(`SlotKey`)마다 자산 선택 |
| 자산 판본 1 : 할당 항목 여러 개 | 기존 `AssetVersionId` 참조 | 여러 개체·슬롯에서 같은 자산 재사용 |
| 개체 : WI 참여 | `world_visual_object_wi_uses` | 무엇을 하는 개체인지 설명하며 시각 할당과 분리 |

개체와 자산은 결과적으로 **다대다** 관계다. 새 할당 테이블을 중복해서 만들 필요는 없다. 한 구성의 동일 역할·슬롯에는 선택 자산 하나를 두되 여러 위치가 필요하면 슬롯을 나눈다. 비교 후보 여러 개를 동시에 최종 할당한 것처럼 저장하지 않는다.

아래 역할명은 설명용 예이며 실제 할당이나 새 게임 기능 승인이 아니다.

| 개체 예 | 역할·슬롯 예 | 참조 자산 | 별도로 남는 확인 |
| --- | --- | --- | --- |
| 농장 NPC | 외형/몸체 | 캐릭터 Prefab | 대상 Rig·Avatar |
| 같은 NPC | 동작/대기, 동작/걷기 | 각 AnimationClip | 같은 대상에서 재생·전이·root motion |
| 같은 NPC | 도구/주손 | 도끼 Prefab | 손 접촉·중단·복귀 |
| 타운 공방 | 건물/외관, 설비/작업대, 용기/제조용 | 각각 다른 Prefab | 출입·실내 크기·상호작용 위치 |

현재 구성 저장은 `Draft`/`NotApplied`이고 자산 지정 후에도 적합성은 `Candidate_FitnessUnreviewed`다. 첫 웹도 이 의미를 유지한다. ‘초안에 선택’과 ‘게임 적용 확정’을 같은 버튼으로 만들지 않는다. 원천 개체/레코드별 단일 대응(`world_entity_visual_bindings`)은 목적이 다르므로 덮어쓰거나 합치지 않는다.

## 5. 전체 목록·애니메이션 연결의 최소 보완

현재 등록은 `.prefab`·GUID·원본 판본을 검사한다. FBX나 Clip을 이 경로에 억지로 넣거나 가짜 `VisualKey`를 만들지 않는다. 권장안은 **기존 구성 항목에 ‘검토용 자산 참조’를 선택적으로 연결**하는 것이다. 아래는 제안 논리 구조이며 실제 테이블명·Migration은 개발 검토 후 확정한다.

1. **검토용 자산 참조:** 기존 목록 사본 ID를 외래키로 참조하고 자산 종류·원본 판본/해시·검토 상태를 보관한다. FBX 내부 Clip은 파일 GUID 외에 하위 자산 식별자까지 포함한다. 이름만으로 구분하지 않는다.
2. **구성 항목 확장:** 기존 `AssetVersionId`를 보존하고 검토용 참조를 선택적으로 추가한다. 미선정은 둘 다 비어 있고, 선택 시에는 둘 중 정확히 하나만 사용한다. 기존 8개 후보와 이력을 자동 변환하지 않는다.
3. **역할 적합성:** 외형에는 Prefab, 걷기에는 Clip 등 종류를 검사한다. Rig·Avatar·반복재생·root motion·전이는 별도 근거로 두며 파일 존재만으로 통과시키지 않는다.
4. **제품 연결 분리:** 검토 참조로 초안을 저장할 수 있어도 Unity 소비 키·계약은 별도 결속한다. FK가 생긴 것을 실제 배치 성공으로 취급하지 않는다.

단독 `.anim` 파일 수는 보유 동작 총수가 아니다. 모델 안의 Clip은 별도 조사해야 한다. 전수 동작 추출 대신 대표 NPC 하나의 외형·대기·걷기부터 검증한다.

## 6. 이미지·동작 근거 보관

이미지 본문은 **로컬 비공개 저장소**, MySQL에는 저장 객체 ID·자산 판본 참조·SHA256·크기·촬영 종류/각도·시점·출처/사용 범위를 저장한다. 임시 `artifacts/local` 이미지를 장기 조회에 쓸 때는 원본/manifest를 대조해 안정된 비공개 보관 위치로 복사한다. 원본을 이동·덮어쓰지 않는다.

기존 `DevelopmentLocalStorageService`의 비공개 기능과 저장 인터페이스를 재사용 후보로 삼는다. `local-storage-private://`는 브라우저에서 바로 열리는 URL이 아니므로 인증된 조회가 파일 ID를 받아 해당 파일만 반환해야 한다. 임의 경로 읽기나 공개 정적 폴더로 대체하지 않는다. ‘파일이 이미 존재함’ 반환만으로 동일 내용이라고 판단하지 않고 해시를 확인한다.

한 자산에 여러 근거를 연결한다. 여러 자산이 함께 나온 화면은 포함 관계를 명시하고 단독 Prefab 사진과 구분한다. 파일과 DB 저장은 원자적 한 작업이 아니므로 실패·누락·재시도 상태를 남긴다. 기존 앱 문맥 이미지 모델의 저장 위치·해시·대체텍스트 패턴은 참고하되 앱 장면/Prompt 판본용 테이블을 Synty 조사 테이블로 전용하지 않는다. 자산 판본–시각 근거 관계의 최소 보완 범위는 조사 산출물과 함께 확정한다.

| 근거 종류 | 확인 가능한 것 | 대신 증명하지 못하는 것 |
| --- | --- | --- |
| 개별 Prefab 실제 미리보기 | 외형·색·구성 | 실제 배치·통행·기능 완료 |
| 여러 자산의 구성 예시 | 상대 배치·구성 의도 | 개별 자산 적합성 전체 |
| 대상 동작의 연속 그림/영상 | 해당 대상·조건의 동작과 전이 | 다른 Rig 호환·실제 플레이 이동 |
| 실제 Game View | 명시한 실행·카메라 조건의 결과 | 다른 판본·상태의 자동 성공 |

없으면 ‘이미지 미확보’, 판본이 바뀌면 ‘재확인 필요’로 표시한다. 무관한 예시나 AI 생성 그림으로 검증을 대신하지 않는다. 기존 그림은 정확한 자산/판본 대응이 있을 때 재사용하고 부족한 소수만 공간 담당 단독 Editor 슬롯에서 촬영하도록 후속 배분한다.

정지 썸네일은 애니메이션 품질 근거가 아니다. 초기에는 기존 연속 그림을 프레임별로 보거나 확보된 영상을 재생한다. 웹 3D 뷰어·실시간 Rig 재생은 첫 구현에서 제외한다.

## 7. 실행 위치·비용·접근 경계

- 기존 `SsalddelAdmin`에 화면을 추가하고 관리자 전용 조회·구성 저장 API와 인증을 재사용한다. 별도 웹 서비스·DB를 새로 운영하지 않는다.
- 같은 PC의 로컬 페이지는 Codex 내장 브라우저에서 여는 방식으로 제안한다. [공식 내장 브라우저 안내](https://learn.chatgpt.com/docs/whats-new#preview-and-operate-work-in-one-place)는 로컬 웹 미리보기를 설명한다. 이 프로젝트의 로그인·이미지·저장 동작은 구현 후 검증한다.
- 포트는 구현 시 확인하고 로컬 연결만 허용한다. 로컬이라도 관리자 인증·권한 검사·변경 요청 위조 방지·이미지 경로 이탈 방지를 유지한다.
- 기존 서버 전체를 무심코 시작하지 않는다. 로컬 실행 설정에서 자동 수집·예약 작업·외부 전송·자동 Migration을 확인하고 필요한 기능만 실행한다. DB 실패를 예시 데이터로 숨기지 않는다.
- 추가 Azure VM·Blob 업로드·외부 이미지 변환은 이번 권장안에서 제외한다. 로컬 디스크·실행 자원은 필요하므로 ‘모든 비용 0’이라고 하지는 않는다. VM 시간표·현재 요금은 이번에 조회·변경하지 않았다.
- 같은 PC의 Codex 표시와 휴대폰 접속은 다르다. `localhost`/`C:/` 경로가 모바일에서 열린다고 보장하지 않으며 원격 접속·공개·터널은 별도 선택이다.
- 과거 [D433 Azure 보관 승인](프리팹이미지-전담조사와Azure보관-2026-08-31.md)은 이력으로 보존하되 이번 실행 수단으로 사용하지 않는다. Prefab·FBX·원본 텍스처 패키지를 웹으로 배포하지 않는다.

## 8. 단계별 구현 제안과 완료 기준

| 단계 | 구현 범위 | 사용자 결과·검증 |
| --- | --- | --- |
| 1. 읽기 검토실 | 개체/WI/자산 조회, 검색·페이지, 정확히 연결된 소수 이미지 | 실제 DB 목록·사진을 로컬 페이지에서 확인. 누락·판본 불일치 표시. 관리자 아닌 접근 거부 |
| 2. 역할별 초안 | 기존 구성 저장·이력 UI, 목록의 검토 참조 연결 | 한 개체에 복수 역할 저장·재조회. 중복 요청·동시 수정·미선정 보존 및 기존 FK/이력 회귀 |
| 3. 동작 비교 | 대표 NPC의 외형·대기·걷기와 기존 미디어 연결 | 같은 대상의 동작 근거·미검증 조건 확인. Clip의 Prefab 오등록 방지 |
| 4. 범위 확대 | 준비된 다른 분야·팩에 같은 방식 적용 | 전수 사진을 기다리지 않고 검토 수·이미지 수·미선정 수를 각각 조회 |

1단계부터 쓸 수 있게 하며 전수 촬영·동작 비교를 선행조건으로 삼지 않는다. 초안 편집은 검토상 선택까지다. 실제 Scene 조립·간격·실내 배치·입력·결과·해제는 기존 배치 구조/제약체계와 Presentation 관문으로 넘긴다. 이 페이지는 배치 엔진을 대체하거나 E를 자동 승격하지 않는다.

개발은 페이지·계약·저장 연결·자동 시험·실제 로컬 브라우저 검증을 맡는다. 프리팹 조사 담당은 판본/이미지 대응을, 애니메이션 담당은 Clip/Rig 근거를, 공간 담당은 필요한 좁은 캡처를 반환한다. **이번에는 제안서만 작성하며 담당 작업을 새로 실행시키지 않는다.**
