## 1. 사용자 의도와 변경 범위

사용자는 무질서한 확장이 아니라 전방위적인 개발을 원한다. Nature 숲에서 출발해 농장에 관심을 가질 수도 있고, 이동하다 Town을 발견하여 와인·맥주 같은 것을 제조하거나 City에서 기존 운영 시스템의 마트·도시 업무와 연결된 경험을 할 수도 있다. 농장 루트는 여러 경로 중 하나이며 그곳에서 일어나는 행위만 계속 파고들 필요는 없다. 여러 영역을 함께 살펴 전체 플레이를 종합 설계한다.

**넓게 기획하고, 기존 승인이 준비된 작은 기능들을 비중첩으로 병행 구현하며, 같은 세계에서 조화되는지를 별도로 확인한다.** 모든 분야를 동시에 완성한다는 약속이나 화면 목업만 늘린다는 뜻은 아니다. 첫 플레이 사례의 세부 질문 순서를 전 개발의 작업 순서로 쓰지 않는다.

- D411의 숲 가장자리↔농장 외곽과 D415의 봄·식사 협력은 유지되는 대표 사례이지 유일한 시작/진행 경로가 아니다.
- Nature 출발도 가능한 경로이며 모든 플레이어의 강제 스폰·농장→Town→Hub→City 직선 해금 순서는 아니다.
- 영역을 자유롭게 발견하는 지향과 실제 지지면/접근·통행/현재 허용 상태는 구분한다. City `Reserved`를 이미 접근·업무 가능하다고 표시하지 않는다.
- [D382의 여러 분야 시각 검토](야간개발-분야별시각진척-2026-08-31.md)는 과거 야간 범위다. 이번 방향에 참고하되 중지된 야간/r129의 실행 권한을 되살리지 않는다.

### 이번에 읽은 자료에서 확인한 차이

- Town 문답에는 주민 소비 주문과 플레이어 상점 보충 주문, 수령대·선반 상태·재고 조달이 구분돼 있다. 새 양조를 기존 주문 원장의 이름만 바꿔 이미 구현된 것으로 만들지 않는다.
- `docs/Architecture` 및 `eng/execution-ledgers`의 와인/맥주/양조/Brewery/Winery 텍스트 조사에서는 해당 구체 기획을 찾지 못했다. 코드·전체 자산·다른 자료 전역에 없다는 판정은 아니며 개발이 범위를 명시해 재사용 가능 부분을 확인한다.
- 기존 Loop 기획 관문에서 Town 주문·Hub 입출고·City 서비스의 `NotStarted`/빈 기획 참조를 읽었다. 현재 운영 코드가 없다는 뜻이 아니며 이 계획만으로 `Approved`로 바꾸지 않는다. 개발이 현행 원문/명세/상태를 다시 대조하고 기존 문답으로 채울 내용과 실제 새 선택을 구분한다.
- 사용자가 회상한 마트 명칭은 기존 문서의 ‘알뜰살뜰 마트’를 재사용 출발점으로 삼는다. 새로운 브랜드나 Hongdal/기존 코드 식별자 변경은 하지 않는다.

## 3. 공통 모듈과 영역별 의미를 나눈다

인벤토리·장착·물품 획득/이전, 제조 과정·용기/열원·진행 시간, NPC 대화·작업 제안, 주문/재고·확정/재조회, 지도/접근·UI/표현은 기존 기능을 먼저 조사한다. 실제 계약/결과가 같을 때 공통 부분을 재사용하고 ‘여러 곳에서 쓰인다’는 이유만으로 새 범용 프레임워크를 만들지 않는다.

예를 들어 물 데우기·약초 달이기와 양조는 과정/상태 표현을 공유할 여지가 있지만 **가열·추출·발효의 규칙과 완료 결과는 같지 않다.** 기존 HB01 내용물 계산을 맥주/와인 제조 완료로 바꾸지 않는다. Recipe·투입물·시간·도구·품질/실패·생산물 조건은 해당 주제 원문을 소유한다. 실제 술 제조법·법률/운영 판매 조사나 수치 선정은 이번에 하지 않는다.

각 작은 작업에는 다음을 함께 기록한다.

1. 일곱 칸 상황과 플레이어 선택, 성공뿐 아니라 중단/거부·돌아온 뒤 다음 선택.
2. 기존 Q/의미 ID·WI·H/AreaSet·기획/Required 연구·명세의 정확 근거와 미정.
3. Logic·Presentation 각각의 현재 근거와 다음 변경, Synty 후보/판본·실제 공급할 상태·입력·결과 표시.
4. 다른 영역과 무관하게 시험할 시작 조건과 완료 증거. 타 영역 연결이 없을 때도 내부 기능을 살펴볼 수 있어야 함.
5. 담당·정확 수정 경로·공유 계약 소유·실제 의존·시험/Unity 검증 범위. 자산 보유/자동시험/실제 게임 화면을 구별.

## 4. 개발 인계 — 첫 묶음과 계속할 기준

첫 개발 묶음은 **기존 문답/20개 주제 Loop·WI 목록/명세/소비 코드의 영역별 준비 대조와 병행 작업 후보 반환**이다. 새 기획서를 만들기 전에 기존 것을 찾고, 전역 전체 소스/자산 전수 조사를 먼저 요구하지 않는다.

개발의 전용 보고는 `docs/Reports/다영역-병행개발-준비대조-2026-08-31.md`, 임시 근거는 `artifacts/local/validation/multi-area-parallel-development/`로 한다. 기존 CURRENT/통합판과 원장을 재사용하고 별도 Queue/대장을 신설하지 않는다. 기획 문서 원문은 개발이 수정하지 않는다.

반환 표는 영역·대표 기능·승인/연구/명세·현재 Logic/Presentation·코드/자산/실제 화면·선행 공백·담당/수정 후보·다음 작업으로 구성한다. 문서 조사를 실제 구현 완료로 세지 않는다. 개발은 다음을 구분해서 부분 반환하고 가능한 독립 일을 이어간다.

- **기존 승인 범위에서 진행 가능한 기술 후속:** 기존 명세/Required Accepted 연구/허용 경로·상한을 대조해 정확 경로를 등록·조율한 뒤 좁게 구현/시험한다. 다른 영역의 미정 때문에 대기하지 않는다. 예전에 중지한 특정 Editor 슬롯을 그대로 재시도하지 않으며 실제 화면은 별도 정확 슬롯을 결속한다.
- **기획/연구 연결 보완:** 기존 확정 문답으로 채울 수 있는 내용과 새 선택을 구분하여 기획에 돌려준다. 전체 기능을 같은 질문으로 다시 승인받지 않는다. 자료상 `NotStarted`를 이유 없이 통과시키거나 순수 데이터 준비를 실제 E5로 올리지 않는다.
- **새 게임 선택:** Town 양조의 주체·자원/기간·실패/회복처럼 원문이 없는 조건은 기획의 단일 문답으로 정한다. 임의 Recipe나 생산량을 만들어 코딩하지 않는다.
- **특정 작업의 실제 차단:** 원인·해결 가능한 기술 대안·가장 이른 재개 책임을 기록한다. 그 차단을 전체 작업 중지나 Farm 완료까지 Town/City 대기로 확대하지 않는다. 같은 실패를 같은 방식으로 반복하지 않는다.

기획의 다음 문답은 Town 제작 경험을 다루어 분야를 전환한다. 이 순서는 사용자가 게임에서 그곳을 반드시 두 번째 방문한다는 뜻이 아니다. City/마트·Hub의 근거 대조는 별도로 병행하며 Town 답변을 전부 기다리지 않는다. 분야별 숫자를 같게 맞추거나 모든 분야의 E5를 이번에 보장하지 않는다.

## 5. 같은 세계의 선택지와 통합

독립적인 개발은 지역별로 단절된 게임을 만들자는 뜻이 아니다. 장기적으로 같은 canonical 세계 안에서 지형·길·랜드마크와 실제 이동을 통해 다른 장소를 발견하고, 그곳의 독립 기능을 선택할 수 있게 한다. 기존 WorldMap→배치→LH의 책임과 AreaSet/H 기준을 재사용한다.

공통 Session/시간·인벤토리·권한·상태 재조회·공간 진입/해제의 연결 검증은 개별 기능 근거와 나눈다. Nature/Farm/Town/Hub/City의 개발 순서와 플레이어 이동 순서는 같지 않다. 모든 기능이나 전체 월드가 완성되어야 작은 실제 배치를 볼 수 있는 구조도 피한다. 단 필수 지지·접근·간섭·상태 공급은 생략하지 않는다. E8/E9/전체 조화 승격은 기존 근거 기준을 따르고 이 방향 승인으로 자동 통과하지 않는다.

## 6. 운영 서버·마트와 게임의 연결 경계

마트/도시 업무는 기존 3.5 주문·재고·피킹/포장·수령/서비스 흐름을 참고하여 게임 경험과 연결할 후보를 정한다. 운영 서버에 코드나 화면이 있다는 사실만으로 게임 City에도 해당 기능이 있거나 적절한 판타지 표현이 있다는 뜻은 아니다.

- 우선 승인 범위는 기존 업무/자료의 읽기 대조와 Simulation에 적용할 의미·표현의 기획이다. 운영 기능의 범용 계약을 재사용할 가능성과 실제 운영 상태 변경은 다르다.
- 실제 운영 업무에 접근하는 기능은 별도 인증·역할·명시적 동의·현재 실행 모드/릴리스 관문을 요구한다. 게임 UI 클릭/퀘스트 결과로 실제 주문·발주·재고 차감·배차·결제·게시를 실행하지 않는다.
- 게임 데이터와 실제 원장의 상태·개인정보/권위·실행 효과를 분리하고 현실 참고 정보는 기존 선택형 열람 원칙을 유지한다. 플레이를 위해 실제 구매·계약·회원 업무를 강제하지 않는다.
- 이번 원문은 운영 DB/API 변경·실제 호출/계정 연결·유료 수집·배포를 승인하지 않는다. ‘도시 업무도 해보고 싶다’는 방향의 구체 경계는 기존 기능 조사와 후속 기획에서 확인한다.

현실에서 알아보고 활동할 길을 열어두되, 게임의 제작 성공을 현실 제조 자격·사업성·안전성 보증으로 쓰지 않는다. 상세보기에서 외부 안내로 나가는 선택, 예약·구매·교육 신청·사업 운영은 서로 다른 단계다. 이번에는 자동 예약/결제·업체 연락·실제 제조/판매 지원을 실행하지 않는다. 주류 관련 체험의 참여 조건·연령·시음 포함 여부도 출처로 확인하고 모르면 미확인으로 남긴다.

공개 메타데이터에서 확인된 범위와 실제 파일/API 응답·사진/상표 이용 범위를 구별한다. 파일 이용조건을 연결 홈페이지 사진이나 로고의 사용조건으로 확대하지 않는다. 공개 페이지는 파일의 비로그인 다운로드와 API의 가입/활용신청을 구분하여 안내하므로 기존 사용자의 로그인/다른 API 신청을 이 자료의 승인으로 추정하지 않는다. 실제 추가 접근이 필요하면 [D404 자료조사 운영](../Architecture/게임자료조사전문운영.md#로그인활용신청이-필요할-때-먼저-보고한다-d404)에 따라 필요한 조치를 먼저 반환하며 키 원문은 인계하지 않는다.

개발은 기존 자료조사 작업 `01a0524f-72e7-75e1-986a-d149951e1240`에 비중첩 범위를 배분하고 전문 → 개발 인수/검증 → 기획으로 반환한다. 전용 조사 산출물은 `docs/Research/GameData/D428/` 아래 개발이 지정한 출처/관계 보고·인계 manifest로 관리하고 raw 표본은 기존 `artifacts/local/game-data-research/` 아래 둔다. 기존 ASP.NET Core 수집·검토·MySQL/D426 대응 체계를 조사 출발점으로 재사용하되 이번 조사만으로 새 공급원 API/DB 쓰기·대량/정기 수집·사용자 게시를 자동 착수하지 않는다. 후속 저장이 필요하면 기존 D424 승인·정확 공급원/경로·권리를 확인하여 기술 범위를 따로 결속한다.

기획 쓰기는 이 원문과 DECISIONS 두 파일이며, 기존 조회의 Asked→Confirmed·신규 의미ID/자료참조 연결과 신선도/문서 검증·CURRENT/통합판은 개발 책임이다. D427 배치 조사와 독립이고 새 양조 코드·Recipe·UI·Scene·E 승격 또는 r129/야간 재개 승인이 아니다.

## 8. 범위와 완료 보고

다영역의 자료 대조·계획·등록 가능한 기술 후속 배분을 진행하는 것이 첫 결과다. 새 계획 작성이나 담당 지정만으로 여러 분야 구현/실제 Scene/E를 완료했다고 하지 않는다. 개발 보고에서 완료 코드/시험, 실제 Unity/입력/화면, 연결되지 않은 준비물, 새 기획 선택을 각각 구별한다.

원본/미소유 dirty·동결 연구·Save·기존 API 의미를 보존한다. 신규 Editor/촬영·가공/패키지·원본 삭제·실제 운영 실행·commit/push, 중지된 야간/r129를 포괄 재개하는 권한은 아니다. 기존 승인 후속의 구현도 정확 소유/명세를 확인한 범위로 진행한다. 기획은 공통 기준과 이 계획을 바탕으로 질문을 계속하고 개발·검증은 기존 개발 담당에게 맡긴다.
