# Synty 자산 MySQL 목록과 개체 관계 우선 구축

- 판본: `synty-mysql-catalog-relations.plan.r1` / D431 / 2026-08-31.
- 상태: `ApprovedScopedWork` — 기존 ASP.NET Core·로컬 Docker MySQL에 자산 메타데이터와 개체 관계를 실제 저장·조회한다.
- 사용자 요청: Unity에서 매번 확인하는 데 시간이 오래 걸리므로 MySQL에 신티 자산 목록을 넣고, 기존 DB 개체들과의 관계를 통해 어떤 개체가 어떤 자산을 사용하는지 먼저 표현·관리한다.
- 의미 식별자: `synty-mysql-catalog-and-entity-relations-first` / `Confirmed`.

## 1. 기존 감사와 구현의 관계

[D430 재검증](기존개체-KAMIS-시각대응-재검증과축적-2026-08-31.md)을 버리지 않고 원천·대응 상태 확인에 사용한다. 다만 전체 자산의 Unity 렌더/적합성 검증이 끝나야 데이터 목록·후보 관계를 저장할 수 있는 방식은 사용하지 않는다. 파일·참조 정합성이 확인된 범위부터 미검토 후보를 등록하고 후속으로 적합성을 보완한다.

[D426 공통 개체/레코드 대응](개체레코드-시각자산대응-확장과개발인계-2026-08-31.md)과 [D425 품목 대응](농수산품목-시각자산대응-기획과개발인계-2026-08-31.md)을 재사용한다. 현재 [개체시각대응DbContext](../../Ssalddel.Infrastructure/Persistence/WorldProjection/개체시각대응DbContext.cs)는 대응·감사 두 테이블을 정의하고, [자산 Catalog](../../Ssalddel/Services/Content/개체시각자산Catalog.cs)는 설정의 검토 사본을 읽는다. 이 정의가 실제 DB에 적용됐는지는 D430의 현행 감사와 구분한다.

이번 추가 승인은 자산 목록의 영속화, 기존 대응에서 그 목록으로의 명시 관계, 서버 가져오기·조회·검토 연결과 실제 로컬 DB 적용이다. 기존 파일 대장/Unity 표현 키를 버리고 새 독립 자산 체계를 만드는 것이 아니다. 과거 원문/hash는 수정하지 않는다.

## 2. MySQL에서 관리할 관계

| 구성 | 저장/참조할 정보 | 재사용·제한 |
| --- | --- | --- |
| 자산 목록 | 안정된 자산 식별자, 공급자/팩, Prefab GUID·표시명, 원본/meta fingerprint, 목록 판본, 기존 표현 키/계열, 분류, 확인/검토 상태·근거 | 기존 대장/Prefab 파일에서 제한 가져오기. Prefab·FBX·텍스처 바이너리나 GameObject를 DB에 넣지 않음 |
| 개체 종류/개별 대응 | 원천 종류·권한 범위, 종류 기본/개별 기록 ID, 원천 판본, 상태·표현 목적, 자산 목록의 정확 식별/판본 참조, 검토 상태·대체 사유 | D426 대응·이력과 선택 정책 재사용. 후보/검토보류 관계도 조회 가능 |
| 공통 품목 코드 | 기존 KAMIS 분류·품목 코드와 공통 품목 ID/관계 상태 | 기존 품목/코드 테이블을 참조. 원천 가격 관측 행마다 자산 관계를 복제하지 않음 |

사람이 조회할 관계는 `기존 개체 종류/개별 기록 → 표현 대응 → 자산 목록`이며 농수산물은 `KAMIS 코드 관계 → 공통 품목 → 상태/목적별 표현 대응 → 자산 목록`으로 연결된다. 이 관계는 실제 상품·시설의 동일성이나 World 배치를 자동 확정하지 않는다.

기존 대응의 JSON 사본은 감사/호환 목적을 보존한다. 자산 참조와 주요 검색 조건은 명시 관계/인덱스 등으로 조회할 수 있게 하고, 관계 열과 JSON의 불일치는 거부한다. 가능한 같은 DB 내부 자산 참조는 외래키/삭제 제한을 사용한다. 여러 DbSet에 걸친 종류/개별 ID는 임의 테이블명 SQL이나 무효한 다형 외래키를 만들지 않고 등록된 Reader의 존재·권한·판본 검사로 보완한다. 정확 테이블/열 이름과 최소 변경은 개발이 현행 스키마에 맞춰 선언한다.

자산 GUID가 같아도 판본이 바뀌면 기존 승인 근거가 그대로 유효하지 않다. 하나의 Prefab이 여러 표현 키/문맥으로 재사용되는 경우와 같은 키의 충돌을 구분한다. 기존 데이터·이력을 삭제하여 맞추지 않는다.

## 3. 등록과 실제 사용 승인은 분리한다

- 목록 등록은 자산 파일 존재·참조/판본을 확인했다는 뜻이다. 외형 적합성 미검토·크기/Collider 미측정도 그대로 기록한다. 필요한 미확인 필드는 미확인/미결속 상태를 허용하며 가짜 근거·hash·Prefab ID로 채우지 않는다.
- 관계 저장은 특정 종류/기록에 이 자산을 검토 중이라는 뜻일 수 있다. 이 후보 관계도 DB 조회 결과에서 보이게 한다. `Draft/PendingReview` 등 기존 상태를 재사용하고 실제 선택용 승인을 자동 부여하지 않는다.
- 제품 선택은 기존 권한/존재/상태·목적·판본과 적합성 근거 검사를 유지한다. 유효한 개별 승인 → 같은 문맥의 승인 기본형 → 미연결이며, 조회 오류/권한 실패를 기본형으로 숨기지 않는다.
- DB 자산 목록 조회와 제품 선택용 Catalog를 구분해 미검토 자산을 후보 목록에서 제외하지 않는다. 기존 설정 사본과 DB 사본의 출처/판본·우선순위는 명확히 하고, 운영 중 서로 다른 두 승인 원장이 경쟁하지 않게 한다. 최소한 이번 가져오기·조회 경로는 DB 사본을 실제로 소비해야 한다.
- 기존 외형 근거가 충분하면 재사용한다. 실제 판독이 필요한 후보만 후속 Unity 점검 대상으로 남긴다. 이 작업의 완료 조건에는 Editor 실행·Play·Game View·Scene 배치가 없다.

## 4. 첫 구현과 실제 저장

1. D430에서 확인한 정확 기존 로컬 컨테이너·DB/원천 테이블과 D426 모델을 대조한다. 앱이 다른 DB를 사용하거나 재시작 중이면 그것을 별도 보고하고 임의로 연결을 바꾸거나 복구하지 않는다. 명시적으로 승인된 로컬 데이터 축적 대상에 한정하여 서버 서비스로 실행할 수 있는 범위를 분리한다.
2. 자산 목록 테이블과 필요한 대응 참조만 추가하고 D426의 대응·이력 테이블이 없으면 그 승인 범위의 제한 DDL을 함께 준비/적용한다. 원천 테이블·데이터 보존, 변경 전 스키마 확인과 변경 후 비교를 수행한다. 전체 Migrate/EnsureCreated·DB/볼륨 교체·초기화는 하지 않는다.
3. 기존 D426의 8개 표현 키/실제 파일·대장 입력을 첫 가져오기 표본으로 사용한다. 현행 hash·GUID를 재대조한 메타데이터만 서버를 통해 저장하고 미검토/기존 근거 상태를 유지한다. 키 수와 고유 자산 수를 각각 보고한다. 새 외부 자산 다운로드·전체 Synty 전수 적합성 승인은 하지 않는다.
4. 실제 존재하는 공통 식품 품목과 독립된 다른 개체 종류 표본을 우선 관계 초안으로 연결한다. 감자만으로 전체 완료라고 하지 않는다. 원천 부재/권한 미확보면 그 종류는 보류하고 다른 실제 표본으로 진행한다. 원천 데이터나 관리자 계정을 만들어 수를 채우지 않는다.
5. 기존 관리자 권한·UseCase/Repository 경계 안에서 `목록 조회 → 개체/품목별 관계 조회 → 후보와 승인 선택 구분`을 구현한다. 데이터 우선 검토용 제한 로컬 실행은 허용하지만 제품 기본 활성화·일반 공개·권한 우회와 구분한다. 공유 appsettings/비밀값을 덮어쓰지 않는다.
6. 같은 확보 입력 재처리의 중복 방지, 판본 변경/고아 참조/충돌/타 권한 거부, 개별/기본 대응·미검토 비선택과 기존 D426 회귀를 검증한다. 별도 DB 조회 문맥에서 저장 결과와 관계를 재조회한다. SQLite/Fake 시험과 실제 MySQL 결과를 나눠 보고한다.

공공자료 추가 수집은 필요하지 않다. 원천 KAMIS/품목/가격/재고·개인정보와 Unity 원본은 변경하지 않는다. 서버 DB에는 자료 목록/참조·검토 근거를 보관하고 실제 Prefab 해석·배치는 기존 Unity/배치 구조가 후속으로 수행한다.

## 5. 소유와 반환

기획은 이 원문과 DECISIONS만 작성한다. 개발은 정확 코드/테이블/가져오기 경로·검증 상한을 선언하고 기존 자료/공간 담당의 파일 근거를 재사용하여 구현·시험·DB 저장/재조회와 통합을 맡는다. 보고는 `docs/Reports/Synty자산-MySQL목록-D431-개발통합-2026-08-31.md`, 실행 근거는 `artifacts/local/validation/synty-mysql-catalog-d431/`를 기본으로 하며 충돌하면 착수 전 다른 정확 경로를 반환한다. CURRENT_WORK/통합판은 개발이 갱신한다.

첫 반환에는 실제 DB/테이블, 등록 자산/키 수, 대응 대상 종류·기록/관계 수, 미검토/승인·미연결 수, 개체→자산 관계 조회 예시, 같은 입력 재처리 결과, 코드·시험·MySQL 실행/Unity 미실행을 구분한다. 전산화 완료와 모든 자산의 시각 적합성·게임 적용 완료를 혼동하지 않는다.

이번 요청은 D430을 매번 Unity 확인 대기로 두지 않고 데이터 관계 구축으로 이어가기 위한 추가 승인이다. 기존 D425/D426 선택·권한·출처 분리, D429 로컬 DB/비밀값 경계와 D430 감사 기록은 유지한다. 새 권리/유료·대량수집·원격 운영 쓰기·일반 게시·Scene/Save/E 변경·r129/야간·commit/push는 승인하지 않는다.
