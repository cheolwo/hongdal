## 현재 목표

운영 서버의 네 업무 흐름에서 상태·전이·수량 보존과 운영 제외 효과를 먼저 추출한다. Simulation은 실제 주문·결제·기사·주소·GPS·알림을 만들지 않고 같은 업무 의미를 가상 session·WorldTick·재고·노동 안에서 실행한다. 개별주문은 시장 감자 300kg에서 주민 주문 20kg을 예약·포장해 시장 잔여 280kg을 만들고, 별도 수령·소비 Confirm 뒤 주민 소비 누계 20kg과 같은 정착지 경제 snapshot에 수렴한다. 화물운송은 같은 Cargo 300kg에 운송 의뢰·배차 후보·차량 용량·상차·운송·하차 도착·별도 인수 확인을 연결했다. 같이주문은 참여자별 명시적 의향을 보존하고 모집 결과 Confirm 뒤 목표 충족은 확정, 미달은 모집종료목표미달로 귀결한다. 음식배달은 가상 주문 접수 뒤 조리·픽업 준비·기사 후보 배정·픽업·전달을 WorldTick 인과로 기록하고, 주문자 수령은 별도 Confirm 뒤에만 완료한다. 외부 교역 준비는 `ExportAgent`로 배분된 수확물만 포장·모의 검사할 수 있고, 통과한 최신 시도는 기존 예약량을 중복 예약하지 않는 Cargo 준비 후보로 이어진다. Cargo 준비와 배송대행지 Simulation 인계를 모두 마친 Cargo만 기존 물류 이동 Preview에 들어가고, 해당 Confirm 뒤 WorldTick에서 출발·진행·도착한다. 목적지 시설과 일치하는 별도 항만 인수 Confirm·Task가 완료되어야 `ReceivedAtPortStaging`이 된다. 이후 서류 묶음과 후속 검사 준비 여부를 자기 진술형 Simulation 입력으로 검토해 `ReadyCandidate` 또는 `ActionRequired`로 기록하고, 보완 뒤 새 stable ID와 부모 검토 계보로 재검토할 수 있다. 준비 후보는 목적 국가·시장·해상/항공 방식·예상 매출·국제물류/취급/기타 비용·예상 기간·위험 점수를 서로 다른 Preview로 비교하고, 선택한 하나만 계획 후보로 확정한다. 계획 실행 Confirm은 결과를 숨긴 채 최악 손실 여력을 예약하고 계획 기간 동안 `InTransit`으로 진행한다. 완료 Tick에서 세션 seed와 실행 stable ID로 결정한 성공은 도착 수량과 순수익 차액을, 손실은 손실 수량과 비용을 한 번만 반영한다. 판로 결정 때 이미 반영한 예상 매출은 결과 정산에서 조정해 중복 수익을 막고, 두 결과 모두 출고 예약 300kg을 종료한다. 통합 판로 결과 projection은 같은 HarvestLot 아래 조합·직판·보관·외부 교역 네 선택지를 고정 순서로 보여주고 선택된 경로만 기존 원장에서 현재 단계·해결/잔여/도착/손실 수량·누적 재정·시장·비축·위험 결과를 읽는다. 조회는 세션 state나 save/replay hash를 바꾸지 않는다. 실제 수출신고·공식 검사·검역 승인·통관·계약·운임 정산·운송 예약·선적은 생성하지 않는다.

## 현재 방향

- Unity는 특정 Web 버전이나 route를 순서대로 3D 복제하지 않는다.
- 전체 Ssalddel 도메인을 `World`, `Data`, `Object`, `Interaction`, `Simulation`으로 구성한다.
- 실제 구현은 공통 계약과 작은 vertical slice 단위로 진행한다.
- 서버가 실제 운영 상태의 최종 권위를 가진다.
- simulation fixture와 operational data를 schema, 상태와 UI에서 구분한다.
- sensor는 일반 관측 상태와 물리 장비 표현을 연결하는 단일 projection이다.
- 외부 asset보다 placeholder와 View socket 계약을 먼저 검증한다.
- Synty 원본 자동 색인과 사람의 의미 연구를 분리하고, 장소·체계 검증 뒤에만 월드 목록 후보로 승격한다.
- `WORLD-SHELL-0 → SETTLEMENT-SCENE-0 → SETTLEMENT-ECONOMY-1 → WORLD-SETTLEMENT-NAV-0 → BRANCH-ADAPTER-1 → SETTLEMENT-VISUAL-BASE-0 → SETTLEMENT-INTERACTION-0 → LOGISTICS-MOVEMENT-1`을 완료했다. `WORKFLOW-RULES-0 → SIM-ORDER-CORE-1 → SIM-INDIVIDUAL-ORDER-1 → SIM-FREIGHT-TRANSPORT-1 → SIM-GROUP-ORDER-1 → SIM-FOOD-DELIVERY-1 → MARKET-CONSUMPTION-1 → EXPORT-1 → EXPORT-2 → EXPORT-CARGO-1 → EXPORT-HANDOFF-1 → EXPORT-LOGISTICS-1 → EXPORT-PORT-RECEIVING-1 → EXPORT-READINESS-1 → EXPORT-SHIPMENT-PLAN-1 → EXPORT-SHIPMENT-SIM-1 → HARVEST-ROUTE-OUTCOME-1 → HARVEST-ROUTE-CARD-1 → HARVEST-ROUTE-REFRESH-1 → HARVEST-ROUTE-RESUME-1 → HARVEST-ROUTE-MULTI-LOT-1`에서는 운영 API를 호출하지 않는 공통 규칙, 감자 20kg 개별주문과 주민 소비·잔여재고 수렴, Cargo 300kg의 가상 운송, 참여 의향 3건·60kg의 같이주문 모집 결과, 조리부터 주문자 수령까지의 가상 음식배달과 수출 준비 포장·모의 검사·재작업·Cargo 준비·배송대행지 Simulation 인계·항만 준비시설 경로 이동·별도 인수·준비성 재검토·선적 계획 비교·결정적 성공/손실 정산·네 판로 통합 읽기·생산자 카드·재접속 갱신·예약 Task 재개·다중 Lot 선택 격리를 연결했다.
- Unity 감자 생산·유통 연구 Scene 9개와 `신티에셋연구소`의 주요 정보 Panel에 Presentation 전용 `접기`, `펼치기`, `닫기`, `다시 열기` 상태를 공통 구현했다. 9개 업무 Scene은 Builder 재생성·wiring 검증을 통과했고 연구소는 기존 Scene에 좁게 적용했다. 이어 감자 이동 연결 Scene 2개를 포함한 관련 Scene 12개를 `감자생산유통`, `생산자판로`, `에셋연구` 세 폴더로 AssetDatabase 이동하고 Builder 경로를 단일 catalog로 모았다. Unity 재컴파일 오류 0건, 공통 상태 전이 EditMode 1/1, Scene 경로·GUID 보존 EditMode 12/12, 10개 Scene 직렬화 연결, 연구소 Play Mode·Game View를 확인했다. 기존 연구소 전체 Builder의 catalog 재생성 뒤 Presenter wiring 오류와 `ScreenSpaceOverlay`를 포함하지 않는 Pipeline 카메라 캡처 한계는 별도 미해결로 남겼다. 서버·Simulation 상태, 운영 API, provider 호출은 수행하지 않았다.

## 현재 작업

운영 서버를 변경하거나 Unity core를 이동하지 않고 `Ssalddel.Simulation.Contracts`, `Ssalddel.Simulation.Domain`, `Ssalddel.Simulation.Server`를 별도 dependency island로 추가했다. API는 session 생성·조회·호환 Tick, 공통 Decision Preview/Confirm, 턴 마감 context·Preview·Confirm, save/restore와 수확 판로 영향 Preview/Confirm을 제공하며 client request·command 멱등성, expected revision, scenario data revision, seed와 rule revision을 보존한다. 플레이 시간은 턴 마감 Confirm에서만 한 WorldTick 진행한다. API는 기본 비활성이고 `SsalddelExecution:Mode=Simulation`에서만 시작한다. 현재 session/save 저장소는 process-local in-memory이므로 개발 fixture 외의 영속 권위로 사용하지 않는다.

Unity의 P0~P7·DIP5R 공통 기반과 외부·공공 데이터 P6-B 결과는 유지한다. DIP6 도심마트 UM0~UM4에 이어 UM5에서 `도심마트ManagerRuntime`과 별도 manager surface sample을 추가했다. Runtime은 manager role이 승인된 `AuthorizedUserWorld` Data context만 받고, Data refresh 뒤 Shared World에 남아 있는 선택만 focus로 유지하며, shelf·task·source-plan·detail을 각각 stable-ID change set으로 반환한다. 업무 우선순위 점수·summary·queue는 만들지 않는다. refresh 실패는 마지막 성공 Presentation과 선택을 유지하고 session·World·authorization 경계 변경은 둘 다 폐기한다. View는 Projector가 결정한 문구·색 token·상자 수만 적용한다.

RG1~RG4, RG4-NPC-A/B와 SC0~SC5는 집단 수요·대표 identity·4주 Engine·Perspective·두 Zone 방문·공급 위험/Presentation과 Unity mapper/applicator/View source까지 구현했다. CC1~CC2의 공통 계약·Projector·대표 7-card adapter에 이어 CC3-A에서 `ConceptCardView`·deck·4종 visual skin, 대표 선택, manager desk, 임시 NavMesh와 Mecanim parameter를 연결했다. 도심 물류센터 sample에는 한 handoff 조회로 Truck과 시설 overview를 함께 만들고 차량 접근·입고 Dock·검수·보관을 보여주는 View를 추가했다. 첫 Engine은 검수·입고·진열 판매가능 전환 작업을 하나의 명시적 Tick capacity로 합산하며, 별도 직원 task·진열 surface는 SC7에서 UM4와 연결한다. 실제 Unity project에는 City Pack 원본을 유지한 채 두 전용 builder와 저장 Scene을 추가했고, 마트·물류센터 Game View와 Play Mode를 확인했다. 구매 asset은 View에만 머물며 canonical Data·stable ID·Command 경계는 기존 Ssalddel 코드가 소유한다.
