# 프리팹 이미지 전담 조사와 Azure 보관·웹 열람

- 판본: `prefab-image-research-azure.plan.r1` / D433 / 2026-08-31.
- 상태: `ApprovedScopedWork` — 전담 작업 생성, 보유 자산 이미지 수집/분류, 기존 Azure Blob의 제한 비공개 보관·서버/DB 연결·웹 열람.
- 사용자 요청: 보유 Synty 프리팹의 외형 이미지를 별도로 조사·저장한다. 동봉된 이미지가 있으면 재사용하고, 별도 프리팹 조사 작업을 만들어 Azure Blob에 보관한 뒤 웹으로 확인할 수 있게 한다.
- 의미 식별자: `prefab-image-dedicated-research-and-azure-storage` / `Confirmed`.

## 1. 기존 데이터·이미지 작업의 연장

[D431 자산 MySQL 목록](Synty자산-MySQL목록과개체관계-구현승인-2026-08-31.md)과 [D432 이미지 비교](개체자산-이미지비교와할당검토-2026-08-31.md)를 유지한다. 이번에는 전담 조사 책임과 **검토된 이미지의 Azure 비공개 업로드·권한 있는 웹 열람**을 추가한다. D432 당시 외부 업로드 제외는 이 정확 범위에서 추가 승인으로 대체하며 공개 재배포·자산 원본 업로드 금지는 유지한다.

MySQL은 자산/개체/이미지의 관계를, Blob은 이미지 파일을 보관한다. 웹은 서버의 권한 있는 조회로 둘을 결합한다. 자산 원본 Prefab·FBX·텍스처·패키지를 Blob에 옮기는 작업이 아니다.

## 2. 전담 작업과 소유권

| 담당 | 책임 | 하지 않는 일 |
| --- | --- | --- |
| 프리팹 조사 | 팩/Prefab별 이미지 재고·동봉 자료·기존 캡처 조사, GUID/판본/이미지 hash 연결, 이용조건/촬영 필요 분류, 전용 목록/근거 인계 | 공통 코드/DB·Azure 비밀값·직접 Editor 점유·Scene 저장·실제 할당 승인 |
| 월드·공간·배치 | 이미지가 없는 정확 후보의 격리 미리보기, 촬영 조건·보존·manifest 반환 | 전담 조사와 중복 전수 조사, 기본 원본/공식 Scene 변경 |
| 개발 | 기존 D431/D432 통합, 정확 소유 배분, 미디어·Azure/인증·제한 업로드·DB 연결/재조회·웹 검증 | 통신 시험을 개발 성과로 대체, 무검토 일괄 승인 |
| 자료 조사 | 필요한 기존 권리/출처 근거를 개발을 통해 공유 | 같은 프리팹 이미지 재고를 중복 소유 |
| 기획 | 목적/범위·사용자 선택을 기록하고 준비된 이미지로 할당 판단 | 직접 공통 코드/DB/Editor 조작 |

사용자가 요청한 별도 `프리팹 조사` 작업은 같은 프로젝트의 독립 worktree로 만든다. 공유 Hongdal/Unity 원본은 읽기 전용으로 참조하고 최신 기획/dirty 소스가 새 worktree에 자동 반영됐다고 가정하지 않는다. 전담은 자신의 `docs/Research/PrefabImages/D433/`의 README·inventory·manifest와 `artifacts/local/prefab-image-research/d433/`만 첫 소유로 삼고 정확 산출물을 개발에 반환한다. 개발이 통합하지 않은 전문 파일을 제품 DB/공유 문서의 완료로 세지 않는다.

## 3. 어떤 이미지인가를 먼저 판별한다

1. 구매/임포트된 팩 안에 프리팹별 PNG/JPEG 등의 외형 이미지가 실제 있는지 조사한다. 텍스처 아틀라스·재질 맵·일반 아이콘은 프리팹 미리보기로 사용하지 않는다. 이름/폴더만으로 이미지의 내용·대상 일치를 확정하지 않는다.
2. 기존 격리 미리보기·공급자 이미지·여러 자산이 섞인 Showcase·실제 Game View를 구분한다. GUID/판본과 정확 대응이 있는 기존 자료를 우선 재사용한다.
3. Unity가 Editor에서 일시 생성한 작은 썸네일은 동봉된 영구 이미지 파일과 구별한다. 필요한 경우 개발/공간이 기존 안전한 Preview 경로로 내보내며 임의 Library 캐시를 자산 원본으로 등록하지 않는다.
4. 후보별 원본/이미지 파일 hash, 크기/형식, 출처 종류, 자산 판본, 촬영/확인 시점, 각도·적합성 한계와 재촬영 필요를 기록한다. 변경되지 않은 자료를 반복 촬영/업로드하지 않는다.
5. 기존 D426/D431의 8키 고유 자산부터 이미지 조사·보관·웹 확인 한 묶음을 완성한다. 나머지 보유 팩은 메타데이터 재고와 미처리 목록을 남기고 후속 작은 묶음으로 확장한다. 전수 이미지 확보까지 첫 결과를 보류하지 않는다.

새 이미지가 필요하면 D432의 공간 단독 슬롯/시작 보존/정확 후보 범위로 촬영한다. 새 공식 Scene·가공/원본 저장·불필요 Play·새 렌더 도구 설치·AI 생성 이미지는 이번의 실제 자산 증거가 아니다.

## 4. 권리와 보관 범위

구매 채널/해당 라이선스와 이미지 종류를 확인한다. 구매했다는 사실만으로 동봉 마케팅 이미지·텍스처 원본의 독립 재게시를 허용한다고 보지 않는다. 자체 자산 미리보기와 공급자 원이미지의 근거를 구분하며, 불명확하면 해당 이미지의 클라우드 업로드만 보류하고 로컬 목록·다른 허용 자료는 진행한다. 새 구매·계정/약관 동의·공급자 연락은 자동 수행하지 않는다.

공식 참고: [Synty 현행 One Time Purchase Licence](https://syntystore.com/pages/one-time-purchase-licence)는 제품 안의 이용과 제한을 설명한다. 2026-07-09 현행 페이지를 구매 당시/다른 채널의 계약에 소급 적용했다고 기록하지 않는다. 이번 파이프라인은 내부 프로젝트 자산 검토이며 공개 자산 배포 사이트·생성형 AI 학습 데이터·3D 생성 입력으로 전용하지 않는다.

## 5. 기존 Azure 경로로 소수 이미지부터 실제 보관

기존 [IObjectStorageService](../../Ssalddel/Services/Storage/IObjectStorageService.cs), [AzureBlobStorageService](../../Ssalddel/Services/Storage/Azure/AzureBlobStorageService.cs), [AzureBlobStorageOptions](../../Ssalddel/Services/Options/AzureBlobStorageOptions.cs)를 재사용한다. 현재 코드에는 Private/Public 분리와 불변 이름 업로드·다운로드가 있지만, 설정 문자열 존재는 실제 인증/컨테이너 준비의 증거가 아니다.

- 개발이 실제 설정의 계정/컨테이너·권한·비공개 정책·대상 경로와 예상 첫 분량을 비밀값 없이 확인한다. 기본 설정 이름을 실제 리소스로 가정하지 않는다. 기존 확인된 비공개 컨테이너의 전용 prefix를 우선 사용한다. 별도 계정/구독·공개 컨테이너/새 비용성 서비스는 만들지 않는다. 필요한 대상/권한이 없으면 정확한 사용자 조치만 반환한다.
- 승인된 이미지 파일만 서버의 기존 인증된 저장 경계를 통해 업로드한다. 첫 묶음은 위 8키의 준비된 대표 이미지이며 추가 각도는 판독에 필요한 경우만이다. 파일 크기/형식을 검사하고 동일 자산판본·이미지 hash에 결정적인 object key를 사용해 덮어쓰기/중복을 피한다.
- Blob 업로드와 MySQL은 단일 트랜잭션이라고 가정하지 않는다. 준비·업로드·DB 결속·검증 단계를 구분하고 재시도 시 같은 파일을 재사용한다. DB 결속 실패 뒤 Blob을 임의 삭제하지 않고 미결속 상태로 기록한다.
- 같은 object key가 이미 있을 때는 ETag나 충돌 응답만으로 같은 이미지라고 하지 않는다. 필요한 hash/크기와 실제 재읽기를 대조하고 다른 내용이면 거부한다. URL 반환을 이미지 접근/웹 렌더 성공으로 보고하지 않는다.
- DB에는 비밀값 없는 미디어 식별자·컨테이너/object key·hash·자산판본·출처/권리 상태를 결속한다. 연결 문자열·키·장기 SAS URL을 저장/로그/대화에 내보내지 않는다.
- 웹은 기존 관리자 인증 뒤 서버 매체 응답 등 검증된 비공개 경로를 사용한다. 브라우저 임의 파일경로/URL 입력으로 서버 파일/Blob을 읽게 하지 않는다. 익명 차단·권한 있는 대표 이미지 열람·원본 확대·오래된 이미지 상태를 검증한다. 로컬 페이지 확인과 실제 원격 웹/모바일 접근은 각각 보고한다.

Microsoft 공식 기준인 [익명 접근 구성](https://learn.microsoft.com/en-us/azure/storage/blobs/anonymous-read-access-configure)과 [Entra ID Blob 권한](https://learn.microsoft.com/en-us/azure/storage/blobs/authorize-access-azure-active-directory)을 참고한다. 이번 기능을 위해 기존 계정의 전체 보안 설정을 임의로 변경하지 않으며 필요한 좁은 기술 보완만 개발이 소유·검증한다.

## 6. 첫 반환과 완료 구분

전담은 동봉 이미지 수/실제 프리팹 대응 수·기존 렌더 재사용 수·미확보/미확인 권리 수를 반환한다. 개발은 로컬 파일 확보, 실제 Azure 업로드/재읽기, MySQL 결속/중복 방지, 권한 있는 웹 열람을 단계별로 반환한다. 하나만 성공해도 먼저 알리되 전체 완료로 확대하지 않는다.

개발 보고 기본은 `docs/Reports/프리팹이미지-Azure-D433-개발통합-2026-08-31.md`, 실행 근거는 `artifacts/local/validation/prefab-image-azure-d433/`다. 정확 코드/웹/테이블 쓰기 경로는 D431/D432 소유와 합쳐 선언한다. 기획 소유는 이 원문/DECISIONS이고 생성된 전담 작업 ID는 결정 또는 개발 상태판에 연결한다. 실제 DB·Azure·웹 작업은 개발 통합 소유이며 D431 관계 구축을 이미지 전체 확보까지 멈추지 않는다.

원천 자료·가격/재고/권위·원본/Scene·E·r129/야간·무관한 중지 작업·commit/push는 재개하지 않는다. 이 추가 승인에서 허용한 것은 확인된 이미지의 비공개 저장과 웹 검토이지 실제 개체 할당의 자동 승인이나 공개 배포가 아니다.
