- 기획 판본: `entity-record-visual-correspondence.plan.r1`

- 사용자 승인: 종류별 기본 표현·개별 기록별 표현을 모두 지원하고, 개별 표현이 없으면 승인 기본형을 사용한다는 선택 및 창고·마트 등으로 확장한 제안에 대한 `Implement the proposed plan.`

## 2. 자료 조사와 표현 단위

`DbSet`은 조사 출발점이지 Unity 객체/Controller를 하나씩 만드는 목록이 아니다. [SsalddelContext](../../Ssalddel.Infrastructure/Persistence/SsalddelContext.cs), [농수산물 Context](../../Ssalddel.Infrastructure/Persistence/AgriculturalFisheries/AgriculturalFisheriesDbContext.cs), [시장 Context](../../Ssalddel.Infrastructure/Persistence/TraditionalMarkets/TraditionalMarketDbContext.cs), 기존 권한별 조회 계약·자산 대장을 현행 파일로 대조한다. 과거 문서의 Entity/Prefab 개수를 현재 전수 확인 결과로 쓰지 않는다.

종류는 안정된 업무 식별자로 구분하고 Entity/DbSet 경로는 내부 추적 근거로 연결한다. 공개 입력으로 CLR 타입·테이블명·속성명을 받아 임의 DB 조회를 하지 않는다. 같은 숫자 ID라도 종류·원천·권한 범위가 다르면 다른 대상이다.

기존 `WorldObject / StateComponent / Panel / WebHandoff / InternalOnly / NoCanonicalSource`를 재사용한다. 건물·밭·선반·차량은 공간 실체, 재고량·관측·이력은 해당 실체의 상태 또는 상세정보, 긴 표·민감한 입력은 정보창/기존 Web 업무로 구분한다. 내부 자료와 권위 원천이 없는 대상은 공개/물리 객체화를 추정하지 않는다. 관측 행마다 새 객체를 생성하지 않는다.

현재 [창고](../../Ssalddel.Domain/창고/창고.cs)는 기본 유형이 가상창고이고 주소·담당자·연락처를 포함한다. 실제 시설 연결이 없으면 창고 건물로 단정하지 않는다. [마트공개상품](../../Ssalddel.Domain/마트/마트공개상품.cs)은 상품 기록이지 매장 건물 기록이 아니므로 해당 행만으로 위치·매장을 생성하지 않는다.

## 3. 공통 정보와 선택 규칙

공통 저장·조회·검토·선택 기능에 분야별 읽기 Adapter를 연결한다. 품목·창고·마트마다 별도 대응 시스템을 만들지 않는다. [공통 품목 ID](../../Ssalddel.Contracts/Common/PublicData/공통식품품목IdentityDtos.cs)와 기존 자산 대장을 복제하지 않으며 기존 필드/계약으로 충족되면 재사용한다.

| 구분 | 최소 정보 |
| --- | --- |
| 대상 | 분야·개체 종류, 종류 기본/개별 기록 구분, 개별 고유 식별자, 원천·권한 범위·대상 판본 |
| 문맥 | 표현 분류, 상태, 목적/역할·표시 위치, 적용되는 WI/H 참조 |
| 표현 참조 | 기존 `VisualKey`/자산 계열, 대장 판본·fingerprint, 주·대체 후보와 사용 제한 |
| 검토 | 미검토·검토·승인·제외, 외형 적합/범주 대체, 근거·검토자·시점·판본·변경 이력 |
| 결과 | 선택 키, 개별/기본 수준, 대체 여부, 선택 또는 미연결·충돌·재검토 사유 |

선택 순서는 **대상·권한 확인 → 같은 문맥의 유효한 개별 승인 → 같은 문맥의 유효한 종류 기본 승인 → 미연결(`Unmapped`)**이다.

- 기본형 승인은 특정 기록의 정확 외형 검증이 아니다. 이름·수량·상태는 권위 조회 결과를 유지하고 `IsFallback`에 해당하는 정보와 이유를 반환한다.
- 다른 상태·목적·권한 범위로 대체하지 않는다. 생육 식물·수확물·포장품·건물·정보창의 역할을 구별한다.
- 미검토·제외·오래된 근거·미등록 키는 선택하지 않는다. 유효한 기본형을 사용해도 개별 후보의 결손/재검토 사유를 숨기지 않는다. 같은 우선순위의 활성 대응 충돌은 첫 행/기본형으로 덮지 않고 거부한다.
- 접근 거부·원천 조회 실패·존재하지 않는 대상은 기본형으로 성공 처리하지 않는다. 대체는 표현 결손의 보완이지 데이터 오류/권한 우회가 아니다.
- 대응·상태/목적·대장 판본·근거 변경은 해당 승인 무효화 또는 재검토로 이어지고 과거 이력은 보존한다. 복수 후보는 기존 결정적 선택과 명시 우선순위를 사용하며 같은 입력/판본은 같은 결과를 낸다.
- 외형으로 현실 코드 관계를 승격하지 않는다. 농사로 콘텐츠30699·작업군210005를 상품 코드로 전용하거나 미확정 어종에 임의 ID를 만들지 않는다. 모델 크기·개수로 재고·중량·가격·생산을 계산하지 않는다.

## 4. 첫 네 분야와 후속 확대

공통 기능 확보 뒤 다음 분야는 독립적으로 진행한다. 감자 외형 완성이 창고·마트의 선행 조건이 아니다.

| 분야 | 기존 대상·조회 근거 | 첫 대응 범위 |
| --- | --- | --- |
| 창고 | 창고·입고상품·재고와 [창고 상태 계약](../../Ssalddel.Contracts/Common/WorldProjection/WarehouseWorldSnapshotDtos.cs) | 물리 시설/정보 구별, 상품상자·Pallet·작업 위치 |
| 마트 | 공개 상품·운영자 선반과 [피킹·포장 계약](../../Ssalddel.Contracts/Common/WorldProjection/MarketPickingPackingWorldSnapshotDtos.cs) | 상품·선반·포장 표시, 공개 상품/운영자 재고 권한 분리 |
| 농장 | 농장·구획·재배작기·센서와 [생산자 관점 계약](../../Ssalddel.Contracts/Common/WorldProjection/FarmProducerPerspectiveDtos.cs) | 농장/밭·작물·센서, 참고자료와 실제 재배상태 분리 |
| 농수산물 | 공통 품목·저장 자료와 [감자 생산·유통 계약](../../Ssalddel.Contracts/Common/WorldProjection/감자생산유통WorldDtos.cs) | 생육·수확·포장별 후보. 감자만을 위한 별도 선택기는 만들지 않음 |

분야마다 실제 존재하는 대상 묶음 최소 하나부터 시작한다. 데이터가 없으면 부재/필요 자료를 반환하고 다른 분야로 이동한다. 수를 채우려고 창고·마트·상품·거래를 만들지 않는다. 합성 자료는 시험 Fixture로만 쓴다.

그 다음 **전통시장·물류 거점 → 음식점·메뉴 → 차량·운송 → 커뮤니티·교육** 순으로 기존 실체를 조사하고 작은 적용을 계속한다. 이는 작업 순서이지 영역 간 필수 업무 인계나 게임 진행 순서가 아니다. 미준비 분야는 사유를 남기고 독립 분야를 진행한다. 개인정보·계약·정산·금융 자료의 자동 공개는 포함하지 않는다.

기존 상태판/보고에 조사·후보·승인·코드 연결·실제 저장/재조회·Unity 미연결을 별도로 기록한다. 목록/후보 개수로 실제 대응 완료율을 만들지 않는다.

## 5. 서버·DB·Unity 연결

- 기존 관리자 정책 아래 종류/분야/상태 조회, 대응 저장, 검토·승인·제외 API를 구현한다. 일반 사용자·익명은 거부한다. 대상 조회의 기존 권한을 재검증하고 내부 근거·개인정보를 공개 응답에 넣지 않는다.
- UseCase·Repository·개정 검사·요청 멱등·감사 패턴을 재사용한다. 저장/이력을 단일 전이로 묶고 활성 중복을 방지한다. 정확 계약/테이블/키·소유 경로는 개발이 기존 구조를 대조해 최소안으로 선언 후 구현한다. 원천 자료와 업무 원장은 변경하지 않는다.
- 서버에는 대응·근거·표현 참조만 저장한다. Prefab·텍스처·`GameObject`·로컬 절대 경로를 업무 계약/업로드로 만들지 않는다. 기존 `상품물류자산`의 사진·증빙을 Prefab 저장소로 전용하지 않는다.
- 실제 DB 적용은 [자료조사 운영](../Architecture/게임자료조사전문운영.md)의 기존 로컬 Docker MySQL 범위만 사용한다. [D424 보고](../Reports/현실자료-서버MySQL축적-D424-개발통합-2026-08-31.md)의 `hongdal-mysql-1/hongdal_dev`는 재확인할 대상이며 별도 실행 앱의 `ssalddel_dev`와 혼동하지 않는다.
- D424는 감자 전용 테이블만 추가하고 전체 마이그레이션 이력을 기록하지 않은 상태다. 현재 스키마/이력을 먼저 확인하여 필요한 대응 테이블·인덱스의 제한 추가만 결속한다. 전체 `Migrate`, 초기화/삭제·볼륨 교체·다른 운영 DB 적용은 하지 않는다.
- 새 외부 수집/키 입력은 이 대응 작업에 필요하지 않다. D424의 별도 승인·실행과 혼동하지 않고 키를 문서/로그/캡처에 넣지 않는다.

Unity 소비는 기존 권한별 조회 결과 → 공통 대응 선택 → 기존 자산 대장 키 해결 → 표현 준비 입력이다. `WorldVisualCatalog`의 등록 키·판본 검사를 유지하며 실제 Prefab 참조는 Unity에서 해결한다.

[D423 책임 구분](배치책임구분-리팩토링승인-2026-08-31.md)과 [D422 계획](Farm월드맵-배치계층경유-점진구성-2026-08-31.md)의 구조·제약 → 계획 → 검증 → 조립·표현을 그대로 통과한다. 이 작업의 출력은 그 경로가 읽는 **검토된 표현 입력**이다. 새 관리 UI·자동 자산 생성·Scene 일괄 배치·새 게임 규칙·실제 업무 실행은 제외한다.

실제 자산 미리보기가 필요하면 개발이 정확 후보·기존 사용조건·보호 기준·전문 단독 점유를 후속 결속한다. 파일/목록 검토나 기본형 저장을 실제 외형 검증으로 보고하지 않는다. 기존 E 기준·원본·Save·r129/야간/무관한 중지는 유지한다.

## 6. 담당·진행·완료 기준

1. **개발:** 현재 구조·DB·명세와 정확 쓰기 경로/공유 소유를 대조하고 공통 계약/선택/저장·관리자 API·분야별 읽기를 구현한다. 필요한 기존 WI 표현 명세 결속은 유지하되 운영 대응을 새 게임 WI/Goal로 자동 등록하지 않는다.
2. **자료조사:** 기존 개체/기록 의미·식별자·상태·출처·공개 조건을 조사한다. 새 대량 수집 대신 저장 자료를 우선한다.
3. **공간:** 기존 Synty 대장·파일·이미지에서 소수 주/대체 후보와 사용 제한을 반환한다. 존재·적합성·실제 조립은 구별한다.
4. **개발:** 각 분야 결과를 통합하고 허용 DB에 후보/대응 저장 → 독립 조회 → 선택 → 재입력/개정을 검증한다. 근거가 부족하면 미검토로 보관하고 실제 승인 선택은 미완료로 보고한다. 통과를 위해 적합 승인을 만들어내지 않는다.
5. **기획:** 표현 목적·신규 플레이 선택을 결정하고 구현/시험은 개발에서 수행한다.

필수 검증은 종류/원천/권한별 ID 충돌, 타 조직 비노출, 개별 우선·동일 문맥 기본 대체, 결손/권한·조회 오류 구별, 상태/목적 불일치·미검토/제외·오래된 판본·미등록 키·중복 대응, 결정성, 개정 충돌·멱등·감사·독립 재조회, 원천/재고/가격/권위 판본 불변이다. 네 Adapter의 공통 기능 실제 소비와 관측/이력의 중복 객체화 방지도 확인한다.

개발은 범위 Fast·관련 Task와 계약 소비자 검증을 수행하고 미실행/차단을 따로 보고한다. 합성/메모리 시험 ≠ 실제 MySQL, 저장 성공 ≠ 외형 승인/Unity/E5다. Scene·실제 입력/Game View는 이번 완료 조건이 아니며 미검증을 명시한다. 분야별 작은 결과마다 기술 보고/CURRENT_WORK/통합상태판을 갱신하고 별도 요청 전 commit/push하지 않는다.

## 7. 인계 상태

기획 소유는 이 원문·DECISIONS의 새 D426·Synty 기준 연결 절이다. 전송 거부 때문에 CURRENT_WORK에는 차단 사실만 기획이 보완한다. 개발 코드/명세·생성물·DB/시험·통합판을 기획이 대신 변경하지 않는다.

전달이 가능해지면 기존 개발 작업이 이 원문 전체/hash·현재 상태·정확 경로를 결속하고 시작한다. 계획 승인과 담당 수신·구현·저장·검증은 별도다. 도구 차단을 우회하는 새 작업 생성이나 다른 실행 경로는 사용하지 않는다.
