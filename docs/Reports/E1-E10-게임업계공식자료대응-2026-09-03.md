# E1~E10 게임업계·엔진사 공식 자료 대응

## 1. 목적과 결론

이 문서는 Mirror의 `E1~E10` 증거 체계가 Unity·Unreal의 공식 개발·시험 관행과 어느 정도 대응하는지 설명한다. 외부 문서를 근거로 현재 단계의 의미를 이해하고 검토할 수 있게 하되, 외부 문서가 Mirror의 단계 번호·판정식·수치 기준을 직접 승인했다고 주장하지 않는다.

결론은 다음과 같다.

- 코드 단위 자동시험, Play Mode·기능시험, 실제 입력, 회귀시험, Replay, 다중 실행 환경, 사람 플레이테스트, 제한 배포와 관측은 게임 개발에서 실제 사용하는 관행이다.
- `E1~E10`이라는 이름, `Logic`·`Presentation` 중 낮은 단계를 통합값으로 삼는 방식, E8의 정확한 반복 횟수, E9의 5점 만점 4점 기준은 Mirror의 프로젝트별 통제 설계다.
- 따라서 이 체계는 업계 표준 번호를 가져온 것이 아니라, 여러 공인 관행을 Mirror의 서버 권위·Unity 표현·Save/Replay·공공자료 경계에 맞춰 누적 관문으로 재구성한 것이다.

## 2. 대응 강도

| 구분 | 의미 |
| --- | --- |
| `Direct` | 공식 도구·문서가 해당 단계의 주 검증 행위를 직접 지원한다. |
| `StrongPartial` | 단계의 주요 행위들이 공식 관행에 존재하지만 Mirror가 여러 행위를 하나의 관문으로 결합했다. |
| `Partial` | 일부 원칙·도구만 대응하며 Mirror 고유 의미가 더 크다. |
| `ProjectSpecific` | 이름·판정식·수치·권위 경계가 Mirror 고유 설계다. 외부 근거는 보조 참고다. |

## 3. E1~E10 대응표

| 단계 | Mirror의 핵심 | 공식 관행과의 대응 | 강도 | Mirror 고유 경계 |
| --- | --- | --- | --- | --- |
| E1 | 행위·자료·경계·완료 조건 계약 | Unity는 기능시험을 명확한 요구사항과 `when this, then that` 수용 조건에 맞춰 설계하도록 설명한다. Unreal Automation Spec은 BDD 방식의 자기 설명적 기대값 구성을 지원한다. | `StrongPartial` | 기획 승인 hash, WI·H·권위 계약과 누적 E 관문은 고유하다. |
| E2 | 서버·Simulation·표현·도구 코드 준비 | Unity Test Framework는 Runtime 코드와 시험 assembly를 분리·참조하도록 하고, Epic은 저수준·기능·통합 시험을 모듈 단위로 구성한다. | `Partial` | “코드 준비”만으로 성숙도를 판정하고 실제 실행과 분리하는 정확한 단계는 고유하다. |
| E3 | 결정성·자동시험·저장 재생 시험 | Unity Test Framework는 Edit Mode·Play Mode·대상 Player 시험을 지원한다. Unreal Automation은 Unit·Feature·Content Stress·Screenshot 시험을 구분한다. | `Direct` | 동일 seed·revision·canonical hash와 Mirror Save/Replay 계약은 프로젝트별이다. |
| E4 | Actor·대상·시간·H·Graph Map·표현 후보·배치 문맥 결속 | Unreal Data Validation은 자산 명명·예산·의존성 같은 사용자 정의 규칙으로 단일 자산부터 전체 자산까지 검증한다. | `Partial` | H 계층, Graph Map, 배치 맵, `VisualKey`, 후보 fingerprint, E5 준비 판정은 Mirror 고유하다. |
| E5 | 실제 권위 세계와 Prefab·배치·InteractionAnchor 발현 | Unity Play Mode 시험은 Runtime 게임 코드를 Editor 또는 대상 Player에서 실행한다. Unreal Functional Test는 Level 안에 시험 Actor를 배치하고 준비·실행·기대 결과를 검증한다. | `StrongPartial` | 서버 권위 상태와 Unity 표현을 같은 revision으로 묶고 활성 Renderer·Collider·Bounds까지 요구하는 조합은 고유하다. |
| E6 | 플레이 전 의미·인과·표현·품질·최신성 정제 | Unity는 수동·자동 QA, 통합·회귀·성능시험의 병행을 권장한다. Unreal Screenshot Comparison은 승인된 Ground Truth와 후속 장면을 비교한다. | `StrongPartial` | AreaSet·현실자료 출처/hash·GIS 선택 경계와 “설명 가능한 정제”는 Mirror 고유하다. |
| E7 | 실제 입력으로 상황→선택→결과→회복·귀환 완주 | Unity Play Mode는 Runtime·대상 Player 시험을 지원한다. Unreal Automation Driver는 클릭·키 입력·스크롤 등 사용자 입력을 모사하고 PIE는 플레이어 제어와 Level Event를 실제로 시험한다. | `Direct` | Preview·Confirm·Tick·재조회와 Game View·Console을 한 폐루프 승인으로 묶는 판정은 고유하다. |
| E8 | 한 PlayableUnit의 반복·Save/Replay·재진입·Local/Remote 안정 | Unreal Replay는 플레이 기록·재생과 버전 정보를 지원하고 Gauntlet은 여러 플랫폼·서버·클라이언트 세션을 실행·관측한다. Unity Multiplayer Play Mode는 한 개발 장치에서 여러 Player를 모사한다. | `StrongPartial` | 논리 3회·표현 2회, 동일 revision/build hash, 두 궤적의 최솟값과 열린 차단 0건은 Mirror 고유 기준이다. |
| E9 | 둘 이상의 안정 Core 조화와 사람 승인 | Unity는 자동시험이 놓치는 UI·밸런스·게임플레이 문제를 위해 수동시험과 대상 플레이어 테스트를 함께 사용하고, 통합·회귀시험을 지속적으로 수행하도록 설명한다. | `StrongPartial` | `AreaHarmonySet`, 인과·선택·귀환·판독·전환 평가표와 4/5 승인선은 Mirror 고유하다. |
| E10 | 불변 후보의 제한 운영·관측·rollback | Unity Game Overrides는 대상 비율별 점진 적용과 환경 분리를 제공하고, Analytics Event는 플레이 행동·진행을 관측하며 Cloud Diagnostics는 충돌·예외를 수집한다. | `StrongPartial` | 운영 DB·Provider·결제·계약·공개를 별도 승인으로 막고 Replay·rollback까지 한 관문에서 요구하는 것은 Mirror 고유하다. |

## 4. 공식 자료

### Unity

- [Unity Test Framework — Write and run tests](https://docs.unity.cn/6000.0/Documentation/Manual/testing-editortestsrunner.html): Edit Mode·Play Mode·Standalone·대상 플랫폼 시험.
- [Edit Mode vs. Play Mode tests](https://docs.unity.cn/Packages/com.unity.test-framework%402.0/manual/edit-mode-vs-play-mode-tests.html): Editor와 Runtime 시험 위치·assembly 경계.
- [Testing and quality assurance tips for Unity projects](https://unity.com/how-to/testing-and-quality-assurance-tips-unity-projects): 단위·통합·회귀·기능·성능·A/B·진단·수동 플레이테스트의 역할.
- [Multiplayer Play Mode](https://docs.unity.cn/Manual/multiplayer.html): 한 개발 장치에서 복수 Player를 모사하는 도구 안내.
- [Game Overrides and Settings](https://docs.unity.com/en-us/remote-config/game-overrides-and-settings): 환경·대상 조건·적용 비율을 이용한 제한적 설정 배포.
- [Unity Analytics Events](https://docs.unity.com/en-us/analytics/events/events): 플레이 행동과 문맥 정보의 관측.
- [Unity Cloud Diagnostics](https://docs.unity.com/en-us/cloud-diagnostics): 실행 중 충돌·예외 관측.

### Unreal Engine

- [Automation Test Framework](https://dev.epicgames.com/documentation/unreal-engine/automation-test-framework-in-unreal-engine?application_version=5.7): Unit·Feature·Smoke·Content Stress·Screenshot 시험 분류.

## 5. 보완한 공백

공식 자료와 현행 Mirror 체계를 대조했을 때 성숙도 번호만으로는 다음 항목의 적용 여부와 누적 검증 시점을 찾기 어려웠다.

- 성능·부하 예산
- 접근성·시간 압박 완화·입력 대안
- 현지화·단위·문화 표현
- 장치·해상도·입력·네트워크 호환
- 보안·개인정보·동의·외부 효과
- 관측 가능성·비식별 진단
- 저장 Migration·rollback
- 콘텐츠·공공자료·자산 권리

이를 E11 같은 새 단계로 추가하지 않고, 필요한 `PlayableUnit`의 E1에서 요구와 예산을 선언하는 **교차 품질 프로필**로 보완했다. 이후 E2~E10은 자기 단계에 해당하는 구현·시험·실행·사람 평가·운영 관측을 누적한다. 적용하지 않는 프로필은 사유 있는 `NotApplicable`을 남긴다. 기준은 [E1 기획 근거 결속 체계](../Architecture/E1기획근거결속체계.md#업계-관행을-반영한-교차-품질-프로필)가 소유한다.

또한 `PLANNING.md`의 기획 문서와 `PlayableUnit` E1 계약 사이의 직접 소유·지원·공통 문맥·무관·미결속 관계를 [기획–E1 결속 인덱스](../AI/generated/playable-loop-planning-e1-index.md)로 분리했다. 기획 문서의 존재를 E1 증거나 구현 완료로 오인하지 않기 위한 보완이다.

## 6. 사용 원칙

1. 외부 자료는 Mirror 증거의 신뢰 근거와 구현 도구 후보이지 자동 승격 근거가 아니다.
2. 공식 도구가 지원된다는 사실과 현재 프로젝트에서 실제 시험을 수행했다는 사실을 분리한다.
3. 공식 관행과 직접 대응하지 않는 H·WI·Graph Map·배치 맵·서버 권위·공공자료 경계는 프로젝트 고유 설계라고 명시한다.
4. 엔진 버전이나 서비스 정책이 바뀌면 링크·지원 범위를 재검토하되 과거 EvidencePackage를 소급 승격하지 않는다.
5. E별 수치와 사람 승인 기준은 프로젝트 경험에 따라 판본화해 조정할 수 있지만, 변경 뒤에는 같은 후보의 기존 상위 증거를 자동 재사용하지 않는다.

조사 기준일: 2026-09-03. 이 문서는 공식 자료 대응을 설명하는 참고 문서이며 `evidence-stages.json`의 기계 판정 기준을 대체하지 않는다.
