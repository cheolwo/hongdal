# E5 성립 조건과 현재 준비 상태

기준 시점: **2026-08-31 08:04 KST** · 대상: Mirror(거울)의 Logic/Presentation E5, 특히 Farm·약초·방문자

이 문서는 기존 단계 정의와 현재 작업 명세·개발 인계를 종합한 **기획 검토용 상태 사본**이다. 새 성숙도 대장이나 실행 승인이 아니며, 아래 준비 정도로 현재 E를 승격하지 않는다. 기준 시점 이후 개발 결과는 해당 작업 명세·통합 보고서를 우선한다.

## 1. 먼저 결론

**E5로 가는 관리 체계와 일부 공통 코드·자산 후보는 갖춰졌다. 하지만 이번에 검토한 세 기능은 ‘권위 있는 상태 → 정확한 표현 선택 → 실제 배치 → 입력과 결과’가 하나로 이어진 E5 완료 상태는 아니다.**

현재 가장 부족한 것은 자산의 개수나 단계 이름이 아니라, 이미 있는 부품을 **같은 대상·같은 원인·같은 판본으로 연결하는 제품 소비 경로**다. 예를 들어 감자 Prefab과 수확 상태 계산이 각각 있어도, 현재 밭의 상태를 읽어 정확한 감자 Prefab을 선택하고 그 밭에서 상호작용하게 하는 연결은 별도 작업이다.

E5에서 난도가 올라간다는 판단은 타당하다. 이 단계에서는 논리, 자산, 공간, 입력, 객체 수명 관리가 처음으로 함께 맞아야 한다. 그렇다고 모든 애니메이션 품질이나 반복 검증까지 E5에 몰아넣지는 않는다. **E5는 세계에서 기능이 성립하는 단계이고, E6는 결함·품질 보완, E7은 실제 플레이의 결과·귀환 검증으로 구별한다.**

| 지금 마련된 것 | 아직 마련 중이거나 연결되지 않은 것 |
| --- | --- |
| 논리·표현 분리 판정, 표현 공통·조건 모듈, E4 자산 조사 절차 | 각 기능의 같은 Session·판본을 사용하는 실제 표현 소비 |
| Farm 읽기 전용 상태 준비 코드와 관련 자동시험 | 준비 상태 → 정확한 자산 계열 → 실제 밭 표현의 연결 |
| Farm·약초·방문자의 기존 Synty 후보와 조사 근거 | 실제 지지면·접근 지점·입력·결과·해제의 결합 검증 |
| D389 연결 사전 검사 승인 및 개발 경로 확정 | D389 구현·시험 완료 인수 및 실제 E5 적용 결과 |

프로젝트 전체에 E5 이상 이력이 없다는 뜻은 아니다. 일부 Nature 폐루프에는 기존 E7 등록이 있다. 다만 **과거 증거를 이번 신규 연결·수정판의 완료 증거로 대신 쓰지 않는다.**

## 2. ‘E5가 온전히 성립한다’의 뜻

기준은 [E1~E7 수직·E8~E10 수평 증거 체계](../Architecture/E1-E7수직폐루프와E8-E10수평증거체계.md), [논리·표현 이중 순환 체계](../Architecture/플레이폐루프논리시각이중순환체계.md), [단계 정의 원장](../../eng/execution-ledgers/evidence-stages.json)이다.

| 구분 | E5에서 확인할 내용 | 이것만으로는 부족함 |
| --- | --- | --- |
| Logic E5 | 유효한 상황에서 WI가 시작되고, Preview/Confirm 또는 권위 판정, 작업·효과, 결과 상태와 다음/귀환 WI가 연결됨. 권위 변경의 원인과 행위 기록이 일치함. | 독립 계산기·메모리 서비스·합성 Fixture의 성공만 존재 |
| Presentation E5 | Logic E5의 같은 판본 상태/행위 기록을 읽고 동결 후보를 실제 Prefab 또는 대체 표현과 연결함. 필요한 배치·상호작용 지점·Renderer/Collider/Bounds가 실제 기능과 맞음. | 후보 선정, Prefab 파일 존재, 격리 렌더, 준비 상태 생성만 성공 |
| 통합 E5 | 위 두 흐름이 같은 WI·대상·명령 원인·판본에서 이어짐. 통합 E는 Logic과 Presentation 중 낮은 값으로 판단함. | 서로 다른 시점의 논리 시험과 화면을 합쳐 완료라고 판단 |

공간 WI라면 H·AreaSet·Graph·통행 등 해당 공간 계약도 검증한다. 비공간·비시각 기능에는 사유 있는 `NotApplicable`을 사용한다. 모든 기능에 Collider·Rig·Clip을 일률적으로 요구하지 않는다.

### 단계별 경계

| 단계 | 주된 질문 |
| --- | --- |
| 표현 E2~E3 | 상태를 안전하게 받아 준비할 수 있는가? 실패·중복·오래된 판본을 시험할 수 있는가? |
| 표현 E4 | 무엇으로, 어디에, 어떤 상태로 보여줄지 정했는가? 후보의 적합성과 연결 공백을 알고 있는가? |
| 표현 E5 | 그 후보가 실제 대상에 연결되어 현재 상태·상호작용·결과를 표현하는가? |
| 표현 E6 | 접촉·가독성·전이·실패 안내 등 발견된 어색함을 보완했는가? |
| 표현 E7 | 실제 입력에서 결과·회복·귀환까지 플레이가 이어지고 화면으로 확인되는가? |
| E8 이상 | 동결 판본의 반복·복원·환경 차이, 영역 내 조화를 검증했는가? |

E4 준비는 Logic E5 전에 할 수 있다. 그러나 **Presentation E5 증거에는 Logic E5 상태 사본이 필요하다.** 코드·자동시험 완료와 실제 적용 증거도 구별한다. 문서상의 모든 기능에 매번 Game View 촬영을 요구하는 것은 아니지만, 배치·입력·카메라처럼 화면에서 판별해야 하는 문제를 코드 시험만으로 해결했다고 할 수는 없다.

## 3. E4에서 E5로 연결되는 구조

```text
승인된 WI·기획·전문 연구·작업 명세
│
├─ 논리 준비: 현재 Session / 대상 / 판본 / 작업·결과·행위 기록
├─ 표현 준비: VisualKey / 상태 대응 / 정확한 자산 / 적용 조건
└─ 공간 준비: 부모·셀·계보 / 지지면 / 접근·상호작용 지점
             │
             ▼
      연결 사전 검사 — D389 구현 중
      Ready / Conditional / Blocked
      ※ Ready도 실제 적용 성공은 아님
             │
             ▼
      소유 범위 내 실제 조립·연결
      상태 공급 → 표시·입력 → 권위 결과 재조회 → 표현 갱신
             │
             ▼
      적용·해제 책임과 필요한 실제 근거 확인
             │
             ▼
      Logic / Presentation / 통합 E5 판정
```

이 구조는 새로운 게임 규칙이나 세 번째 성숙도 축을 만드는 것이 아니다. 이미 있는 준비 코드·자산 조회·배치 계약·소유권 도구 사이의 누락을 조립 전에 드러내는 방식이다.

아래 ‘준비됨’은 해당 부품이나 절차가 있다는 의미다. 기능 전체가 통과했다는 의미가 아니다.

**재사용할 것은 근거까지 재사용한다.** 같은 자산·같은 판본·같은 용도에서 이미 확인한 항목은 전수 조사를 반복하지 않는다. 반대로 소스 파일이 같아도 대상 Rig, Scene 연결, 상태 공급이 달라졌다면 그 변경된 경계는 다시 확인한다.

## 5. 대표 기능별 현재 위치

다음 수치는 현재 등록 범위의 Logic / Presentation / 통합 E다. 넓은 주제 전체의 완성률이 아니다.

### 5.1 Farm: 부품은 있으나 실제 밭 소비가 비어 있음

현재 네 후보는 다음 역할로 조사돼 있다. 정확한 경로·GUID·hash는 [Farm 작업 명세](../../eng/execution-ledgers/work-orders/farm-crop-cycle.e7-work-order.json)의 `presentationE4Preparation.assetSurvey`를 기준으로 한다.

| 표현 역할 | 기존 후보 | 유의할 점 |
| --- | --- | --- |
| 밭의 흙두렁 | `SM_Env_Dirt_Rows_01` | 외형 약 25.294㎡를 생산 100㎡와 동일시하지 않음 |
| 성장 중 감자 | `SM_Prop_Plant_Potato_01_S` | 기존 관찰 Collider 0. 필요한 선택·접근 처리는 별도 |
| 수확 가능한 감자 | `SM_Prop_Plant_Potato_01_L` | 같은 이유로 파일 존재만으로 상호작용 준비 완료가 아님 |
| 밭에 남은 수확물 | `SM_Prop_Box_Potato_01` | 포장·집하 완료를 뜻하지 않음 |

D386 코드가 준비하는 상태는 `Growing / HarvestReady / Harvested`다. 기존 표현 모듈에는 `CropGrowing / CropHarvested`, 자산 계열에는 `plants:potato / props:crate`가 사용되지만 실제 재고는 `plants:potato-s / plants:potato-l / plants:box-potato`로 구분된다. **정확 계열 조회에서 이 차이를 처리할 연결이 필요하다.**

또한 준비 코드의 실제 제품 호출은 D388 조사 범위에서 발견되지 않았다. 과거 실제 Scene 조사에서 밭의 null 컴포넌트와 비활성 표현·초점 문제도 남았다. 이는 감자 모델링을 더 하면 해결되는 문제가 아니라 상태 공급·직렬화/컴포넌트·보기 정책의 연결 문제다. 이 보고를 이유로 Scene을 자동 수리하거나 전체 Farm을 켜지는 않는다.

첫 정적 성장/수확 표현은 기존 승인 범위에서 검토할 수 있다. 이 범위에 필요하지 않은 캐릭터 리깅·모든 농사 동작을 먼저 완성할 필요는 없다.

### 5.2 약초: ‘처방을 안다’와 ‘달여 마신다’를 분리

선정된 조리용기는 `SM_Prop_CookingPot_01`, 컵 후보는 `SM_Gen_Prop_Mug_01`이다. 좁은 목의 `SM_Prop_Camp_Pot_01`은 냄비 역할에서 제외됐으며 원본은 보존됐다. `SM_Prop_CampFire_01`도 후보 파일이 있지만 냄비 지지·접근·열원 소비가 검증된 것은 아니다.

현재 확보한 내용물 계산 시험 44개는 물량·전송·온도/계보 보존 등의 순수 규칙 근거다. **달이기 시간, 권위 있는 실행·음용, 실제 용기 상태 표시를 포함한 완성 기능의 44개 시험이 아니다.**

기존 수면 연출 모닥불의 축소·바닥 보정·빛은 HB01 열원 계약이 아니다. 열원 `Accessible` 값도 실제 냄비 지지면이나 접근 지점 계산을 대신하지 않는다. 다음 연결은 [HB01 명세](../../eng/execution-ledgers/work-orders/nature-herbal-hb01-contents.e7-work-order.json)에 따라 이 공백을 분리해서 진행해야 한다.

### 5.3 방문자: 동작 자산은 있으나 상태를 소비하는 제품 연결이 남음

남성 Actor·Avatar·Idle/Walk/Greet·Controller와 기존 격리 자료는 재사용할 수 있다. 하지만 Controller 파일 존재가 Prefab 연결을 뜻하지 않으며, 준비 계약에 Clip 이름을 복사했다고 해당 동작을 실행한 것도 아니다.

필요한 연결은 **도착 대기 → 선택에 따른 임시 체류 또는 이탈**이다. 같은 대기 상태의 재조회/복원으로 인사가 반복되지 않아야 하고, 이동 작성자는 하나여야 한다. 대기·손님 휴식·이탈 지점도 현재 공간과 연결해야 한다. 실제 Session·Actor 권한·판본 원자성·Save/Replay 공백은 표현 애니메이션으로 대신할 수 없다.

일부 Walk 가져오기 기록과 fallback hash 기록의 불완전성도 남아 있다. 기존 Library 평가를 새 가져오기 성공으로 확대하지 않고 [방문자 명세](../../eng/execution-ledgers/work-orders/nature-camp-visitor-stay.e7-work-order.json)의 조사·연결 범위로 관리한다.

- `Ready`: 요구된 연결 전제의 관측이 확인됨. 실제 적용은 아직 별도다.
- `Conditional`: 필수 항목 중 아직 관측하지 못한 것이 있음.
- `Blocked`: 필수 항목의 실제 누락·불일치가 확인됨.

이 판정은 [승인된 D389 계획](../AI/Presentation-E4-E5연결사전검사-2026-08-31.md)에 따른 구현 대상이다. 기준 시점 파일 확인에서는 예정된 공통 Preflight 소스가 아직 없었으므로, 구현 완료로 기록하지 않았다.

관리 도구의 별도 기존 문제도 있다. 두 구형 r4 작업 명세 때문에 전체 E7 명세/개발 시스템 검사가 `ProtocolRevisionInvalid`로 차단된 이력이 있다. 이는 현재 기능의 실제 배치 성공/실패와 다른 관리 정합성 문제이며, 개별 통과를 전체 관리 검사 통과로 확대하지 않는다.

## 7. E5까지 남은 실행 순서와 완료 확인

다음은 작업의 선후 관계를 설명하는 것이며, 중지된 야간 작업·Editor를 재개하는 지시가 아니다. 기존 승인 범위의 개발·시험은 개발 스레드가 수행하고 실제 캡처는 공간 담당이 맡는다.

| 순서 | 다음에 닫을 공백 | 완료로 확인할 산출물 |
| --- | --- | --- |
| 1 | 대상 WI와 성공/실패·다음 선택을 좁힘 | 같은 명세 안에서 이번 실제 연결의 대상·제외 범위가 명확함 |
| 2 | 권위 상태 공급과 표현 대응을 준비 | Session/판본/행위 원인과 상태→VisualKey→정확 후보 대응. 서로 독립인 조사는 병행 가능 |
| 3 | D389 사전 검사를 첫 소비자에 연결 | 정상·누락·불일치·오래된 판본·소유 충돌 시험과 구체적인 차단 목록 |
| 4 | 실제 대상의 배치·컴포넌트·소유 문제를 해결 | 필요한 지지/통행/접근·정확 컴포넌트·자기 변경 해제 근거. 임의 대체나 권위 주입 없음 |
| 5 | 제품 입력에서 결과까지 연결 | 현재 대상 입력→권위 처리→같은 판본 재조회→표현 갱신·다음 행동 가능 |
| 6 | 같은 판본의 근거를 통합 | 자동시험과 필요한 실제 적용/화면 근거를 분리해 Logic·Presentation E5 판정 |

**가장 작은 성공 단위는 ‘기능 하나를 예쁘게 보여주는 이미지’가 아니라 ‘실제 상태를 가진 대상 하나가 올바르게 보이고, 그 대상의 행동 결과를 다시 보여주는 연결’이다.** 넓은 분야의 시각 시안은 기획 검토에는 유용하지만 이 연결을 대신하지 않는다.

사용자가 확인할 최종 인수 항목은 다음 여섯 가지면 된다.

1. 무엇을 할 수 있게 됐는가 — 대상 WI와 플레이어 선택.
2. 어떤 실제 상태를 읽는가 — Session·대상·판본·원인.
3. 무엇으로 어디에 보여주는가 — 정확한 후보·배치·상호작용 지점.
4. 입력하면 결과가 어떻게 이어지는가 — 권위 처리와 표현 재조회.
5. 실패·해제 때 무엇을 보존하는가 — 중복·소유 충돌·낡은 상태 방지.
6. 무엇으로 검증했는가 — 코드/시험/실제 적용/화면 및 남은 미검증을 구분.
