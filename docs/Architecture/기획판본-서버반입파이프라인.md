# 기획 문서 → 로컬 관계형 DB 파이프라인

## D439 승인 범위와 책임

2026-08-31 사용자는 기획 문서에서 Codex가 기존 WI 재사용·특수화·보편화·신규 후보, 게임 객체와 자산 관계를 판단하고 그 결과를 관계형 DB로 정리하는 파이프라인을 요청했다. 이후 **같은 로컬 환경이므로 API 전송은 필수가 아니며, 작성된 표준 문서를 바로 기존 ASP.NET Core 저장 기능과 MySQL에 연결**하도록 정정했다. 기획 측 도구는 이 작업에서 직접 구현한다.

기획의 의미 판단은 Codex와 사용자 검토가 소유한다. 서버가 자연어를 다시 해석하거나 자동으로 WI를 창작하지 않는다. 문서가 의미 기준이며 DB는 검토된 관계의 조회·이력 저장소다. API·메시지 큐·새 서버·파일 감시 데몬을 선행 조건으로 만들지 않는다.

```text
지금·여기·나·너·이렇게 / 결과·다음 선택
  → 기존 WI·객체·자산 조회와 기획 판단
  → 같은 Markdown 안의 표준 관계 블록
  → 원문·참조·판본 검사 / 변경 없는 저장용 사본
  → 로컬 명시 실행 → 기존 ASP.NET Core UseCase → 기존 MySQL 표
  → 같은 입력 재실행·독립 조회 → 기획에 저장 결과 환류
```

이는 E/G/H·게임 실행 명세를 대체하지 않는다. `ReviewedForHandoff`는 작성자가 저장 검토를 마쳤다는 선언이고 사용자 승인·권리 허용·자산 적합성을 암호학적으로 증명하는 상태가 아니다. 도구 성공이나 DB 저장을 자산 선택·Unity 배치·게임 기능 완료로 올리지 않는다.

## 표준 문서

[공통 기획 관점](플레이어중심게임개발업무구조.md)과 [기존 문답 절차](PlayableLoop문답정밀화체계.md)를 유지한다. 전체 옛 문서를 일괄 전환하지 않고 이번에 정리할 문서에 `planning-release` JSON 코드 블록 하나를 둔다. 별도 수기 원장을 다시 만들지 않는다. [첫 작성 문서](../AI/기획판본-D439-기존벌목관계-첫로컬반입.md)를 최소 예제로 사용한다.

| 항목 | 기록할 내용 |
| --- | --- |
| `planningId`, `revision`, `state` | 문서 식별자·변경 판본·Draft 또는 ReviewedForHandoff |
| `context` | now/here/self/target/action/result/nextChoices 일곱 칸. 모르는 조건은 미정이라고 적기 |
| `catalog` | 실제 기존 WI 대장의 revision·SHA256. 기존 WI 등록을 이 문서로 대신하지 않기 |
| `evidence` | 중복 없는 key, 상대 path, 실제 sha256, 정확 quote. 본인 문서의 자기 hash 순환 금지 |
| `wiDecisions` | key, Reuse/Specialize/Generalize/NewCandidate/Unresolved, existingIds, 판단 이유와 evidenceKeys |
| `objects` | key, 기존 definitionId 또는 null, name, Actor/Physical/Information/Unresolved와 evidenceKeys |
| `uses` | key, wiKey, objectKey, Actor/Target/Tool/Input/Result/Place 역할, evidenceKeys, catalogProof |
| `visuals` | 객체 key·시각 역할, Unselected/Candidate/Selected, assetVersionId 또는 null, 근거. 함께 쓰는 부품과 대안 후보를 별도 기획 판단 |

`catalogProof`는 없으면 null이다. 기존 WI 직접 근거로 저장할 때만 실제 ruleRevision·허용 field·전체 문자열 또는 배열 원소 quote를 적는다. Markdown만 있는 근거를 가짜 WI 필드로 바꾸지 않는다. `Selected`도 문서의 선언일 뿐 실제 DB 선택 승인이 아니며 기존 검토/권리/판본 절차를 통과해야 한다. 비밀키·접속 문자열·개인 정보·권리 미확인 원자료를 문서나 저장 사본에 넣지 않는다.

## 구현된 첫 로컬 저장 범위

[판본 도구](../../eng/planning-inquiries/manage-planning-release.ps1)는 JSON 모양·중복·참조·정확 원문·현재 WI 판본을 검사하고 저장용 불변 사본을 만든다. 같은 ID/판본의 변경은 거부하며 수정은 새 판본으로 남긴다. [로컬 실행기](../../eng/planning-inquiries/local-import/Program.cs)는 이를 다시 현재 문서와 대조한 뒤 [기존 WI 참여 UseCase](../../Ssalddel/Services/Content/게임객체WI참여UseCase.cs)를 같은 프로세스에서 호출한다. HTTP는 사용하지 않는다.

첫 지원은 **기존 WI 하나 재사용 + 이미 저장된 객체 정의 참조 + 기존 WI 필드 직접 근거**의 참여 관계다. [첫 문서](../AI/기획판본-D439-기존벌목관계-첫로컬반입.md)의 기존 벌목→나무 대상 관계 하나를 로컬 반입·재조회하는 범위를 포함한다. 새 정의/자산 선택/DDL은 수행하지 않는다.

- 기존 `world_visual_object_definitions`와 구성 판본을 읽고 `world_visual_object_wi_batches`·`world_visual_object_wi_uses`에 저장한다. 새 기획 전용 DB/테이블은 만들지 않는다.
- 일곱 칸·문서 경로/hash·기획 ID/판본·판단 이유는 기존 관계의 `ContextNote`에 구조화해 보존한다. WI/정의/역할은 기존 관계형 열로 조회한다. 일곱 칸 각각의 SQL 인덱스/전용 열은 아직 없다.
- 같은 기획 ID/판본은 멱등 요청이며 내용 충돌은 거부한다. 새 판본은 다른 참여 문맥으로 추가하고 과거 행을 삭제/교체하지 않는다. 서로 다른 문서에 같은 객체가 나와도 기존 정의를 재사용한다.
- `preview`는 실제 DB에서 정의·관계 충돌을 읽기 확인한다. `apply`만 기존 트랜잭션 저장 기능을 호출하고 동일 입력 재처리·새 EF 조회·참조 정의 불변을 검증한다.
- 대상은 기존 `hongdal-mysql-1` / 로컬 `127.0.0.1:13306` / `hongdal_dev` / 비root 계정이다. 명시 유지보수 주체 `local-maintenance:planning-d439`를 사용한다. 앱 사용자 로그인으로 위장하지 않고 앱 설정/기능 플래그를 바꾸지 않는다. 접속 비밀은 실행 메모리에서만 사용한다.
- DB 쓰기는 개발의 다른 인수 작업과 먼저 조율한다. 기존 D437/D438 원장·원천·Context·DI와 충돌할 때 같은 표를 병렬 수정하지 않는다. 출력과 claim은 매 실행 별도 `artifacts/local/` 경로에 남긴다.

## 미지원 부분은 저장하지 않고 이유를 남긴다

새 객체 정의 생성, 특수/보편/신규 WI 후보의 실제 등록, 독립 Markdown 근거만 있는 참여, 자산 구성/선택 변경은 첫 로컬 반입 범위가 아니다. 문서에는 모두 적을 수 있지만 도구가 `NotReady`와 해당 이유를 반환한다. 지원되는 부분만 몰래 저장하지 않는다. 필요하면 기획에서 명시적으로 독립된 작은 문서로 나누고 저장되지 않은 관계를 보고한다.

기존 계약의 관계64개·관계 문맥1500자 상한을 그대로 적용한다. 긴 기획을 임의 잘라 저장하지 않는다. 별도 저장 기능 보완이 필요하면 기존 D434/D435 계약을 확장하는 후속으로 다루며 새 API를 자동 필수로 두지 않는다.

파일 hash는 로컬 위변조/신선도 대조이지 전자 서명이나 의미 승인 증명은 아니다. 파일과 MySQL을 하나의 분산 트랜잭션으로 잠그지는 않는다. 실행 중 입력 변동·DB 충돌은 실패로 남기고 저장 시도 여부를 보고한다. DB 저장 후 후속 검증이 실패했다면 자동 삭제하지 말고 결과·재조회를 통해 확인한다.

## 실행과 결과 확인

[도구 사용법](../../eng/planning-inquiries/README.md#d439-기획-문서의-로컬-mysql-정리)과 [회귀시험](../../eng/tests/planning-release.ps1)을 따른다. 기본 검사는 파일만 읽고, 저장용 사본 생성도 DB에 접속하지 않는다. 로컬 실행기의 `preview`와 `apply`는 분리한다.

기획 기록/참조 검사, 로컬 DB 읽기, 실제 저장·멱등·독립 조회, 이미지·선택·Unity 적용의 결과를 각각 보고한다. 현재 실제 실행 결과는 [D439 구현 보고](../Reports/기획판본-D439-구현-2026-08-31.md)에 남긴다. 이 승인으로 r129/야간/Scene·게임 규칙·E·운영 원천·공개 게시·commit/push를 재개하지 않는다.
