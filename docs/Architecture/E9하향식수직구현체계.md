# E9↔E1 반복 왕복 구현 체계

> 호환 문서: 이 문서는 과거 증거 모델 `legacy-change-adaptive.r10`과 기존 `.e9-work-order.json`을 읽기 위해 유지한다. 현재 새 `PlayableUnit` 작업은 [E1~E7 수직 폐루프와 E8~E10 수평 증거 체계](E1-E7수직폐루프와E8-E10수평증거체계.md)에 따라 E7→E1 영향 검토와 E1→E7 검증을 사용한다. 여기서 말하는 과거 E9 변화 봉투는 현재 E9 영역 조화·사람 승인 증거가 아니다.

## 목적

새 기능을 코드 한 조각으로 시작하지 않고, 그 기능이 최종적으로 살아 있는 세계를 어떻게 바꾸고 다시 안정화해야 하는지부터 정한다. Codex와 사람이 같은 작업 단위를 읽으며 E9부터 E1까지 영향을 분해하고, 가장 낮은 누락을 구현한 뒤 E1부터 E9까지 조립·검증한다. 상향 과정에서 새 영향이나 잘못된 가정이 발견되면 다시 E9→E1 검토로 내려가며 이 왕복을 안정 상태까지 반복한다.

이 체계에서 **E9를 먼저 쓴다**는 것은 E9 완료를 먼저 주장하거나 처음 하향 통과를 고정한다는 뜻이 아니다.

```text
[하향 검토]
E9 → E8 → E7 → E6 → E5 → E4 → E3 → E2 → E1
최종 목표에서 계약까지 영향·누락 분해
  ↓
가장 낮은 미완료 의존성 구현
  ↓
[상향 조립·검증]
E1 → E2 → E3 → E4 → E5 → E6 → E7 → E8 → E9
실행 증거·호환·회귀 확인
  ↓
새 영향·누락·가정 변경 발견
  └──────── 다시 하향 검토로 이동 ────────┐
                                           ↓
명시적 차단 상태 또는 선택 범위의 새 안정 revision
```

첫 하향 검토는 출발점일 뿐 최종 설계가 아니다. E2 구현에서 계약 한계가 드러나면 E9 변화 봉투와 E7 플레이 약속을 다시 검토할 수 있고, E5 세계 발현에서 통행 문제가 발견되면 E4 실행 문맥의 공간 적용 판정과 E1 공간 계약을 다시 열 수 있다. 다시 내려가는 것은 실패나 초기화가 아니라 방금 얻은 증거로 영향 지도를 고치는 정상 작업이다.

작업 명세는 별도의 계획본과 검증본을 계속 늘리지 않고 현재 왕복 주기의 상태 사본을 유지한다. 구현하다가 중단되더라도 어느 층이 다시 열렸는지, 왜 다음 층으로 올라가지 못했는지, 기존 세계에 무엇을 남겼는지가 보존된다.

## 한 번의 왕복 주기

1. 현재 목표와 방금 얻은 증거를 기준으로 E9→E1 영향을 다시 검토한다.
2. `Gap`·`Blocked` 중 지금 선택한 가장 낮은 의존성을 구현한다.
3. E1부터 도달 가능한 상위 단계까지 조립·시험·실행 증거를 확인한다.
4. 상향 결과가 상위 약속이나 하위 계약을 바꾸면 관련 E를 다시 `Affected`·`Gap`·`Blocked`로 열고 다음 하향 검토를 시작한다.
5. 선택 범위가 실제 증거로 안정됐거나 남은 차단이 명시됐을 때만 그 왕복 주기를 닫는다.

따라서 한 작업은 `하향 1회 + 상향 1회`가 아니라 `하향 → 상향 → 하향 → 상향`의 필요한 횟수만큼 진행한다. 이미 통과한 단계도 새 영향이 생기면 `ReusedWithVerification` 또는 미완료 상태로 다시 판정한다.

## 두 종류의 E9 시작

| 작업 종류 | 시작 의미 | E9 승격 조건 |
| --- | --- | --- |
| `NewVerticalSlice` | 새 기능의 최종 세계 목표를 E9 관점에서 먼저 선언 | 먼저 E1~E8 세계를 실제로 완성한 뒤, 후속 실제 변화 단위에서만 E9 가능 |
| `ExistingE8Change` | 이미 증명된 E8 안정 revision에 규칙·공간·콘텐츠 변경 적용 | 기준 E8, 하향 영향, Migration·호환, E1~E8 재검증과 새 안정 revision 모두 필요 |

신규 기능 작업 명세의 `targetEvidenceStage = E9`는 장기 완결 방향이다. 현재 단계는 `currentEvidenceStage`로 따로 기록하며, `promotionEligible = false`인 동안 E9 증거가 아니다.

## E9에서 E1까지 하향 질문

| 층 | 먼저 고정할 질문 | 대표 산출물 |
| --- | --- | --- |
| E9 | 무엇을 바꾸며 어느 안정 revision으로 만들고 어떻게 되돌리는가? | 변화 봉투, 기준·목표 revision, Migration·rollback |
| E8 | NPC가 플레이어 없이도 변화 속에서 계속 살아가는가? | 역할군, 목표·기억·예약, 지속 폐루프, Save/Replay |

하향 통과에서 각 층은 `Defined`, `Affected`, `ReusedWithVerification`, `Gap`, `Blocked` 중 하나로 판정한다. 해당 없음으로 층 전체를 지우지 않는다. 현실 자료처럼 선택 가능한 항목은 E6 내부에 `NotApplied`와 근거를 기록하되 E6 질문 자체는 남긴다.

## E9~E1 모듈 이름과 빈 책임

하향 질문을 검토할 때 아홉 단계를 곧바로 프로젝트·어셈블리·서비스로 만들지 않는다. 먼저 다음 이름을 작업 명세의 책임 자리로 사용하고, 실제 책임 혼합이나 구현 필요가 확인된 자리만 선택한다.

| E | 관리 | 한국어 이름 | 기술 식별자 | 담아 둘 내용 |
| --- | --- | --- | --- | --- |
| E9 | G4 | 변화 봉투 | `E9변화봉투Module` | 변경 제안, 영향 지도, 호환 계획, rollback |
| E8 | G3 | 생활 연속성 | `E8생활연속성Module` | NPC 정체성, 목표, 자율 생활, 기억 |
| E7 | G2 | 플레이 경험 폐루프 | `E7플레이경험폐루프Module` | 입력, 플레이 흐름, 피드백, 실행 증거 |
| E6 | G1 | 세계 정제 | `E6세계정제Module` | 의미, 인과, 근거, 플레이 준비 질문 |
| E5 | G1 | 세계 발현 | `E5세계발현Module` | 발생 조건, 권위 상태 전이, Task·Effect, 결과·후속 WI |
| E4 | G1 | 실행 문맥 결속 | `E4실행문맥결속Module` | 발생원, 주체, 대상, 자료·자원·시간, 선택적 공간 문맥 |
| E3 | G1 | 회귀 증거 | `E3회귀증거Module` | 계약, 결정성, Save/Replay, 소비자 회귀 |
| E2 | G1 | 실행 경계 | `E2실행경계Module` | Shared Core, Local/Remote Adapter, Unity 투영 |
| E1 | G1 | 핵심 계약 | `E1핵심계약Module` | 목적, 권위, 식별자·판본·시간, 허용 발생원, 완료·제외 |

이 이름은 계획용 코드와 검증용 코드를 따로 만들라는 뜻이 아니다. 같은 모듈을 하향할 때는 필요한 책임과 누락을 적는 자리로, 상향할 때는 실제 조립과 증거를 확인하는 자리로 사용한다. 예를 들어 `E4실행문맥결속Module`은 하향 검토에서 WI의 발생원·주체·대상·자료·자원·시간과 공간 적용 여부를 적고, 상향 검증에서 필요한 문맥이 실제로 결속됐는지 확인한다.

E1~E3의 범위가 넓어 실제 코드를 찾기 어려운 문제는 상위 모듈을 더 늘리지 않고 사람용 하위 모듈로 해결한다. E1은 세션 권위·세계 상호작용·공간·저장/재생·전투/위협 계약, E2는 세션 실행·세계 상호작용 실행·로컬 권위 Adapter·원격 Host Adapter·Unity 권위 Client, E3는 계약·결정성·저장/재생·로컬/원격 동등성·Unity 소비자 회귀로 나눈다. 안정 key와 현재 코드 결속의 단일 기준은 [E 성숙도 책임 메타데이터](SsalddelCodeMetadata.md#e1e3-사람용-하위-모듈)를 따른다. 이 하위 분류 역시 새 E 단계, 별도 증거 단계 또는 물리 프로젝트를 뜻하지 않는다.

E 단계의 주어는 WI 또는 WI 폐루프다. H1~H5와 AreaSet·Graph는 공간 포함 깊이와 공간 조립 증거를 소유하지만 E 단계 자체를 소유하지 않는다. 공간이 필요한 WI는 E4에서 H 능력·용량·연결구를 문맥으로 결속하고 E5에서 실제 공간 조립을 발현 증거로 사용한다. 비공간 WI는 공간을 `NotApplicable`로 기록하고 자료·상태·인과 경로로 E4·E5를 검증한다.

### 모듈 상태

| 상태 | 의미 |
| --- | --- |
| `Named` | 이름과 책임만 정해 둔 골격 |
| `Outlined` | 검토하면서 하위 항목을 적은 상태 |
| `Selected` | 가까운 구현 대상으로 선택됨 |
| `Implemented` | 필요한 코드·문서·대장이 생김 |
| `Verified` | 해당 E 관문의 실제 증거가 통과함 |
| `Deferred` | 필요성은 남기되 지금 구현하지 않음 |

기본값은 `Named`다. `Named`·`Outlined`는 E 증거가 아니고, `Implemented`도 실제 완료 관문 없이 `Verified`나 E 승격으로 바뀌지 않는다. 새 아이디어나 리팩토링에서는 각 모듈에 대해 `영향 여부`, `이름이나 빈 자리 필요 여부`, `지금 선택할지 미룰지`만 먼저 정해도 된다. 실제 구현은 `Selected` 모듈의 가장 낮은 미완료 의존성부터 진행한다.

세부 슬롯과 상태의 기계 기준은 `e9-refactor-module-catalog.json`이 소유한다. 모듈은 WI나 H를 새로 소유하지 않으며 `e9-wi-h-module-bindings.json`은 기존 WI 고유 식별자와 H1~H4 참조를 E 책임 관점으로 읽기 위한 비권위 결속 대장이다.

코드 타입과 선택된 WI 공개 메서드에는
`SsalddelEvidenceResponsibilityAttribute`로 이 책임 자리를 연결한다. Attribute는
현재 증거 상태가 아니라 검토 책임을 나타내며, 적용 범위·제외 사유·전수 검사와
생성 지도의 기준은 [코드 탐색 메타데이터](SsalddelCodeMetadata.md#e-성숙도-책임-메타데이터)가
소유한다.

## 한 주기의 상향 조립과 다음 하향 재검토

하향 검토를 E1까지 작성했다고 아홉 단계를 모두 곧바로 구현할 필요는 없다. 위의 모듈 이름과 빈 책임을 검토하고, 실제로 `Selected`로 고른 모듈이 있을 때만 가장 낮은 미완료 의존성부터 구현한다.

```text
E1 계약·결정
  → E2 공통 Core와 Adapter
  → E3 자동 시험·결정성·Save/Replay
  → E4 WI 공간 모판
  → E5 Actual AreaSet·배치 통제
  → E6 플레이 전 정제·필요 근거
  → E7 Solo·Hosted 실제 플레이
  → E8 NPC 생활세계
  → E9 실제 변경·Migration·재검증
```

상향 실행은 상위 목적에 종속된 작업을 실제 의존 관계대로 닫는 과정이다. Codex는 상위 층의 빈칸을 잊지 않으면서 현재 `currentEvidenceStage` 바로 다음의 미완료 관문을 구현한다. 상향 중 계약·공간·플레이 약속의 영향이 달라졌다면 같은 작업 명세를 갱신해 다시 하향 검토하고, 새 최저 누락을 고른 뒤 다음 상향 조립을 진행한다.

## Solo·Hosted 권위 적용

- 규칙·Session·Preview·Confirm·Task·Effect·WorldTick·Revision·Save/Replay는 `SharedSimulationCore`가 소유한다.
- Solo는 Unity 프로세스의 `LocalProcess`, Hosted는 서버 Host의 `RemoteHost`에서 같은 Core를 실행한다.
- Unity `GameObject`, `Update()`와 Presentation 상태는 Solo 권위가 아니다.
- 작업 명세는 두 실행 위치의 같은 seed·명령·시간 입력이 같은 canonical 상태와 replay hash를 만드는지 E3와 E7에서 각각 요구한다.
- 운영 주문·계약·결제·입고 원장은 게임 Simulation 권위 위치와 별개이며 명시적 승인 없이 작업 범위에 넣지 않는다.

## H와 배치 통제 적용

H1~H5는 공간의 의미 포함 깊이다. 배치 통제 계층은 H4.5나 새 E 단계가 아니다.

```text
E5 하향 질문
├─ H4 AreaSet 의도와 허용 범위
├─ H3 경관 Graph와 복귀 경로
├─ H2 판단 Block과 도로·전면·이격 규칙
├─ H1 발자국·능력·소켓
└─ 배치 통제
   ├─ Player 상대 크기
   ├─ 경사·능선 회피
   ├─ 객체 이격
   ├─ 울타리 연속성
   ├─ 출입구 공백
   └─ placement mask·통행
```

Synty Prefab을 배치했다는 사실은 E5가 아니다. H 고유 식별자, 입력 revision·hash, 결정적 위치, Graph 관계, 통행과 배치 검증 기록이 함께 있어야 한다.

## Codex 작업 규칙

1. 의미 있는 새 게임 기능·공간 변경뿐 아니라 권위 위치·저장·Replay·Local/Remote Adapter를 바꾸는 리팩토링도 JSON 작업 명세를 만들거나 기존 명세에 연결한다.
2. 각 하향 주기에서 E9→E1 아홉 항목을 모두 다시 판정하고 자료가 없으면 `Gap` 또는 `Blocked`로 남긴다.
3. `currentEvidenceStage`보다 높은 화면·문서·코드가 존재해도 하위 관문을 건너뛰어 완료로 표현하지 않는다.
4. 검토 뒤 구현 대상으로 선택한 모듈이 있을 때만 가장 낮은 미완료 의존성부터 진행하고, 이름만 정한 `Named` 모듈은 구현을 강제하지 않는다.
5. Solo·Hosted, H 의미 계층·배치 통제 계층, Simulation 권위·Unity 표현을 각각 분리한다.
6. 상향 조립 뒤 E1→E9 검증 상태와 증거를 갱신하고, 새 영향이 발견되면 다음 하향 주기를 같은 작업 명세에서 다시 연다.
7. 한 번의 상향 통과를 작업 종료로 간주하지 않는다. 선택 범위의 안정 상태 또는 명시적 차단이 있어야 현재 왕복 주기를 닫는다.
8. 기준 E8이 없는 신규 기능은 E8까지 완성해도 그 사실만으로 E9가 되지 않는다. 다음 실제 변화와 Migration·회귀가 필요하다.

## 현재 Nature 적용 판정

현재 적용본은 E9 목표부터 E1까지 구조가 모두 작성됐고 Nature·Local Runtime·Save/Replay 집중 시험을 근거로 `currentEvidenceStage = E3`다. 그러나 `promotionEligible = false`다.

- E1: Nature 목적·권위·시간·StableId·Save 경계 정의
- E2: 공통 `LocalSimulationRuntime`과 Unity Package 경계 구현·컴파일
- E3: Nature·Local Runtime·Save/Replay를 포함한 전체 Simulation `760/760`, Unity 독립 시험 `496/496`
- E4: WI-NATURE-05~12의 발생원·주체·대상·자원·시간과 Required 공간 문맥을 Actual E5 Graph에 결속
- E5: V15 실행 인스턴스는 Invocation·권위 전이·Task/Effect·결과·후속 선택을 `ManifestationPartial`로 기록한다. H 공간 대기는 닫혔지만 전체 후속·복귀 폐루프의 `Manifested` 증거는 남아 있다.
- E6: 정제 질문표와 현실자료 NotApplied 근거 필요
- E7: 서버 없는 Solo와 Hosted 실제 입력·Game View 미검증
- E8: 지속 NPC 생활세계 미구현
- E9: 기준 E8·실제 변화·Migration·상향 재검증 없음

이 판정은 이미 구현한 코드를 폐기하지 않는다. 구현이 어느 상위 약속을 위해 존재하며 다음에 무엇을 닫아야 하는지를 고정한다.

## 현재 Solo Runtime 리팩토링 적용 판정

서버 중심 실행을 `SharedSimulationCore`의 `LocalProcess`·`RemoteHost` 구조로 바꾸는 작업은 단순 내부 정리가 아니다. 권위 위치, 저장·재생, Unity Adapter와 실제 플레이 폐루프에 영향을 주므로 별도 E9↔E1 왕복 작업 명세로 관리한다.

현재 적용본은 E9부터 E1까지 영향을 모두 기록했고 `currentEvidenceStage = E3`다.

- E1: Solo 기본 권위, Hosted Host, 저장·운영 제외 경계 통과
- E2: 공통 Runtime과 Nature·턴 마감·Farm 선택·물류 Local Adapter 구현·컴파일 통과
- E3: 전체 Simulation `760/760`, Unity 독립 시험 `496/496`, V1~V15 Save/Replay 회귀 통과
- E4: `WI-FARM-04~06`과 `WI-NATURE-01~04`는 조건부 H 문맥 결속, `WI-NATURE-05~12`는 Required 공간 근거가 `Bound`
- E5~E6: 선택된 19개가 공통 Pipeline과 발현 원장에 연결됐다. `WI-CON-01`의 결정적 건설·취소·학습 방문은 `Manifested`, Farm 04~06과 Nature 01~15는 현재 증거 범위에서 `ManifestationPartial`이다. E6 실제 플레이 전 정제는 아직 통과시키지 않음
- E7: Solo·Hosted 동일 실제 입력·Save/Load 폐루프 미완료
- E8: NPC 지속 생활세계 미완료
- E9: 기준 E8과 실제 변화·Migration·rollback 없음

다음 후보는 Nature Core 자식의 Hosted 동등성과 전체 후속·복귀 `Manifested` 증거다. Hub 입고·전투·탐험 이관은 현재 WI 원장에서 폐루프 단위로 명시 선택한 뒤에만 같은 Pipeline으로 확장한다.
