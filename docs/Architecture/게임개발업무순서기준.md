# Ssalddel 게임 개발 업무 순서 기준

## 목적

Ssalddel의 게임 개발은 아이디어가 생길 때마다 기능을 하나씩 덧붙이는 방식으로 진행하지 않는다. 현재 프로젝트는 WI 상태 전이, H 공간, Simulation 서버 권위, `SimulationWorldShell`, E 증거와 G 관리 체계를 이미 사용하고 있으므로, 앞으로의 작업도 이 구조에 맞춰 같은 순서로 선택하고 완료한다.

이 문서는 사용자와 Codex가 계속 개발할 때 다음 세 가지를 결정하는 기준이다.

1. 지금 무엇을 먼저 해야 하는가.
2. 한 작업을 어디까지 해야 완료라고 말할 수 있는가.
3. 다음 작업으로 넘어가기 전에 무엇을 남겨야 하는가.

## 기본 업무 흐름

```text
현재 목표 확인
  → 플레이어 약속과 선택 폐루프 정의
  → 플레이 단위 선택
  → E9 목표 봉투 선언
  → E9→E1 하향 영향·누락 검토
  → 가장 낮은 미완료 의존성부터 구현
  → E1→E9 상향 조립·증거 검증
  → 새 영향이 있으면 다시 E9→E1 검토
  → 안정 또는 명시적 차단까지 왕복
```

모든 작업이 모든 단계를 수정할 필요는 없다. 다만 건너뛴 단계가 있다면 해당 없음인지, 이미 준비됐는지, 아직 미완료인지 구분한다.

E9를 먼저 적는 것은 E9 완료를 먼저 주장하는 것이 아니다. 상위 세계 목적부터 NPC·플레이어·현실 문맥·AreaSet·WI 공간·시험·코드·계약까지 빠짐없이 분해하기 위한 첫 검토 방향이다. 실제 증거는 E1부터 다시 올라가며, 상향 결과에서 새 영향이 나오면 다시 내려가 작업 명세를 고친다. 기준 E8과 Migration·회귀가 없으면 E9로 승격하지 않는다. 상세 형식은 [E9↔E1 반복 왕복 구현 체계](E9하향식수직구현체계.md)를 따른다.

기존의 `WI·권위 계약 확인 → Simulation 세로 조각 → H 공간 결속 → Unity 조립 → 필요한 실제 증거 확인` 책임은 이 반복 왕복 안에 그대로 포함한다.

모든 단계에 공통으로 적용하는 플레이어 관점은 [플레이어 중심 게임 개발 업무 구조](플레이어중심게임개발업무구조.md)를 따른다. 기술 작업을 시작하기 전에 플레이어가 무엇을 보고, 왜 선택하고, 어떤 재료·비용·위험을 감수하며, 결과로 무엇을 체감하고 다음 무엇을 선택하는지 먼저 닫는다. 이 관점은 상태 권위를 Unity나 플레이어에게 넘기는 규칙이 아니다.

## 1. 현재 목표부터 확인한다

새 아이디어보다 먼저 [현재 작업](../AI/CURRENT_WORK.md), [완료 원장](../AI/authority-maps/07_CURRENT_COMPLETION_LEDGER.md), [확정 결정](../AI/DECISIONS.md)을 확인한다.

현재 목표를 막는 항목이 있으면 새 확장보다 먼저 처리한다. 특정 영역이나 연결 순서를 이 문서에 고정하지 않고 `CURRENT_WORK.md`의 최신 목표와 순서를 따른다.

## 2. 기능이 아니라 플레이 단위를 고른다

기본 작업 단위는 플레이어가 이해할 수 있는 상황·선택·준비·행동·결과·귀환의 가장 작은 묶음이다.

```text
플레이어가 어떤 상황과 필요를 알아차리는가?
  → 어떤 선택과 대가·위험을 비교하는가?
  → 어떤 재료·도구·장소를 찾고 모으는가?
  → 무엇을 Preview하고 Confirm하는가?
  → 권위 상태와 H 공간이 어떻게 바뀌는가?
  → 어떤 피드백을 보고 귀환하거나 다음 무엇을 선택하는가?
```

예를 들어 “카드 UI 추가”만으로 작업을 잡지 않는다. 어떤 플레이 상태에서 어떤 선택을 위해 카드를 열고, 어떤 서버 Preview와 Confirm으로 이어지며, 결과 뒤 무엇이 달라지는지를 함께 정한다.

“오두막 건설”도 Prefab 배치만으로 잡지 않는다. 나무를 어디서 발견하고, 어떤 도구와 시간을 들여 모으며, 다른 사용처와 비교해 얼마를 배정하고, 배치 결과를 확인한 뒤 어떤 생활 능력과 다음 선택이 열리는지까지 같은 작업 약속에 둔다.

선정한 플레이 단위에는 `eng/execution-ledgers/work-orders/`의 E9 왕복 작업 명세를 하나 연결한다. 새 작업이면 템플릿을 복사하고, 기존 작업의 작은 수정이나 상향 중 발견한 새 영향은 기존 명세의 하향 판정과 상향 검증 상태를 다시 갱신한다.

## 3. WI와 상태 권위를 먼저 확인한다

작업을 시작하기 전에 다음을 적는다.

- 기존 WI로 표현할 수 있는가.
- 시작 상태와 완료 상태는 무엇인가.
- Preview는 무엇을 계산하고 무엇을 바꾸지 않는가.
- Confirm은 어떤 StableId와 ExpectedRevision을 보내는가.
- Decision·Task·Effect·WorldTick 중 어디에서 상태가 바뀌는가.
- 프레임 실시간, 권위 실시간 시계, WorldTick·BattleTick 중 어떤 시간 경계를 사용하는가.
- Save/Replay와 기존 hash에 영향이 있는가.
- Unity는 어떤 결과를 표현만 하는가.

공개 계약, 저장 값과 StableId는 문서 편의를 위해 바꾸지 않는다. Unity가 비용·효과·작업 성공을 다시 계산하지 않는다.

시간 기반 기능의 상세 구분은 [WorldTick과 실시간 실행 경계](WorldTick과실시간실행경계.md)를 따른다.

## 4. 가장 작은 Simulation 세로 조각을 먼저 닫는다

새 상태 전이가 필요하면 다음 순서로 구현한다.

```text
Contract
  → Application
  → Domain Aggregate
  → Persistence·Server
  → 집중 자동 시험
  → Save/Replay·결정성 확인
```

첫 검증은 작은 결정적 Fixture를 사용한다. Fixture 성공은 실제 HTTP, 운영 DB, Provider 호출이나 Unity 실제 플레이의 증거가 아니다.

## 5. WI가 요구하는 H 공간을 연결한다

Simulation 규칙을 만든 뒤 그 플레이가 실제로 어디서 일어나는지 확인한다.

| 공간 질문 | 확인 대상 |
| --- | --- |
| 행동은 어디서 일어나는가? | 직접 H1 |
| 대기·보관·회복·인계는 어디서 일어나는가? | 지원 H1 |
| 여러 H1을 어떤 판단 단위로 묶는가? | H2 블록 |
| 시작과 결과가 어떤 경로로 다시 연결되는가? | H3 경관·복귀 경로 |
| 특정 세계에 실제로 배치됐는가? | H4 AreaSet·Actual E5 |
| 현실 근거가 필요한가? | 선택한 E6 자료·계보 |

새 H가 필요한 `SpatialInventoryGap`과 기존 H의 증거가 부족한 `EvidenceGap`을 구분한다. Synty Prefab과 GameObject는 H를 표현하지만 H StableId나 공간 능력을 만들지 않는다.

플레이어는 H1을 직접 배치·복구·연결할 수 있다. H2와 H3는 플레이어가 목표로 삼고 유도할 수 있지만, 필요한 H1·연결구·용량과 플레이 폐루프가 닫혔는지를 세계 규칙이 판정한다. H4·H5 계약은 현재 단계에서 플레이어가 임의 생성하지 않는다. 세계 자원·Lot, 조립법·비용, 배치 Preview, H1 인스턴스, H2/H3 성장 판정과 Synty 시각 자산을 각각 다른 상태로 기록한다.

## 6. Unity는 기존 공식 Scene에 조립한다

게임 기능은 새 공식 Scene을 만들지 않고 canonical `SimulationWorldShell`의 모듈로 연결한다.

```text
플레이어 입력
  → 서버 Preview
  → 명시적 Confirm
  → 서버 상태 변경·WorldTick
  → canonical 상태 재조회
  → Unity 화면·애니메이션·피드백 갱신
```

카메라, 선택, 드래그, 애니메이션과 Synty 표현은 `WorldTick`이나 Revision을 직접 변경하지 않는다. 검토용 `ReviewFixture`를 실제 서버 연결로 표현하지 않는다.

## 7. 목표 E에 필요한 증거까지만 정확히 확인한다

작업을 시작할 때 목표 E와 판정 단위를 정한다. 작업이 끝난 뒤에는 아래 증거를 따로 보고한다.

```text
코드 존재
≠ 자동 시험 통과
≠ Actual E5
≠ E6 플레이 전 정제·필요 근거
≠ 실제 서버 실행
≠ Play Mode·Game View
≠ 운영 효과
≠ commit·push·deploy
```

화면에서만 확인할 수 있는 입력·카메라·배치 문제나 E7 판정은 저장 Scene, Play Mode 실제 입력, Game View와 Console을 확인한다. 문서·계약·자동 시험 작업은 필요한 수준까지만 검증하되 미실행 범위를 명시한다.

## 8. 작업이 끝나면 현재 상태와 다음 순서를 다시 정한다

의미 있는 작업을 마치면 다음을 확인한다.

1. `CURRENT_WORK.md`가 최신 목표·검증·다음 순서를 반영하는가.
2. 장기 판단이 바뀌었다면 `DECISIONS.md`에 대체 관계가 기록됐는가.
3. WI·H·E/G·완료 판정이 바뀌었다면 관련 권위 지도가 갱신됐는가.
4. 실제 화면을 바꿨다면 증거 수준과 변경 기록을 남겼는가.
5. 하지 않은 commit·push·배포를 완료처럼 표현하지 않았는가.

다음 작업은 아래 우선순위로 고른다.

## 다음 작업 선택 우선순위

| 우선순위 | 선택 기준 | 예 |
| --- | --- | --- |
| 1 | 현재 목표의 직접 차단 항목 | Nature WI의 H 추적, Farm 내부 반환 계약 |
| 2 | 현재 플레이 폐루프의 서버·저장·Unity 증거 | Solo Session, Save/Replay, Game View |
| 3 | 현재 변경으로 생긴 회귀·배선 실패 | 관련 집중 시험, 저장 Scene 배선 |
| 4 | 준비도가 낮은 영역의 독립 내부 폐루프 | Hub·Town·City 중 독립 실행이 약한 영역 |
| 5 | 양쪽이 준비된 영역 간 통합 | Farm→Hub, Hub→Town |
| 6 | NPC 생활세계 E8 | 지속 NPC 선택·이동·협력·기억 |
| 7 | 실제 변화 적응 E9 | 계절·경제·역할 변경과 Migration·회귀 |

새 아이디어가 중요해 보여도 현재 목표의 직접 차단 항목을 임의로 밀어내지 않는다. 우선순위를 바꿀 필요가 있으면 왜 현재 순서를 바꾸는지 먼저 기록한다.

## 영역 개발 순서의 원칙

Farm·Hub·Town·City는 각각 내부 플레이·Fixture·Save/Replay·공간 증거를 먼저 가진다. 먼저 구현된 Farm의 화물이나 성과를 다른 영역의 필수 시작 상태로 사용하지 않는다.

```text
영역 내부 폐루프
  → 독립 검증
  → 다른 영역도 독립 준비
  → 영역 간 통합을 별도 작업으로 선택
```

따라서 Farm→Hub→Town은 존재 가능한 통합 흐름이지만 자동 다음 순서는 아니다.

## 한 작업을 시작할 때 적을 최소 항목

새 업무 문서는 길게 작성할 필요가 없다. 다음 항목만 먼저 고정한다.

```text
목표
플레이어 약속
상황·선택·대가·재료·결과·귀환
관련 WI
관련 H
상태 권위 소유자
목표 E와 필요한 증거
포함 범위
제외 범위
변경 후보 파일
검증 계획
완료 후 다음 판단
```

[게임 개발 작업 단위 템플릿](../ProjectOverview/templates/게임개발작업단위템플릿.md)을 복사해 사용할 수 있다.
