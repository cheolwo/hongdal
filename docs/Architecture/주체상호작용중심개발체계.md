# 주체·상호작용 중심 개발 체계

## 목적

게임 개발의 첫 단위를 `PlayableLoop`가 아니라 **상태와 정체성을 가진 주체**로 둔다. 주체를 먼저 확립한 뒤 두 주체 사이의 `WorldInteraction(WI)` 하나를 개발 Goal로 선택하고, 직접 결과와 파생 작용을 순서대로 검증한다. 여러 WI가 함께 성공·실패·회복·귀환의 반복 경험을 이루는 경우에만 `PlayableLoop`를 선택적 검증 묶음으로 사용한다.

이 체계는 기존 `PlayableLoop`, Goal, E1~E10, Graph Map, Story Beat의 안정 ID와 증거를 삭제하지 않는다. 기존 Loop 중심 Goal은 주체·WI Goal로 읽을 수 있게 호환 투영하고, 새 Goal은 Loop 참조 없이도 등록할 수 있다.

## 핵심 관계

```text
기획 맥락·Story Beat
  ↓ 문맥 제공
주체 기반 확립
  ↓
주체 A ── WI 하나 ──> 주체 B
  ↓                     ↓
직접 결과          직접 상태 변화
  └────── 파생 작용 0~2 hop ──────┘
              ↓ 필요할 때만
      선택적 PlayableLoop 검증 묶음
```

- `주체`: Actor, NPC, 물체, 장비, 차량, 시설, 자연물, 환경 또는 세계 규칙의 역할·권위·초기 해석·저장 정체성 계약이다.
- `WI`: 주체 사이에서 가능한 행위와 직접 상태 전환을 소유한다.
- `Goal`: 정확히 WI 하나를 구현·검증한다. 같은 WI의 Logic·Presentation 하위 작업은 충돌하지 않는 범위에서 병렬화할 수 있다.
- `파생 작용`: 직접 결과 뒤에만 평가하는 0~2 hop 영향이다. 자동 생성하지 않고, 필요 없으면 이유 있는 `NotApplicable`을 기록한다.
- `PlayableLoop`: 여러 WI를 반복 경험으로 함께 검증할 필요가 있을 때 참조하는 선택적 묶음이다. WI나 Goal의 존재 조건이 아니다.
- `Story Beat`: 왜 이 상호작용이 등장하는지 설명하는 서사 문맥이다. Command, 상태 전이, 실행 순서의 권위가 아니다.
- `Graph Map`: 공간·접근·관계가 선택이나 결과에 영향을 줄 때만 여는 조건부 설계다.

## 주체 기반 관문

`Ready` 주체는 다음을 모두 가져야 한다.

1. 안정 `subjectStableId`와 주체 종류
2. 상호작용에서 맡을 역할
3. 권위 상태 소유자
4. 최초 상태 또는 Runtime 인스턴스 해석 방법
5. 영속 경계
6. Save/Replay에서 동일 주체를 식별하는 근거
7. 현재 코드·대장·계약의 출처

`Ready`는 계약 준비를 뜻한다. 로그인 사용자, Scene `GameObject`, Prefab, Runtime 인스턴스 또는 E5 배치가 이미 존재한다는 증거가 아니다.

현재 기존 107개 WI의 호환 전환에는 실행 주체 네 종류와 `권위 WI 계약에서 결정되는 직접 대상`을 사용한다. 직접 대상은 실행 시 Actor 자신, 다른 인물, 물체, 시설, 환경 또는 세계 규칙으로 해석될 수 있으며, 구체 대상이 기획 의미를 바꾸는 신규 WI는 범용 대상을 계속 쓰지 않고 별도 주체 정의를 추가한다.

## 개발 순서

### 1. SubjectFoundation

상호작용에 참여할 행위 주체와 직접 대상 주체가 모두 `Ready`인지 확인한다. 한스, 플레이어, 농가주택처럼 구체 정체성이 선택·관계·저장 결과를 바꾸면 별도 주체로 등록한다.

### 2. InteractionCore

Goal 하나가 WI 하나만 소유하도록 고정한다. Actor·직접 대상, 허용 발생원, 입력 조건, 권위 소유자와 금지 경계를 결속한다.

### 3. DirectResult

WI 자체의 시작·완료 상태와 직접 `EffectCode`를 먼저 구현한다. 직접 결과가 결정적이지 않으면 주변 노드나 공동체에 미치는 효과를 추가하지 않는다.

### 4. DerivedEffects

직접 결과가 확립된 뒤에만 1-hop 또는 2-hop 파생 작용을 연다. 파생 작용에는 효과, 인과 근거, 멱등성, Save/Replay 결속이 필요하다. 2-hop은 중간 결과를 건너뛰어 추론하지 않도록 별도 인과 증거를 요구한다.

### 5. OptionalPlayableLoopValidation

다음 중 하나가 필요할 때만 `PlayableLoop`를 연결한다.

- 둘 이상의 WI가 성공·실패·회복·귀환을 함께 닫아야 한다.
- 반복 플레이의 시작점과 재진입점을 검증해야 한다.
- 한 WI만으로는 플레이어 약속을 입증할 수 없다.

단일 WI의 계약·결과·귀환이 자체적으로 닫히면 Loop 없이 E1~E7을 진행할 수 있다. Loop를 연결해도 그 Loop가 WI의 Command나 결과를 새로 만들지는 않는다.

## E1~E7 적용

E1~E7의 기본 수직 판정 주체는 `WI Goal`이다.

| 단계 | 주체·상호작용 관점 |
| --- | --- |
| E1 | 참여 주체·역할·WI 의도·직접 결과 계약 |
| E2 | 권위 계약·Adapter·소비 경로 연결 |
| E3 | 같은 입력의 직접 결과 결정성과 저장·복원 시험 |
| E4 | 주체 표현, 대상 판독, 필요한 공간·자산 후보 동결 |
| E5 | 같은 revision의 주체·WI·직접 결과가 Runtime과 표현에 실제 결속 |
| E6 | 실패·중단·애니메이션·파생 작용·자료 계보 정제 |
| E7 | 실제 입력으로 직접 결과와 귀환 또는 다음 선택 확인 |

Loop가 연결된 Goal은 E7에서 묶음 전체의 폐쇄성도 함께 판정한다. Loop가 없는 Goal은 해당 WI의 종결·귀환·다음 선택 경계까지만 판정하며 다른 WI를 억지로 만들지 않는다. E8은 같은 WI Goal 또는 명시적으로 동결한 Loop 묶음의 반복 결정성을 검증하고, E9는 같은 영역의 독립 결과 둘 이상을 조화시킨다.

## 기획과 Story Beat 인계

기획은 먼저 등장 주체 후보와 각 주체가 무엇을 알고·소유하고·원하며·어떤 권위 상태를 갖는지 기록한다. 그 뒤 Story Beat의 사건을 WI 후보에 연결한다.

```text
Story Beat
  → 등장 주체 후보
  → 기존 주체 재사용 또는 새 주체 승인
  → 주체 사이 WI 후보
  → WI 하나의 Goal
  → 필요할 때만 Loop 결속
```

Story Beat 순서가 곧 서버 Command 순서는 아니다. 같은 Beat가 여러 선택 가능한 WI를 열 수 있고, WI 하나가 여러 Beat에서 재사용될 수 있다. Story Beat 변경이 주체 정체성이나 WI 의미를 바꾸면 새 기획 revision을 승인하고 가장 이른 E를 다시 연다.

## 기존 자료의 호환

- `codex-playable-loop-goals.json`의 각 기존 항목은 `nextWorldInteractionId`를 소유하는 단일 WI Goal로 투영한다.
- 기존 `loopStableId`는 삭제하지 않고 `optionalPlayableLoopValidationRef`로 보존한다.
- 기존 Goal에 기록되지 않은 파생 작용은 만들지 않고 이유 있는 `NotApplicable`로 둔다.
- 기존 Loop·Evidence·작업 명세의 E를 새 체계 도입만으로 승격하거나 강등하지 않는다.
- 신규 Loop 없는 Goal은 `subject-interaction-development.json`의 `nativeInteractionGoals`에 등록한다.
