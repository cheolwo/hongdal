# PlayableLoop 전문 심화 연구 분기·재결속 체계

## 목적

PlayableLoop의 Logic·Presentation 순환이 빠르게 돌아가더라도 건물, 공간, 배치, 애니메이션 같은 구체 설계가 얕은 가정으로 굳어지지 않게 한다. 폐루프 기획에서 필요한 전문 문제를 별도 연구 문서로 분기하고, 검토된 기준선만 다시 승인 기획서와 E7 작업 명세에 결속한다.

이 체계는 E·G·H·WI를 대체하거나 새 성숙도 축을 추가하지 않는다.

```text
PlayableLoop Draft
  -> 필요한 전문 연구 판정
     |- 건물 연구
     |- 공간 연구
     |- 배치 연구
     `- 애니메이션 연구
  -> 분야별 기준선 검토
  -> PlayableLoop 재결속 검토
  -> Approved 기획서
  -> E7 영향 검토와 구현
  -> 실제 입력·Play Mode 피드백
  -> 잘못된 가정의 연구만 다시 열기
  -> 같은 폐루프에 재결속
```

## 두 종류의 문서

### 공통 기준 문서

여러 폐루프가 공유하는 문법과 기술 경계를 정의한다. 예를 들어 건물 발전 문법, H 공간 계층, 실내·실외 배치 계약, 공용 애니메이션 재사용 경계가 여기에 해당한다. 공통 기준 문서는 개별 폐루프의 좌표, 시간, 자산 또는 완료 증거를 대신하지 않는다.

### 폐루프 적용 연구

특정 `playable-loop:*`와 WI에 공통 기준을 어떻게 적용할지 결정한다. 필요한 치수, 이동 거리, 상호작용 위치, 배치 밀도, 애니메이션 접촉점과 대체 표현처럼 구현 전에 합의해야 하는 구체 기준을 소유한다.

같은 내용을 두 문서에 복제하지 않는다. 폐루프 적용 연구는 공통 기준을 참조하고 이번 적용에서 달라지는 결정만 기록한다.

## 연구 분야

| 분야 | 답해야 하는 질문 | 최소 산출물 |
| --- | --- | --- |
| 건물 | 이 폐루프에 어떤 건물 상태와 구조가 필요한가? | 유형, 규모, 바닥 면적, 출입구, 내부 구역, 건설·손상·복구 상태, 카메라·충돌·이동 경계 |
| 공간 | 플레이어가 어떤 거리·시간·시야·밀도로 이동하고 되돌아오는가? | 동선, 이동 시간, 시야선, 방향 인지, 경사·평탄화 범위, 카메라 판독 기준 |
| 배치 | 어떤 권위 상태가 어떤 실내·실외 배치 차이로 보이는가? | 배치 역할, Surface·Slot·Clearance, 상태별 변형, 밀도·변주, 결정적 Seed·Hash, 대체 자산 |
| 애니메이션 | 행위의 준비·수행·결과·취소가 몸과 도구로 어떻게 읽히는가? | 상태 전이, Clip·Rig 후보, 손·도구 접촉점, Task 시간 동기화, 취소 구간, Audio·FX, fallback |

분야 목록은 첫 공통 프로필이다. 다른 전문 연구가 필요하면 같은 계약으로 추가할 수 있지만 새 E 단계나 별도 Goal로 만들지 않는다.

## 필요성 판정

각 분야는 다음 중 하나로 판정한다.

- `Required`: 이번 플레이어 약속이나 WI 구현 전에 구체 기준이 필요하다.
- `NotRequired`: 이번 범위에 필요하지 않으며 기획서에 짧은 사유를 남긴다.

다음 조건 중 하나라도 해당하면 `Required`로 둔다.

1. 플레이어 선택·대가·성공·실패·회복의 의미가 분야 결정에 따라 달라진다.
2. H Capability, 권위 상태, Save/Replay 또는 LocalProcess·RemoteHost 동등성에 영향을 준다.
3. 실제 입력, 카메라, Collider, NavMesh, 접촉점 또는 화면 판독을 좌우한다.
4. 자산 후보가 여럿이고 선택 기준이나 fallback이 정해지지 않았다.
5. 개발 중 임의 수치나 임시 배치가 장기 계약으로 굳을 가능성이 있다.

단순 코드 정리, 테스트 보조 구현, 의미를 바꾸지 않는 성능 개선만으로는 새 연구를 요구하지 않는다.

## 상태와 승인

연구 문서는 다음 상태를 사용한다.

```text
NotRequired
Required -> Draft -> Reviewed -> Accepted -> Obsolete
```

- `Draft`: 조사와 대안 비교가 진행 중이다.
- `Reviewed`: 구현 입력으로 삼을 후보 기준선이 준비됐다.
- `Accepted`: 선택 기준, 측정값, 영향 범위, 검증법과 무효화 조건이 합의됐다.
- `Obsolete`: 더 새 revision이 대체했거나 플레이어 약속 변경으로 적용할 수 없다.

`Accepted`는 연구 기준선의 승인이지 E 승격이나 Runtime 증거가 아니다. 실제 코드, Scene, Play Mode와 Game View 증거는 Goal·작업 명세·EvidencePackage가 소유한다.

## 연구 문서 필수 항목

1. 연구 고유 식별자, 대상 PlayableLoop·WI, revision과 상태
2. 연구 질문과 플레이어 사용 문맥
3. 현재 코드·문서·Scene·자산·시험 재고
4. 변경할 수 없는 권위·호환·성능 경계
5. 비교한 대안과 장단점
6. 선택한 기준선과 선택 이유
7. 치수·시간·거리·밀도·접촉점 같은 측정 가능한 값
8. 자산 연결, 대체 표현과 보류 사유
9. Logic·Presentation·H·Save/Replay 영향
10. 프로토타입·자동시험·실제 화면 검증 방법
11. 다른 연구와의 의존 또는 충돌
12. 무효화 조건, 검토자와 승인 근거

모르는 값은 `미정`으로 보존한다. `Required` 연구에 플레이어 경험을 좌우하는 미정 값이 남으면 해당 PlayableLoop를 `Approved`로 올리지 않는다.

## 기획서 재결속

PlayableLoop 기획서는 `requiredDetailStudyRefs`에 네 분야 판정을 기록한다.

```text
building: Required -> study:...building.r1 -> Accepted
spatial: Required -> study:...spatial.r1 -> Accepted
placement: NotRequired -> 이번 WI는 기존 고정 배치만 읽음
animation: Required -> study:...animation.r1 -> Accepted
```

기획서 승인 전 다음을 확인한다.

1. 모든 `Required` 참조가 실제 문서를 가리킨다.
2. 참조 문서 상태가 `Accepted`이고 대상 PlayableLoop·WI가 일치한다.
3. 연구 기준선의 결과가 플레이어 약속, WI 책임, H Capability와 충돌하지 않는다.
4. 연구가 바꾼 Logic·Presentation E7→E1 영향과 검증법이 개발 인계 묶음에 반영됐다.
5. 모든 `NotRequired`에 범위 사유가 있다.

연구끼리 충돌하면 기획 스레드가 플레이어 약속을 기준으로 조정한다. 개발 스레드는 어느 연구를 우선할지 임의로 결정하지 않는다.

## 개발과 피드백

개발 스레드는 승인 기획서에서 현재 WI에 연결된 `Accepted` 연구만 구현 입력으로 읽는다. 연구에 없는 내부 클래스 구조나 시험 보조 코드는 기술 재량으로 결정할 수 있지만, 기준 치수·동선·접촉·상태 차이를 바꿀 때는 연구 revision과 기획 승인을 다시 연다.

실행 중 문제가 발견되면 다음처럼 분류한다.

- 구현이 기준선과 다름: 같은 Goal의 구현 결함으로 고친다.
- 기준선 자체가 부자연스럽거나 틀림: 영향받은 연구를 `Draft`로 다시 열고 관련 E를 재개한다.
- 플레이어 약속이 달라져야 함: 주제 기획 revision 또는 새 PlayableLoop 판단으로 돌아간다.

연구를 다시 열어도 Goal을 자동 교체하지 않는다. 수정된 연구가 재승인되면 같은 Goal과 E7 작업 명세에서 가장 이른 영향 E부터 다시 조립한다.

## 첫 적용 순서

첫 적용은 Nature의 보관·수면·다음 날 계획 반환 폐루프로 제한한다.

1. 오두막의 내부 구역과 상태를 정하는 건물 연구
2. 보관함·침상·계획 선택 지점 사이의 생활 동선을 정하는 공간 연구
3. 보관함·침상·계획판과 실내 소품을 정하는 배치 연구
4. 보관·수면·기상·계획 선택의 행위 판독을 정하는 애니메이션 연구

이 네 연구가 `Accepted`되기 전에는 해당 폐루프의 새 표현 E5 이상 구현을 시작하지 않는다. 현재 활성 전술 이동 Goal의 승인 범위와 진행 상태는 바꾸지 않으며, 다음 관련 기획 revision부터 적용한다.
