# E9 리팩토링 모듈 골격

## 목적

E9부터 E1까지 모든 기능을 미리 구현하지 않는다. 먼저 이름과 책임이 있는 빈 모듈 자리를 만들고, 검토를 거쳐 필요한 모듈만 세부 설계와 구현으로 진행한다.

기계 판본의 기준은 [`e9-refactor-module-catalog.json`](../../eng/execution-ledgers/e9-refactor-module-catalog.json)이다. 현재 WI와 H1~H4를 이 모듈에 연결한 비권위 결속 대장은 [`e9-wi-h-module-bindings.json`](../../eng/execution-ledgers/e9-wi-h-module-bindings.json)이다.

## 모듈 이름

| E | 관리 | 한국어 이름 | 기술 식별자 | 담아 둘 내용 |
| --- | --- | --- | --- | --- |
| E9 | G4 | 변화 봉투 | `ChangeEnvelopeModule` | 변경 제안, 영향 지도, 호환 계획, rollback |
| E8 | G3 | 생활 연속성 | `LifeContinuityModule` | NPC 정체성, 목표, 자율 생활, 기억 |
| E7 | G2 | 플레이 경험 폐루프 | `PlayableExperienceLoopModule` | 입력, 플레이 흐름, 피드백, 실행 증거 |
| E6 | G1 | 세계 정제 | `WorldRefinementModule` | 의미, 인과, 근거, 플레이 준비 질문 |
| E5 | G1 | 실제 세계 조립 | `ActualWorldAssemblyModule` | AreaSet, Graph, 배치 통제, 통행 |
| E4 | G1 | 상호작용 공간 결속 | `InteractionSpatialBindingModule` | WI, H1 능력, 용량·예약, 연결구 |
| E3 | G1 | 회귀 증거 | `RegressionEvidenceModule` | 계약, 결정성, Save/Replay, 소비자 회귀 |
| E2 | G1 | 실행 경계 | `RuntimeBoundaryModule` | Shared Core, Local/Remote Adapter, Unity 투영 |
| E1 | G1 | 핵심 계약 | `CoreContractModule` | 목적, 권위, 식별자·판본·시간, 완료·제외 |

이 이름은 프로젝트나 어셈블리를 지금 즉시 만들겠다는 뜻이 아니다. 이후 실제 중복과 책임 혼합이 확인될 때 폴더, namespace, 계약 또는 서비스 이름의 후보로 사용한다.

## 한 번 만들고 두 방향으로 사용

하향 모듈과 상향 모듈을 따로 만들지 않는다.

```text
하향 검토
E9 ChangeEnvelopeModule
 ↓
...
 ↓
E1 CoreContractModule

상향 조립·검증
E1 CoreContractModule
 ↑
...
 ↑
E9 ChangeEnvelopeModule
```

예를 들어 `InteractionSpatialBindingModule`은 하향할 때 “어떤 WI와 H1 결속이 필요한가?”를 적는 자리이고, 상향할 때 “그 결속이 실제로 실행되는가?”를 확인하는 자리다. 같은 책임을 계획용·검증용 코드로 복제하지 않는다.

## 상태

모듈은 다음 상태만 사용한다.

| 상태 | 의미 |
| --- | --- |
| `Named` | 이름과 책임만 정해 둔 골격 |
| `Outlined` | 검토하면서 하위 항목을 적은 상태 |
| `Selected` | 가까운 구현 대상으로 선택됨 |
| `Implemented` | 필요한 코드·문서·대장이 생김 |
| `Verified` | 해당 E 관문의 실제 증거가 통과함 |
| `Deferred` | 필요성은 남기되 지금 구현하지 않음 |

기본값은 모두 `Named`다. `Named`와 `Outlined`는 E 증거 완료가 아니다. 사용자가 구조를 검토한 뒤 선택하지 않은 모듈은 그대로 두거나 `Deferred`로 남길 수 있다.

## 적용 방식

새 아이디어나 리팩토링이 생기면 먼저 아홉 모듈 이름을 훑는다. 각 모듈에 세부 기능을 전부 채우지 않고 다음 세 가지만 기록해도 된다.

1. 이 변화가 해당 모듈에 영향을 주는가.
2. 검토할 이름이나 빈 자리가 필요한가.
3. 지금 선택할 것인가, 나중으로 미룰 것인가.

실제 구현은 `Selected` 모듈만 대상으로 한다. 현재 Solo-first 리팩토링은 E1~E3에 기존 구현과 증거가 있지만, 이 모듈 카탈로그 자체는 전체를 `Named` 골격으로 유지한다. 작업 명세의 증거 상태와 모듈 카탈로그의 설계 준비 상태를 섞지 않는다.

## 이름 사용 예

향후 세부 구조는 다음처럼 붙일 수 있다.

```text
RuntimeBoundaryModule
├─ SharedCore
├─ LocalAdapter
├─ RemoteAdapter
└─ UnityProjection

InteractionSpatialBindingModule
├─ WiBinding
├─ H1Capability
├─ CapacityReservation
└─ Connector

PlayableExperienceLoopModule
├─ InputFlow
├─ PlayerLoop
├─ InteractionFeedback
└─ RuntimeProof
```

이 골격을 보고 세부 기능을 정한 뒤, 실제 책임 분리가 필요한 경우에만 코드 구조를 만든다.

## WI·H 결속

E 모듈은 WI나 H를 새로 소유하지 않는다. WI의 계약·구현·통합 상태는 `world-interactions.json`, H1~H4의 공간 포함 관계는 Synty 하향식 정의와 게임플레이 공간 완성도 대장이 계속 소유한다. 결속 대장은 그 고유 식별자를 참조해 같은 기능을 E1~E9 책임 관점으로 읽게 한다.

```text
WI 고유 식별자
  ├─ H1 작업공간
  ├─ H2 블록
  ├─ H3 경관
  └─ H4 지역
       ↓
E9→E1 하향 영향 검토
       ↓
E1→E9 상향 조립·증거 확인
```

현재 첫 범위는 Nature↔Farm 기준 플레이에 직접 등장하는 WI 7개다.

| WI | H1~H4 결속 요약 | 현재 E 관점 |
| --- | --- | --- |
| `WI-FARM-04` 수확 | 생산·수확 대기 → 고지대 생산·세척선별포장 → Farm 경관·가공 캠퍼스 → Farm 지역 | E6 근거는 있으나 E7 실행 증거 없음 |
| `WI-FARM-05` 수확물 집하 | 수확 대기·작업장 → 세척선별포장·가공출하 → 가공 캠퍼스 → Farm 지역 | E6 근거는 있으나 E7 실행 증거 없음 |
| `WI-FARM-06` 출하 준비·포장 | 작업장·수확 대기 → 세척선별포장·가공출하 → 가공 캠퍼스 → Farm 지역 | E6 근거는 있으나 E7 실행 증거 없음 |
| `WI-NATURE-01` 위협 관찰 | 위협 관찰·사건 흔적 → 위협 대응 → 위협·회복 경관 → Nature 지역 | 공간 참조만 결속, 통합은 미선택 |
| `WI-NATURE-02` 긴급 후퇴 | 긴급 후퇴·안전 회복 → 위협 대응·복원 회복 → 위협·회복 경관 → Nature 지역 | 공간 참조만 결속, 통합은 미선택 |
| `WI-NATURE-03` 복원 | Nature 복원·Farm 복원 자원 → 양쪽 복원 인계 → 양쪽 회복 경관 → Nature·Farm 지역 | 영역 간 원인·복원 인계 후보, 통합은 미선택 |
| `WI-NATURE-04` 파티 회복 | 안전 회복 → 복원 회복 → 위협·회복 경관 → Nature 지역 | 공간 참조만 결속, 통합은 미선택 |

`SpatialRefsBound`는 H 참조가 연결됐다는 뜻일 뿐 Actual E5, E6, E7을 자동 증명하지 않는다. 마찬가지로 `SourceEvidenceClaimed`는 WI 원장의 기존 주장을 복사한 상태 사본이며 이번 결속 검사가 해당 시험을 다시 실행했다는 뜻이 아니다.
