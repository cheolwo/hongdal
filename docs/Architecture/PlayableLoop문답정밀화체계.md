# PlayableLoop 문답 정밀화 체계

## 목적

짧은 정차·대기 시간에도 PlayableLoop 기획을 안전하게 정밀화하고, 여러 번의 대화를 저장소 문서로 이어 붙여 승인 가능한 기획서로 만든다. 기본은 핵심 질문 하나이며 사용자가 연속 숫자 답변을 선호하면 같은 주제·깊이의 질문을 3~5개 묶어 제시한다. 완성된 기획서를 한 번에 요구하지 않고 플레이어 경험에서 전문 설계까지 단계적으로 묻는다.

문답은 공식 기획 절차의 `Draft` 단계다. 대화 기록 자체는 구현 명세나 승인 근거가 아니며, 매 회차의 정리 결과를 판본화된 문답 기록과 주제 기획서에 반영해야 저장소 인계 자료가 된다.

```text
대상 PlayableLoop 선택
  -> 문답 기록 개설
  -> 질문 하나 또는 3~5개 질문 묶음
  -> 사용자 답변 하나 또는 순서형 숫자 답변
  -> 해석·확정 후보·미정·영향 정리
  -> 다음 질문
  -> 분야별 전문 연구 질문 분기
  -> 전체 모순·누락 검토
  -> 주제 기획서로 합성
  -> 사용자 검토
  -> ReadyForReview
  -> 전문 연구 Accepted·재결속
  -> Approved
```

## 안전한 사용 경계

- 이동 중이거나 운전에 주의를 기울여야 할 때 답변을 요구하지 않는다.
- 사용자가 안전하게 정차했거나 대기 중일 때만 문답을 이어간다. 즉시 답변할 필요가 없으며 다음 안전한 시점에 같은 질문부터 재개할 수 있다.
- 질문은 짧고 한 번에 하나를 기본으로 한다. 사용자가 묶음 답변을 요청하면 같은 주제·현재 깊이의 독립 질문 3~5개를 제시하고 `1 3 2 2 1`처럼 질문 순서에 대응하는 숫자 답변을 허용한다.
- 묶음 안에서 앞 질문의 답에 따라 뒤 질문의 의미가 크게 달라지는 종속 질문은 함께 제시하지 않는다. 이 경우 앞 질문만 먼저 닫고 다음 묶음에서 이어간다.
- 긴 표 작성, 정밀 수치 비교, 화면 확인이 필요한 질문은 묶음에 억지로 넣지 않고 별도 검토 회차로 보낸다.
- 배달 위치, 고객 이름, 연락처, 실제 운행 시각처럼 게임 기획에 필요하지 않은 개인·업무 정보는 기록하지 않는다. 답변에 포함되어도 기획 의미만 일반화한다.

## 한 회차의 계약

기획 스레드는 한 회차마다 다음 순서를 지킨다. 묶음 회차에서도 각 질문은 아래 계약을 독립적으로 만족해야 한다.

1. 현재 대상 PlayableLoop, 주제, 탐구 깊이와 질문 고유 식별자를 밝힌다.
2. 질문이 필요한 이유를 한 문장으로 설명한다.
3. 하나의 핵심 질문을 제시한다. 묶음이면 서로 독립적으로 답할 수 있는 핵심 질문을 3~5개까지 제시한다.
4. 선택지가 도움이 될 때만 2~3개 선택지와 차이를 짧게 제시한다. 자유 답변과 `보류`를 항상 허용한다.
5. 답변을 받은 뒤 아래 다섯 항목으로 정리한다.
   - 사용자가 말한 의도
   - 확정 후보
   - 남은 미정 또는 충돌
   - 영향을 받는 WI·Logic·Presentation·H·전문 연구
   - 다음 질문
6. 사용자가 의미를 확인하면 문답 기록의 `Confirmed` 항목으로 올린다. `추천 전체 승인`처럼 묶음을 한 번에 승인한 답변은 각 질문의 추천 선택을 개별 결정으로 풀어 기록한다.

짧은 답변을 임의로 완성된 규칙으로 확대하지 않는다. 수치, 보상, 실패 손실, 공간 규모, 애니메이션 시간처럼 플레이 의미를 바꾸는 항목은 해석을 다시 보여주고 확인받는다.

### Synty 자산·H 동반 설계 관문

문답에서 건물, 시설, 지형, 도구, 작물, 실내외 소품, 작업 상태처럼 Unity에서 구체적으로 보여야 하는 대상이 발견되면 해당 질문을 답변만으로 닫지 않는다. 다음의 짧은 동반 조사를 수행하고 결과를 같은 문답 기록 또는 연결된 배치 연구에 남긴다.

```text
플레이어가 보아야 할 의미·상태 차이
  -> 필요한 표현 역할
  -> 보유 Synty 실제 Prefab·자산 계열 조사
  -> 직접 사용 / 조합 가능 / 부족 / 보류 판정
  -> H1 기능 공간과 배치 객체 조립안
  -> H2 동선·서비스·생활 관계
  -> H3 반복 폐루프·영역 정체성·성장 관계
  -> VisualKey·fallback·검증 조건
```

- 팩 이름을 Farm·Town·City 같은 게임 영역 권위로 사용하지 않는다. 실제 Prefab 증거와 기능 역할을 먼저 본다.
- `H1`은 플레이어가 직접 사용하거나 판독하는 최소 기능 공간, `H2`는 여러 H1의 동선·서비스 관계, `H3`는 여러 H2가 반복 폐루프와 영역 정체성을 만드는 조합으로 기록한다.
- 하나의 Prefab이 H가 되는 것은 아니다. 여러 자산이 기능·동선·상태 차이를 함께 표현할 때 H 조립 후보가 된다.
- 자산이 충분하면 승인 후보 `assetFamilyId`와 `VisualKey`를 남기고, 부족하면 억지 대체하지 않고 `CompositeRequired`, `DedicatedAssetRequired`, `NeedsReview` 중 하나로 남긴다.
- Synty 원본은 수정하지 않는다. 프로젝트 고유 조합 Prefab과 배치 계획은 원본 GUID·출처·구성 revision을 참조한다.
- 자산 조사는 표현 가능성의 근거일 뿐 H 승인, Scene 배치 또는 E 증거가 아니다. 실제 조립·통행·상태 판독은 별도 연구와 Runtime 증거로 검증한다.
- 같은 질문에서 자산 후보가 명확하면 가벼운 재고 조사로 닫고, 조합 치수·통행·충돌·상태 변화가 플레이를 좌우하면 배치 전문 연구를 `Required`로 분기한다.

### 추천 선택지의 Synty 기반 기획 이미지

공간·건물·Actor·도구·실내외 배치처럼 글만으로 형태와 규모를 상상하기 어려운 질문에서는, 추천 선택지를 설명하는 저해상도 기획 이미지를 함께 제시할 수 있다. 이 이미지는 이후 개발 스레드가 목표 형태와 배치 의도를 이해하는 참고 자료이며 실제 Prefab 조립·Scene 저장·Game View 증거를 대신하지 않는다.

- 이미지 생성 전에 현재 설치된 Synty Prefab과 승인 후보 `assetFamilyId`를 먼저 조사한다. 구매했지만 아직 임포트하지 않은 팩은 공식 구성에 근거한 `PurchasedNotImported` 후보로 분리하고 실제 보유 경로나 GUID를 추정하지 않는다.
- 보유 Synty 자산으로 충분히 조립 가능한 추천안만 이미지화한다. 전용 자산·고급 Shader·새 팩이 없으면 성립하지 않는 형태는 기본 추천안으로 만들지 않는다.
- 프롬프트에는 실제 후보 자산의 기능 역할과 조립 가능한 범위를 적고, 원본 마케팅 이미지를 그대로 복제하거나 존재하지 않는 Prefab을 보유 자산처럼 그리지 않는다.
- 생성 이미지에는 `기획 이미지`, `실제 Scene·Game View 미검증` 경계를 명시한다. 이미지의 건물 크기·통행 폭·Collider·상호작용 위치는 배치 전문 연구와 Runtime 검증 전까지 권위 수치가 아니다.
- 사용자가 선택을 확정해 이후 구현 참고 자료가 되면 `docs/assets/planning/` 아래에 보존하고, 문답 기록에 질문 ID, 선택 번호, 이미지 경로, 참고 화면, Synty 후보 계열, 프롬프트 요약, 알려진 차이를 남긴다.
- 실제 팩 임포트 뒤에는 Prefab Gallery 또는 canonical `SimulationWorldShell`의 저장 Scene 캡처를 참고 자료로 다시 사용한다. 새 기획 이미지가 이전 선택의 의미를 바꾸면 같은 질문의 새 revision으로 재확인한다.
- 이미지가 유용하지 않은 Simulation 수치·권위·Save·API 질문에는 억지로 이미지를 만들지 않는다. 추천안을 시각적으로 판독하는 데 도움이 되는 질문에만 사용한다.

## 질문 식별자와 탐구 깊이

깊이와 Evidence 준비 관계의 기계 단일 원본은 `eng/execution-ledgers/playable-loop-inquiry-depths.json`, 생성 상태판은 [PlayableLoop 문답 깊이와 Evidence 준비 관계](../AI/generated/playable-loop-inquiry-depths.md)다.

새 질문은 다음의 사람이 읽는 식별자를 사용한다.

```text
Q-{주제Code}-D{깊이}-{주제내연번} · 전체 Q-{전체연번}
```

예시는 다음과 같다.

```text
Q-병영-D1-01 · 전체 Q-223
Q-병영-D2-03 · 전체 Q-227
Q-Farm농지-D4-02 · 전체 Q-241
```

- `주제Code`는 `병영`, `Farm농지`, `공동체마음`, `회랑방위`처럼 사용자가 즉시 알아볼 수 있는 짧은 한국어 이름을 우선한다.
- `D1~D5`는 문답의 **탐구 깊이**다. Evidence와 동일한 단계는 아니지만 각 깊이는 아래의 `예상 E 준비 범위`를 가진다. 질문 답변은 해당 E의 작업 명세를 준비할 뿐 코드·시험·Runtime 증거 없이 E를 자동 승격하지 않는다.
- `주제내연번`은 같은 주제 안에서 질문 진행량을 보여 주며 두 자리 이상으로 증가시킨다.
- `전체연번`은 프로젝트 전체 문답량과 과거 `Q-001` 참조를 잇는 호환 번호다. 한 번 부여한 전체 번호는 문서 이동이나 주제 재분류 때문에 바꾸지 않는다.
- 기존 `Q-001` 형식의 질문은 그대로 유효하다. 주제별 문서로 이관할 때 새 식별자를 별칭으로 추가할 수 있지만 기존 ID를 삭제하거나 재번호화하지 않는다.
- 확인된 질문의 깊이를 나중에 바꿔야 하면 기존 ID를 조용히 수정하지 않는다. 새 깊이에서 후속 질문을 만들고 `Superseded` 또는 연결 참조를 남긴다.

### 전체 Q 번호와 실제 구현 순서의 분리

`전체 Q-001~`은 질문이 생긴 시간과 결정의 출처를 찾는 **추적 색인**이면서, WI 후보를 빠짐없이 찾는 첫 순회의 순서다. `Q-001 → Q-339`로 한 번 순회해 기존 WI, 새 WI 후보, 직접 WI가 아닌 공통 규칙을 분류한다. 다만 이 번호를 그대로 코드 구현 우선순위로 사용하거나, 질문 하나를 코드 기능 하나로 만들지는 않는다.

실제 구현은 다음 순서로만 선택한다.

```text
Q-001부터 Q-339까지 순차 순회
  -> 기존 WI / 신규 WI 후보 / 직접 WI 없음 추출
  -> 같은 의미의 WI 후보를 StableId로 정규화·통합
  -> 질문을 추출된 WI별 근거 묶음으로 다시 결속
  -> 등록·승인된 현재 PlayableUnit·WI 하나 선택
  -> E7에서 E1까지 영향·누락 검토
  -> 가장 이른 미완료 책임에서 조립 시작
  -> Logic·Presentation을 오가며 코드·시험·Runtime·Evidence 검증
  -> 새 누락이 드러나면 가장 이른 영향 E를 다시 열고 반복
```

따라서 **질문 추출은 번호순**, **구현과 증명은 WI 의존성과 E 피드백 순환**이다. Q 번호가 연속이어도 다른 PlayableLoop·WI에 속하면 같은 구현 묶음이 아니다. 반대로 떨어진 번호라도 같은 승인 기획 revision과 동일 WI의 한 책임을 설명하면 하나의 작은 구현 묶음으로 합성할 수 있다. 최초 조립은 가장 이른 E에서 시작하지만 `E1→E7`을 한 번 직선으로 통과하지 않는다. Logic 또는 Presentation에서 계약·공간·피드백 누락이 드러나면 해당 책임의 가장 이른 E를 다시 열어 왕복한다.

활성 Goal과 무관한 후보 코드·시험은 원장에 `ParkedCandidate` 또는 `ImplementedParked`로 남길 수 있지만 활성 E를 올리거나 다음 번호 구현을 정당화하지 않는다. `Active` 작은 구현 묶음은 최대 하나이며, 승인 대기 중인 현재 묶음은 `WaitingForApprovedRevision`으로 기록해 코딩 WIP에 포함하지 않는다. `Q 순차 WI 추출`에서 발견된 신규 이름은 `plannedWorldInteractionIds`일 뿐, WI 권위 대장 등록·승인 기획 revision 전에는 구현 순환에 들어가지 않는다.

작은 구현 묶음의 `worldInteractionIds`에는 현재 WI 권위 대장에 등록된 ID만 적는다. 문답에서 책임은 확인됐지만 아직 등록·승인되지 않은 채집·제작·섭취 같은 행위는 `plannedWorldInteractionIds`로 분리한다. 생성 상태판은 이를 `planned:WI-*`로 표시하며, 이는 실제 계약·Runtime·E 증거나 WI WIP가 아니다. 현재 `Active` 또는 `WaitingForApprovedRevision` 묶음에는 planned WI를 넣을 수 없고, 기획 revision과 WI 등록을 마친 뒤에만 활성 묶음으로 전환한다.

탐구 깊이는 다음처럼 판정한다.

| 깊이 | 다루는 질문 | 예상 E 준비 범위 | 질문 뒤에도 별도로 필요한 증거 |
| --- | --- | --- | --- |
| `D1` | 존재 목적, 플레이어 약속, 첫 적용 영역과 역할 | Logic·Presentation `E1` 정의 준비 | 승인 기획 revision·hash와 E1 작업 명세 검증 |
| `D2` | 핵심 폐루프, 조작, 기본 규칙과 첫 임무 | Logic·Presentation `E2` 계약 준비 | 실제 Contract·Application·Unity 투영 코드와 경계 시험 |
| `D3` | 비용, 실패, 부상, 회복, 성장과 손익 | Logic `E3~E4`, Presentation `E3` 검증 준비 | 결정성·거부·회복 시험과 LocalProcess·RemoteHost 동등성 |
| `D4` | 건물, H 공간, 배치, Synty 자산, UI·애니메이션 | Presentation `E4`와 Logic·Presentation `E5` 착수 준비 | 후보 fingerprint, H 결속, 실제 Prefab·World 배치·Renderer·Collider·상태 발현 |
| `D5` | Save/Replay, NPC 연속성, 멀티플레이, 영역 통합과 Runtime 완료 조건 | `E6~E7` 작업 명세와 후속 `E8~E9` 캠페인 준비 | 실제 입력·Play Mode·Game View·Save 재진입·반복 안정성·사람 승인 |

문답 기록은 다음 네 값을 분리해 보여 준다.

```text
현재 문답 깊이: D3
예상 E 준비 범위: Logic E3~E4 / Presentation E3
저장소에서 실제 검증된 E: Logic E2 / Presentation E1 / 통합 E1
다음 차단: 결정성 시험과 실제 Unity 상태 사본 투영
```

- `예상 E 준비 범위`는 질문이 충분히 답변됐을 때 **어느 E 구현을 설계할 수 있는지**를 보여 주는 전망이다.
- `실제 검증된 E`는 `playable-loops.json`, 활성 E7 작업 명세와 EvidencePackage만을 읽어 표시한다.
- 전망보다 실제 E가 낮으면 구현·시험 공백이 있다는 뜻이고, 실제 E가 더 높으면 기존 구현을 새 기획 revision으로 재검증해야 하는지 확인한다.
- Logic과 Presentation의 예상 범위 및 실제 E를 따로 기록하고, 통합 E는 기존 원칙대로 두 실제 궤적 중 낮은 값으로만 판정한다.
- D4 질문이 모두 확인돼도 실제 Prefab과 H 결속이 없다면 Presentation E5가 아니다. D5 질문이 모두 확인돼도 Play Mode·Game View·Save 재진입이 없다면 E7·E8이 아니다.

질문 묶음 앞에는 현재 위치를 다음처럼 표시한다.

```text
[병영 기획 — 현재 깊이 D3/5]
확정: D1, D2
진행 중: D3
대기: D4, D5
예상 E 준비: Logic E3~E4 / Presentation E3
실제 검증 E: 미등록 또는 원장 조회값
다음 Evidence 차단: 결정성·거부·회복 시험
답변 형식: 1 3 2 2 1
```

깊이는 반드시 D1부터 한 번만 통과하는 선형 단계가 아니다. D4 자산 조사에서 기본 규칙 누락이 드러나면 같은 주제를 유지한 채 D2 또는 D3 질문으로 돌아간다.

## 질문 순서

질문은 아래 순서를 기본으로 하되 앞 답변에서 더 이른 책임이 다시 열리면 돌아갈 수 있다.

1. 플레이어 상황과 욕구
2. 반복하고 싶은 핵심 선택
3. 시간·자원·위험의 대가
4. 성공·실패·취소·후퇴·회복·귀환
5. WI 단일 책임과 발생원
6. 권위 상태·행위 기록·Save/Replay
7. H 공간 능력과 이동 흐름
8. 건물 유형·상태·성장
9. 실내·실외 배치와 상태 차이
10. 애니메이션·도구 접촉·Task 시간
11. UI·카메라·소리·피드백
12. LocalProcess·RemoteHost·외부 자료 경계
13. 실제 입력·Play Mode·Game View 완료 조건
14. 제외 범위와 다음 폐루프로의 반환

### 질문 균형과 세부 분기 예산

위 순서는 한 방향으로 끝까지 내려가는 체크리스트가 아니라 핵심 폐루프를 여러 관점에서 반복해 살피는 순환 기준이다. 한 답변에서 흥미로운 하위 체계가 열려도 그 체계만 계속 질문해 PlayableLoop 전체를 가리지 않는다.

- 같은 세부 시스템의 연속 질문은 기본적으로 세 개 이내로 제한한다.
- 세 질문 안에 남은 내용은 `확정 후보`, `전문 연구`, `후속 Extension`, `구현 가설`, `제외 범위` 중 하나에 귀속하고 핵심 폐루프 질문으로 돌아간다.
- 사용자가 특정 분야의 심화를 명시적으로 요청한 경우에만 연속 질문 예산을 늘리며, 이때도 원래 PlayableLoop와 별도 연구 분기를 구분한다.
- 질문을 고를 때 최근 질문의 분야 편중을 확인하고, 아직 다루지 않은 가장 이른 핵심 책임을 우선한다.
- 최소한 `상황·욕구`, `선택`, `대가`, `실패·회복·귀환`, `WI`, `H 공간`, `표현`, `저장·실행 경계`에 각각 후보가 생기기 전에는 한 성장축의 세부 수치 조정으로 들어가지 않는다.
- 3~5개 질문마다 만드는 중간 상태 사본에는 `질문 분야 분포`, `과도하게 깊어진 분기`, `다음에 돌아갈 핵심 책임`을 함께 기록한다.

균형 재정렬이 필요하면 새 질문을 바로 던지지 않고 현재 답변을 합성한 뒤 문답 상태를 잠시 `Synthesizing`으로 둔다. 다음 안전한 회차에 다른 책임의 질문 하나로 재개한다.

### Unity 게임 완성 구성요소 대장

질문 균형의 최종 기준은 주제별 질문 횟수가 아니라 **해당 PlayableLoop를 canonical Unity 게임에서 완성하는 데 필요한 구성요소의 공백**이다. 문답 기록은 아래 대장을 유지하고, 다음 질문은 단순 순환 순서가 아니라 플레이어 약속을 실제 게임으로 닫는 데 가장 먼저 필요한 빈 구성요소에서 고른다.

| 구성요소 | 기획에서 채울 내용 | 최종 구현·증거 |
| --- | --- | --- |
| 플레이어 경험·콘텐츠 | 상황·욕구·선택·대가·반복 이유·성공·실패·귀환 | 실제 플레이 흐름과 다음 선택 |
| Simulation 권위·규칙 | 소유 상태·판정식·시간·난수·Revision·Effect | LocalProcess·RemoteHost 동일 결과 |
| WI·Task 실행 | 발생원·Preview·Confirm·Task·취소·결과·행위 기록 | 같은 WI·Command·Revision 파이프라인 |
| 플레이어 조작·카메라 | 이동·선택·상호작용·입력·시점·조작권 반환 | 실제 Input System 조작 |

| 시험·Game View·빌드 | 단위·통합·실제 입력·화면·Build Settings·패키징 | EvidencePackage·대표 화면·실행 가능한 빌드 |

각 구성요소 상태는 `미질문`, `후보`, `전문연구필요`, `확정후보`, `기획반영`, `구현증거`, `Runtime증거`, `NotApplicable` 중 하나로 기록한다. `NotApplicable`에는 이유가 필요하다.

- 질문이 이미 충분한 구성요소를 다시 파고드는 것보다 가장 이른 차단 공백을 우선한다.
- 모든 칸을 같은 깊이로 만드는 것이 목적은 아니다. 해당 폐루프에 필요한 칸은 Runtime까지 닫고, 불필요한 칸은 사유 있는 `NotApplicable`로 닫는다.
- E/G/H/WI는 그대로 유지한다. 이 대장은 그것들을 대체하는 새 성숙도 축이 아니라 Unity 게임 완성 누락을 찾는 질문·인계용 관점이다.
- Logic이 높아도 조작·애니메이션·UI·Scene·Game View가 비어 있으면 질문과 완료 판정은 그 공백으로 이동한다.
- 문답이 합성될 때 이 대장의 `확정후보` 이상 항목을 기획서 절과 E7 작업 명세에 연결하고, 개발 뒤 `구현증거`와 `Runtime증거`는 별도 EvidencePackage가 갱신한다.

건물·공간·배치·애니메이션 질문이 단순 선택을 넘어 조사와 대안 비교를 요구하면 [전문 심화 연구 분기·재결속 체계](PlayableLoop전문심화연구분기재결속체계.md)의 `Required` 연구로 분기한다. 문답에서 전문 답을 추정해 `Accepted`로 처리하지 않는다.

### 개발 인계 판정

문답을 모두 닫을 때까지 개발을 무조건 미루지는 않는다. 3~5개 질문을 합성했거나 Unity 게임 완성 구성요소 하나가 `확정후보`에 도달하면, 현재 범위가 독립적인 구현 묶음으로 동결 가능한지 확인한다. 실제 승인·인계 조건과 인계 묶음은 [주제 기획 기반 PlayableLoop 개발 체계](주제기획기반PlayableLoop개발체계.md#장기-기획-goal과-실제-개발-스레드-인계)를 따른다.

문답 기록의 개발 인계 상태는 다음 중 하나다.

```text
NotReady -> ReadyToDispatch -> Dispatched -> EvidenceReturned
                                 |                  |
                                 +-> FeedbackRequired <-+
```

- `NotReady`: 핵심 미정, 승인 기획서, Accepted 연구, 활성 WI 또는 E7 작업 명세 중 하나 이상이 부족하다.
- `ReadyToDispatch`: 구현 범위와 제외 범위가 동결됐고 모든 기획 관문을 통과했다.
- `Dispatched`: 판본화된 인계 묶음을 개발 스레드에 보냈다. 대화 요약만 보낸 상태는 여기에 포함하지 않는다.
- `FeedbackRequired`: 구현 조사에서 플레이어 약속이나 연구 기준선을 다시 열어야 할 발견이 돌아왔다.
- `EvidenceReturned`: 개발 결과와 EvidencePackage를 읽어 인계 범위의 결과가 돌아왔음을 확인했다. 구현 완료나 E 승격 여부는 각 원장과 증거가 별도로 판정한다.

기획 스레드는 `Dispatched` 뒤에도 다른 구성요소나 다음 묶음의 문답을 계속할 수 있다. 다만 개발 중인 같은 WI·기획 revision의 의미를 조용히 바꾸지 않고, 변경 후보는 다음 revision 또는 `FeedbackRequired`로 기록한다.

## 문답 기록 상태

문답 기록은 다음 상태를 사용한다.

```text
Open -> Synthesizing -> Confirmed -> Incorporated -> Closed
```

- `Open`: 다음 질문이 있고 답변을 수집 중이다.
- `Synthesizing`: 답변 사이의 의미와 충돌을 정리 중이다.
- `Confirmed`: 사용자에게 다시 보여준 핵심 해석이 확인됐다.
- `Incorporated`: 확인된 결정이 특정 기획 revision에 반영됐다.
- `Closed`: 남은 미정이 기획서·전문 연구·제외 범위 중 하나에 모두 귀속됐다.

문답 기록은 E 단계가 아니다. `Confirmed`나 `Closed`도 기획서 `Approved`, 코드 구현 또는 Runtime 증거를 뜻하지 않는다.

## 저장과 재개

각 문답 기록은 다음을 가진다.

- `inquiryStableId`
- 대상 `topicStableId`와 `playableLoopStableId`
- 기록 revision과 상태
- 현재 질문 ID와 전체 호환 번호
- 현재 주제와 탐구 깊이
- 마지막으로 확인된 질문 ID와 전체 호환 번호
- 확정 후보, 확인된 결정, 미정, 충돌
- 전문 연구 분기 후보
- 반영 대상 `designRevision`
- 다음 질문

세부 질문·답변은 원문 전체를 복사하지 않고 게임 기획 의미로 요약한다. 표현 하나가 계약에 중요할 때만 짧은 원문을 보존한다. 대화가 끊기면 주제·깊이·현재 질문 ID·전체 호환 번호와 다음 질문을 기준으로 재개하며 이미 확인한 질문을 처음부터 반복하지 않는다.

3~5개 질문이 끝나거나 하나의 질문 분야가 닫힐 때마다 중간 상태 사본을 만든다.

```text
이번에 확인된 결정
남은 미정
새로 발견된 충돌
필요한 전문 연구
기획서에 반영한 절
다음 질문
```

## 기획서 합성 관문

문답을 주제 기획서로 합성하기 전에 다음을 확인한다.

1. 플레이어 약속과 반복 이유를 한 문장으로 설명할 수 있다.
2. 핵심 선택과 대가가 서로 대응한다.
3. 성공·실패·회복·귀환이 끊기지 않는다.
4. WI 후보가 한 번에 하나의 권위 책임을 가진다.
5. Logic과 Presentation 요구가 구분된다.
6. H와 전문 심화 연구 필요성이 판정됐다.
7. Save/Replay·Local/Remote·외부 효과 경계가 정해졌다.
8. 미정 항목이 승인 차단, 전문 연구, 구현 가설 또는 제외 범위로 분류됐다.
9. 사용자가 핵심 해석을 확인했다.

합성된 문답 기록은 기획서의 `sourcePlanningDocumentRefs`에 연결한다. 기획서는 확인된 결정만 규칙으로 사용하고 미정·가설을 완료된 사실처럼 바꾸지 않는다.

## 질문 작성 원칙

- “어떻게 할까요?”보다 현재 결정해야 할 차이를 드러내는 질문을 쓴다.
- 구현 기술보다 먼저 플레이어가 보고 선택하고 잃고 얻고 돌아오는 경험을 묻는다.
- 답변에 모순이 있으면 맞춰 쓰지 않고 두 해석을 나란히 보여준다.
- 이전 답을 바꾸는 것은 허용한다. 바뀐 결정은 새 기록 revision으로 남기고 영향받는 기획·연구를 다시 연다.
- 답변하지 않은 침묵, 대화 종료 또는 짧은 동의 표현만으로 전체 기획을 승인하지 않는다.
