# 세계 상호작용 단위 중심 공간–Simulation 통합

상태: 첫 감자 생산→Hub 보관 인과선 E3 구현됨, 경관 그래프 공간 승격 대기
기준일: 2026-08-17

## 1. 목적

이 문서는 공간과 Simulation을 별도 기반 시설로 먼저 완성하지 않고, 세계에서 실제로 이어지는 행위 하나를 처음부터 끝까지 완결하는 구현 기준을 정한다.

핵심 문장은 다음과 같다.

> 공간은 무엇이 가능한지를 제공하고, Simulation은 그 가능성 안에서 무엇이 실제로 일어났는지를 결정한다.

`WI`는 세계 상호작용 단위의 작업 식별자다. 새 업무 엔티티나 공개 API가 아니며, 기존 결정–작업–효과를 공간·행위자·자원·시간·저장·Unity까지 종단 검증하기 위한 설계·실행 원장 단위다.

기본 구현 완료선은 `E3`다. 계약과 서버 코드, 자동 시험, 시험 HTTP 호스트, 저장·재생을 닫으면 구현은 완료로 기록한다. 이후에는 `E4` 실제 의미 공간 귀속, `E5` 이동 가능한 경관 조직, `E6` WI 필수 공공데이터 경관 연결, `E7` 실제 플레이 폐루프로 승격한다. 두 상태를 한 완료 표시에 섞지 않는다. 전체 37개 단위의 최신 계약과 증거는 [세계 상호작용 단위 대장](../AI/generated/world-interaction-catalog.md)에서 확인한다.

### 증거·승격 단계

| 단계 | 의미 | 완료 관문 |
| --- | --- | --- |
| E3 | 행위 구현 | 계약·서버 코드·자동 시험·시험 HTTP·저장 재생이 닫힌다. |
| E4 | 실제 의미 공간 귀속 | WI가 실제 `LandscapeGraph` Node의 역할·능력·용량에 연결되고 필수 선후행 공간 전이가 닫힌다. `Scenario` 공간만으로는 통과하지 않는다. |
| E5 | 이동 가능한 경관 조직 | 도로·교차로·Gate가 만든 Block에 공간 역할과 `LandscapePattern`을 배정하고 WI 공간 사이 경로를 결정적으로 확인한다. 사람의 Play Mode 조작은 아직 요구하지 않는다. |
| E6 | WI 필수 공공데이터 경관 연결 | 선정 WI의 공간 판정에 필요한 공공데이터만 E5 경관에 연결하고 출처·기준일·좌표계·원본과 파생 hash·한계를 보존한다. 관계없는 자료의 부재는 차단하지 않는다. |
| E7 | 실제 플레이 폐루프 | 사람이 `SimulationWorldShell`과 실제 서버에서 이동·선택·Preview·Confirm·Tick·재조회를 수행하고 Game View와 Console로 확인한다. 자동 전이는 부모 명령 뒤 관찰한다. |

E6의 공공데이터는 실제 공간을 제약하는 근거이지 행위 결과의 최종 결정 권한이 아니다. E7에서도 Unity는 입력과 표현만 담당하고 성공·효과·개정은 서버 상태 재조회로 확인한다. 패키징 빌드·배포·운영 공개는 E7의 기본 완료 조건에 포함하지 않는다.

## 2. 권위와 책임

```text
AreaSet 지역 세계 의도
        ↓
경관 그래프 공간 정의 ── 공간 능력·기본 용량
        ↕
Simulation 공간 요구 ── 현재 Session 공간 상태
        ↓
미리보기 → 명시적 확정 → 예약 → 작업 → 효과
        ↓
상태 사본·저장·재생
        ↓
Unity + Synty 표현
```

- AreaSet은 지역 세계의 의도와 경관 그래프 관계를 선언한다.
- 경관 그래프는 위치·연결·형태와 승인된 공간 능력을 제공한다.
- Simulation 규칙은 행위에 필요한 공간 능력과 용량을 서버에서 결정한다.
- Session은 점유·예약·접근과 활성 작업 같은 가변 공간 상태를 가진다.
- Unity와 Synty는 선택된 공간, 차단, 예약, 진행과 완료를 표현하지만 업무 상태를 확정하지 않는다.

공간 정의에는 Prefab 이름, GUID, Unity 경로와 Synty 팩 이름을 넣지 않는다. 클라이언트도 필요한 능력·용량·기간을 보내지 않는다. 클라이언트가 보낼 수 있는 공간 선택 값은 선택적 `PreferredSpatialStableId`뿐이며, 부적합할 때 서버가 다른 공간으로 몰래 대체하지 않는다.

## 3. 세계 상호작용 단위

하나의 단위는 다음 흐름을 함께 닫는다.

```text
세계 행위
→ 서버 ActionCode
→ 행위자 조건
→ 공간 요구
→ 공간 후보와 현재 상태
→ 미리보기
→ 명시적 확정
→ 자원·공간 예약
→ 작업 진행
→ 효과
→ 공간·재고 상태 변화
→ 상태 사본
→ 저장·재생
→ HTTP
→ Unity 표현
```

공통 기반은 두 개 이상의 실제 단위에서 반복이 확인될 때만 추출한다. 단일 행위에만 필요한 추상화를 먼저 범용 체계로 올리지 않는다.

## 5. 고정 정의와 Session 가변 상태

공간 정의와 현재 사용 상태를 분리한다.

### 공간 정의

- 공간·시설·AreaSet·경관 그래프·경관 노드 고유 식별자
- 근거 종류와 원본 참조
- 능력 코드
- 기본 용량
- 정의 개정과 SHA-256

### Session 공간 상태

- 접근 상태
- 사용 중 용량
- 예약 용량
- 활성 작업 식별자
- 상태 개정

가용 용량은 별도 권위 값으로 저장하지 않고 `기본 용량 - 사용 중 - 예약`으로 계산한다. 공간 상태는 별도 Simulation이나 별도 공간 개정을 만들지 않고 기존 Session의 `WorldRevision`으로 보호한다.

## 6. WI-001 진부 Hub 입고 검수

세계 행위는 “도착한 화물을 담당 NPC가 진부 Hub에서 검수한다”이다.

| 항목 | 구현 계약 |
| --- | --- |
| 서버 행위 | `WarehouseInboundInspection` |
| 필수 공간 능력 | 화물 접근, 작업자 접근, 검수 작업 영역 |
| 예약 | `WorkArea` 1자리 |
| 완료 전 재고 | `PendingInspection` |
| 완료 후 재고 | `StorageEligible` |
| 완료 공간 변화 | 작업 영역 예약 해제 |

미리보기는 Cargo, NPC, 공간 능력, 접근, 예약 충돌과 현재 개정을 함께 검사하고 상태를 바꾸지 않는다. 확정은 결정·작업·NPC 배정·기존 자원 예약·공간 예약을 하나의 Session 변경으로 등록한다. 완료 Tick에서 재고를 보관 가능 상태로 바꾸고 작업 영역을 반환한다.

## 7. WI-002 진부 Hub 창고 적재

세계 행위는 “검수를 마친 재고를 진부 Hub 창고에 적재한다”이다.

| 항목 | 구현 계약 |
| --- | --- |
| 서버 행위 | `WarehouseStorageMove` |
| 필수 공간 능력 | 보관, 화물 접근, 작업자 접근, 적재 작업 영역 |
| 예약 | 재고 수량만큼 `StorageCapacity`, `WorkArea` 1자리 |
| 완료 전 재고 | `StorageEligible` |
| 완료 후 재고 | `PutAwayCompleted` |
| 완료 공간 변화 | 보관 예약을 사용 중 용량으로 전환, 작업 영역 해제 |

확정 뒤에는 같은 보관 용량과 작업 영역을 다른 활성 작업이 중복 사용할 수 없다. 완료하면 보관 예약량은 0이 되고 사용 중 보관량이 증가한다.

## 7.1 첫 E3 공급선: 감자 300kg 생산에서 Hub 보관까지

첫 확장 단위는 별도 범용 기반 시설을 먼저 만들지 않고 다음 실제 인과선을 닫았다.

```text
WI-FARM-04 수확
→ WI-FARM-05 집하
→ WI-FARM-06 출하 준비·포장
→ WI-LOG-01 상차
→ WI-LOG-02 Farm 출발
→ WI-LOG-03 Farm→Hub 이동
→ WI-LOG-04 Hub 하차
→ WI-LOG-05 Hub 인수
→ WI-001 입고 검수
→ WI-002 창고 적재
```

시나리오 Fixture는 재배 면적 100m², 기준 생산량 3kg/m²와 보정 계수 1을 사용해 300kg을 결정적으로 만든다. 이 수치는 실제 평창 생산량이 아니라 규칙·계보·예약을 검증하기 위한 시험 값이다. 수확 결과는 `수확 Lot → 포장 Lot → Cargo → 출하 배분 → 화물 운송 → Hub 재고` 계보를 유지한다.

화물 이동은 하나의 공간으로 축약하지 않는다.

| 공간 역할 | 요구 능력 | 예약·해제 |
| --- | --- | --- |
| 출발지 상차 | 상차 영역, 차량·화물·작업자 접근 | 작업 영역 1자리, 출발 Tick에 해제 |
| 운송 회랑 | 화물 이동 회랑 | 첫 개정은 용량 예약 없이 적합성만 확인 |
| 목적지 하차 | 하차 영역, 화물·작업자 접근 | 작업 영역 1자리, 도착 Tick에 해제 |

각 역할은 선택적 선호 공간 고유 식별자를 독립적으로 받는다. 선호 공간이 부적합하면 다른 공간으로 자동 대체하지 않는다. 필요한 능력과 예약량은 클라이언트가 보내지 않고 `CargoRouteMovement` 서버 규칙이 정한다.

## 8. 미리보기·확정·취소

- 미리보기 전후에는 Tick, 개정, 작업, 재고, NPC 배정, 공간 상태와 예약이 같아야 한다.
- 확정은 기존 예상 개정과 명령 멱등성 규칙을 그대로 사용한다.
- 같은 `CommandId`와 같은 내용의 재전송은 같은 결과를 반환한다.
- 낮은 예상 개정은 거부한다.
- 취소는 예정 또는 차단된 작업에서만 허용하며 해당 작업 계보의 예약·NPC 배정·임시 재고만 되돌린다.
- 입고 검수 취소는 그 작업이 만든 검수 대기 재고만 제거한다.
- 창고 적재 취소는 보관·작업 영역 예약을 반환하지만 이미 검수된 `StorageEligible` 재고는 유지한다.

취소 API는 다음 경로를 사용한다.

```text
POST /api/simulation/v1/sessions/{sessionStableId}/tasks/{taskStableId}/cancel
```

요청은 `CommandId`, `ExpectedRevision`, `ReasonCode`만 가진다.

## 9. 저장·재생

공간 정의가 없는 기존 Session은 `simulation-save.v1` 형식과 기존 재생 해시를 유지한다. 공간 정의·상태·예약 또는 작업 취소 계보가 필요한 Session은 `simulation-save.v2`로 저장한다.

동일한 Session seed, 명령 로그, 공간 정의와 규칙 개정에서는 공간 점유·예약·재고·작업을 포함한 최종 상태와 재생 해시가 같아야 한다. 기존 v1 자료도 계속 읽고 재생할 수 있다.

## 10. 두 공간 근거 관문

### 관문 1: 시나리오 공간 근거 — 구현됨

현재 진부 Hub와 Farm–Hub 회랑 경관 그래프에는 이 업무에 사용할 승인된 실제 조립 노드가 없다. 첫 공급선은 다음 시나리오 공간으로 규칙을 종단 연결한다.

| 공간 | 능력·용량 | 근거 |
| --- | --- | --- |
| 검수 공간 | 화물 접근, 작업자 접근, 검수 영역 1자리 | `Scenario` |
| 창고 | 보관 10,000kg, 적재 영역 1자리, 화물·작업자 접근 | `Scenario` |
| 농장 수확·집하·포장 공간 | 각 작업 능력과 작업 영역 1자리 | `Scenario` |
| 농장 상차 공간 | 상차, 차량·화물·작업자 접근, 작업 영역 1자리 | `Scenario` |
| Farm–Hub 회랑 | 화물 이동 회랑 | `Scenario` |
| Hub 하차 공간 | 하차, 화물·작업자 접근, 작업 영역 1자리 | `Scenario` |

이 값은 공공데이터가 증명한 실제 건물·도로·작업 면적이라고 표현하지 않는다.

### 관문 2: 경관 그래프 공간 근거 — 대관령 Farm 일부 진행

`spatial-capabilities.v1.json`은 공간 역할, 필요한 능력, 작업 용량과 근거를 WI별로 승인한다. 현재 대관령 Farm의 `agriculture-region` Node를 생산구획으로 사용해 WI-FARM-01~03의 공간 폐루프를 닫았다. WI-FARM-04 수확은 결과를 넘길 작업마당이 없어 차단하며 Scenario로 자동 대체하지 않는다. 진부 Hub의 실제 경관 노드는 계속 대기 상태다.

승격 조건은 다음과 같다.

1. AreaSet과 진부 Hub 경관 그래프 개정·해시가 확정된다.
2. 실제 경관 노드의 위치·연결·공간 역할이 조립된다.
3. 공간 능력과 기본 용량의 근거·검토 상태가 승인된다.
4. 같은 WI 자동 시험·HTTP·저장·재생을 경관 그래프 근거로 다시 통과한다.
5. Unity에서 근거 종류가 “경관 그래프 공간 근거”로 표시된다.

`1 slot`은 실제 면적이 아니라 한 WI를 동시에 한 건 수행할 수 있다는 Simulation 작업 용량이다. 실제 사용 가능 면적이 확보되면 별도 용량 규칙 개정으로 다시 계산한다.

## 11. Unity 표현

Unity 진부 Hub 입고 정보판은 서버 미리보기에서 선택한 공간 고유 식별자와 근거 종류를 읽는다. 시나리오 근거와 경관 그래프 근거를 구분하고, 공간 정의 없음·능력 부족·용량 부족·접근 불가·예약 충돌을 한국어로 표시한다.

NPC 이동과 작업 애니메이션, 창고 상자 표현은 서버 상태의 결과다. 애니메이션 종료나 GameObject 상태로 작업 완료·재고·공간 점유를 역추론하지 않는다.

## 13. 우선순위와 다음 확장 순서

작업은 `P0 핵심 인과선 → P1 세계 공통 규칙 → P2 원장·문서 일치 → P3 전체 회귀·빌드`로 나눈다. E4~E7 공간 귀속·경관 조직·공공데이터·실제 플레이 승격은 대표 WI를 별도 선정하는 후속 작업이다.

다음 항목은 E3로 승격했으며, 후속에서는 동일 순서로 E4~E7 대표 흐름을 선정한다.

1. 밭갈기·파종·관수와 재배 관리
2. Hub 출고 요청·피킹·출고 준비
3. Hub에서 Town으로 운송
4. 마트 입고·진열
5. 주민 주문·수령·소비

공간 능력 대장은 이 단위들이 실제로 요구할 때만 확장한다. `LandscapePattern`은 공간 패턴 설계가 정식 계약으로 확정되기 전까지 이 구현의 선행 조건으로 만들지 않는다.
