# 기획 원자 분해와 E1 조립 체계

## 목적

여러 이야기·시스템·공간 결정을 포함한 기획 문서를 그대로 E1이라고 부르지 않는다. 기획을 검증 가능한 `플레이 원자 계약 모듈`로 나누고, 필수 모듈의 순서·분기·실패·회복·귀환을 조립해 한 `PlayableUnit`의 Logic·Presentation E1을 성립시킨다.

기계 판독 입력은 검토 전 초안인 [`playable-loop-planning-atomic-e1-outlines.json`](../../eng/execution-ledgers/playable-loop-planning-atomic-e1-outlines.json)과 계약 검토를 마친 [`playable-loop-planning-atomic-e1-modules.json`](../../eng/execution-ledgers/playable-loop-planning-atomic-e1-modules.json)로 나눈다. 전체 기획의 분해 상태는 [기획–E1 결속 인덱스](../AI/generated/playable-loop-planning-e1-index.md)에서 조회한다.

## 원자성 정의

플레이 원자 계약 모듈은 다음을 하나씩 가진다.

1. 플레이어 의도
2. 주된 권위 상태 전이 계보
3. 원인·상관관계 revision
4. 결과 재조회
5. 실패·중단·복구 경계
6. 다음 선택으로 돌아가는 상태

DB 쓰기가 한 번이라는 뜻은 아니다. `확정 → 진행 Task → 완료 Effect`처럼 새 플레이어 선택 없이 같은 상관관계로 닫히는 비동기 행동은 하나의 원자 모듈이 될 수 있다. 중간에 새 선택, 독립 권위 확정, 별도 보상 또는 다른 실패 복구가 생기면 모듈을 나눈다.

## 공식 절차

### 1. 기획 원본 동결

- `PLAN-*`, 문서 경로, revision, hash와 상태를 확인한다.
- 미답변·가정·후속 연구를 확정 계약과 분리한다.
- 같은 의미의 기존 기획·WI·PlayableUnit을 먼저 찾는다.

### 2. 플레이 결과 문장 추출

기획에서 플레이어가 직접 알아차리거나 선택하고, 세계 상태가 달라지며, 다음 선택으로 이어지는 문장만 추출한다. 이야기 설명·분위기·자료 조사·관리 절차는 `SupportingContext` 또는 `NoDirectE1Impact`로 남긴다.

### 3. 원자성 검사와 분해

각 후보에 다음 질문을 적용한다.

- 플레이어 의도가 하나인가?
- 권위 상태 전이 계보가 하나인가?
- 새 선택 없이 완료되는가?
- 성공과 실패가 함께 설명되는가?
- 완료 뒤 다시 무엇을 선택할 수 있는가?

하나라도 둘 이상이면 나눈다. 결과 상태가 없는 관찰도 후속 선택을 여는 독립 조회 계약이면 원자 모듈이 될 수 있다.

### 4. WI 대조

- 의미와 권위 경계가 같은 WI가 있으면 재사용한다.
- 일부만 같으면 `PartiallyReused`로 두고 빠진 계약을 기록한다.
- 없으면 WI를 즉시 만들지 않고 `Candidate`와 필요한 책임만 기록한다.
- 하나의 모듈에는 주된 WI 하나만 둔다. 보조 조회·표현 WI는 참조로만 연결한다.

### 5. Logic·Presentation E1 계약 작성

- Logic: 진입 상태, Preview, Confirm/Task/Effect, 읽기·쓰기 권위, 멱등성, 오류, 성공, 실패·회복, 귀환
- Presentation: 플레이어가 판독할 순간, Actor·대상·행동 표현, 상태 사본·행위 기록 소비, 권위 불변, 실패·완료 피드백

두 궤적 중 하나라도 비어 있으면 원자 모듈은 E1 조립 입력이 될 수 있지만 통합 E1은 성립하지 않는다.

### 6. E1 조립

필수 원자 모듈, 선택 모듈, 순서·분기, 공유 revision, 최종 성공·회복·귀환을 `E1Assembly`로 묶는다. 기존 PlayableUnit을 재사용할 수 없고 독립 플레이어 약속이 명확할 때만 새 PlayableUnit 후보를 제안한다.

```text
기획 문서
  → 플레이 원자 계약 모듈 여러 개
    → WI 재사용 또는 후보
      → E1Assembly
        → 승인된 PlayableUnit의 Logic E1 + Presentation E1
```

### 7. 리뷰와 인계

- 기획: 의미·선택·대가·성공·실패·회복·귀환 승인
- 개발: WI·권위·저장·오류 계약 검토
- 공간·표현: H·Graph Map·배치 맵·자산·판독 계약 검토
- 통합: 같은 revision에서 필수 모듈과 두 궤적이 닫혔는지 판정

승인 전 모듈·조립안은 코드·Scene·실제 배치·E 승격 권한이 아니다.

## 하나씩 닫는 기본 운영

원자 분해 이후의 기본 개발 순서는 `원자 폐쇄 대상 하나`를 주 목표로 고르는 것이다. 기존 WI를 정확히 재사용할 수 있고, 승인 기획 관문을 갖추며, 열린 계약 결손이 적고, 실패·회복·귀환이 분명한 후보를 먼저 고른다. 선택한 대상은 E1 계약부터 E7 실제 입력 완주까지 올리거나, 더 이른 단계의 정확한 차단 사유를 남긴 뒤에만 다음 우선 대상으로 이동한다.

원자 모듈 하나마다 새 `PlayableUnit`을 만드는 것은 아니다. 독립된 플레이어 약속과 시작·성공·실패·귀환이 스스로 닫힐 때는 기존 또는 새 `PlayableUnit`의 후보가 될 수 있고, 그렇지 않으면 여러 원자 모듈을 기존 `PlayableUnit` 안에서 조립한다. `미리보기 → 명시적 확정`처럼 새 플레이어 선택이 생기는 경계는 분리하되, 확정 뒤 같은 상관관계로 이어지는 Task·완료·결과 재조회는 한 원자 모듈로 유지할 수 있다.

이 기본 운영은 현재 기획 흐름의 주 목표를 하나씩 선명하게 닫기 위한 것이며, 서로 다른 파일과 권위를 가진 독립 작업까지 전역적으로 하나만 허용하는 WIP 제한은 아니다. 병렬 작업 결과도 현재 원자 폐쇄 대상의 동일 revision·계약에 합쳐질 때만 그 대상의 E를 높일 수 있다.

## E1~E7에서의 소비

| 단계 | 원자 모듈 | 조립된 PlayableUnit |
| --- | --- | --- |
| E1 | 입력·상태 전이·실패·복구 계약 | 필수 모듈·순서·분기·최종 귀환 |
| E2 | 구현과 Adapter | 모듈 간 인계 구현 |
| E3 | 결정성·멱등성·저장 시험 | 순서·중단·재조립 시험 |
| E4 | Actor·대상·시간·H·표현 후보 | Graph Map·배치 맵 전체 문맥 |
| E5 | 권위 상태와 실제 표현 발현 | 모듈 간 실제 결과 인계 |
| E6 | 개별 의미·피드백 정제 | 전체 인과·속도·실패·귀환 정제 |
| E7 | 실제 입력으로 원자 행동 완료 | 시작부터 다음 선택까지 완주 |

원자 모듈 하나의 E7 성공은 전체 PlayableUnit E7이 아니다. 반대로 상위 실행이 우연히 성공해도 필수 원자 모듈의 하위 계약 결손을 덮을 수 없다.

## 오행 공동 준비 묶음과 함께 성장하는 E5~E7

같은 생활 영역의 원자 WI가 동일한 시간·공간·도구·Actor·표현 후보를 반복 사용한다면 하나만 E7까지 직렬로 올리기보다 `AtomicClosureCohort`로 묶을 수 있다. 묶음은 공통 오행 문맥과 Presentation E4 자료를 한 번 정리하고, E5·E6·E7 실행을 파동별로 조율하는 효율 단위다.

- E1~E4: 괘성 분류, 계절·상태 데이터, H·Graph Map·배치 맵, 도구·Actor·자산 후보, 기준점·접근·통행·피드백을 공유한다.
- E5~E7: 같은 Farm 판본과 공간 문맥을 재사용하되 각 WI의 실제 배치·입력·권위 결과·귀환 증거는 독립 판정한다.
- E5 진입 전: 해당 WI에 적용되는 오행 분류와 상생·상극 관계, WI 판본과 표현 후보 판본을 E4 준비 묶음에서 동결한다. 관계가 적용되지 않으면 사유를 남긴다.
- 묶음의 표시 단계는 구성 WI의 평균이나 최고값이 아니라 **가장 낮은 단계**다. 한 WI의 성공으로 나머지를 승격하지 않는다.
- 다섯 괘를 모든 WI에 억지로 채우지 않는다. 직접 필요한 괘는 WI에 붙이고, 역할·약속·회복처럼 아직 별도 계약이 필요한 괘는 `SupportingGap`으로 남긴다.
- 기존 PlayableUnit과 WI 안정 식별자를 유지한다. 묶음은 새 권위·새 성숙도 축·새 PlayableUnit이 아니다.

첫 표본 `atomic-closure-cohort:farm-life-five-elements.v1`은 `WI-FARM-01~06`을 포괄한다. 경작·파종·생육·수확은 첫 개발 파동, 집하·포장은 두 번째 파동으로 두며, 두 기존 PlayableUnit의 독립 성공·실패·귀환 계약을 합치지 않는다.

## 기존 기획 전환

현행 기획 목차 순서를 보존하며 다음 상태로 전수 관리한다.

- `ReviewedAtomicModules`: 실제 원자 모듈과 조립안이 검토됨
- `OutlinedAtomicCandidates`: 본문을 플레이 결과 후보로 1차 분해했지만 WI·권위·실패·귀환 계약 검토는 남음
- `NeedsAtomicReview`: 기존 WI/E1 근거는 있으나 원자 분해가 미완료
- `NeedsDecomposition`: 플레이 기획이나 아직 E1/WI 결속이 없음
- `ContextOnly`: 공통 원칙·관리·자료·표현 조사로서 단독 원자 모듈을 만들지 않음

첫 표본은 `PLAN-STORY-FIRST-FARM-DISCOVERY-001`이다. 기존 `WI-NATURE-06`, `WI-NATURE-18`은 재사용하고, 울타리 관찰·전체 수리·이탈/사후 발견·재진입·첫 신뢰는 후보로 남긴다. 이 표본은 아직 승인 PlayableUnit 또는 E1 증거가 아니다.

두 번째 검토 표본은 `PLAN-PLACEMENT-CROSS-AREA-BUILDING-001`의 Farm 건물 배치 범위다. 검토 전의 청사진 선택·미리보기·확정·진행·확인 다섯 초안을 다음 세 계약으로 정리한다.

1. 청사진 하나와 배치 후보를 상태 변경 없이 검사한다. 기존 `WI-CON-01`의 Preview 계약을 부분 재사용한다.
2. 플레이어가 다시 확정하면 `WI-CON-01`의 같은 상관관계에서 예약·건설 진행·완료·결과 재조회까지 잇는다. 새 선택이 없는 비동기 진행을 억지로 별도 WI로 나누지 않는다.
3. 진행 중 취소는 새 플레이어 선택과 별도 복구 경계를 가지므로 `WI-WORLD-03`을 사용하는 선택 모듈로 분리한다.

`WI-FARM-01~04`는 경작·파종·생육·수확 계약이므로 건물 배치에 재사용하지 않는다. 조립 대상은 기존 `playable-loop:farm-player-placement.v1`이지만, 이 PlayableUnit의 승인 기획 문서·동결 revision/hash와 Farm 전용 `WI-CON-01` 권위 경계가 없으므로 조립안은 `Blocked`다. 원자 검토 완료는 이 공백을 숨기거나 E1을 성립시키지 않는다.

그 밖의 원자 분해 대상 기획은 먼저 `OutlinedAtomicCandidates`로 전수 분리한다. 이 초안은 누락과 중복을 찾는 검토 순서이며, `ReviewedAtomicModules`로 승격하기 전에는 새 WI·PlayableUnit·E1을 생성하지 않는다.
