# Unity 농사 환경 생육 턴 규칙 제안

- 상태: P0 `FARM-ENV-0`, P1 `NONGSARO-CROP-1`, P2 `KMA-WEATHER-1` 구현; 토양 관측 연결은 후속 Gate

- 적용 범위: 토양·햇빛·강수·작물 요구조건을 하루 단위 Simulation 턴으로 결합
- 비적용 범위: 실제 농업 처방, 수확량 예측, 운영 농장 자동 제어, Unity의 독자 판정

> 토양·공공자료 모판: [Unity 에셋 모판·공공데이터·토양자료 연결 제안](UnityAssetSeedbedPublicSoilDataProposal.md)  
> 권위 경계: [D-021, D-036, D-070, D-073~D-076](../AI/DECISIONS.md)

## 구현 현황

`FARM-ENV-0`은 기존 FARM-3 경과일 규칙을 바꾸지 않고 `Ssalddel.Unity`의 독립된 Fixture 계산기로 구현했다. 감자 환경 Rule, 토양 기준, 일별 기후, 재배 환경 일일 Snapshot, 생육·스트레스 State와 하루 판정 Result를 별도 계약으로 둔다.

정상·연속 건조·집중호우·저일사·공식 관측 결측 시나리오와 Fixture/공식 관측 혼합 차단을 검증했다. 이 단계에는 농사로 수치, 기상청 실관측, 토양 표본, 서버 Preview·Confirm API와 Unity Scene 표현이 포함되지 않는다.

`KMA-WEATHER-1`은 기상청 ASOS 일자료의 관측소·날짜 한 건을 서버에서 읽는 client와 공유 Snapshot을 구현했다. 평균·최저·최고기온, 일강수량, 합계일사, 합계일조, 가조일조시간, 평균상대습도를 서로 다른 관측항목으로 보존하고 원문 SHA-256, 단위, 품질, 조회시각, 지점 공간 한계를 함께 남긴다. 결측은 0으로 변환하지 않고 `Incomplete`로 표시하여 Simulation 사용을 차단한다. 농장과 관측소 거리는 외부에서 근거 URL이 있는 좌표 context를 제공한 경우에만 계산한다.

현재 User Secrets의 `PublicData:DataGoKrServiceKey`로 2026-08-10·서울 108 표본을 호출한 결과 HTTP 403이었다. 인앱 브라우저의 공공데이터포털 세션도 로그아웃 상태였으므로, 활용신청·승인 상태와 해당 key의 서비스 연결은 아직 실제 응답으로 검증하지 못했다. 코드의 정상 응답·결측·공간거리·지점 선택·D-1 차단·외부 오류 6건은 결정적 테스트로 검증했다.

`NONGSARO-CROP-1`에서는 기존 서버 농사로 client로 `farmWorkingPlanNew`의 작업군·일정·상세·시기 operation을 대조했다. 공식 응답에서 `210005=밭농사`, 밭농사 목록의 `30699=감자`, 상세 응답의 같은 콘텐츠번호·제목·작업군을 확인했다. 토양·물과 강수·기온·햇빛·생육 단계·재배 작형을 여섯 개 근거 Topic으로 구조화했지만 모두 `LocatedNeedsReview`이고 Profile은 `PendingHumanReview`, `CanPublishSimulationRule=false`다. `210005`는 감자 상품코드가 아니므로 기존 농사로 상품 관계는 `Unlinked`를 유지한다.

## 1. 결정할 문제

현재 `FARM-3` 감자 Fixture는 파종 후 지난 일수만으로 `발아 → 영양생장 → 괴경비대 → 수확가능` 단계를 진행하고, 수확량도 300kg으로 고정한다. 이 구조는 생애주기와 Preview·Confirm·Tick을 검증하기에는 충분하지만 다음 질문에는 답하지 못한다.

- 같은 5일이 지나도 비가 너무 적거나 많으면 어떻게 다른가?
- 햇빛이 부족한 날이 이어지면 생육이 얼마나 늦어지는가?
- 같은 기후라도 토양의 배수성·보수력·화학성이 다르면 무엇이 달라지는가?
- 농사로의 작물 일정과 재배 정보가 게임 규칙에 어떤 근거로 반영되었는가?

따라서 다음 생육 모델은 단순 경과일이 아니라 아래 흐름을 따른다.

```text
작물 요구조건 + 토양 기준 + 전날 토양수분
                    + 오늘의 햇빛·강수·기온
                              ↓
                     하루 환경 Snapshot
                              ↓
                   생육점수 + 환경 스트레스
                              ↓
                생육 단계·수확 잠재량·근거 갱신
```

## 2. 네 요소를 한 세트로 읽는 원칙

### 2.1 작물: 무엇을 필요로 하는가

농사로의 농작업 일정과 작물 자료는 작물 identity, 재배 시기, 생육 구간, 토양·수분 관리 설명을 확인하는 **현실 기준정보**다. 원문 문장을 자동으로 숫자 임계값으로 바꾸지 않는다. 사람이 근거와 한계를 검토한 뒤 별도의 versioned `작물생육요구RuleSnapshot`을 게시한다.

농사로 품목구분Code는 KAMIS 품목코드나 `product:potato`와 같은 식별자가 아니다. 공식 교차 근거가 확인될 때만 canonical 품목 아래 source relation으로 연결한다.

### 2.2 토양: 느리게 변하는 기반과 매일 변하는 물을 분리한다

토양은 두 층으로 나눈다.

| 층 | 예시 | 갱신 성격 | Simulation 역할 |
| --- | --- | --- | --- |
| `토양기준Snapshot` | pH, 유기물, 유효인산, 전기전도도, 배수·보수 특성, 시료 시각 | 느림 | 장기 적합도와 물 저장 한계 |
| `토양수분SimulationState` | 현재 저장수분, 포화 초과, 관수량 | 매일 | 가뭄·과습 판정과 다음 날 입력 |

공개 토양도나 지역 통계는 특정 Unity 밭의 실측값이 아니다. 좌표·PNU처럼 민감하거나 정밀한 위치는 사용자가 명시적으로 선택한 범위 안에서만 서버가 조회하며, Unity에는 필요한 공간 정밀도와 한계만 투영한다.

### 2.3 햇빛: 일사량과 일조시간을 같은 값으로 보지 않는다

식물에 들어온 에너지에 가까운 일별 누적 일사량을 우선한다. 일조시간만 있을 때는 `대체 관측`임을 표시하고 별도 변환 규칙과 revision을 사용한다. 둘을 단위 변환 없이 합치거나 같은 임계값에 넣지 않는다.

기상청 종관기상관측(ASOS) 일자료는 기온·강수·습도·일사·일조 관측의 우선 후보이고, 시간자료는 일별 Snapshot을 검증하거나 더 세밀한 모델이 필요할 때 사용한다.

### 2.4 강수: 비의 양이 아니라 토양에 남은 물을 계산한다

강수량을 생육점수에 직접 더하지 않는다. 비가 내려도 유출·배수·증발산으로 사라질 수 있고, 지나치면 과습 스트레스가 생긴다.

```text
다음 토양수분
= 이전 토양수분
 + 유효강수
 + 관수
 - 증발산
 - 지표유출
 - 배수
```

첫 Fixture에서는 각 항을 명시적인 단순 규칙으로 제공한다. 실제 증발산·유출 모델을 검증하기 전에는 현실 농업 계산이라고 부르지 않는다.

## 3. 하루 한 턴의 판정 규칙

### 3.1 입력 Snapshot

`재배환경일일Snapshot`은 다음을 한 날짜에 고정한다.

| 구분 | 필수 내용 |
| --- | --- |
| 작물 | `CanonicalProductStableId`, 생육 단계, 요구 Rule ID·revision |
| 시간 | Simulation 날짜, 관측 기준 날짜, 시간대 |
| 기후 | 평균·최저·최고 기온, 강수량, 일사량 또는 일조시간, 습도, 관측소·거리·품질표시 |
| 토양 | 기준 Snapshot ID·시료 시각·공간 정밀도, 전날/당일 수분 상태 |
| 출처 | provider, dataset, source record ID, 수집 시각, 원문 hash, 단위 |
| 실행 | `SimulationFixture` 또는 `PublicObservationReference`, scenario seed |

예보는 미래 계획 `Preview`에는 쓸 수 있지만 지나간 턴의 확정 환경이 되지 않는다. 확정 Tick은 관측 Snapshot 또는 명시적인 Fixture Snapshot 하나를 고정해 사용한다.

### 3.2 환경 계수

각 동적 조건은 `0.0~1.0` 범위의 계수로 해석한다.

- `온도계수`: 현재 생육 단계의 적정 범위와 일 최저·최고·평균 비교
- `햇빛계수`: 단계별 일사 요구량과 관측값 비교
- `수분계수`: 계산된 토양수분이 단계별 적정 범위에서 얼마나 벗어났는지 비교
- `토양적합계수`: 느리게 바뀌는 토양 기준과 작물 요구조건 비교

첫 규칙은 네 값을 단순 평균하지 않는다. 하루의 가장 부족한 동적 조건이 생육 속도를 제한하고, 토양 기반이 이를 보정하도록 한다.

```text
하루 유효생육점수
= 기본발달속도
 × min(온도계수, 햇빛계수, 수분계수)
 × 토양적합계수
```

이 식은 검증 가능한 게임 규칙이지 작물 생리 모델의 확정식이 아니다. rule revision이 바뀌면 이전 재배작기는 기존 revision을 계속 고정해 replay 결과를 보존한다.

### 3.3 단계 전이와 스트레스

생육 단계는 `경과일`이 아니라 누적 유효생육점수가 단계 임계값에 도달할 때 전이한다. 경과일은 여전히 화면과 감사 기록에 남긴다.

동시에 부족 또는 과다 조건을 원인별로 누적한다.

```text
가뭄 스트레스
과습 스트레스
저온 스트레스
고온 스트레스
저일사 스트레스
토양부적합 스트레스
```

스트레스는 생육점수와 별도 원장으로 보존한다. 같은 단계에 도달했더라도 어떤 환경을 지나왔는지 설명하고, 향후 `Simulation 수확잠재량지수`에 반영할 수 있어야 한다. 실제 수확량 예측이나 농업 권고로 표시해서는 안 된다.

## 4. 결측·오래된 자료·재현 규칙

각 입력 채널은 `Valid`, `Stale`, `Missing`, `Fixture` 중 하나의 품질 상태를 가진다.

- `SimulationFixture`: seed가 고정된 합성값으로 계속 진행할 수 있다.
- `PublicObservationReference`: 필수 관측이 없거나 오래되면 확정 Tick을 막고 `자료 부족`을 반환한다.
- 일부 관측이 없다는 이유로 Fixture나 평년값을 조용히 섞지 않는다.
- 일조시간 대체, 인근 관측소 대체, 토양 지역통계 대체는 모두 별도 Interpretation code와 한계를 남긴다.
- 여러 날 진행 Command도 내부적으로 하루씩 순서대로 판정한다. 합산 강수와 평균 햇빛만으로 건조 후 폭우 같은 순서를 지우지 않는다.
- Confirm 입력에는 session revision, 재배작기 revision, rule revision, 날짜, 환경 Snapshot hash를 넣고 같은 Command 재시도는 멱등이어야 한다.

## 5. 서버와 Unity의 책임

```text
공식 API / Fixture
       ↓
서버 원문 보존·정규화
       ↓
환경 Snapshot 준비
       ↓
Turn Preview → 사용자 Confirm → 하루 Tick
       ↓
새 재배작기 Snapshot과 판정 근거
       ↓
Unity 재조회·표현
```

서버가 source·단위·품질·공간 기준을 검증하고 생육 규칙을 계산한다. Unity는 원문 기후·토양값으로 자체 계산하지 않는다. Unity 카드에는 다음 네 막대와 가장 큰 제한 요인을 한국어로 보여준다.

```text
오늘의 생육 조건

토양   양호
햇빛   부족
수분   적정
기온   적정

오늘 생육 +0.63
주요 제한: 햇빛 부족
누적 단계: 영양생장 42%
자료: 기상청 관측 + 토양 Fixture
```

색만으로 상태를 전달하지 않고 값·단위·출처·기준 날짜·Fixture 여부를 함께 표시한다. 에셋의 색, 크기, 흔들림, 마름 효과는 Presentation이며 원장을 변경하지 않는다.

## 6. 첫 감자 규칙의 구현 순서

| 우선순위 | Gate | 결과 | 완료 조건 |
| --- | --- | --- | --- |
| P0 | `FARM-ENV-0` | 감자 Fixture용 환경 Snapshot·Rule·하루 계산기 | **완료:** 정상·가뭄·과습·저일사·결측 및 source 혼합 차단 test |
| P1 | `NONGSARO-CROP-1` | 농사로 감자 일정과 설명의 사람 검토용 요구조건 profile | **완료:** 콘텐츠 30699·밭농사 210005 분리, 여섯 근거 Topic, rule 게시 차단 |
| P2 | `KMA-WEATHER-1` | 관측소·날짜 하나의 기온·강수·햇빛 일자료 | **구현:** 원문 hash·단위·품질·지점 한계·결측 차단; **미확인:** 승인 key 실제 응답 |
| P3 | `SOIL-OBS-1` | 공개 표본 지역의 토양 기준 Snapshot | 자료 이용 승인과 위치·시료 시각·통계/실측 구분 확인 |
| P4 | `FARM-ENV-1` | 현실 기준정보를 사용한 Simulation 비교 실행 | Fixture와 관측 참조 결과를 섞지 않고 나란히 비교 |
| P5 | `FARM-ENV-UI-1` | 모판과 Farm Scene의 한국어 환경 카드 | 서버 판정만 reconcile하고 Game View 증거 확보 |

P0에서는 현재 `FARM-3`의 일수 기반 규칙을 조용히 바꾸지 않는다. 새 환경 규칙을 병렬 Fixture profile로 추가해 같은 Command log가 같은 결과를 내는지 먼저 검증한 뒤 migration 여부를 결정한다.

## 7. 첫 검증 시나리오

감자 한 재배작기와 같은 초기 토양을 사용해 다음을 비교한다.

1. `기준일`: 모든 계수 1.0에 가까워 정상 진행
2. `연속 건조`: 토양수분이 매일 감소하고 가뭄 스트레스 누적
3. `집중호우`: 저장 한계 초과분과 배수 뒤 과습 스트레스 누적
4. `저일사`: 물이 충분해도 햇빛이 제한 요인이 되어 단계 전이 지연
5. `자료 결측`: 관측 참조 모드의 Confirm 차단, Fixture 모드는 명시적으로 계속

각 시나리오는 생육 단계뿐 아니라 `환경 Snapshot → 계수 → 하루 점수 → 스트레스 → 다음 상태` 전체 계산 근거를 비교한다.

## 8. 공식 자료 후보와 확인 경계

- [기상청 종관기상관측(ASOS) 일자료](https://www.data.go.kr/data/15059093/openapi.do): 일별 기온·강수·습도·일사·일조 관측 후보
- [기상청 종관기상관측(ASOS) 시간자료](https://www.data.go.kr/data/15057210/openapi.do): 시간별 강수·일사와 품질 정보 확인 후보
- [농촌진흥청 농사로 Open API](https://www.nongsaro.go.kr/portal/ps/psz/psza/contentMain.ps?menuId=PS00191): 농작업 일정·작물 기준정보의 공식 진입점
- [농사로 감자 농작업 일정](https://www.nongsaro.go.kr/portal/ps/psb/psbl/workScheduleLst.ps?code=210005&menuId=PS00087): 감자 일정과 재배 작업 설명의 검토 후보
- [팜맵기반 토양검정 조회 서비스](https://www.data.go.kr/data/15058655/openapi.do): 필지·시료 기반 토양 관측 후보
- [토양도 기반 작물별 토양적성 통계정보 V2](https://www.data.go.kr/data/15144182/openapi.do): 지역 단위 작물 토양적성 후보

현재 확인한 것은 공식 서비스의 제공 범위와 기존 농사로 client 경계다. 실제 토양 API 응답과 감자 수치 임계값은 아직 확보·검증하지 않았다. 따라서 첫 P0의 숫자는 모두 `Fixture`이고, 농사로 또는 기상청의 실제 권고값으로 표기하지 않는다.
