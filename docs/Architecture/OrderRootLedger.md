# 주문 원장 중심 통합 구조

## 목적

살뜰의 주문, 판매, 창고 입출고, 배송과 운송은 서로 다른 OS와 API에서 처리되지만 사용자는 하나의 주문 맥락으로 진행 상황을 확인할 수 있어야 한다.

주문 원장을 한 사람 또는 한 주문 의사의 기본 업무 단위로 두고 다음 이행 원장을 필요에 따라 포함한다.

- 판매 원장
- 창고 입고 원장
- 창고 출고 원장
- 배송 원장
- 운송 원장

## 저장 원칙

MongoDB `community_ledgers`의 주문 원장이 포함 관계의 원본이다. 주문 원장은 하위 원장의 전체 데이터나 상태를 복제하지 않고 다음 참조 정보만 보관한다.

- 하위 `원장Id`
- 하위 `원장템플릿Key`
- 역할: 판매, 창고입고, 창고출고, 배송, 운송
- 필수 여부
- 표시 순서

하위 원장의 블록, 참여자, 증빙과 상태는 각 하위 원장에 독립적으로 저장한다. 통합 조회는 주문 원장의 참조를 따라 각 하위 원장의 최신 상태를 읽어 조합한다. 따라서 배송 또는 운송 상태가 변경되어도 주문 원장 안의 복제 상태를 다시 맞출 필요가 없다.

RDB는 확정된 업무 엔티티만 투영한다. 원장 블록, 원장 관계, 다이어그램 배치 정보는 MongoDB에 두며, 주문 원장 관계를 이유로 판매, 입출고, 배송 또는 운송의 업무 데이터를 별도 RDB 주문 테이블에 중복 저장하지 않는다.

## 지원하는 주문 루트

- 일반 주문 원장: `order`
- 음식 주문 원장: `food-order`
- 알뜰살뜰 마트 원장: `ssalddel-mart`

기존 구체 주문 원장은 계속 독립적으로 동작하며 필요할 때 하위 이행 원장을 포함할 수 있다.

## 공동주문 묶음

공동주문은 새로운 종류의 거대한 주문이 아니라 여러 개별 주문 원장을 합친 집합이다. `group-purchase` 원장은 각 참여자의 주문 내용을 직접 복제하지 않고 `개별주문` 역할로 주문 원장 참조만 보관한다.

```text
공동주문 묶음 원장
  +-- 개별 주문 원장 A
  |     +-- 판매/입출고/배송/운송 원장
  +-- 개별 주문 원장 B
  |     +-- 판매/입출고/배송/운송 원장
  +-- 개별 주문 원장 C
        +-- 판매/입출고/배송/운송 원장
```

공동주문의 수량과 금액은 연결된 주문 원장을 집계한 결과다. 수입 결정, 해외 선적, 통관, 공동 입고와 분배는 공동주문의 정의 자체가 아니라 주문 묶음이 확정된 뒤 열리는 후속 이행 절차다.

## 개별 주문자 서명

서명 책임의 기본 단위는 공동주문 묶음이 아닌 각 개별 주문 원장이다. 공동주문 원장은 서명 증적을 복제하지 않고, 연결된 개별 주문의 서명 상태를 조회해 다음만 집계한다.

- 서명 대상 주문 수
- 서명 완료 주문 수
- 미서명 주문 ID 목록
- 전체 주문 서명 완료 여부

서명 정보는 MongoDB `community_ledger_order_signatures`에 원장별로 분리 저장한다. 계약 문서, 동의문, 접속 IP와 서명 원본을 일반 원장 응답에 노출하지 않고 각 값의 Hash와 서명 시각을 증적으로 관리한다. 공동주문 통합 조회에는 서명 상태 요약만 포함한다.

## 역할별 조회와 원장 공개 요청

주문 원장을 기점으로 하지만 모든 참여자에게 모든 하위 원장의 세부 내용을 반환하지 않는다. 역할별 Query Handler는 다음 범위만 조합한다.

| 조회 역할 | 조합하는 원장 |
| --- | --- |
| 주문자 | 주문 원장과 모든 하위 원장의 참조. 하위 원장 상세는 별도 권한 판정 |
| 판매자 | `판매` 역할 원장 |
| 창고 담당자 | `창고입고`, `창고출고` 역할 원장 |
| 운송 담당자 | `배송`, `운송` 역할 원장 |

원장 상세 DTO는 다음 중 하나를 충족할 때만 반환한다.

- 현재 사용자가 해당 원장의 소유자다.
- 현재 사용자가 `참여자목록.UserId`에 직접 등록되어 있다.
- 원장 소유자가 해당 사용자의 상세 공개 요청을 승인했고 승인 기간이 만료되지 않았다.

이 조건을 충족하지 못한 연결 원장은 ID, 템플릿, 주문 안의 역할만 반환하고 `원장상세`를 `null`로 반환한다. 공개 요청은 MongoDB `community_ledger_disclosure_requests`에 독립 저장하며, 대기 요청은 14일, 승인 공개는 1~90일 범위에서 만료한다. 승인 상태를 원장 문서나 RDB 업무 엔티티에 복제하지 않는다.

## API

- `GET /api/v1/community/order-ledgers/{주문원장Id}`: 주문자 기본 보호형 조회
- `GET /api/v1/community/order-ledgers/{주문원장Id}/views/orderer`: 주문자 Query Handler 조회
- `GET /api/v1/community/order-ledgers/{주문원장Id}/views/seller`: 판매자 Query Handler 조회
- `GET /api/v1/community/order-ledgers/{주문원장Id}/views/warehouse`: 창고 담당자 Query Handler 조회
- `GET /api/v1/community/order-ledgers/{주문원장Id}/views/transport`: 운송 담당자 Query Handler 조회
- `POST /api/v1/community/order-ledgers/{주문원장Id}/children`: 기존 하위 원장 연결 또는 연결 메타데이터 수정
- `DELETE /api/v1/community/order-ledgers/{주문원장Id}/children/{하위원장Id}`: 주문 원장에서 하위 원장 분리
- `POST /api/v1/community/order-ledgers/{주문원장Id}/signature-request`: 개별 주문자 서명 요청 준비
- `POST /api/v1/community/order-ledgers/{주문원장Id}/signatures`: 문서·동의문·서명 증적 Hash로 서명 등록
- `GET /api/v1/community/order-ledgers/{주문원장Id}/signature`: 인증된 주문자의 서명 상태 조회
- `POST /api/v1/community/order-ledgers/{주문원장Id}/disclosure-requests`: 관련 원장 상세 공개 요청
- `GET /api/v1/community/order-ledgers/disclosure-requests/inbox`: 내가 승인할 공개 요청 목록
- `POST /api/v1/community/order-ledgers/{주문원장Id}/disclosure-requests/{요청Id}/decision`: 원장 소유자의 승인 또는 거절

연결과 분리는 주문 원장의 `Revision`을 사용해 낙관적 동시성을 검사한다. 다른 요청이 먼저 관계를 바꾼 경우 최신 주문 원장을 다시 조회한 뒤 재시도해야 한다.

## 불변 조건

- 주문 루트와 공동주문 묶음으로 허용된 템플릿만 하위 원장을 포함할 수 있다.
- 주문 원장은 자기 자신을 포함할 수 없다.
- 같은 하위 원장을 중복해서 포함할 수 없다.
- 주문 원장과 하위 원장은 같은 커뮤니티에 속해야 한다.
- 공동주문 묶음에는 `개별주문` 역할의 주문 원장만 직접 연결할 수 있다.
- 공동주문 묶음 자체에는 주문자 서명을 등록할 수 없고, 연결된 각 개별 주문에 서명해야 한다.
- 역할별 Query Handler는 역할 범위 밖의 하위 원장을 응답에 포함하지 않는다.
- 소유·직접 참여·승인 공개 중 하나가 없으면 원장 상세를 반환하지 않는다.
- 공개 요청은 같은 주문 원장에 직접 관련된 참여자만 생성할 수 있고, 대상 원장 소유자만 결정할 수 있다.
- 일반 주문 원장에는 `개별주문` 역할을 사용할 수 없고 판매, 창고입고, 창고출고, 배송, 운송 원장을 연결한다.
- 필수 하위 원장이 모두 완료되었다는 통합 조회 결과만으로 주문 상태를 자동 완료하지 않는다. 주문 완료 확정은 별도 상태 변경 규칙과 사용자 확인을 거친다.

## 다음 단계

1. 주문 생성 UseCase가 일반 주문 원장을 먼저 만들고 판매 또는 이행 원장을 연결하도록 전환한다.
2. 하위 원장 상태 변경 이벤트에서 주문 원장 화면 갱신 알림을 발행한다.
3. 주문 유형별 필수 하위 원장 규칙과 전체 완료 판정 정책을 분리한다.
4. 주문 원장 통합 조회를 클라이언트의 현재 원장 Context와 다이어그램에 연결한다.
