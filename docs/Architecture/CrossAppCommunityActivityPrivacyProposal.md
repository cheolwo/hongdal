# 각 앱 업무 활동의 커뮤니티 환류 제안서

## 1. 제안 요약

살뜰의 각 역할 앱에서 발생한 업무 활동을 커뮤니티 안에서 볼 수 있게 한다.
다만 업무 원장, 사용자 행위 로그 또는 개인정보를 그대로 공개하지 않고,
공개 가능한 사실만 별도의 **커뮤니티 활동 신호**로 재가공한다.

권장 흐름은 다음과 같다.

```text
각 앱의 성공한 Command·Event
  -> 비공개 활동 후보
  -> 공개 가능 유형 allowlist
  -> 참여자·조직 동의와 공개 범위 확인
  -> 개인정보·영업정보 제거
  -> 시간·지역·수량 집계
  -> 운영 정책 또는 자동 안전검사
  -> 커뮤니티 활동 신호·완료 사례
```

핵심 결정은 다음 네 가지다.

1. 사용자 행위 로그는 공개 피드의 원천으로 직접 사용하지 않는다.
2. 기본 공개 범위는 비공개이며, 공개는 별도 동의나 안전한 집계 조건을 통과해야 한다.
3. 개인 단위 활동보다 여러 참여자의 흐름을 집계한 공동체 신호를 우선한다.
4. 활동 공개, 친구 후보, 친구 요청, 연락처 공개와 업무 실행은 각각 분리된 상태로 관리한다.

이 기능의 목적은 사람을 감시하거나 실적을 평가하는 것이 아니라,
“이 커뮤니티에서 어떤 일이 실제로 함께 이루어지고 있는지”를 안전하게 보여 주어
다음 대화와 참여를 돕는 것이다.

## 2. 제품 목적

### 기대 효과

- 커뮤니티 대화가 실제 공동행동으로 이어진 사례를 확인할 수 있다.
- 음식점, 살들마트, 주문자, 기사, 화주와 창고 참여자가 서로의 업무 흐름을 이해할 수 있다.
- 같은 일을 새로 시작하려는 사람이 절차, 필요한 역할과 예상되는 어려움을 배울 수 있다.
- 앱별로 흩어진 완료 경험이 다시 커뮤니티의 신뢰와 다음 제안으로 돌아온다.
- 개인별 순위가 아니라 공동체의 활동성과 협력 경험을 보여 줄 수 있다.

### 하지 않는 일

- 사용자별 업무량, 속도, 수익 또는 실패 횟수 공개
- 개인이나 업체의 자동 신뢰 점수·검색 순위 생성
- 활동 기록을 이용한 자동 친구 관계·연락처 공개
- 커뮤니티 반응만으로 계약, 발주, 배차, 결제 또는 정산 실행
- 업무 원장 원문, 증빙, 위치, 주문 상세를 커뮤니티에 복제

## 3. 현재 구조와 보완 필요성

현재 `GET api/v1/community/activity-signals`는 성공한 `사용자행위로그`를 읽고
route와 역할을 기준으로 공개 활동 신호를 만든다. 응답에서 사용자 ID, 이름,
IP와 원문 metadata를 제외하고 관리자·인증·보안·파일 route를 차단하는 보호 장치는 있다.

그러나 `사용자행위로그` 원본에는 사용자 ID, 사용자명, 역할, masked email,
전화번호 일부, route, trace ID, IP, user agent와 metadata가 함께 저장된다.
이를 공개 신호의 직접 원천으로 계속 사용하면 다음 위험이 남는다.

- 특정 앱·역할·정확한 발생 시각의 조합으로 개인을 다시 추정할 수 있다.
- 조회·실패·내부 점검 같은 행위가 업무 성과처럼 오해될 수 있다.
- 참여자 공개 동의, 조직 정책, 철회와 보유기간을 활동별로 증명하기 어렵다.
- route 이름이 바뀌면 공개 의미가 함께 바뀌어 업무 의미가 안정적이지 않다.
- 한 사람의 반복 행동이 커뮤니티 전체의 활동처럼 과대표현될 수 있다.

반면 `CommunityActivityPostPublisher`와 완료 원장 환류는 Command·Event와 완료 상태에서
공개용 문장을 별도로 만들고, 원장 상세·연락처·주소·금액·증빙 원문을 제외하는 방향을
이미 갖고 있다. 새 구조는 이 Event 기반 경로를 기준으로 통합하는 것이 적절하다.

## 4. 공개 모델

### 공개 범위 단계

| 단계 | 열람자 | 예시 | 기본값 |
| --- | --- | --- | --- |
| `Private` | 활동 당사자 본인 | 내가 완료한 업무와 공개 가능 여부 | 기본 |
| `Participants` | 같은 원장의 당사자 | 공동 작업 완료와 다음 인계 상태 | 명시적 업무 권한 |
| `CommunityScoped` | 선택한 게시판·생활권·조직 커뮤니티 | 이번 주 지역 공동 입고 집계 | 동의와 집계 조건 |
| `PublicAggregated` | 비로그인 포함 공개 | 이번 달 비식별 완료 사례 12건 | 엄격한 집계·운영 정책 |

개별 사용자의 활동을 익명 이름으로 바꾸는 것만으로는 충분하지 않다.
활동이 드문 지역·시간·역할에서는 익명 역할도 개인을 드러낼 수 있으므로,
공개 범위가 넓어질수록 시간과 지역을 더 크게 묶고 최소 집계 수를 요구한다.

### 공개 상태

```text
Candidate
  -> ConsentPending
  -> Eligible
  -> Aggregated
  -> Published
  -> Withdrawn / Suppressed
```

- `Candidate`: 업무 Event에서 생성된 비공개 후보
- `ConsentPending`: 참여자 또는 조직의 공개 선택 대기
- `Eligible`: 공개 정책과 동의를 충족
- `Aggregated`: 최소 인원·건수·시간 구간을 충족한 집계
- `Published`: 커뮤니티 읽기 모델에 게시
- `Withdrawn`: 동의 철회로 공개 투영을 숨김
- `Suppressed`: 재식별·분쟁·신고·정책 위반 위험으로 운영 차단

철회는 커뮤니티 공개 투영을 숨기는 것이며, 법적·운영상 보존해야 하는 원본 업무 기록을
임의로 삭제한다는 뜻이 아니다. 두 기록의 목적과 보유기간을 분리한다.

## 5. 공개 가능한 정보와 금지 정보

| 공개 가능 후보 | 조건 |
| --- | --- |
| 앱 또는 업무 영역 | 실제 앱 내부 route 대신 안정적인 업무 코드 사용 |
| 업무 종류 | 입고 완료, 인수 완료, 공동 원장 완료처럼 allowlist에 등록된 상태 |
| 역할 분류 | `음식점`, `마트 운영`, `기사` 등 넓은 역할군만 사용 |
| 시간 | `오늘`, `이번 주`, `이번 달`과 같은 bucket |
| 지역 | 시·도 또는 충분히 큰 생활권 단위, 최소 집계 수 충족 |
| 건수·참여 조직 수 | 한 명의 반복 행동을 제거한 distinct 집계 |
| 절차 단계 | 개인정보를 제거한 템플릿·다이어그램 단계 |
| 참여자가 작성한 후기 | 별도 발행 동의와 운영 정책 통과 |

다음 정보는 기본적으로 공개하지 않는다.

- 사용자·업체·음식점·마트·창고의 내부 ID
- 실명, 계정명, 이메일, 전화번호, IP와 단말 정보
- 상세 주소, 정확한 좌표, 이동 경로와 실시간 위치
- 정확한 발생 시각, 교대시간과 반복 패턴
- 주문번호, 계약번호, 발주번호, 운송·통관·문서 번호
- 상품명·SKU·수량·단가·금액·마진·정산 내역
- 차량번호, 기사 식별자, 사업자등록번호와 계좌
- 사진·서명·신고·분쟁·검수 증빙과 메모 원문
- 오류 메시지, trace ID, route 원문과 metadata JSON

상품명, 지역 특산물, 절감액과 같은 정보가 공동체 학습에 필요한 경우에는
참여자별 동의와 별도 공개 정책을 거쳐 완료 사례로 발행한다.

## 6. 앱별 활동 신호 제안

| 앱·영역 | 커뮤니티에 보여 줄 수 있는 신호 | 공개하지 않는 세부값 |
| --- | --- | --- |
| 주문자 | 함께 사고 싶은 품목군의 관심 증가, 공동 원장 완료 | 개인 주문, 수량, 주소, 결제 |
| 음식점 | 여러 음식점의 식재료 공급조건 검토·인수 완료 집계 | 상호, 메뉴 원가, 공급자별 계약 |
| 살들마트 | 도심 재고 보충·검수·피킹 완료 집계 | 거점, SKU, 실시간 재고, 매출 |
| 창고 | 입고·검수·피킹·포장 절차 완료 집계 | 창고 위치, 작업자, 화주, 물량 |
| 기사 | 운송·배달 인계 완료 집계 | 기사, 차량, 경로, 시각, 운임 |
| 화주·판매자 | 운송 의뢰·인수 확인·판매 이행 완료 집계 | 업체, 화물, 거래처, 계약금액 |
| 공동구매·같이 수입 | 참여 동의를 거친 원장 단계와 완료 사례 | 참여자, 개별 부담액, 신고 원문 |
| 관리자·보안 | 공개 신호를 생성하지 않음 | 운영·감사·신고 활동 전체 |

공개 카드 예시는 다음과 같다.

- `이번 주 수도권 음식점 7곳이 산지 식재료 공급조건을 검토했습니다.`
- `이번 달 도심 마트 재고 보충 18건이 검수 완료 단계까지 진행됐습니다.`
- `최근 7일 동안 창고 입고에서 운송 인계까지 이어진 비식별 절차가 9건 완료됐습니다.`
- `같은 유형의 공동 원장 4건이 완료되어 절차 다이어그램을 참고할 수 있습니다.`

`익명 기사 한 명이 방금 배송을 완료했습니다`처럼 개인·정확한 시각에 가까운 문장은
공개 피드에서 사용하지 않는다.

## 7. 권장 서버 구조

```text
Controller API
  -> UseCase / Command
  -> 업무 원장 상태 전이
  -> Domain Event
  -> CommunityActivityCandidate Outbox
  -> 공개정책·동의·비식별 Policy
  -> 집계 Projection
  -> CommunityActivitySignal Read Model
  -> 커뮤니티 게시판·피드
```

### 원장과 책임

| 구성요소 | 책임 |
| --- | --- |
| `CommunityActivityCandidate` | Event에서 받은 비공개 활동 후보와 원천 참조 |
| `CommunityActivityPublicationPolicy` | 공개 허용 Event, 필드, 시간·지역 bucket, 최소 집계 수 |
| `CommunityActivityPublicationConsent` | 사용자·조직·원장별 공개 범위, 버전, 철회 이력 |
| `CommunityActivityAggregate` | 중복 제거와 최소 집계 기준을 통과한 통계 |
| `CommunityActivityProjection` | 커뮤니티가 읽는 비식별 최종 투영 |
| `CommunityActivityPublicationAudit` | 정책 버전, 변환 결과, 발행·철회·차단 사유 |

원본 Event payload는 Outbox 처리에 필요한 최소 기간만 비공개로 보존한다.
공개 투영에는 원본 payload를 복제하지 않으며, 공개 ID에서 업무 원장 ID를 역산할 수 없게 한다.

### API 제안

기존 `GET api/v1/community/activity-signals` route는 호환을 위해 유지하되,
조회 원천을 `사용자행위로그`에서 `CommunityActivityProjection`으로 교체한다.

추가 API 후보:

- `GET api/v1/community/activity-publication/preferences`
- `PUT api/v1/community/activity-publication/preferences`
- `GET api/v1/community/activity-publication/candidates`
- `POST api/v1/community/activity-publication/candidates/{candidateId}/consent`
- `POST api/v1/community/activity-publication/projections/{projectionId}/withdrawal`
- `GET api/v1/admin/community/activity-publication/review`
- `POST api/v1/admin/community/activity-publication/{projectionId}/suppress`

공개 응답에는 정확한 `OccurredAtUtc` 대신 시간 bucket을 우선하고,
다음 필드를 추가한다.

- `VisibilityScope`
- `AggregationCount`
- `DistinctParticipantCount`
- `TimeBucket`
- `RegionBucket`
- `PrivacyPolicyVersion`
- `ConsentBasis`
- `WithdrawalAvailable`

## 8. 동의와 개인정보 보호

### 동의 분리

다음 동의는 하나의 체크박스로 합치지 않는다.

1. 업무 참여 동의
2. 업무 당사자끼리 상태를 공유하는 동의
3. 비식별 활동 신호의 커뮤니티 공개 동의
4. 후기에 닉네임·역할을 표시하는 동의
5. 친구 후보 기록 허용
6. 친구 요청·수락
7. 연락처 공개

친구 후보와 연락처 공개 기준은
[업무 경험에서 친구 요청으로 이어지는 커뮤니티 설계 기준](FriendRequestCommunityDesignStandard.md)을
그대로 따른다.

### 재식별 방지

- 공개 집계의 기본 최소값을 distinct 참여자 또는 조직 5 이상으로 둔다.
- 민감한 지역·역할·품목 조합은 최소값을 더 높이거나 공개하지 않는다.
- 한 명이 여러 번 수행한 활동은 공개 집계에서 한 참여자로 계산한다.
- 정확한 시각을 공개하지 않고 일·주·월 단위로 묶는다.
- 좁은 지역과 드문 역할을 동시에 필터링하지 못하게 한다.
- 필터 조합으로 최소 집계 기준을 우회하지 못하도록 서버가 최종 집계를 다시 검증한다.
- 삭제·철회 직후 이전 cache나 검색 색인에서도 공개 투영을 제거한다.

### 보유와 감사

- 업무 원본, 공개 후보, 동의, 공개 투영과 감사 기록의 보유기간을 각각 둔다.
- 정책 버전과 동의 문구 버전을 함께 저장한다.
- 발행·수정·철회·운영 차단을 멱등 Event로 기록한다.
- 신고 또는 분쟁 중인 원장은 완료 사례와 활동 신호의 신규 발행을 보류한다.
- 운영자는 공개 전후의 변환 결과를 볼 수 있지만 원본 개인정보 열람은 별도 권한으로 제한한다.

## 9. 화면 제안

### 각 앱

- 앱 홈의 `커뮤니티` 모드에서 같은 활동 피드를 조회한다.
- `내 활동 공개 검토함`에서 비공개 후보, 공개 예정 요약과 공개 범위를 확인한다.
- 원문 업무 화면으로 돌아가는 링크는 당사자에게만 보인다.
- 공개 카드에는 `왜 이 정보가 보이는지`, 집계 수와 정책 버전을 표시한다.

### 커뮤니티

- 게시판을 앱별로 계속 늘리지 않고 업무 목적별 활동 게시판과 태그를 사용한다.
- `진행·공동 원장`에는 집계된 진행 신호를, `완료 사례·후기`에는 동의된 완료 사례를 둔다.
- 피드에서 같은 업무를 시작할 수는 있지만 이전 원장의 참여자·연락처·거래조건은 복제하지 않는다.

### 운영자

- 공개 후보의 민감도, 집계 충족 여부, 동의 상태와 차단 사유를 검토한다.
- 개인정보 신고가 들어오면 공개 투영을 즉시 숨기고 원본 업무 상태와 분리해 조사한다.
- 특정 앱이나 Event 유형의 발행을 독립적으로 중지할 수 있게 한다.

## 10. 단계별 구축안

### 1단계: 현재 활동 신호 안전화

- 공개 API가 `사용자행위로그`를 직접 읽는 구조를 중단한다.
- `Read` 행위와 관리자·보안·신고·파일 활동은 공개 후보에서 제외한다.
- 정확한 발생 시각을 시간 bucket으로 바꾼다.
- 공개 Event allowlist와 정책 버전을 만든다.
- 기본 Feature를 끄고 검증 profile에서만 새 투영을 비교한다.

### 2단계: Event 기반 후보·동의 원장

- 각 앱의 성공 Event에서 `CommunityActivityCandidate` Outbox를 생성한다.
- 사용자·조직·원장별 공개 동의와 철회를 영속화한다.
- 발행 전 개인정보·영업정보 필드 차단 테스트를 추가한다.
- 실패 시 업무 상태 전이를 되돌리지 않고 Outbox를 재처리한다.

### 3단계: 집계 피드와 완료 사례

- 최소 집계 수, 시간·지역 bucket과 중복 제거를 적용한다.
- `CommunityActivityProjection` 읽기 모델로 기존 조회 API를 전환한다.
- 완료 원장의 비식별 다이어그램과 활동 집계를 연결한다.
- 각 앱의 커뮤니티 모드에서 같은 결과를 재조회한다.

### 4단계: 사용자 공개 검토함과 운영

- 내 활동 공개 후보의 preview·동의·철회 화면을 추가한다.
- 운영자 차단, 신고, cache·검색 색인 삭제와 감사 조회를 연결한다.
- 공개 카드가 실제 공동 참여로 이어지는지 측정하되 개인별 생산성 점수는 만들지 않는다.

## 11. 완료 기준

- 공개 API가 사용자 행위 로그 원문을 직접 조회하지 않는다.
- 공개되지 않은 활동은 비로그인 사용자에게 어떤 조합의 필터로도 나타나지 않는다.
- 공개 카드에 사용자·조직·원장 ID, 연락처, 주소, 정확한 시각과 금액이 포함되지 않는다.
- 참여자·조직 동의와 정책 버전이 없는 개인 단위 활동은 발행되지 않는다.
- 집계 공개는 최소 distinct 기준과 시간·지역 bucket을 서버에서 검증한다.
- 동의 철회 뒤 피드, 상세, cache와 검색 색인에서 공개 투영이 제거된다.
- Event 재처리로 같은 활동이 중복 발행되지 않는다.
- 활동 신호 실패가 원래 업무 Command의 성공을 취소하지 않는다.
- 친구 후보, 친구 요청, 연락처 공개와 활동 공개 상태가 서로 독립적이다.
- 신고·분쟁·보안·관리자 활동은 공개 신호가 되지 않는다.

## 12. 권고 결론

각 앱의 활동을 커뮤니티에서 보여 주는 방향은 커뮤니티를 제품의 중심으로 만드는 데
효과적이다. 다만 “모든 앱 로그를 익명화해서 공개”하는 방식이 아니라,
**공동체에 도움이 되는 업무 성립 사실만 Event에서 선별하고, 동의·비식별·집계한 뒤
별도 읽기 모델로 공개하는 방식**이어야 한다.

첫 구현은 화면 확대보다 현재 활동 신호의 원천을 `사용자행위로그`에서 분리하는 작업부터
시작한다. 그 다음 완료 원장 환류, 공개 동의와 철회, 집계 피드를 작은 세로 단위로 연결한다.
