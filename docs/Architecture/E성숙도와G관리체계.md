# E 성숙도와 G 관리 체계

## 목적

이 문서는 세계의 완료 증거인 `E`, 그 증거를 다음 단계로 끌어올리는 관리 체계인 `G`, 공간 포함 깊이인 `H`를 분리하는 기준이다.

```text
E = 세계가 어디까지 실제 증거를 갖추었는가
G = 다음 E 증거를 만들기 위해 어떤 종류의 작업을 관리하는가
H = 공간이 어떤 포함 깊이로 조립되는가
```

`G1 완료 = E6`, `G2 완료 = E7`처럼 관리 체계의 작업 상태를 증거 단계와 같게 취급하지 않는다. E 승격은 반드시 [`evidence-stages.json`](../../eng/execution-ledgers/evidence-stages.json)의 해당 완료 관문과 실제 증거를 통과해야 한다. G의 기계 기준은 [`evidence-management-systems.json`](../../eng/execution-ledgers/evidence-management-systems.json)이다.

## 플레이어 관점은 E1부터 적용한다

G2가 플레이어 경험 구현을 주로 관리한다고 해서 플레이어 관점이 E7에서 처음 시작되는 것은 아니다. E1 계약부터 E9 변화까지 각 단계가 어떤 플레이어 선택을 위해 존재하는지 추적한다.

```text
E1  플레이어 약속과 의미 있는 선택
E2  그 의도를 받는 실행 경계
E3  선택·비용·결과의 결정성과 저장
E4  WI 발생원·주체·대상·자료·자원·시간과 선택적 H 문맥 결속
E5  WI의 권위 전이·Task/Effect·결과·후속 선택이 실제 세계에서 발현
E6  장소·원인·피드백·귀환을 이해하게 하는 플레이 전 정제
E7  실제 입력으로 닫히는 플레이어 선택 폐루프
E8  NPC 생활이 플레이어 선택을 바꾸는 세계
E9  새 선택을 더해도 기존 선택과 저장이 유지되는 세계
```

이는 E 완료 관문을 UI 만족도나 주관적 느낌으로 바꾸는 규칙이 아니다. E1~E6은 여전히 계약·코드·시험·WI–H·Actual AreaSet·정제 증거를 요구하고, E7에서 저장 Scene과 실제 입력·Game View 증거를 확인한다. 세부 질문은 [플레이어 중심 게임 개발 업무 구조](플레이어중심게임개발업무구조.md)를 따른다.

## 전체 관계

```text
E1 ───────────── E6
       G1 세계 성립 관리
                     │
E6 ───────────── E7  │
       G2 플레이어 경험 관리
                     │
E7 ───────────── E8  │
       G3 NPC 생활세계 관리
                     │
E8 ───────────── E9  │
       G4 변화·확장 적응 관리
```

G의 구간은 **주 적용 범위**다. 예를 들어 G2 작업 중 발견한 공간 의미 결함은 G1 책임으로 되돌려 고칠 수 있다. 그러나 그 왕복이 E 증거를 자동으로 올리거나 내리지는 않는다. 입력 계약이나 증거 hash가 바뀌면 해당 증거의 최신성 정책에 따라 재검증한다.

## G1 — 세계 성립 관리

주 적용 범위는 `E1 → E6`이며 핵심 질문은 **“이 세계가 제대로 성립했는가?”**다.

- WI 정의와 Simulation 구조
- H1~H5 공간 설계와 AreaSet 조립
- 공간 Pattern·Graph와 이동·인과 폐루프
- 현실 근거 결속
- Revision·Hash·Lineage
- E 단계 준비도와 생성·검토·승격

Farm의 H1/H2/H3 검사, WI 연결, 현실 문맥 질문, Evidence Snapshot, E6 적격 판정은 G1 작업이다. G1 산출물이 존재한다는 사실만으로 E6가 되지 않으며 E1~E6의 해당 완료 관문을 각각 통과해야 한다.

G1도 플레이어와 무관한 배경 제작이 아니다. 어떤 욕구와 선택을 위해 WI와 H 공간이 필요한지, 플레이어가 재료·도구·경로와 결과를 이해할 수 있는지를 함께 검토한다.

E6는 E5까지 세계에서 발현한 WI 또는 WI 폐루프를 E7 실제 플레이에 올리기 전 정제하는 관문이다. `E6 정제 질문표`로 의미·인과·배치·통행·권위·최신성 결함을 걸러내고 필요한 현실 문맥만 출처·판본·hash·한계와 함께 결속한다. 현실자료 `NotApplied`는 허용할 수 있지만 정제 질문 자체를 생략하는 근거는 아니다.

## G2 — 플레이어 경험 관리

주 적용 범위는 `E6 → E7`이며 핵심 질문은 **“사람이 이 세계를 실제로 플레이할 수 있는가?”**다.

- HUD와 카드 서랍
- 입력·카메라·이동·선택·드래그앤드롭
- 서버 Preview·Confirm과 canonical 재조회
- 상호작용 피드백
- `DirectAction`과 `TacticalCommand`
- canonical `SimulationWorldShell`의 Game View 플레이 흐름

다음이 모두 있어야 E7 증거가 된다.

```text
E6 세계
+ 필요한 G2 구현
+ 실제 Simulation 서버
+ 저장된 SimulationWorldShell
+ 실제 Play Mode·Game View·Console 검증
= E7 증거
```

Unity는 입력과 표현을 담당하고 서버가 결과·Effect·개정을 확정한다.

Solo에서는 Unity 프로세스 안의 `LocalSimulationRuntime`, Hosted에서는 Simulation 서버가 같은 Core를 실행한다. 어느 경우에도 Unity 표현이 비용·공간 성장·결과를 다시 계산하지 않는다.

## G3 — NPC 생활세계 관리

주 적용 범위는 `E7 → E8`이며 핵심 질문은 **“플레이어가 없어도 다른 주체가 이 세계를 살아갈 수 있는가?”**다.

- NPC 정체성·역할·욕구·목표
- 행동 후보·우선순위·자율 의사결정
- 생활 이동과 업무 이동
- 공간·자원 경쟁
- 협력·인계와 기억·연속성
- NPC 행동 표현

NPC 생활은 플레이어와 분리된 배경 연산으로 끝나지 않는다. 자원 경쟁·협력·위협 대응·인계가 플레이어가 볼 수 있는 단서와 달라진 선택 후보로 되돌아와야 한다.

다음이 모두 있어야 E8 증거가 된다.

```text
E7 세계
+ G3 NPC 체계
+ 실제 지속 행동 폐루프
+ 경쟁 또는 협력과 후속 선택 변화
+ Save·Replay 동일성
+ 실제 서버·Unity 실행 증거
= E8 증거
```

세부 완료 관문은 [E8 NPC 생활세계 폐루프 정의](E8-NPC생활세계폐루프정의.md)를 따른다.

## G4 — 변화·확장 적응 관리

주 적용 범위는 `E8 → E9`이며 핵심 질문은 **“세계를 안전하게 변화시킬 수 있는가?”**다.

- 변경 제안과 영향 범위 분석
- E8에서 E1까지의 하향 의존 관계 추적
- Revision과 데이터 Migration 계획
- Save·API 호환성과 결정성 회귀 검사
- 기존 플레이어·NPC 폐루프 회귀 검사
- 신규 기능 승격과 변경 후 세계 재검증

G4는 기능 수를 세는 체계가 아니다. 새 규칙·콘텐츠·공간·사건·카드·역할 또는 시스템이 기존 세계 계약에 미치는 영향을 추적하고, 필요한 개정을 만든 뒤 `E1 → E8`을 다시 검증해 새 안정 상태를 만드는 체계다. 세부 완료 관문은 [E9 변화 적응형 세계 정의](E9-변화적응형세계정의.md)를 따른다.

변화는 새 기능 이름보다 새 플레이어 선택으로 설명한다. 무엇을 새로 발견·수집·조립·판단하게 됐는지와 기존 선택·Save/Replay가 왜 보존되는지를 함께 증명한다.

신규 기능도 E9 관점의 최종 안정 세계부터 E1 계약까지 먼저 내려가 영향을 검토할 수 있다. 이후 가장 낮은 누락부터 상향 조립하고 새 영향이 발견될 때마다 다시 하향 검토하는 왕복을 반복한다. 이때 E9는 목표 봉투이고 실제 미완료 구간은 G1·G2·G3가 관리한다. 작업 명세 작성이나 G4 관점 사용만으로 E9가 되지 않으며, 상세 절차는 [E9↔E1 반복 왕복 구현 체계](E9하향식수직구현체계.md)를 따른다.

## 축과 이름의 호환 원칙

- `E0~E9`는 증거 성숙도에만 사용한다.
- `G1~G4`는 이 문서의 관리 체계에만 사용한다.
- `H1~H5`는 공간 포함 깊이에만 사용한다.
- 과거 WI–H 공동 진척 문서에서 공간 생산 순서를 가리키던 `G1~G4`는 `H관문-1~4`로 이관한다.
- 다른 문서의 제품·공급자별 단계는 `Google-1`처럼 소유 영역을 포함한 이름을 사용해 G 관리 체계와 구분한다.
- 기존 공개 계약·저장 값·외부 문서의 안정 식별자에 G 문자열이 포함된 경우에는 무조건 이름을 바꾸지 않는다. 별칭과 이관 관계를 기록하고 소비자 호환성을 먼저 확인한다.

## 현재 판정

이 정의를 도입한 것 자체는 E8이나 E9 증거가 아니다. 현재 세계 상호작용 원장의 기본 통합 목표 `E7`도 자동 변경하지 않는다. E8은 선정된 NPC 생활세계 단위, E9는 선정된 E8 세계에 실제 변경을 적용한 변화 단위별로 별도 증거를 쌓는다.
