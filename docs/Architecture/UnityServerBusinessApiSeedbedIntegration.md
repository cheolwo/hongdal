# Unity 서버 업무 API 모판 연결

## 1. 목적

감자 한 품목의 생산 규칙 실험을 넘어 서버에 이미 존재하는 여러 품목과 업무 API를 Unity 모판에서 같은 방식으로 읽고 실행 후보로 표현한다.

핵심은 서버의 비즈니스 로직을 Unity에 복사하는 것이 아니다. 서버가 권한·동의·현재 상태·멱등성을 검증하고 원장을 기록하며, Unity는 다음 흐름을 담당한다.

```text
서버 관점별 조회 결과
    ↓
Unity용 데이터 변환
    ↓
품목·배치 객체·가능 행동 표현
    ↓
행동 미리보기와 명시적 확인
    ↓
서버 API 요청
    ↓
같은 업무 기록 재조회
    ↓
Unity 표현 갱신
```

## 2. 첫 다품목 적용 범위

기존 도심마트 Simulation 표본에는 감자·쌀·양파가 있다. 이 세 품목을 같은 마트 모판 투영기로 처리한다.

| 품목 | 현재 연결 깊이 | 연결된 서버·Simulation 의미 | 아직 없는 것 |
| --- | --- | --- | --- |
| 감자 | 생산에서 마트까지 | 감자 생산 Fixture 규칙, 공개 상품·가격·판매 가능 수량, 비구속 주문 의향 | 생산 Lot과 운영 마트 상품 사이의 기준 원장 연결 |
| 쌀 | 마트 업무 | 공개 상품·가격·판매 가능 수량, 비구속 주문 의향 | 쌀 생산 규칙, 재배체·수확 Lot·생산 계보 |
| 양파 | 마트 업무 | 공개 상품·가격·판매 가능 수량, 비구속 주문 의향 | 양파 생산 규칙, 재배체·수확 Lot·생산 계보 |
| 그 밖의 운영 상품 | 마트 업무 자동 수용 | `mart-product:{id}` 공개 상품을 동적으로 투영 | 생산 품목 기준 고유 식별자와 시각 자산 연결 |

쌀과 양파는 감자 생산 규칙의 수치나 상태를 재사용하지 않는다. 현재 실제로 존재하는 마트 공개 상품 API의 범위까지만 연결한다.

모든 품목은 도심마트 Shop, 운영자 재고 Shelf, 집단수요 Cart Table과 관계를 표시할 수 있다. 감자만 현재 감자 재배체와 수확 상자를 추가로 참조한다. 운영자 Shelf는 권한이 필요한 내부 재고를 표현하는 배치 객체이며, 주문자 공개 판매 가능 수량을 내부 재고라고 표시하지 않는다.

## 3. 첫 서버 업무 API 대장

| 업무 | HTTP | API 경로 | 서버 의미 | Unity 상태 |
| --- | --- | --- | --- | --- |
| 공개 상품 목록 | GET | `api/v1/orderer/mart/products?판매가능만=false&page=1&pageSize=50` | 주문자 공개 상품과 판매 가능 수량 조회 | 실제 Unity Client 구현·집중 검증 완료 |
| 공개 상품 상세 | GET | `api/v1/orderer/mart/products/{productId}` | 상품 상세와 개인정보가 제거된 구매 근거 조회 | 계약 준비 |
| 내 주문 의향 목록 | GET | `api/v1/orderer/mart/order-requests` | 인증된 사용자의 비구속 의향 조회 | 계약 준비 |
| 내 주문 의향 상세 | GET | `api/v1/orderer/mart/order-requests/{orderRequestId}` | 기록 직후 같은 의향 재조회 | 실제 Unity Client 구현·집중 검증 완료 |
| 주문 의향 등록 | POST | `api/v1/orderer/mart/order-requests` | 비구속 구매 의향 기록 | 실제 Unity Client 구현·집중 검증 완료 |
| 의향 수량 변경 | PUT | `api/v1/orderer/mart/order-requests/{orderRequestId}/quantity` | 제출 상태의 본인 의향 변경 | 대장 등록 |
| 의향 철회 | POST | `api/v1/orderer/mart/order-requests/{orderRequestId}/withdrawal` | 본인 의향 철회 | 대장 등록 |

실제 Unity 프로젝트에는 공통 `UnityWebRequestApiClient`를 사용하는 공개 상품·주문 의향 Client를 추가했다. 공개 상품은 인증 없이 조회하고, 주문 의향 등록과 상세 재조회는 인증을 요구한다. 운영 요청이 실패하면 Simulation 상품으로 바꾸지 않고 실패를 그대로 드러낸다. 다만 실제 서버 주소와 인증 토큰 제공자를 Scene 조립부에 연결해 서버를 호출한 단계는 아니다.

Unity 서버 연결 설정은 실제 운영 서버와 예행연습·게임 세계 서버를 별도 주소로 관리한다. 공개 상품과 주문 의향 Client는 운영 서버 주소만 사용하고, WorldTick과 가상 생산·소비·운송·창고 Client는 예행연습·게임 세계 서버 주소만 사용한다. 공통 `UnityWebRequest` 전송 구현은 재사용하지만 두 역할의 Client 인터페이스는 분리해 잘못된 서버 주입을 컴파일 단계에서 차단한다.

## 4. 비구속 주문 의향 규칙

Unity 미리보기는 다음을 보여준다.

- 선택 품목과 판매 단위
- 요청 수량
- 공개 단가와 예상 합계
- 공개 판매 가능 수량
- 서버 요청을 막는 사유

서버 요청 전 후보 검증 항목은 다음과 같다.

- 인증 여부
- 신청 개인정보 동의 증적
- 신청 출처
- 멱등성을 위한 클라이언트 요청 ID
- 수량 1~100
- 현재 공개 판매 가능 수량 이내
- 현재 안내 버전 `2026-07-20`
- 비구속 주문 요청임을 명시적으로 확인

이 검증은 사용자에게 빠르게 이유를 설명하기 위한 미리보기다. 서버는 요청을 받을 때 같은 조건과 현재 상품 상태를 다시 검증한다.

서버에 의향이 기록돼도 다음은 발생하지 않는다.

- 내부 재고 차감 또는 예약
- 결제
- 주문 확정
- 피킹·포장
- 배송 또는 계약

Unity는 등록 응답만으로 완료하지 않는다. 서버가 반환한 주문 요청 ID로 상세 API를 다시 조회하고, 품목·수량·금액·상태·제출 시각·재고 예약·결제 여부가 일치할 때만 재조회 조화 완료로 표시한다.

## 5. API 계약 호환

서버 JSON 필드는 기존 계약을 그대로 유지한다.

```text
신청개인정보동의증적Id
신청출처Code
클라이언트요청Id
공개상품Id
수량
비구속주문요청확인
안내버전
```

응답도 `주문요청Id`, `상태코드`, `재고예약됨`, `결제됨` 등 기존 필드 이름을 그대로 사용한다. Unity 내부 표현 모델만 사람이 읽는 역할에 맞게 분리한다.

## 6. 현재 검증 범위

독립 패키지의 집중 테스트 12개로 다음을 검증한다.

- 감자·쌀·양파 동시 투영
- 감자만 생산 규칙 연결로 분류
- 쌀·양파의 마트 업무 한계 표시
- 임의 개수의 운영 상품 동적 투영
- Simulation 상품의 운영 API 호출 차단
- 서버 API 대장의 조회·Command 구분
- 양파 주문 의향 미리보기·등록·상세 재조회 폐루프
- 인증·개인정보 동의·수량 차단
- 재고 예약 또는 결제를 주장하는 비정상 응답 거부
- 등록 응답만으로 완료 처리하지 않음
- API UseCase의 등록 후 상세 재조회 강제
- 기존 한국어 JSON 계약 필드명 보존

실제 Unity 프로젝트의 집중 EditMode 테스트 4개로 다음을 추가 검증했다.

- 공개 상품 목록 경로와 감자·쌀·양파 JSON 변환
- 공개 조회의 비인증 요청과 주문 의향 등록·상세 조회의 인증 요청 구분
- 주문 의향 등록 시 기존 한국어 JSON 필드와 수량·확인 값 보존
- 등록 응답의 ID를 상세 재조회 경로에 사용
- HTTP 실패 시 Simulation 자료로 대체하지 않음

열린 Unity 6000.5.6f1 Editor에서 재컴파일 오류 0건과 집중 EditMode 4/4 통과를 확인했다. 실제 서버 기동, 인증 세션, 운영 DB 저장, 실제 HTTP 왕복, Scene 조립, Prefab, Play Mode와 Game View는 아직 검증하지 않았다.

## 7. 다음 확장 순서

1. 상품 상세의 구매 근거를 모판 정보 Panel에 연결한다.
2. 실제 운영 서버 인증 토큰 제공자와 Unity 모판 조립부를 연결하고 공개 조회와 인증 재조회를 검증한다.
3. 서버 공개 상품에 생산 품목 기준 고유 식별자를 추가할지 계약·DB 영향을 검토한다.
4. 쌀 또는 양파 가운데 하나를 두 번째 생산 규칙 연구 대상으로 정한다.
5. 주문 의향 이후의 주문자 관점, 상차·하차·창고 관점별 조회 결과를 같은 품목 계보에 연결한다.
6. 공통 실험대 Prefab과 한국어 효과 비교 Panel을 실제 전시관 Scene에 배치한다.
