# 프로젝트 불변 개발 골격

## 목적

최근의 게임 개발 원칙을 일시적인 작업 방식이 아니라 이후 리팩토링과 기능 개발이 지켜야 하는 프로젝트 골격으로 고정한다. 이 문서는 개별 기능의 설계를 대신하지 않는다. 기능·규칙·공간·화면은 계속 바꿀 수 있지만, 아래 경계를 바꾸려면 새 확정 결정, 호환 계획과 소비자 회귀 근거가 먼저 필요하다.

기계 판본은 [`project-invariant-baseline.json`](../../eng/execution-ledgers/project-invariant-baseline.json)이다. 문서와 대장은 E 증거를 만들거나 현재 작업을 승격하지 않는다.

## 불변 기준선

| 고유 식별자 | 유지할 골격 | 바꿀 수 있는 부분 |
| --- | --- | --- |
| `INV-AUTHORITY-01` | Operations는 실제 업무 원장, Simulation은 게임 세계, Unity는 입력·표현을 소유한다. Integration은 독립 권위가 아니다. | 서비스·Adapter·화면의 구체 구현 |
| `INV-CORE-01` | Solo `LocalProcess`와 Hosted `RemoteHost`는 같은 Simulation Core의 규칙·Session·Save/Replay를 실행한다. Unity `GameObject`는 권위가 아니다. | Host 전송 방식과 저장 Adapter |
| `INV-COMMAND-01` | 권위 변경은 Preview·명시적 Confirm·Task/Effect·Revision·상태 사본 재조회 경계를 통과한다. | WI별 요청 필드와 피드백 표현 |
| `INV-TIME-01` | 표현 실시간, 권위 실시간, WorldTick, BattleTick과 WorldRevision은 서로 다른 의미다. | Profile별 주기와 균형 수치 |
| `INV-EGH-01` | E는 증거 성숙도, G는 관리 체계, H는 공간 포함 깊이다. 계획·문서·관리 완료는 E 승격이 아니다. | 단계별 세부 질문과 증거 형식 |
| `INV-SPACE-01` | 플레이어는 H1을 조립할 수 있고 H2·H3는 집합·연결·폐루프를 Simulation이 성장 판정한다. H4·H5는 현재 임의 생성 대상이 아니다. | H1 청사진, 비용, 배치 후보와 성장 조건 |
| `INV-WORLD-01` | 공식 Unity 진입점은 `SimulationWorldShell` 하나다. Nature↔Farm은 첫 기준 왕복이며 Farm·Hub·Town·City는 독립 폐루프를 먼저 가진다. | 검토 Scene, 영역 내부 콘텐츠와 후속 통합 경로 |
| `INV-COMPAT-01` | 공개 Stable ID·API·직렬화·Save/Replay 판본과 hash 의미는 명시적 Migration 없이 바꾸지 않는다. | 내부 이름·파일·부분 클래스·호환 facade 뒤 구현 |

## 변경 가능한 구조를 다루는 법

- 파일과 폴더 이동, 클래스 분할, 좁은 인터페이스 추가는 공개 의미와 소비자 검증을 보존하면 가능하다.
- 기존 공개 이름이 새 책임과 맞지 않으면 값을 즉시 바꾸지 않고 새 내부 이름을 추가한 뒤 기존 이름을 호환 facade로 둔다.
- `CityHub`처럼 과거 저장 값에 남은 결합 이름은 호환 값으로 보존하되 새 기능 판단에서는 Hub와 City를 분리한다.
- `ReviewFixture`는 플레이 권위 위치가 아니라 실행 목적이다. 기존 enum 값은 호환용으로만 남기고 신규 코드는 `SimulationRuntimePurpose`를 사용한다.
- Synty 자산과 Unity Prefab은 교체 가능한 표현이다. 배치됐다는 사실만으로 자원 소비, H 성립, Simulation 결과 또는 운영 완료를 주장하지 않는다.

## 리팩토링 순서

```text
현재 플레이·저장·소비자 시험 기준선
  → 불변 항목과 호환 표면 확인
  → 새 내부 책임 이름·좁은 경계 추가
  → 기존 공개 표면을 facade로 연결
  → Domain·Application을 새 책임으로 이관
  → Save/Replay와 .NET·Unity 소비자 회귀
  → 현재 E 상태를 올리지 않고 결과 기록
```

새 기능을 함께 구현해야 한다면 별도 E9↔E1 반복 왕복 작업 명세로 분리한다. 리팩토링 성공은 동작·저장·소비자 호환이 유지됐다는 뜻이며 E7·E8·E9 플레이 증거가 아니다.

## 현재 호환 경계

- `SimulationRegionalIncidentCodes`는 기존 API·저장 소비자를 위한 facade다. 신규 Nature 위협과 지역 인과 구현은 각 전용 코드 계열을 사용한다.
- `ISimulationSessionGameplayRuntime`과 `ISimulationWorldInteractionRuntime`은 기존 소비자 facade다. 신규 소비자는 필요한 좁은 Runtime 포트를 선택한다.
- `SimulationAuthorityLocation.ReviewFixture`와 `SimulationRuntimeDescriptor.IsReviewFixture`는 호환 표면이다. 신규 실행 판단은 권위 위치와 실행 목적을 분리한다.
- `UnityPackage/Runtime` 이관은 .NET과 Unity가 같은 실제 Core 소스를 컴파일하기 위한 패키징 변경이다. 공개 namespace와 assembly 의미를 바꾸지 않는다.
