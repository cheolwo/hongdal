# 개별수출·공동수출 원장 모델

## 목적

수출을 하나의 선적 상태로 축약하지 않고, 주로 `커뮤니티 교류 → 당사자의 별도 주문 동의 → 개별주문 → 개별수출 확장 → 필요 시 공동수출 물류 집계`로 표현한다. 완료 경험은 참여자가 다시 동의한 경우에만 교류장으로 환류한다.

```text
community-conversation
  └─(Reference, 선택적 1:N)─> export-exchange-community
       └─(명시적 주문 제안·조건 동의, Handoff, 선택적 1:N)─> order
            └─(개별수출, Contains, 선택적 1:N)─> individual-export
                 └─(완료·별도 공유 동의, Reference, 선택적 N:1)─> export-exchange-community

group-export
  └─(개별수출, Contains, 필수 1:N)─> individual-export
```

- `export-exchange-community`는 새 주문·계약 원장이 아니라 기존 커뮤니티 게시글, 비구속 관심과 선택적 가원장을 조립하는 `수출 교류장` OS 모듈이다.
- `order`는 상품, 수량, 가격, 계약과 서명의 원본이다.
- `individual-export`는 수출자, 해외 구매자, 거래 조건, 요건·서류, 신고·수리·적재와 대금 증빙을 덧붙이는 확장 원장이다.
- `group-export`는 여러 개별수출의 집하, 합포장, 운송 방식 검토, 포워더 인계, 통합 포장목록과 공통 비용을 조율한다.
- 공동수출은 개별 주문이나 신고를 하나로 다시 작성하는 원장이 아니다. 수출자, 구매자, B2B/B2C 문맥, 신고번호, 상업송장, 신고 수리와 적재 실적은 각 `individual-export`에 남긴다.

## 수출 교류장과 개별수출의 순환

수출 교류장은 상품을 먼저 파는 목록이 아니라 문화·사용 경험, 서로의 원함, 상호 이익과 기여, 비용·노동·위험을 나누는 비구속 커뮤니티다.

- 사람의 마음, 호감과 관심을 점수화하거나 신뢰 순위·거래 자격·자동 주문의 근거로 쓰지 않는다.
- 관심 표시, 연락처 공개, 가원장, 주문 제안, 주문 조건·서명, 수출 실행과 완료 경험 공유는 각각 별도의 동의다. 한 단계의 동의가 다음 단계로 승계되지 않는다.
- 수출 교류장에서 주문으로 넘어갈 때에는 상품, 수량, 가격, 책임과 계약 조건을 당사자가 별도로 확인한 `order`를 먼저 만든다. 교류 게시글이나 가원장이 주문 원본을 대신하지 않는다.
- `individual-export`는 원천 교류 게시글·가원장을 선택적으로 참조할 수 있지만, 이미 당사자가 직접 합의한 B2B/B2C 주문은 교류장 없이도 수출 확장으로 이어질 수 있다. 여기서 “주로”는 권장 사용자 여정이지 서버의 강제 조건이 아니다.
- 완료 환류는 선적·적재 실적 확인 뒤 참여자가 공개 범위와 비식별 처리에 다시 동의한 경우에만 가능하다. 연락처, 주문 상세, 신고번호와 서류 원본은 공개 환류에서 제외한다.
- 환류된 경험과 편익은 다음 대화의 출발점일 뿐, 다른 사용자의 주문이나 수출을 자동 생성하지 않는다.

## 공식 자료에서 확인한 업무 경계

### 수출신고와 적재

관세청은 수출통관을 수출신고, 세관의 심사·수리, 외국무역선·항공기 적재로 이어지는 절차로 설명한다. 신고 자료에는 수출자·신고인, 거래구분, 결제방법, 목적국, 적재항 같은 정보가 포함되고 상업송장과 포장명세서가 기초 서류로 쓰인다.

수출신고 수리 후 적재에는 기한이 있으며 연장·취소 가능성도 있으므로 원장에 다음을 분리한다.

- 신고 상태·신고번호·신고일
- 수리 상태·수리번호·수리일
- 적용 적재기한·연장 여부·근거
- 실제 선적·적재일과 실적 근거

관세 규정과 금액 기준은 바뀔 수 있다. 관세청은 2026년 자료에서 간이수출신고 기준 상향 계획도 안내했다. 따라서 원장은 일반·간이·목록 신고 후보를 자동 확정하거나 금액 기준을 상수로 저장하지 않고 `공식 출처, 기준 시행일, 사람 확인 상태`를 함께 보존한다.

### 공동수출과 합포장

관세청 전자상거래 수출 지원 자료에는 여러 수출자의 간이신고 물품을 하나의 포장·배송 단위로 합포장할 수 있는 절차가 설명되어 있다. 이때에도 수출신고와 적재 실적 관리는 사라지지 않는다.

이 원칙을 코드에서는 다음처럼 해석한다.

- 물류 단위는 묶을 수 있다.
- 수출자와 개별수출 원장은 합쳐 지우지 않는다.
- 통합 포장목록은 `공동 선적 참조 ↔ 개별수출 원장 ID ↔ 포장번호 ↔ 품목·수량` 매핑이다.
- 한 건이 미도착하거나 요건을 충족하지 못하면 해당 개별수출을 분할 선적으로 전환할 수 있어야 한다.

### 전략물자·원산지·Incoterms

- 전략물자 여부는 자가판정 또는 전문판정과 허가 검토 영역이다. 엔진은 후보와 누락만 제안하고 판정 결과를 직접 확정하지 않는다.
- 원산지증명은 특혜·비특혜, 기관발급·자율발급과 협정별 요건이 다르므로 모든 거래에 동일하게 필수라고 처리하지 않는다.
- Incoterms는 세 글자 코드뿐 아니라 규칙 버전과 지정장소를 함께 저장해야 비용, 위험, 수출·수입 통관 책임을 해석할 수 있다.
- 영세율 관련 자료는 세무 신고의 근거 후보로 저장할 뿐 원장이 영세율 적용을 보증하지 않는다.

## 개별수출 원장

템플릿 Key는 `individual-export`이며 `IsExtensionTemplate = true`다. 일반 흐름 분류기가 독립 루트로 자동 제안하지 않는다.

| 블록 | 주요 데이터 |
| --- | --- |
| 원천 수출 교류장(선택) | 게시글 ID, 가원장 ID, 교류 시작 맥락, 참조 동의 상태 |
| 원천 개별주문 | 주문 원장 ID, 상품·수량·가격, 계약·서명 참조 |
| 거래 문맥 | B2B/B2C, 판매자·구매자 유형, 세금·증빙 검토 상태 |
| 당사자 | 수출자, 수출신고인, 위임 근거, 해외 구매자, 수하인, 목적국 |
| 물품 | 품명·규격, 수량·단위, 금액·통화, HS 후보와 근거 |
| 원산지·인도조건 | 원산지·FTA 근거, Incoterms 규칙·버전·지정장소, 비용·위험 책임 |
| 요건·서류 | 전략물자·목적국 요건 상태, 전문 검토자, 상업송장·포장명세 참조 |
| 신고 | 신고 방식 후보, 공식 근거·시행일, 신고·수리번호와 상태 |
| 적재 | 적용 적재기한, 연장 근거, BL/AWB, 선박·항공편, 적재일·실적 |
| 정산·사후 | 수출 대금, 영세율 증빙 준비, 반품·재수입과 원수출 참조 |
| 완료 후 교류 환류 동의 | 참여자별 공개 동의, 공개 범위, 비식별 처리, 철회 상태 |

상태 전이 원칙은 다음과 같다.

1. 원천 개별주문이 먼저 존재한다.
2. 수출자·구매자, 물품, HS 후보, Incoterms·지정장소를 특정한다.
3. 전략물자·목적국 요건, 원산지와 상업송장·포장명세를 사람의 검토 상태와 함께 기록한다.
4. 적용 신고 방식을 확인한 뒤 신고·수리 정보를 기록한다.
5. 수리와 적재기한을 확인한 뒤 포워더 회신과 실제 적재 실적을 기록한다.
6. 원천 교류장이 있고 참여자가 다시 동의한 경우에만 비식별 경험과 편익을 환류한다.

## 공동수출 원장

템플릿 Key는 `group-export`다. 하나 이상의 `individual-export`만 `개별수출` 역할로 포함할 수 있다.

| 블록 | 주요 데이터 |
| --- | --- |
| 개별수출 집합 | 개별수출 원장 ID, 원천 주문 ID, 수출자, 목적국·수하인 |
| 거래 문맥 집계 | B2B/B2C별 건수·금액, 혼합 여부, 분리 필요 사유 |
| 신고 보존 | 수출자별 신고·수리·상업송장·적재 실적 참조 |
| 집하·합포장 | 집하 장소·마감, 포장 그룹, 온도·위험물, 중량·부피 |
| 운송 검토 | FCL/LCL/항공 후보, 선정 근거, 일정과 포워더 회신 |
| 통합 포장목록 | 공동 선적 참조, 개별수출 원장 ID, 포장번호, 품목·수량 매핑 |
| 실적·비용 | 공동 선적 참조, 개별 적재 실적 연결, 공통비 배부 기준·금액 |
| 예외 | 미도착, 요건 미충족, 분할 선적과 재계획 상태 |

FCL·LCL·항공은 사용자나 OS가 미리 하나로 고정하지 않는다. 물량, 포장, 온도·위험물, 목적지, 일정과 포워더 회신을 근거로 후보를 비교하고 사람이 선택한다.

## OS·엔진·API 경계

- 수출 교류장, 개별수출과 공동수출의 대상 OS는 현재 `CommunityTrust`다. 별도 수출 OS를 형식적으로 추가하지 않고, 기존 OS가 `교류 → 별도 주문 동의 → 개별수출 → 선택적 환류`와 물류 집계 순서를 조율한다.
- `수출 통관·규제 검토 엔진`은 HS, 요건, 누락 서류와 집계 후보를 반환할 수 있지만 신고, 허가, 계약, 포워더 선정과 선적을 확정하지 않는다.
- 실제 상태 변경은 기존 `주문원장Controller → I주문원장통합UseCase → 원장 저장소` 경계를 재사용한다.
- 전용 생성 API는 계약 후보로만 선언한다.
  - `POST api/v1/community/order-ledgers/{orderLedgerId}/individual-export-extension`
  - `POST api/v1/community/group-export-ledgers`
- 저장 원본은 MongoDB `community_ledgers`다. 신고·선적 외부 참조를 RDB 업무 엔티티로 투영할 때에는 별도 Command/Event/Outbox와 멱등 정책을 먼저 마련한다.

## 버전과 실행 경계

- `1.5`: 수출 교류장, 별도 동의 경계, 공급·가격·무역 준비, 원장 계약, 근거·상태·포워더 handoff와 선택적 환류 기록
- `2.0`: 실제 국제·국내 운송 수행자와 선적 실행 연동
- `2.5`: 창고 입출고, 재고, 판매채널·반품 이행

현재 구현은 Simulation 경계다. 외부 포워더 자동 전송, 수출신고 제출, 전략물자 판정·허가 신청, 계약 서명, 결제와 운송 지시를 실행하지 않는다.
