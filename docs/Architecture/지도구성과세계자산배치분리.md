# 지도구성과 세계자산배치 분리

## 목적

기존 LH 셀 공급 안에 섞인 지도 골격과 객체 배치 책임을 분리한다. 지도구성은 지면·셀·통로·H 결속·배치 Anchor를 만들고, 실외자산배치와 실내공간조립은 각각 건물 밖과 안의 계획을 만든다. LH는 지면과 셀만 준비하며 자산 Prefab 생성·배치·해제를 소유하지 않는다.

```text
Simulation 권위 상태
  -> 공간변화 Projection
  -> 지도구성Engine
  -> LH 지면·셀 준비
  -> Sky 대기 표현 적용
  -> 실외자산배치Engine + 실내공간조립Engine
  -> World공간표현조립Coordinator
  -> Unity VisualKey 표현·셀 활성
```

이 순서는 Unity 조립 순서다. Simulation의 세계 대기 상태 계산은 LH에 의존하지 않으며, Coordinator가 동일 revision의 이미 계산된 상태 사본을 지면 준비 뒤 적용한다.

## 배치 책임 구분 — D423 (2026-08-31)

사람이 읽는 기획·설명에서 모호한 **배치 계층**은 **배치 구조·제약 체계**로 구체화한다. 기존 H 의미 계층이나 Scene의 부모·자식 구조 전체를 이 이름으로 합치지 않는다. 아래 네 항목은 기존 코드에 적용할 책임 구분이지 새 엔진·관리자 네 개를 만드는 요구가 아니다. [D423 리팩토링 승인](../AI/배치책임구분-리팩토링승인-2026-08-31.md)에 따라 개발이 실제 호출 관계와 회귀를 확인하며 적용한다.

| 책임 | 답하는 질문 | 입력·출력 | 맡지 않는 일 |
| --- | --- | --- | --- |
| 배치 구조·제약 체계 | 무엇을 어디에 포함하고, 어떤 조건을 지켜야 하는가? | 기존 영역·외곽·기준점·크기·통로·지지·소유 규칙을 배치에 필요한 조건으로 제공 | Prefab을 생성하거나 H 성립·게임 상태를 확정하지 않음 |
| 배치 계획 엔진 | 그 조건 안에서 어떤 후보를 어디에 놓을 것인가? | 같은 상태 사본·지도·자산 후보·규칙으로 배치 객체, 위치·방향, 계획 판본/hash를 계산 | Unity 객체 생성·삭제나 권위 결과 확정이 아님 |
| 배치 검증 | 계획과 실제 적용이 각각 조건을 충족하는가? | 구조/참조 검사, 계획의 지지·점유·접근·통행 검사, 적용 후 실물 대조를 범위별로 반환 | 구조 검사 하나를 실제 지면·통행·입력 통과로 확대하지 않음 |
| 월드 조립·표현 | 검증된 계획을 어떻게 보여주고 안전하게 해제·재적용할 것인가? | 실제 Prefab/대체 표현 연결, 배치 객체·Renderer·Collider·상호작용 연결, 소유 자원 수명과 적용 결과 | 계획을 몰래 재설계하거나 Simulation 상태·명령 결과를 변경하지 않음 |

기본 관계는 **구조·제약을 참조하여 계획 계산 → 계획 검증 → 실제 조립 → 실물 대조·해제·재적용**이다. 계획 엔진은 후보를 찾는 중에도 기존 공통 검사를 호출할 수 있다. 검증은 독립된 책임이지만 반드시 새 서비스나 한 번뿐인 단계일 필요는 없다. 실패하면 해당 책임의 가장 작은 입력·계획·연결부터 보완한다.

### H·지도·LH와의 관계

- H는 장소의 의미·포함·성립 관계다. `H1 운영 증거 → H2/H3 성립 → H4 준비도`의 확정 권위는 Simulation에 있다. [상향식 성립 기준](상향식배치성립통제계층.md)을 유지한다.
- World/Area/H 외곽에서 내려오는 위치·크기·접근 조건은 배치 구조·제약 체계가 참조하는 제약 축이다. H의 상향식 성립과 물리 배치의 제약 방향을 같은 것으로 해석하지 않는다. 감각 표현 채널도 새 H나 배치 단계가 아니다.
- 지도구성은 지형·셀·통로·영역 기준점을 제공한다. 배치 계획 엔진은 그 지도 조건을 읽어 자산 배치 계획을 계산한다.
- LH는 필요한 지면·셀·관심 범위와 준비·활성·캐시·해제를 조율한다. 개별 배치 자산의 생성·해제는 기존 월드 조립·표현 소유자가 수행한다. LH가 별도의 배치안을 계산하거나 모든 Renderer를 직접 소유하는 구조로 바꾸지 않는다.
- Sky의 대기 표현, Simulation의 시간·WI·공간 성립 권위, 기존 통합 파이프라인의 요청 세대/판본·실패·회복 경계는 그대로 유지한다.

### 검증 이름과 실제 범위

현행 `배치통제계층Root.Validate`는 선언된 참조·판본·계층/규칙 구성의 정합성 검사다. 실제 활성 Renderer·Collider·지지면·통행 전체를 검사하는 보편 배치 검증기로 부르지 않는다. 기존 계획 검증기와 조립 후 실물 확인을 각각 연결한다. 특정 과거 모판의 여러 영역·합성 지면 조건은 그 시험 범위이며, 작은 Farm 적용에 모든 영역을 강제하는 보편 조건으로 옮기지 않는다.

성공 기록도 `구조·참조 확인 / 계획 조건 확인 / 실제 조립 확인 / 통행·입력 확인 / 해제·재적용 확인`으로 구분한다. 자산 키를 찾았다는 사실이나 셀 활성/적용 반환값만으로 기대한 모든 배치 객체가 실제 나타났다고 판정하지 않는다. 현재의 위치 보정·누락 건너뛰기 경로는 숨기지 않고 기록하며, 동결 계획과 충돌하는 변경은 [D422 Farm 적용](../AI/Farm월드맵-배치계층경유-점진구성-2026-08-31.md)의 별도 연결 범위에서 다룬다.

### 호환과 적용 범위

기존 `배치통제계층Root`, `Configure*`, `Validate`, `placement-control-hierarchy.v1`~`v4`와 파일 경로·직렬화 필드·GUID·저장 값은 호환 식별자로 유지한다. 기존 문서의 ‘배치 계층/통제 계층’은 이 안내를 통해 읽으며, 명칭 정리를 이유로 동결 원문이나 과거 증거를 일괄 치환하지 않는다. 이하 D363~D406의 당시 결정·증거는 보존한다.

D423은 책임·이름·구현 경계의 리팩토링 승인이다. 기존 판정·계획 결과를 바꾸는 새 배치 규칙 승인이 아니며, 문서 반영만으로 코드 리팩토링·실제 배치·E5 완료를 선언하지 않는다. Farm의 작은 실제 적용은 D422 범위로 이어가고, 다른 영역·중지된 작업 전체를 자동 재개하지 않는다.

## 현재 작업 범위 — 월드 적용 전 패턴 조합·규칙 검토 (D442, 2026-08-31)

사용자는 실제 월드 배치보다 여러 패턴의 조합과 자연스러움을 위한 배치 규칙 검사를 먼저 구현하도록 정정·승인했다. 현재 범위는 [D442 승인 원문](../AI/패턴조합-배치규칙검증-D442-개발인계-2026-08-31.md)에 따라 `패턴/자산 근거 → 검토용 조합 후보 → 기존 규칙의 전달·검사 보완 → 격리 미리보기 → 국소 개선`에서 끝난다. 이번 원문이 아래 D406/D422의 실제 지도·보행 우선보다 현재 실행 범위에 우선하며, 과거 승인·증거를 삭제하지 않는다.

H/AreaSet과 위 D423의 책임 분리는 유지한다. 필수 지지·점유·출입/통행·경계 조건과 장소별 밀도·반복·여백의 시각 비교 기준을 구분하고, 패턴 내부뿐 아니라 공간상 이웃·접점·전체 조합을 검사한다. 기존 판본/실행 결과는 보존하고 새 규칙은 명시적인 검토 판본으로 연결한다. 수치/측정 누락을 통과로 바꾸거나 미관 점수로 필수 실패를 상쇄하지 않는다.

Graph Map 레벨 2는 이 책임 구분의 조회·인계 표면이다. [배치 규칙 결속 대장](../../eng/world-seedbeds/graph-maps/placement-rule-bindings.v1.json)이 H5 Area별 기존 규칙 코드, H1~H4 계층, LH·플레이어 조립 방식의 판본을 참조하고 각 Graph 제약의 직접 적용 여부를 구분한다. Graph Map은 배치 규칙 원본·계획 엔진·H 성립 권위를 흡수하지 않으며, 아직 대상·수치·실측이 없는 규칙을 `AvailableNotSelected`로 남긴다.

개발이 코드·시험·명세와 전문 배분을 맡고 공간 담당은 공식 World와 분리된 임시 공간에서만 자산 조합을 보여준다. 정상/문제 후보의 비교는 허용하지만 공식 Scene·실제 Session·World·Save는 변경하지 않는다. 검토 성공 뒤 실제 월드 적용으로 자동 이어가지 않으며 r129/야간을 재개하지 않는다. D440/D441 자산 할당·분류의 독립 범위는 유지하고 실제 적용은 별도 후속 지시 대상으로 둔다.

## 현재 실행 우선순위 — 지도 기반과 보행 먼저 (D406, 2026-08-31)

> 기존 제목/앵커는 호환을 위해 유지한다. 이 절은 D406 당시 범위이며, 이번 작업에서는 위 D442의 월드 적용 전 검토 범위가 우선한다.

사용자는 Play 전 화면에 흩어진 사람·집·창고 등의 불필요한 초기 표시를 정리하고, 큰 월드맵의 지형 기반을 먼저 마련한 뒤 실제 플레이어가 돌아다니는 것을 확인하기를 원한다. 그 위에 Farm·Town·City 등 각 영역의 건물/시설을 배치한다. [D406 실행 범위·보존·실제 화면 기준](../AI/월드맵우선-초기표시정리와보행검증-2026-08-31.md)을 따른다.

이번 우선순위는 `정확 초기 표시 식별/정리 → 기존 지도 기반 연결/큰 구도 → 실제 보행과 재진입 → 영역별 배치`다. 아래 D363의 당시 배치 우선보다 이번 지도 기반을 먼저 다루되 D364/D405의 내부 책임·조립 순서는 유지한다. 전체 월드맵 완성이나 Farm→Town→City 경로를 개별 WI의 필수 선행으로 만들지 않으며, 기존 기능·원본·권위 상태는 보존한다. D406의 좁은 Editor/Play/캡처·조건부 자기 변경 저장 승인은 과거 야간/r129 전체 재개와 다르다.

## 배치 고도화 우선순위 — D-363 (2026-08-30, 당시 결정)

사용자는 LH 자체의 확장보다 **배치 엔진 고도화**를 먼저 진행하고, LH는 그 결과가 필요한 곳에서 원활히 나타나도록 지원하는 방향을 선택했다. 이는 개발 우선순위와 책임 구분이며 위의 실행 순서를 뒤집는 결정은 아니다.

| 책임 | 우선 다룰 내용 | 넘겨받은 결과를 임의로 바꾸지 않는 경계 |
| --- | --- | --- |
| 지도구성 | 지형·하천·길·H 공간과 배치 기준점 제공 | 배치 장식 때문에 생산 면적·지형 권위를 변경하지 않음 |
| 실외·실내 배치 엔진 | 자산의 실제 크기, 점유·통행·작업 접근, 군집·여백·가림과 기능별 조립을 반영한 재사용 가능한 계획 | 자산 모양만으로 재고·작물·NPC·조명 기능을 확정하지 않음 |
| LH | 계획에 필요한 셀의 선행 준비·활성·캐시·해제 및 재진입 지원 | 승인된 배치 구도를 다시 설계하거나 셀 로드로 세계 상태를 초기화하지 않음 |
| Unity 조립·표현 | 배치 계획과 같은 상태 사본을 소비하여 객체·Renderer·Collider·조명·LOD 등을 실제 화면으로 연결 | 실제 렌더링 책임을 LH의 계획·수명 관리와 혼동하지 않음 |

현재 첫 적용은 기존 Farm 부지 확대 및 LS-01 승인 범위를 유지한 A/B 후보 준비다. 실외 배치의 크기·통행·하천·작업 공간 보존과 경관 구성을 먼저 확인하고, 검증된 규칙을 재사용한다. 실내 책임도 유지하지만 이번 결정만으로 실내 추가 제작을 승인하지 않는다.

LH는 전면 개편하지 않는다. 배치 소비를 막는 오류, 실제 능력과 준비 표시의 차이, 경계 통과·재진입의 중복/누락은 필요한 기술 연결로 계속 검증한다. 높은 시점의 원경 표현이나 새 거리·성능 수치는 별도 확인 사항이며 자동 확정하지 않는다.

기존 연구·기획의 동결 판본/hash, 후보 승인·실제 조립·Game View의 구분을 보존한다. 새 알고리즘·계약 변경이 필요하면 개발이 영향과 작업 명세를 결속하며 이 우선순위 결정을 새 Scene·Save 변경이나 E 승격 근거로 사용하지 않는다. 관련 정적 조사: [LH 현행 연결과 경관 공백](../Reports/LH공간실행-현행결속과경관공백조사-2026-08-30.md).

## 하나의 공간 실행 파이프라인 — D-364 (2026-08-30)

사용자는 Simulation·배치·LH를 하나의 파이프라인에서 조율하고 실행·해제를 통합 관리하는 방향을 선택했다. **외부 진입과 진행 상태는 통합하고, 내부 책임과 권위는 분리한다.** D-363 배치 고도화 우선순위와 기존 조립 순서는 유지한다.

- Simulation은 권위 상태·시간·WI 결과를 소유한다. 파이프라인은 검증된 상태 사본을 읽거나 기존 권위 명령 경계를 호출하며 독자적인 세계 원장을 만들지 않는다.
- 지도·실외/실내 배치는 해당 상태와 지형에 맞는 계획을 제공한다. 계획 작성/검증과 실제 Unity 객체 조립을 분리한다.
- LH는 필요한 셀과 관심 범위를 준비·유지·캐시·해제한다. Unity 조립·표현은 그 범위의 계획과 상태 사본을 소비한다.
- 통합 조율은 요청 세대, 공간 식별자, 권위 개정, 계획 판본/hash를 연결해 준비·적용·실패·해제·재진입을 추적한다. 구체 계약은 기존 필드와 조율 객체를 우선 재사용한다.

통합 관리에서 관찰할 흐름은 다음과 같다. 이는 새 enum/API의 확정이 아니라 구현 수용 방향이다.

| 상황 | 파이프라인이 조율할 일 | 보존할 경계 |
| --- | --- | --- |
| 지역 접근·관심 등록 | 상태 사본/계획 확인, 필요한 셀 준비, Sky·실외·실내 표현 적용 | 기존 조립 순서 유지. 준비와 실제 통행·상호작용 성공을 구분 |
| WI 결과·계획 변경 | 해당 개정의 필요한 변경만 반영 | 배치 재계산이나 재조회가 명령·비용·행위 기록을 중복 생성하지 않음 |
| 지역 이탈 | 다른 플레이어/NPC/관심 요청의 필요 여부 확인 후 표현 캐시·해제 | 한 카메라의 이탈만으로 공유 관심 공간 전체를 해제하지 않음 |
| 늦은 응답·취소·실패 | 낡은 요청의 적용 차단, 자신이 소유한 미완성 표현/자원 정리, 단계별 실패 기록 | 표현 실패를 이유로 성공한 Simulation 명령을 되돌리지 않음 |
| 재방문 | 보존된 계획 식별자와 최신 권위 상태로 표현 재구성 | 작물·재고·NPC 업무 상태를 초기화하거나 새 발생 원인을 만들지 않음 |
| 세션 종료 | 기존 세션 저장·종료 경계와 표현 자원 정리 순서를 조율 | 셀 해제와 세션 종료를 같은 동작으로 취급하지 않음 |

공간 해제는 렌더링·충돌 등 표현 자원의 수명 관리다. 화면 밖의 작물 성장·NPC 업무는 기존 Simulation 시간/진행 규칙을 따르며, 이를 위해 모든 셀에서 프레임별 연산을 계속해야 한다는 의미도 아니다. 게임이 실행되지 않는 동안의 진행 규칙을 새로 승인하지 않는다.

기술 적용은 기존 `World공간표현조립Coordinator`, LH 실행 경로, 계획/표현 정합 처리와 권위 명령 경계의 호출 관계부터 대조한다. 기존 Coordinator에 Simulation 권위 코드를 흡수하거나, 새 최상위 관리자를 무조건 추가하지 않는다. 중복 조율 책임만 좁게 정리하고 구체 코드 소유는 개발이 작업 명세에 결속한다.

첫 적용은 진행 중인 Farm/LS-01 배치 소비 검증과 연결한다. 원A·승인 원문/hash·연구 기준선을 보존하고 후보·결속 검증·지면/통행·실제 조립·Game View 증거를 나눈다. 이 결정은 통합 운영 방향이며 신규 Save 규칙·게임 효과·Scene 적용·후보 시각 승인·E 승격을 자동 허용하지 않는다. 기존 승인 코드 작업을 새 이름/문서 대기로 중단하지 않는다.

## 절기별 산·숲 표현과 세 공간 엔진의 협력 — D405

2026-08-31 사용자는 한국24절기에 따라 산·나무·숲의 색감이 달라지는 표현과 월드맵·배치·LH의 협력을 원했다. 승인 의미는 [시간·절기 문답 r5](PlayableLoops/PlanningSessions/시간절기/seasonal-time-context.inquiry.r1.md)에 있다. D363/D364의 책임과 조립 순서를 유지하면서 계절 경관의 연결 지점을 정한다. 여기서 ‘월드맵 엔진’은 지도구성 책임을 가리키는 사람용 묶음이며 새 코드 이름이나 기능 구현 완료를 뜻하지 않는다.

| 책임 | 계절 경관에서 맡을 일 | 맡지 않는 일 |
| --- | --- | --- |
| 월드맵·지도구성 | 산·숲·하천·길의 큰 구조와 지역/H·지형·배치 기준점을 제공하고, 연결된 지역 문맥을 배치에 전달 | 절기가 바뀔 때 산 지형·길·H 계보를 재생성하거나 새로운 기후 규칙을 임의 생성 |
| 실외 배치·환경표현 계획 | 지형·수종·군집·밀도·여백·작업 접근을 고려한 배치에 계절별 표현 후보/판본을 연결. 실내 책임은 기존대로 별도 유지 | 색 변화만으로 나무의 ID/위치·벌목/작물 상태·재고·수량을 변경 |
| LH | 플레이어와 관심 범위에 필요한 지면·셀 준비, 활성·캐시·해제·재진입을 관리하고 현재 표현 판본의 재결속을 지원 | 팔레트·수종·산 위치를 독자 결정하거나 실제 Prefab 생성·해제 책임을 다시 흡수 |
| Unity 조립·표현 | 기존 조율자와 실외 표현 소비자가 확인된 후보를 실제 잎/줄기/지면/원경 Renderer·재질·LOD에 적용하고 복원 | 공유 원본을 재색칠하거나 독자 시간/게임 결과를 계산 |
| Sky | 같은 권위 문맥의 빛·환경광·안개·구름·기상으로 경관의 분위기를 표현 | 단풍 표현 대신 모든 Renderer 기본색을 일괄 변경하거나 나무 배치를 결정 |
| Simulation | 공통 권위 시간·계절/지역 문맥과 실제 WI 상태·결과를 소유 | 화면의 색·카메라·셀 로딩을 시간 경과나 수확 완료 근거로 사용 |

따라서 세 공간 엔진은 **구조·계획·공간 수명**을 나누어 하나의 흐름으로 관리하고, 실제 색/모양은 기존 Unity 표현이 담당한다. 시간의 권위와 Sky 표현까지 없애고 세 엔진만으로 세계 전체를 계산하자는 뜻은 아니다. 이미 적용할 상태 사본을 준비하는 일과 `지도구성 → LH 준비 → Sky 적용 → 실외/실내 조립` 실행 순서도 구별한다.

### 준비할 내용과 재사용 단서

- 기본 산·숲 배치와 계절 표현 판본을 구별한다. 계절 변경은 필요한 표현만 갱신하는 방향이며, 기존 공간 식별자·좌표·통행·WI 대상 상태를 보존한다. 낙엽/적설에 따른 실제 이동 비용·시야·생산 효과가 필요하다면 별도 규칙이다.
- 24절기 전체의 개별 Prefab 복제나 매번 숲 재배치를 필수로 삼지 않는다. 수종/지역별 재사용 팔레트·기존 Variant·전환 방식은 조사 후 제안한다. 정확 색·전환 시점/속도·원경 거리·성능 수치는 아직 정하지 않았다.
- 기존 `SimulationSeparatedLhCellContentSource`에는 기본 배치 hash와 `SeasonCode`/`SeasonRuleVersion`을 결합한 표현 hash, `SeasonPresentation` 능력 표기가 있다. 이는 파일 읽기로 확인한 재사용 단서이며 24절기 팔레트나 실제 화면 변색의 구현 증거가 아니다. 기존 실외환경표현 Engine·Coordinator와 함께 개발이 실제 소비/공백을 검증한다.
- [LS01 기존 연구](PlayableLoops/Farm경관-LS01-공간배치연구.md)는 Birch 줄기/잎 재질 슬롯과 LOD 단서, 공유 재질과 실제 제어 미검증을 기록한다. 그 보고/자산 목록을 재사용하되 과거 가림 연구의 수용을 계절 재질 가공 승인으로 전용하지 않는다. 산 후보의 존재·계절 적합성도 이번에 확인한 것으로 보고하지 않는다.
- Synty 조사에는 산/바위 실루엣 후보와 기존 수목·풀의 원본 GUID/hash, 잎/줄기/LOD·공유 재질/텍스처 구조, 기존 색 변형, 접지/Collider·주변 WI 간섭을 구분한다. `재사용 가능 / 연결 보완 / 가공 필요 후보 / 미검사`를 기록하고 새 구매나 Blender 제작부터 시작하지 않는다.

### 후속 검증의 기준

같은 기획/후보 판본에서 같은 지형·카메라·시간대·날씨로 계절 표현만 바꾼 대조와, 실제 시간/기상까지 함께 흐르는 통합 대조를 구분한다. 가까운 나무뿐 아니라 산/숲 원경, 인접 셀·LOD 경계, 플레이어 이동 왕복·표시 해제/재적용에서 색이 튀거나 이전 계절이 남는지 확인한다. 화면 밖에서 절기가 바뀌어도 재방문 시 현재 문맥을 사용하되 권위 상태를 초기화하지 않는다.

실제 Renderer 적용·복원과 원본 불변, 변경 대상 밖 오염, 상호작용 대상 식별성, 기본 배치/상태 불변을 함께 확인한다. 자동시험·격리 자산 비교·실제 Game View는 별도 근거이며 캡처는 공간 담당이 수행한다. 미확인 장식 색감 때문에 무관한 WI의 개별 성립을 막지 않되, 실제 대상 가림·통행 등 필수 조건의 실패는 유지한다.

현재 인계 범위는 **개발의 기존 코드/명세 연결 조사 + 공간의 기존 자산/연구 파일 조사 + 준비안 반환**이다. 정확 파일 소유는 개발이 지정하며 새 Editor 실행·촬영·원본 가공·Scene 저장·Save/게임 규칙 변경을 이번 문서만으로 시작하지 않는다. 실제 조립/시각 검증은 첫 지역/후보와 필요한 전문 연구를 명세에 결속한 뒤 이어간다. D403 자료조사·D404 접근 보고 및 D396의 독립 승인 준비는 계속한다.

## 권위 경계

- 채집 가능한 자원, 적대 개체와 WI 대상은 Simulation Core가 WorldTick에서 확정하고 Save/Replay한다.
- 그루터기·공사 자재·보관 소품처럼 권위 상태에서 파생되는 배치는 계획 hash를 갖지만 별도 게임 효과를 만들지 않는다.
- 풀·야생화·작은 돌 같은 주변 표현은 `PresentationOnly`이며 Unity나 LH가 재고·확률·개체 수 권위를 만들지 않는다.
- 확률은 정수 가중치로 표현하고 `WorldSeed + CellStableId + SpawnEpoch + RuleRevision + CandidateStableId + ProjectionHash`에서 결정적으로 판정한다.
- Spawn Epoch는 WorldTick·주기 경계·관련 권위 개정에서만 바뀌며 셀 재진입이나 Save Load는 새 발생 원인이 아니다.
- Sky·지면 상태는 첫 판본에서 `ExteriorEnvironmentPresentation`만 바꾼다. 비가 와도 나무·건물의 Stable ID와 기본 위치, 채집량, 이동 비용과 Spawn 결과는 바뀌지 않는다.

## 실내 결속

기존 `I실내공간조립Engine`의 v1·v2 고정 계획을 별도 실내 실행 경계가 소비한다. 기본 Fixture 계획과 변화 기반 LooseItem Overlay는 서로 다른 hash를 가진다. 보관량이나 안전 상태가 바뀌어도 침대·싱크대·선반이 자동 이동하지 않는다. 날씨는 실내 조명·창문 노출·강수 차폐만 바꾸며 실내 계획 hash에 들어가지 않는다. 증축·개조는 별도 WI와 새 Definition revision을 요구한다.

## 첫 Nature 결속

- `Standing`, `Stump`, 지면 통나무와 조우는 기존 Nature 권위 상태를 그대로 투영한다.
- 소음은 적대 흔적 가중치를 올리고 오두막 안전 반경은 적대 후보를 억제한다.
- 벌목 압력은 온전한 수목 주변 표현을 낮추고 그루터기·가지·개방 초지 후보를 높인다.
- 오두막 보관량은 빈 상태·부분 적재·가득 찬 소품 Overlay로 표현한다.
- 작업대 건설 중과 운영 가능 상태는 서로 다른 외부 공구·자재 소품을 사용한다.

## 호환

새 배치 상태를 사용하지 않는 세션은 기존 `lh-world.v1`, Interior v1·v2와 `simulation-save.v25` 이하 canonical hash를 유지한다. 새 상태가 있는 세션만 `simulation-save.v26`을 사용한다. 최신 규칙이나 Catalog로 기존 저장 세계를 자동 재생성하지 않는다.

v26은 세션이 원래 선택했을 기반 저장 스키마를 `WorldAssetPlacementBaseSchemaVersion`으로 함께 봉인한다. 기존 스키마 replay hash와 `WorldAssetPlacement.StateHashSha256`를 합성하므로 대기 상태가 없는 세션을 v25로 오인하지 않고 v1~v25 hash 계산도 바꾸지 않는다.

## 현재 구현 상태

- `SimulationScenario지도구성Engine`: H 결속·연결구·고정 Anchor만 생성한다.
- `Simulation결정적세계자산배치Engine`: 기존 LH 절차 배치 호환 모드와 Nature 변화 기반 모드를 제공한다.
- `Simulation분리세계자산배치Coordinator`: 기존 v26 통합 계획을 한 번 계산한 뒤 `Simulation실외자산배치Plan`과 `Simulation실내자산배치Plan`으로 파생하고 통합 계획은 Save/Replay 호환 Facade로 보존한다.
- `Simulation결정적실외환경표현Engine`: 실외 Stable ID·위치를 유지하면서 Sky·지면 상태에 따른 건조·젖음·적설·바람 표현 hash만 만든다.
- `SimulationNature공간변화ProjectionBuilder`: 자원 Node·지면 통나무·오두막·보관·소음·방어·건물 발전·조우를 revision이 있는 변화 사실로 투영한다.
- `NatureCabinInteriorGrammar`: 휴식·보관·작업 Zone의 고정 기본 실내를 생성하고, 보관량은 별도 LooseItem Overlay로만 반영한다.
- `SimulationSeparatedLhCellContentSource`: 기존 `lh-world.v1` 셀 내용과 base/presentation hash를 보존한 채 분리 엔진을 기본 LH 공급 경로에 연결한다.
- `SimulationNatureWorldCellAssemblyEngine`: 공통 Simulation Application에서 LH 셀 하나와 Nature 권위 상태를 같은 `WorldRevision`의 `WorldAssetAssembly`로 조립한다. LocalProcess와 RemoteHost는 이 엔진을 각각 로컬 Repository와 HTTP Controller 경계에서 호출하며 Unity가 같은 규칙을 다시 구현하지 않는다.
- Unity `공간LHStreamingEngine`은 지면 Mesh·Collider와 셀 능력만 준비하고 `World공간표현조립Coordinator`에 인계한다. `실외자산배치Runtime`과 `실내자산배치Runtime`이 자산 생성·캐시·해제를 각각 소유한다.
- Unity 로컬 경로의 `Nature세계자산배치LHRepository`는 Nature 표현 원점이 속한 L3 셀과 셀 내부 offset을 계산해 공통 조립 엔진에 전달한다. 권위 좌표의 원점은 Controller GameObject가 아니라 기존 Nature `visualRoot`다.
- `World공간표현조립Coordinator`는 배치 고유 식별자로 실외 객체를 멱등 조정하고, 표면 높이에 보이는 하단을 정렬하며, 오두막 아래에 고정 실내 본문과 변화 Overlay를 별도 Root로 만든다. 선택형 주변 표현 실패는 셀 통행을 막지 않고 같은 경고를 반복하지 않는다.
- `simulation-save.v26`: 배치 상태를 로컬 Save 요청으로 전달하고 봉인·복원한다.
