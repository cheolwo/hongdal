# 업무단위 간괘 게시판과 Command·Event·Page 묶음

## 결정

커뮤니티 게시판은 두 층으로 구성한다.

1. 사람이 글의 목적을 선택하는 일반 게시판
2. 하나의 업무 책임을 깊게 살피는 운영 점검 게시판

운영 점검 게시판의 식별 기준은 제품 버전이 아니라 **업무단위**다. `0.0`부터 `3.5`까지의 버전은 구현 범위와 성숙도를 설명하는 보조 metadata로만 남긴다. 따라서 같은 버전에 여러 업무 게시판이 있을 수 있고, 사용자는 배차·상차·인수처럼 관심 있는 일 하나를 독립적으로 조망할 수 있다.

각 업무 게시판은 간괘 `☶`의 산으로 표현한다. 산 하나는 독립된 책임 경계를, 카드 안의 Command·Event·Page 연결은 그 책임의 입력·결과·화면을 뜻한다.

## Command가 적어 보였던 이유와 표시 원칙

이전 분류는 공개 게시글을 자동 생성하는 신호만 세어, 실제 업무 관계 Command를 충분히 보여주지 못했다. 이제 카드에는 관련 Command와 Event를 모두 표시하고 다음 두 상태를 구분한다.

- `업무 관계`: 화면과 UseCase의 책임을 파악하기 위한 연결이다. 실행만으로 공개 글을 만들지 않는다.
- `게시 투영`: 성공·완료 사실을 개인정보 없이 운영 게시글로 투영한다.

현재 구현된 관계는 Command 27개, Event 25개이며 그중 공개 게시 투영 신호는 28개다. 음식 배달 인계처럼 Command/Event 경계가 아직 없는 업무도 게시판을 없애지 않고 빈 상태로 표시해 다음 구현 대상을 드러낸다.

## 글 생성과 조회

- Command pipeline은 성공 응답 뒤 `게시 투영`으로 승인된 Command만 발행한다.
- Event handler는 승인된 Event의 발생 사실만 발행한다.
- 고정 안내 글은 해당 업무 산의 모든 Command, Event와 관련 페이지를 열거한다.
- 예전 버전 게시판 key는 대표 업무 게시판의 별칭으로만 보존한다.
- 게시판 글은 관찰용 투영이며 원장 상태를 확정하거나 다음 Command를 자동 실행하지 않는다.

## 정보 수집 배치 연결

`CommunityWorkBoardEditorialPlanCatalog`가 16개 업무 게시판마다 주제, 현재 실행 가능한 정보 원천, 앞으로 연결할 공식 원천과 주기를 정의한다. KAMIS·USDA·공식 레시피처럼 이미 수집 가능한 원천과 관세청·국가물류통합정보센터·한국산업안전보건공단처럼 connector가 더 필요한 원천을 구분한다.

아직 승인 채널이 확정되지 않은 업무는 특정 YouTube 채널을 임의로 고정하지 않는다. 승인된 감시 채널 안에서 업무 주제로 후보를 수집하고 편집 검토를 통과한 자료만 게시한다. 계획된 connector 실패를 sample 자료로 대체해 정상 게시처럼 보이게 하지 않는다.

## 공개 경계

- 공개 글에는 사용자·업체 식별자, 연락처, 상세 주소, 위치, 금액, 결제 정보, 첨부와 원본 payload를 넣지 않는다.
- 신고·분쟁, 결제 승인 상세, 파일 업로드와 법적·민감 Event는 활동 게시판 발행 대상에서 제외한다.
- 넓은 버전 범위를 한 게시판에 합쳐 업무 책임과 개인정보 경계가 흐려지지 않게 한다.
