# WI 애니메이션·리깅 정밀화 계획

- 판본: `wi-animation-rigging-audit-plan.r1`
- 작성: 2026-08-30 / D380
- 상태: `ReadyForReview` — 조사·계획 산출물. 아래 신규 제작 순위와 수용 기준은 제안이며 일괄 제작 승인이 아니다.
- 요청: 확정 문답과 보유 Synty 자산을 대조하여 부족한 동작·리그·연결을 조사하고, 구현보다 계획을 먼저 작성한다.
- 범위: 기존 WI/PlayableLoop 재사용. 신규 WI·게임 규칙·Save·E 승격·새 자산 구매·Scene 변경 없음. 기존 승인된 D359/D379 및 야간 개발을 중단하거나 대체하지 않는다.

## 1. 결론과 작업 구분

우선 과제는 모든 자산을 새로 리깅하거나 동작을 새로 만드는 것이 아니다. **보유 동작의 실제 상태 연결 → 대상 체형·도구에 맞는 접촉과 전환 보완 → 재사용할 수 없는 동작만 신규 제작** 순서가 적절하다.

| 작업 종류 | 실제로 바꾸는 것 | 프로젝트의 예 |
| --- | --- | --- |
| 모델링 | 형상·분리 부품·메시 구성 | 필요할 때만 나무 절단부, 분리 가능한 뚜껑, 도구 손잡이 수정 |
| 리깅·스키닝 | 뼈, 관절 제어, 메시 변형 가중치 | 캐릭터 체형과 Avatar 대응, 필요한 비인간형 생물의 골격 |
| 오브젝트 애니메이션 | 물체의 위치·회전·부품 움직임 | 나무 넘어짐, 문 열림, 바퀴 회전. 반드시 Humanoid 리그가 필요한 것은 아님 |
| 캐릭터 애니메이션·리타깃 | 준비·동작·접촉·복귀 자세와 전환 | 도끼 스윙, 줍기, 컵 들기, 농기구 사용 |
| Unity 상태 연결 | 실제 행동 상태와 동작·소리의 재생 관계 | 취소 시 복귀, 완료 때만 낙하, Load 후 중복 인사·타격음 방지 |

Blender 담당의 포괄 업무명은 **3D 자산·리깅·애니메이션**으로 부를 수 있다. 개별 작업은 도구 이름보다 “대상 + 필요한 변화 + Unity에서 확인할 결과”로 명명한다. 나무가 넘어지는 요구는 애니메이션이며, 형상을 바꿔야 할 때만 모델링을 추가한다.

전체 질문 조회 체계는 재사용하지만 이번에 모든 질문의 모든 자산을 의미 단위로 재검사한 것은 아니다. 직접 대조한 주요 WI와 공통 동작을 먼저 계획하고 나머지는 조사 대기 항목으로 남긴다.

### 현재 파일 대조

Unity 루트는 `C:/Users/user/ssalddel`이다. `Assets/Synty`에서 세 애니메이션 패키지 디렉터리를 확인했다.

| 패키지 | FBX meta 파일 | Controller 파일 | 독립 .anim 파일 |
| --- | ---: | ---: | ---: |
| AnimationBaseLocomotion | 721 | 174 | 0 |
| AnimationEmotesAndTaunts | 283 | 0 | 0 |
| AnimationSwordCombat | 242 | 1 | 0 |

이는 **파일 수**이며 고유 동작 수·실제 사용 가능한 Clip 수가 아니다. FBX 내부 Clip이 있으므로 `.anim=0`을 애니메이션 부재로 해석하지 않는다. 8월 9일의 [기존 재사용 설계](../UnitySyntyAnimationReuseAndRetargetDesign.md)에 있는 자산 수치는 구매 팩 추가 전 기록으로, 현행 재고 판정에 사용하지 않는다.

이번에 Walk/Run/Turn/Sheathe 원본 FBX와 meta 8개의 SHA256을 D361 표와 대조하여 일치를 확인했다. Walk/Run meta에는 `Copied Avatar Rig Configuration mis-match` 진단 문자열과 `importAnimation:1`이 함께 있다. **저장된 import 진단**이며 현재 Editor의 Avatar 실패를 새로 재현한 증거는 아니다. 리그 재검증 대상으로 분류한다.

직접 읽은 `Assets/Ssalddel/Presentation/World/공용AnimationContract.cs`의 공통 의도는 Idle/Walk/Run/Guard/Attack/Stagger다. `Npc업무행동View.cs`는 Navigating을 Walk에, 그 밖을 Idle에 연결한다. 따라서 이 View만으로 세부 농사·운반 자세가 준비됐다고 할 수 없다. 별도 전문 Adapter까지 없는 것으로 확대 판정하지 않는다.

## 4. 리그·물체별 점검표

| 대상 분류 | 반드시 확인할 것 | 잘못된 결론 방지 |
| --- | --- | --- |
| Humanoid Actor | 실제 Avatar valid/human, 뼈 대응·rest pose·축/단위, 피부 가중치, 손/발/도구 위치, root motion 작성자 | FBX가 존재하거나 Humanoid 설정이라는 이유로 호환 통과 아님 |
| 비인간형/사족 Actor | Generic 골격·내장 동작·이동 방식·지면 접점, 전용 전환 가능성 | Sword 사람형 동작을 자동 적용하지 않음 |
| 단일 고정 메시 소품 | pivot, 스케일, 접촉 anchor, Collider, 손 부착 좌표 | 뼈가 없다는 이유만으로 결함이나 재리깅 대상으로 세지 않음 |
| 문·뚜껑·기계 부품 | 실제 분리 가능 부품/축, 회전 범위·관통, 닫힘·열림 상태 | 외형에 뚜껑이 보이는 것과 개폐 가능한 구조를 구분 |
| 나무·유연한 물체 | 밑동 pivot/지지면, 기존 낙하 방식, 메시/가지 변형 필요성 | 단순 회전으로 충분하면 신규 스킨 리그를 만들지 않음 |

대표 Actor에서 통과한 뒤 체형이 다른 후보를 추가한다. 모든 캐릭터에 동일 오프셋을 적용하거나 Bounds만으로 그립점·용량·접촉 위치를 결정하지 않는다. 허용 오차는 대상 연구에서 정하고, D359의 B 보정 목표를 다른 작업의 승인 수치로 복사하지 않는다.

## 5. 각 제작 후보의 필수 명세

기존 D361 대조 보고를 확장하는 방식으로 다음 항목을 채운다. 별도 권위 WI 원장을 중복 생성하지 않는다.

1. 기획 원문/질문·WI·PlayableLoop·현재 승인 판본과 상태. 미정은 해당 분기만 표시.
2. Actor/도구/대상 Prefab의 경로·GUID·hash, Clip의 FBX 경로·fileID·구간, Rig/Avatar와 실제 확인 방식.
3. 분류: 그대로 재사용 / 대상 조정 / 연결 부족 / 새 제작 후보 / 근거 부족 / 동작 불필요. 이름 검색 0건만으로 새 제작 판정 금지.
4. 준비→행동→접촉→완료→복귀, 중단 지점과 재시작. 어느 상태가 실제 권위 결과이고 어느 부분이 시각 연출인지 명시.
5. 1인칭 손·도구와 3인칭 전신, 높은 관리 시점에서의 판독. 같은 Actor/행동이 이중 재생되지 않도록 소유권 명시.
6. 손 점유·도구 anchor·발 접지·몸/대상 관통, root motion/이동/뼈를 쓰는 단일 담당. 경사·높이·좌우 접근의 적용 범위.
7. ActionCue/AudioCue와 접촉·완료 근거, Session/Actor/OriginCommand/세대 구분. 취소/Load/중복 조회에 소리·완료 연출 반복 금지.
8. 원본 불변, 작업 복사본·출력 경로, Blender가 필요한 이유와 사용조건. Blender 모델링/리깅/애니메이션 산출물을 각각 구별.
9. 실패 fallback과 미지원 조합의 명시적 거부. 표현 실패가 자원·피해·성장·시간을 새로 계산하지 않도록 검증.
10. 자동시험, 실제 입력 연속 화면, 실제 청취 각각의 상태와 근거. Clip 생성·컴파일만으로 E5를 선언하지 않음.

## 7. 예상 결과와 검증 한계

다음 검토에서 받을 결과는 “모든 애니메이션 완성”이 아니라 **제작 필요성이 근거로 확인된 작업 목록**이다. 각 후보에 보유 자산, 실제 부족, 최소 수정 방식, 선행 상태, 예상 작업 난이도와 미확인을 붙인다. 시간은 대표 작업의 제작/왕복/실제 입력 검증 뒤 추정하고 사전 숫자로 완료를 약속하지 않는다.

이번 확인 완료: 세 패키지 파일 재고, 대표 FBX/meta 8hash 대조, 공통 의도와 NPC 업무 View의 이동/Idle 연결, 기존 전문 보고·기획의 경계 확인.

이번 미수행: 전체 FBX 내부 Clip 의미 분류, 전 캐릭터·몬스터 Rig 검사, 현재 Editor 재import/Avatar 확인, Blender 제작, Unity 새 연결, 실제 입력/접촉/음원 청취, 모든 질문의 시각 요구 전수 판정. 과거 보고의 미완료가 최신 코드에서도 그대로인지 전문 후속 검토에서 재확인한다.

신규 구현은 이 계획 검토와 필요한 연구 결속 뒤 별도 좁은 작업으로 진행한다. 이미 승인된 야간 작업은 기존 명세대로 계속하며 본 계획 때문에 다시 대기시키지 않는다.
