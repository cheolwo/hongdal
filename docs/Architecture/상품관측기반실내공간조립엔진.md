# 상품 관측 기반 실내공간조립엔진

## 목적

Town 주거 생활공간과 이후 상점·창고·식당·병영의 내부를 하나의 결정적 문법으로 조립한다. 이 계층은 H와 LH 사이에 있지만 새 H 단계가 아니다. H는 공간의 의미를, 실내공간조립엔진은 내부 배치 계획을, LH는 계획의 준비·활성·캐시·해제를, Unity는 `VisualKey`의 실제 표현을 소유한다.

```text
게임 기획과 WI
  -> H 공간 의미
  -> 실내공간조립엔진
  -> InteriorPlacementPlan
  -> LH 준비와 활성화
  -> Unity VisualKey 투영
```

첫 검증 대상은 `SimulationWorldShell` 안의 Town 저층주택 한 채다. 거실, 주방, 침실, 욕실, 작업공간을 구분한다. 새 공식 Scene을 만들지 않는다.

## 고정 책임 경계

| 계층 | 소유하는 질문 | 소유하지 않는 것 |
| --- | --- | --- |
| H | 어떤 생활과 WI를 수용하는 공간인가 | 가구 좌표, Prefab, 스트리밍 시점 |
| 실내공간조립엔진 | 건물 내부에 무엇을 어디에 놓는가 | WorldTick, 재고, 가격, 소유권, WI 실행 |
| LH | 어떤 실내 계획을 어느 상세도로 준비하는가 | Zone·Fixture·Slot 재배치 |
| Unity | 의미 기반 `VisualKey`를 어떤 Prefab으로 보여주는가 | 계획 hash, 상품 승인, Simulation 상태 |
| 상품 관측 | 현실에 어떤 물품 종류가 관측되는가 | 세계 권위, 게임 재고, 구매 추천 |

첫 판본의 Fixture와 LooseItem은 모두 `PresentationOnly`다. 읽기 전용 Reference 카드도 WI가 아니다. 이후 객체가 실제 세계 상태를 바꾸게 될 때만 별도 WI, Preview, Confirm, Task, Effect 계약으로 승격한다.

## 구현 모듈

| 모듈 | 주요 계약 또는 구현 |
| --- | --- |
| `Ssalddel.Interior.Contracts` | `InteriorDefinition`, `Zone`, `Fixture`, `Surface`, `Slot`, `InteriorPlacementPlan`, `InteriorPlanHandle`, `PresentationWorldDefinition` |
| `Ssalddel.Interior.Domain` | `DeterministicInteriorLayoutEngine`, 계획·승인 Catalog canonical hash |
| `Ssalddel.Simulation.Application` | `SimulationLhInteriorPlanHandleService`; LH 셀을 이미 생성된 Plan handle과 연결 |
| `Ssalddel` 외부 Adapter | Apify Source 등록 옵션, Amazon·Alibaba normalizer, 명시적 승인 Catalog 생성 |
| `Ssalddel.Unity` | Object Focus별 표현 투영과 개인정보·상품 경계가 제거된 Reference 카드 |

두 Interior 모듈은 `netstandard2.1`과 Unity Package 계약을 함께 제공한다. Simulation Application은 엔진을 사용할 수 있지만 엔진은 Simulation 또는 LH를 참조하지 않는다.

## 결정적 생성 계약

Seed fingerprint는 다음을 결합한다.

```text
WorldSeed
+ BuildingPlacementStableId
+ InteriorDefinitionRevision
+ ApprovedReferenceCatalogRevision
+ GeneratorRevision
```

후보 Fixture, LooseItem, Reference와 Zone은 Stable ID로 정규화한 뒤 선택한다. 같은 입력이면 입력 배열 순서와 관계없이 같은 `InteriorPlacementPlanHashSha256`가 생성된다. 기존 세계는 다음 값을 `InteriorPlanHandle`에 고정한다.

- `InteriorDefinitionRevision`
- `ReferenceCatalogRevision`
- `InteriorPlacementPlanHashSha256`

새 Catalog가 승인되어도 기존 handle은 자동으로 최신 Catalog로 이동하지 않는다. `WorldLayoutHashSha256`와 실내 계획 hash도 같은 값으로 취급하지 않는다.

엔진은 직사각형 Structure·Zone 경계 안에서 필수 Fixture 후보를 정렬해 배치한다. 문·출입·고정 구조물은 `ExclusionBounds`, 이동 목표는 `TraversalAnchors`로 받는다. 객체 겹침, Zone 이탈, 제외 영역 침범, Slot 최대 크기 위반을 거부하고 격자 탐색으로 통로 연결을 확인한다. 적합 후보가 없는 선택 LooseItem Slot은 비워 둔다. 필수 Fixture를 놓지 못하면 `UnresolvedRequiredFixtureCodes`에 남긴다.

## 상품 관측과 승인

```text
외부 Marketplace
  -> Apify Actor Gateway
  -> Raw item batch
  -> Marketplace normalizer
  -> Normalized observation
  -> 사람의 명시적 승인 결정
  -> ApprovedInteriorReferenceCatalog
  -> 상품근거특성Profile 승인
  -> 상품특성효과RuleSet
  -> 상품근거ItemDefinition
  -> 실내공간조립엔진·상세 정보 후보 근거
```

`ApifyInteriorProducts:Enabled`와 Source별 `Enabled` 기본값은 false다. Source는 Actor ID·build·입출력 계약 revision·normalizer·이용 조건 검토 상태를 가진다. 전역 Apify 허용 목록과 비용 상한도 함께 통과해야 한다. Actor ID는 코드에 고정하지 않는다.

normalizer는 상품 식별자, 원상품명, HTTPS 원문 URL, 관측시각, 원문 hash와 Source revision만 남긴다. 가격, 이미지, 브랜드 로고, 구매 이력, 주민 소유 정보는 승인 Catalog Projection에 포함하지 않는다. Amazon·Alibaba 허용 host가 아닌 URL은 거부한다.

Reference 카드는 다음 문장을 항상 표시한다.

> 현실 상품 관측을 기반으로 한 공간 참고 자료이며 게임 재고나 소유 물품이 아닙니다.

실제 유료 Actor 호출, 운영 자동 승인, 사용자 맞춤 구매 추천은 현재 범위 밖이다.

## 상품 근거 특성과 효과 정의

Synty는 범주형 외형만 소유하고 Marketplace 관측은 같은 외형 안에서 달라질 수 있는 게임용 특성·효과의 근거가 된다. 상품 제목 문자열이나 실시간 페이지를 Runtime에서 직접 해석하지 않는다.

```text
ApprovedInteriorReference
  + 사람이 승인한 상품근거특성Profile
  + revision 고정 상품특성효과RuleSet
  + 범주형 VisualKey
  -> 상품특성효과DerivationEngine
  -> 상품근거ItemDefinition
```

`상품근거특성Profile`은 밝기·크기·재질·전력·내구성·안락성·기능처럼 게임에서 사용할 수 있도록 승인된 일반화 값과 간단한 근거 설명을 가진다. 비공개 Raw Observation에 추가 규격이 있더라도 승인 Profile로 승격되지 않은 값은 효과 계산에 사용하지 않는다. 현재 normalizer가 보존하는 공개 Reference 정보만으로 특성을 자동 추정하지 않는다.

`상품근거ItemDefinition`은 다음 계보를 hash에 고정한다.

- 승인 Reference Catalog revision과 hash
- Trait Profile revision과 hash
- Effect Rule revision과 hash
- 범주형 `VisualKey`
- 파생 특성과 효과 목록

동일 입력 순서가 달라도 같은 정의와 hash를 만들며 Rule revision이 바뀌면 새 정의를 만든다. 이 정의의 초기 상태는 항상 `DefinitionOnly`, 효과 권위는 `SimulationCoreRequired`다. 따라서 Unity 상세 정보는 효과 후보를 표시할 수 있지만 실제 상태에는 적용할 수 없다.

```text
상세 정보 열기
  -> 읽기 전용 Projection
  -> WI 아님

Item 사용·설치·장착
  -> 별도 WI Preview / Confirm
  -> Simulation Core 규칙 검증
  -> Task / Effect / WorldTick
  -> 실제 상태 변경
```

상세 정보에는 현실 상품의 성능을 그대로 보장하지 않으며 승인 특성을 게임 규칙으로 변환한 값이라는 경계를 함께 표시한다. 가격·재고·브랜드·주민 소유 정보는 효과 근거로 사용하지 않는다.

## LH와 Unity 활성화

LH는 `InteriorPlacementPlan` 본문을 재작성하지 않고 `InteriorPlanHandle`만 소비한다.

| LH 상태 | 실내 표현 |
| --- | --- |
| Prefetch / Overview Focus | 건물 외형, 실내 handle 메타데이터만 |
| Active / Zone Focus | Zone과 주요 Fixture 후보 |
| Detail / Object Focus | `InteriorRoot`, Fixture, Surface, 작은 LooseItem |

Unity 투영은 handle의 Definition revision, Catalog revision, Plan hash가 실제 계획과 모두 같을 때만 활성화한다. 하나라도 다르면 `PinnedInteriorPlanMismatch`로 닫고 외형만 유지한다. `VisualKey`와 Synty Prefab의 대응은 Unity Visual Mapping Catalog가 별도로 소유한다.

## 현재 검증과 남은 범위

현재 자동 시험은 다음을 확인한다.

- Town 저층주택의 5개 Zone, 필수 Fixture와 PresentationOnly LooseItem 생성
- 입력 배열 순서를 바꾸어도 같은 Plan과 hash 생성
- Catalog hash 위조 거부와 통로 검사
- LH Detail·Active·Prefetch를 Object·Zone·Overview Focus로 변환하면서 `LhDeterminesPlacement=false` 유지
- Unity가 Object Focus에서만 작은 물품과 승인 Reference 카드를 표시
- pinned plan 불일치 시 fail-closed
- Amazon·Alibaba 출력의 안전한 필드 정규화, 명시적 승인, 수집 기본 비활성
- 상품 특성·효과 규칙의 입력 순서 독립 결정성과 revision별 정의 hash
- 승인 Catalog에 없는 Reference의 효과 정의 거부
- Unity 상세 Projection의 특성·효과·출처 표시와 `CanApplyWorldEffect=false`

아직 `SimulationWorldShell`의 실제 Town 건물 Structure·Synty Prefab Mapping·저장 Scene 배선은 하지 않았다. 상품 효과도 실제 WI·Simulation Aggregate·Save/Replay에 연결하지 않았다. 따라서 현재 증거는 계약·결정적 정의·Adapter·읽기 전용 Projection·자동 시험 수준이며 Play Mode·Game View 또는 실제 효과 완료가 아니다. Scene 적용 전 실제 Town H1 기준안과 건물 `BuildingPlacementStableId`를 선택하고, 승인된 VisualKey→Prefab 대응표를 별도 검토해야 한다.

## 확장 순서

1. 실제 Town H1과 저층주택 Structure revision을 선택한다.
2. 승인 Fixture Snapshot으로 `InteriorPlacementPlan`을 생성하고 hash를 세계 정의에 고정한다.
3. LH Object Focus에서 handle을 소비하도록 canonical Scene CompositionRoot에 연결한다.
4. Synty Town/Farm 등 승인 Prefab을 `VisualKey`에 대응한다.
5. 승인 Trait Profile과 Effect Rule Snapshot을 Item 정의로 고정하고 읽기 전용 상세를 연결한다.
6. 저장 Scene, Play Mode 통행, Game View 문맥을 검증한다.
7. 실제 세계 상태를 바꾸는 객체만 별도 WI와 Simulation 효과로 승격한다.
8. 주택 문법이 안정된 뒤 Retail, Warehouse, Restaurant, Military Grammar를 같은 엔진에 추가한다.

## 원칙

- H는 공간의 의미를 소유한다.
- 실내공간조립엔진은 H 의미를 결정적인 내부 배치로 구체화한다.
- 상품 관측은 실내 다양성을 위한 외부 참고 근거일 뿐 게임 세계의 권위가 아니다.
- LH는 실내를 설계하지 않고 계획의 준비·활성·캐시·해제를 담당한다.
- Unity는 `VisualKey`를 실제 표현으로 투영한다.
- Marketplace 관측은 승인 특성의 근거이고 Synty는 범주형 외형이다. 둘을 동일 상품 복제로 취급하지 않는다.
- 상품 특성 효과는 고정 Rule revision으로 결정적으로 정의하고 Unity에서 재계산하지 않는다.
- 실제 물품이 세계 상태를 바꿀 때에만 WI와 Simulation 상태로 승격한다.
