# 용어집

홍달 문서에서 반복해서 쓰는 주요 용어를 정리한다.

| 용어 | 정의 |
| --- | --- |
| HIOPS | Hongdal Integrated Operations & Policy System. 홍달의 최상위 운영 체제 이름으로, 여러 참여자의 입장과 책임을 더 잘 알아보고 조율하기 위해 하위 OS, 워크플로우, 화면, 엔진, 스케줄링 정책을 조합하는 운영 기준 |
| 알뜰살뜰 | 홍달의 핵심 개발 철학. 사용자가 돈, 시간, 이동, 노동, 신뢰, 관계를 낭비하지 않고 생활 가까운 일을 서로 더 잘 알아보고 맡기고 나눌 수 있게 만드는 기준 |
| HIOPS 층위 모델 | 원장/원장 블록, 조합 규칙, 하위 OS, 엔진, API/UseCase, 저장소가 어느 책임을 맡는지 나누는 기준. 자세한 내용은 `docs/Architecture/HIOPSLayerModel.md`에 둔다 |
| 하위 OS | HIOPS 안에서 특정 운영 목적을 맡는 실행 단위. 예: 국내 화물 운송 OS, 공동주문 수입 OS, 창고·커머스 이행 OS |
| 원함 확인 | 원장을 입력하기 전에 사용자가 무엇을 원하는지, 홍달이 어디까지 도울 수 있는지, 사용자가 직접 확인해야 할 책임이 무엇인지 먼저 맞추는 단계 |
| 원함-원장 판단 보고서 | 사용자의 원함을 원장으로 만들 수 있는지 판단하기 위해 원함, 홍달 지원 범위, 원장화 판정, 필요한 원장 블록, 사용자 확인 책임, OS/엔진/API 연결을 함께 정리하는 보고서 |
| AI 판단 보조 | 거리, 시간창, 대기, 비용, 증빙, 책임 같은 상황 신호를 분석해 배정, 추천, 보류, 인계 판단을 돕는 기능. 최종 목적은 한쪽 효율만 높이는 것이 아니라 참여자 입장의 균형을 찾는 데 있다 |
| 원장 블록 | 원장을 구성하는 재사용 가능한 업무 조각. 참여자, 장소, 물건, 재고, 상태, 증빙, 정산, 인계처럼 UI, AI 판단, 구성 규칙, OS/API handoff가 함께 이해할 수 있는 최소 단위 |
| 참여자 입장 해석 AI | 화주, 기사, 수령자, 운영자 같은 참여자의 기대, 부담, 책임, 기다림을 정리해 사용자 뷰에서 서로의 입장을 헤아릴 수 있게 돕고, 서버 판단 입력으로도 남기는 HIOPS AI |
| 국내 화물 운송 배차 조율 AI | 서버에서 기사 실시간 위치, 기사 상태, 현재 운송 의뢰, 차량 적합성, 거리, 시간창, Aging, 증빙 조건을 함께 보고 기사 추천, 제외, 보류, 공개배차 전환을 제안하는 HIOPS AI |
| 중용 | HIOPS의 운영 철학 중 하나. 여러 참여자의 입장을 함께 보면서 과하거나 모자라지 않은 적절한 균형점을 찾는 기준 |
| 워크플로우 | 하나의 업무 절차를 완성하기 위해 여러 API와 앱 화면이 묶인 단위 |
| 엔진 | OS가 호출하는 판단 도구. 집단화, 출고 배치, 피킹 배치, 운송 의뢰 배차처럼 특정 판단을 맡는다 |
| 스케줄링 정책 | 대기 중인 작업을 어떤 순서와 기준으로 처리할지 정하는 운영 규칙 |
| FCFS | First-Come, First-Served. 먼저 들어온 작업을 먼저 처리하는 정책 |
| SJF | Shortest Job First. 처리 시간이 짧은 작업을 먼저 처리하는 정책 |
| EDF | Earliest Deadline First. 마감 시간이 가까운 작업을 먼저 처리하는 정책 |
| MLFQ | Multi-Level Feedback Queue. 여러 단계의 큐를 두고 실패, 대기, 만료 상태에 따라 작업을 승격하거나 전환하는 정책 |
| Aging | 오래 기다린 작업이나 참여자의 우선순위를 점진적으로 올려 기아 상태를 막는 정책 |
| 기사대기 Aging | 기사가 오랫동안 추천을 받지 못했을 때 제한된 보정점수를 더해 다음 추천 후보가 될 가능성을 높이는 정책 |
| 온보딩 | 새 사용자가 계정, 역할, 기본 설정, 기존 주문/창고/거래 단서를 연결해 실제 업무를 시작할 수 있게 만드는 초기 절차 |
| 주문자 집단 | 같은 주소, 생활권, 공동주택, 초대코드 같은 단서를 공유해 공동 주문이나 공동 입고를 함께 할 수 있는 사용자 묶음 |
| 물류대행사/3PL | 보관, 입고, 피킹, 포장, 출고 같은 물류 업무를 대신 수행하는 외부 물류 업체 |
| 출고 예약 | 재고가 충분한 주문이나 운송 요청에 대해 실제 피킹/포장 전에 해당 물량을 출고 대상으로 잡아두는 상태 |
| 출고 배치 | 주문이 들어왔을 때 어느 창고의 어떤 재고를 어떤 수량으로 출고할지 정하는 계획 |
| 피킹 배치 | 출고 배치 결과를 적재대, 피킹 작업자, 포장 작업자 단위로 나누는 현장 작업 계획 |
| 운송 | 상차지에서 하차지까지 화물이나 물건을 실제로 이동시키는 실행 흐름. 홍달 1.0의 화물/용달 흐름에서는 `운송 의뢰`, `배차`, `상차`, `하차`, `인수 확인`을 묶는 상위 도메인 용어로 쓴다 |
| 배송 | 주문자나 수령자 입장에서 물건이 도착하는 서비스 표현. 내부 실행 단계나 기사 배차 판단을 설명할 때는 가능하면 `운송`, `배달`, `전달`, `인계` 중 더 구체적인 말을 쓴다 |
| 배달 | 음식, 마트 즉시배송처럼 짧은 생활권 안에서 픽업 후 고객에게 전달하는 흐름. `음식 배달 OS`, `알뜰살뜰 마트 도심 물류 OS`처럼 도메인명이 된 경우에 쓴다 |
| 운송 인계 | 창고 출고, 공동주문 반출, 마트 포장 완료 같은 앞단 작업이 끝난 뒤 실제 이동이 필요해 국내 화물 운송 OS나 음식 배달 OS로 넘기는 경계 |
| 배차대기 | `운송원장` 안에서 기사 추천, 공개배차, 확정으로 넘어가기 전인 상태. 별도 테이블이 아니라 업무 상태로 다룬다. |
| 레그 | 운송 경로를 나눈 한 구간. 예를 들어 `현재 위치 -> 상차지`, `상차지 -> 하차지`, `하차지 -> 다음 상차지`가 각각 하나의 레그가 된다 |
| POD | Proof of Delivery. 수령자에게 전달되었거나 하차/인수 확인이 끝났음을 증명하는 기록. 하차 완료 사진, 수령자 서명, 인수자 이름/소속, 완료 시각, 위치, 바코드 스캔 기록, 인수증 사진이 포함될 수 있다 |
| BL | Bill of Lading. 선박 운송에서 화물이 선적되었음을 증명하는 선하증권 |
| LCL | Less than Container Load. 한 컨테이너 안에 여러 화주의 화물을 함께 싣는 혼재 운송 |
| FCL | Full Container Load. 한 화주 또는 한 운송 건이 컨테이너 하나를 단독으로 쓰는 운송 |
| 보세구역 | 수입 통관 전후 화물을 세관 관리 아래 보관하거나 반출하는 구역 |
| 운송 의뢰 배차 엔진 | 운송 의뢰를 기사 후보 추천, 수락, 상차, 하차, 증빙 흐름으로 넘기는 판단 엔진 |
| RAG | Retrieval-Augmented Generation. AI가 자기 지식만으로 답하지 않고, 운영 매뉴얼, 판단 사례, 운송 기록 같은 관련 자료를 먼저 찾아 참고한 뒤 설명이나 판단 보조 답변을 생성하는 방식 |
