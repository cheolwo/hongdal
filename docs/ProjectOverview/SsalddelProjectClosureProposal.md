# 살뜰 프로젝트 마무리 제안서

> 기준일: 2026-08-01
>
> 제안 결론: 살뜰을 **3.5 전체 실운영 제품**으로 선언하지 않고, **커뮤니티·공공데이터 중심 공개 프리뷰**와 **0.5~3.5 통합 시제품 자산**으로 구분해 마무리한다.

## 1. 제안 요약

살뜰은 더 이상 기능의 수가 부족해서 끝내지 못하는 단계가 아니다. 서버, 공통 contract, 역할별 Web/MAUI 앱, 관리자, 공공데이터, 주문·무역·운송·창고·판매 흐름, 자동 검증과 Azure 배포 구성이 이미 큰 폭으로 갖춰져 있다. 지금 필요한 일은 새 기능 추가가 아니라 다음 네 가지다.

1. **공개할 제품의 정체성을 하나로 고정한다.**
2. **실제로 운영하는 기능과 시뮬레이션·연구 자산을 분리한다.**
3. **현재의 소수 실패 검증과 운영 증거를 정리한다.**
4. **남은 기능을 결함이 아니라 후속 자산으로 동결한다.**

권장 공개 명칭은 **“살뜰 커뮤니티·공공데이터 프리뷰 1.0”**이다. 저장소의 0.5~3.5 구현은 삭제하지 않고 “통합 시제품”으로 보존하되, 결제·계약·수입 실행·유상 운송·재고 이동·정산 같은 외부 효과는 운영 준비가 끝날 때까지 공개 운영 범위에서 제외한다.

## 2. 현재 상태에 대한 판단

### 2.1 이미 갖춰진 기반

| 영역 | 확인된 현재 상태 | 마무리 판단 |
| --- | --- | --- |
| 코드 구조 | 1차 관리자 통합 뒤 28개 project로 정리됐으며 서버, 공유 contract/domain/infrastructure, 역할별 Web/MAUI 앱, 통합관리자와 test project가 함께 존재한다. | 새 구조를 만들기보다 기존 구조를 동결·정리한다. |
| 화면 | `@page` 선언 Razor 파일이 약 456개이고, 통합 WebApp과 역할별 앱 화면이 넓게 구현돼 있다. | 모든 화면을 같은 완성도로 다듬는 일은 종료 조건에서 제외한다. |
| API | API Controller가 약 189개다. | 새 API 추가보다 공개 route와 capability 분류를 확정한다. |
| 검증 | 1차 구조 정리 뒤 전체 test 4,066개가 모두 통과한다. | 이후 리팩토링에서도 전체 통과 상태를 유지한다. |
| 배포 | 공개 포털과 01~05 역할 URL, `/health/live`, `/health/ready`가 현재 HTTP 200과 Healthy를 반환한다. | 배포 기반을 새로 만들 필요는 없고, 현재 설정과 문서의 일치가 필요하다. |
| 운영 자동화 | release readiness가 버전별 build/test와 배포 bundle 검증을 수행하고, staging readiness에는 migration·backup·restore 절차가 있다. | staging 절차를 실제로 한 번 실행하고 결과를 증거로 남긴다. |
| 콘텐츠 이미지 | 앱별 이미지 생성·DB/Blob URL 활용 코드와 생성 자산 작업이 진행돼 있다. | 전체 수량보다 검수된 소수 대표 자산만 공개한다. |

이 숫자는 제품 가치의 척도라기보다, 기능 추가를 중단해도 될 만큼 구현 폭이 충분하다는 근거다.

### 2.2 아직 “전체 실운영 완성”으로 부를 수 없는 이유

- [0.0 출시 체크리스트](../Versions/v0.0/checklist.md)는 아직 증거 기준으로 판정되지 않은 항목이 많다.
- 2.0 이후에는 허가·보험·책임, 실제 기사 인계, 재고·피킹·상차, 결제·정산 같은 운영 게이트가 남아 있다.
- 3.5는 최종 목표 흐름을 보여 주지만 마트 주문부터 기사 인계까지의 실운영 종단 증거가 완성됐다고 볼 수 없다.
- 개발·sample fallback이 여러 앱에 존재하므로 운영 profile에서 확실히 꺼지는지 최종 확인이 필요하다.
- 2026-08-01 현재 공개 서버는 1.0/1.5 관련 일부 feature flag가 켜져 있지만, 기본 배포 문서와 0.0 집중 원칙은 그 이후 기능을 기본 비활성으로 설명한다. 공개 제품의 정체성과 실제 설정이 일치하지 않는다.
- 현재 작업 트리에는 이미지 자산 연동을 포함한 다수의 미커밋 변경이 섞여 있다. 이를 분류하지 않은 채 release tag를 만들면 재현 가능한 기준점을 얻을 수 없다.

따라서 “모든 것이 완성됐다”는 선언보다, **무엇을 완성으로 인정하고 무엇을 보존 자산으로 넘기는지 명시하는 마무리**가 적절하다.

### 2.3 프로젝트 통합 기준

1차 통합에서는 실제 화면 없이 같은 공통 shell만 실행하던 `Ssalddel.FoodDelivery.Admin`, `Ssalddel.FreightDelivery.Admin`, `Ssalddel.OrderWarehouse.Admin`과 전용 `Ssalddel.BusinessPackages.AdminUi` project를 제거했다. 기존 세 URL과 업무 패키지 catalog는 `SsalddelAdmin`이 그대로 제공한다.

반면 다음 project는 파일 수가 적더라도 실행·배포 경계가 있으므로 유지한다.

- 01~05 역할 WebApp: 같은 화면 source를 재사용하지만 역할별 path base, assembly와 정적 배포 결과가 다르다.
- 역할별 MAUI 앱: 지도, 알림, 스캔, 인쇄 등 플랫폼 adapter와 배포 대상이 다르다.
- `SsalddelAdmin`과 `SsalddelAdminApp`: Web 운영 화면과 모바일 검토 화면의 실행 환경이 다르다.
- `Ssalddel`, `Ssalddel.Contracts`, `Ssalddel.Domain`, `Ssalddel.Infrastructure`: API, 공유 계약, 도메인과 영속성의 의존 방향을 유지한다.

앞으로는 **독립 실행 효과나 배포 이유가 없는 thin host만 흡수**하고, 단지 project 수를 줄이기 위해 플랫폼·권한·영속성 경계를 합치지 않는다.

## 3. 최종 제품 범위

### 3.1 공개 운영 범위

다음 기능을 공개 프리뷰의 중심으로 둔다.

- 세계지도와 지역 탐색을 통한 문화·음식·농수산물 정보 확인
- KAMIS, AMS 등 출처·기준 시각·단위·지역이 드러나는 가격 관측과 비교
- 게시판, 글, 댓글, 참여 의사와 개인정보 공개 범위
- 한국·미국 지역 코드와 상품·HS 계열 코드에 기반한 읽기 중심 비교
- 공동행동의 가원장·역할·진행 상태를 설명하는 투명한 정보 화면
- 커뮤니티 중심의 통합 관리자와 공공데이터 상태 확인

공개 화면에서는 정보의 출처, 단위, 통화, 관측 시각, 지역, 갱신 주기와 “참고 정보이며 거래 확정이 아님”을 함께 표시한다.

### 3.2 시뮬레이션·연구 자산으로 보존할 범위

| 버전/영역 | 마무리 후 지위 |
| --- | --- |
| 0.5 개별 의향 | 비구속 의향·비용 검토 시뮬레이션 |
| 1.0 같이 주문 | 수요 집계와 공동 원장 시뮬레이션 |
| 1.5 무역 준비 | HS·통관·서류 준비의 읽기/준비 프리뷰 |
| 2.0 국내 운송 | 배차·증빙 UX 시제품, 실운송 비활성 |
| 2.5 창고 | 입출고·피킹 UX 시제품, 실재고 이동 비활성 |
| 3.0 판매·배달 | 주문·배달 연계 시제품, 실결제·정산 비활성 |
| 3.5 마트·도심 물류 | 전체 목표를 설명하는 통합 시연 자산 |

### 3.3 공개 운영에서 제외할 외부 효과

- 실제 결제, 대금 보관과 정산
- 계약 체결과 수입·통관 실행
- 유상 운송 추천·주선·자동 배차와 운임 수취
- 창고의 실재고 증감, 출고 확정과 기사 인계
- 실제 판매채널 주문 확정과 음식 배달 실행
- 사람의 승인 없이 수행되는 상대 선택이나 역할 배정

코드는 보존하되 `SsalddelExecution:Mode`, feature flag, 권한과 운영 profile로 차단한다.

## 4. 마무리 실행안

### 1단계 — 기준점 동결 (1~2일)

1. 신규 기능과 신규 화면 추가를 중단한다.
2. 현재 변경을 기능 코드, test, 문서, 생성 이미지, 로컬 산출물로 분류한다.
3. 검수되지 않은 생성 이미지는 공개 asset으로 간주하지 않는다. 대표 자산만 승인 상태로 DB/Blob에 게시한다.
4. 공개 profile을 하나로 정한다.
   - 권장: `0.0 커뮤니티·공공데이터 + 읽기 전용 가격·무역 정보`
   - 나머지 버전은 `Simulation` 또는 비활성
5. 공개 서버의 feature flag를 선택한 profile과 일치시킨다.

### 2단계 — Release Candidate 정리 (3~5일)

첫 구조 정리에서 다음 세 가지 불일치를 해소했다.

1. 친구 요청 진입점 test를 실제 ‘내 정보’ 화면 책임과 일치시켰다.
2. 창고 루트 test를 실제 운영 홈으로 위임하는 현재 구조와 일치시켰다.
3. 지역별 농산물 가격 비교 route 2개를 capability catalog에 명시했다.

전체 test 4,066개 통과 상태를 기준점으로 삼고 다음을 수행한다.

- 전체 test 통과 상태를 유지한다.
- 0.0 Release build와 관련 Web/MAUI 소비 project build를 통과시킨다.
- 전체 route를 `공개`, `프리뷰`, `체험`, `준비 중`, `숨김` 중 하나로 분류한다.
- 운영 profile에서 sample seed, memory adapter, 개발용 권한 fallback이 사용되지 않음을 검증한다.
- 관리자 시작 화면은 커뮤니티·공공데이터 운영을 중심으로 유지하고, 패키지별 관리 화면은 해당 capability가 활성일 때만 노출한다.

### 3단계 — 운영 증거 확보 (6~8일)

- 보호된 staging 환경에서 migration 적용, backup, restore rehearsal을 한 차례 수행한다.
- 포털 → 지도/지역 → 가격 정보 → 게시판 → 참여/원장 조회의 대표 사용자 여정을 검증한다.
- 커뮤니티 글·댓글·신고·연락처 공개와 철회 권한을 확인한다.
- Web과 Android의 대표 경로를 실제 렌더링으로 확인한다. iOS를 검증하지 못하면 “미검증”으로 명시하고 프리뷰 종료를 막지는 않는다.
- secret, API key, 개인정보와 원문 공공데이터가 source·log·capture에 남지 않았는지 확인한다.
- health, DB, 외부 공공데이터 실패가 sample 성공으로 위장되지 않는지 확인한다.

### 4단계 — 공개·보존 (9~10일)

1. 체크리스트를 추측이 아니라 test, capture, log, 배포 URL 증거로 판정한다.
2. `Known Limitations`, 운영 profile, backup/restore, 장애 시 되돌리기 문서를 확정한다.
3. 대표 화면과 이미지 중 검수된 것만 장기 자산으로 남긴다.
4. 종료 기준을 모두 충족한 commit에 release tag를 붙인다.
5. 미완 항목은 “나중에 고쳐야 할 현재 제품 결함”이 아니라 `후속 실운영 전환 backlog`로 이동한다.

## 5. 최종 종료 기준

아래 항목이 모두 충족되면 프로젝트 마무리로 판정한다.

- [ ] 공개 제품 명칭, 범위와 URL이 README·화면·배포 설정에서 일치한다.
- [ ] 전체 test가 4,064개 이상 모두 통과한다.
- [ ] 0.0 Release build와 공개되는 역할 WebApp build가 통과한다.
- [ ] 포털, 01~05 URL과 live/ready health가 통과한다.
- [ ] 공개 서버 feature flag가 승인된 공개 profile과 일치한다.
- [ ] 대표 사용자 여정의 실제 Web/Android 렌더 증거가 있다.
- [ ] 운영 profile에서 sample fallback과 외부 효과가 비활성이다.
- [ ] staging migration·backup·restore rehearsal 증거가 있다.
- [ ] 개인정보 공개·철회·신고와 관리자 접근 경계가 검증됐다.
- [ ] 공개 이미지에는 승인 상태, 출처/생성 정보와 DB/Blob URL이 연결돼 있다.
- [ ] 알려진 제한, 미검증 플랫폼과 후속 backlog가 문서화돼 있다.
- [ ] 작업 트리가 의도한 source 기준으로 정리되고 재현 가능한 release commit/tag가 있다.

## 6. 마무리를 막지 않아야 할 항목

다음은 의미 있는 후속 과제지만 이번 프리뷰의 종료 조건으로 두지 않는다.

- 456개 안팎의 모든 화면을 같은 수준으로 시각 개선하는 일
- 생성 예정 이미지 전체를 공개하는 일
- 2.0~3.5의 실운송·실창고·실판매 운영 승인
- 실제 결제·정산·계약과 모든 외부 사업자 연동
- iOS App Store와 각 역할별 독립 앱의 동시 출시
- 모든 국가의 행정·상품·무역 코드와 공공데이터를 한 번에 연결하는 일
- 모든 0.5~3.5 시나리오의 실사용 운영 증거

이 항목들을 종료 조건에 포함하면 살뜰은 계속 확장되지만 끝나지 않는 프로젝트가 된다.

## 7. 최종 산출물

마무리 시에는 다음 일곱 가지가 남아야 한다.

1. 공개 프리뷰 포털과 대표 사용자 여정
2. 커뮤니티·공공데이터 중심 관리자
3. 공개/프리뷰/시뮬레이션 capability 목록
4. 전부 통과한 자동 test와 Release build 기록
5. migration·backup·restore 및 장애 대응 기록
6. 검수된 대표 화면·이미지와 알려진 제한 문서
7. 재현 가능한 release commit/tag와 후속 실운영 전환 backlog

## 8. 최종 제안

살뜰의 마무리는 코드를 줄이거나 지금까지의 확장을 부정하는 일이 아니다. 이미 만든 0.5~3.5 흐름은 “앞으로 갈 수 있는 통합 설계와 시제품”으로 보존하고, 지금 사람들이 실제로 이해하고 사용할 수 있는 커뮤니티·지도·문화·가격·공공데이터 경험만 명확하게 공개하는 일이다.

따라서 앞으로의 기본 질문을 “무엇을 더 만들까?”에서 다음으로 바꾼다.

> **이 기능은 공개 프리뷰에 필요한가, 이미 증명됐는가, 아니면 후속 자산으로 보존할 것인가?**

이 기준으로 10일 안팎의 동결·정리·검증을 마치면, 부족한 부분을 숨기지 않으면서도 살뜰을 하나의 완결된 공개 프리뷰로 마무리할 수 있다.
