# 음식점 주문 거절·조리·픽업 준비 상태 전이

- 날짜: 2026-07-28
- 대상: `RestaurantDeskApp`, 음식 주문 contract·Command·RDB 상태 이력
- 화면 확인: Windows MAUI 로그인 화면 직접 확인, 보호된 진행 변경 화면 간접 확인

## 변경

- 음식점 수신함에서 정확한 주문번호를 다시 조회한 뒤 주문 수락 또는 사유가 있는 거절을 선택한다.
- 수락된 주문은 조리 예상 시간을 다시 변경할 수 있고, 실제 조리가 끝난 시점에 픽업 준비 완료를 기록한다.
- 음식점 거절은 `거절` 종료 상태로 분리해 주문자 안내와 배차 후보에서 제외한다.
- 기사 픽업·전달은 기사 앱의 기존 책임으로 유지한다. 음식점 화면은 픽업 준비까지만 확정한다.

## 서버 상태와 멱등성

- 허용 전이는 `주문대기 → 거절`, `조리중 → 조리중(시간 변경)`, `조리중 → 픽업대기`다.
- 음식점 수락과 진행 변경은 인증된 음식점 처리자만 기록하며 요청 본문의 처리자 값은 신뢰하지 않는다.
- 상태 이력에 주문별 `클라이언트요청Id` 고유 인덱스와 처리 사용자 ID를 저장한다.
- 같은 수락 요청을 다시 보내도 배차 생성 이벤트를 다시 발행하지 않는다.
- 상태 변경 뒤 커뮤니티 원장 Outbox와 음식점 SignalR 상태 알림을 후속 처리한다.

## 주문 상품 스냅샷 보완

공개 메뉴 검증에 사용한 메뉴 ID를 RDB 음식 주문 상품에도 저장한다. 메뉴명과 단가
스냅샷뿐 아니라 원본 공개 메뉴 참조를 함께 유지해 이후 품절·조리·분쟁 확인에
사용할 수 있다.

## 실제 화면 확인 제한

`RestaurantDeskApp.exe`를 다시 실행해 WebView DOM, 계산된 style, WebView 자체
capture와 일반 Windows 창 capture를 비교했다. `/login` 화면은 두 capture에서
정상 렌더됐고, 이전 흰 화면은 최초 capture 시점의 WebView2 표면 합성 문제로
확인했다.

다만 이번 재확인에서는 음식점 계정으로 로그인해 거절·조리시간 변경·픽업 준비
버튼을 다시 조작하지 않았다. 실제 테스트 계정과 관계형 DB의 상태 전이·앱 재시작
복구는 통합 E2E 범위로 유지한다.
