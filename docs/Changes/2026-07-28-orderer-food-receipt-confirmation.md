# 기사 전달과 주문자 음식 수령 확인 분리

- 날짜: 2026-07-28
- 대상: `OrdererApp`, `FDriverApp`, 음식 주문 contract·Command·RDB 상태 이력
- 화면 확인: 공용 UI와 세 소비 앱 빌드로 간접 확인

## 변경

- 음식 배달 기사의 전달 완료와 주문자의 실제 수령 확인을 서로 다른 음식 주문 상태로 분리했다.
- 기사 앱은 기존처럼 전달 완료 후 서버 업무공간을 다시 조회하며, 이 행동은 주문을 `전달완료`로 기록한다.
- 주문자 상세는 기사 전달과 주문자 확인을 두 단계로 보여 주고, 전달 완료 뒤에만 `음식 수령 확인` 버튼을 활성화한다.
- 주문자가 확인하면 같은 음식 주문번호 상세와 현재 목록 page를 다시 조회해 `수령확인` 상태를 표시한다.
- 배차 실패와 추천 만료는 주문 취소나 환불로 자동 해석하지 않고 기존 복구 안내를 유지한다.

## 서버 경계

- 수령 확인 API는 인증된 사용자 ID로 음식 주문 소유권을 검사하며 요청 본문의 주문자 ID를 받지 않는다.
- `전달완료` 이외 상태에서는 수령 확인을 거부한다.
- 상태 이력에 주문자, 클라이언트 요청 ID, 선택 메모와 확인 시각을 저장한다.
- 같은 클라이언트 요청 ID의 재시도는 상태와 원장 동기화 Event를 중복 생성하지 않는다.
- 새 상태는 기존 음식 공동 원장 Outbox와 음식점 SignalR 알림으로 후속 반영한다.

## 검증

- 음식·Food·주문자 공용 UI 관련 테스트 306개 통과
- 주문자 수령 확인 소유권, 전달 전 차단, 요청 ID 멱등성, Event 단일 발행과 같은 주문번호 재조회 확인
- `OrdererApp`, `RestaurantDeskApp`, `FDriverApp` Windows target: 각각 경고 0, 오류 0

## 실제 화면 확인 제한

수령 확인 버튼은 인증된 주문자의 `전달완료` 주문에서만 나타난다. 이번 작업에서는
별도 실제 관계형 DB와 테스트 계정으로 해당 상태를 다시 만들지 않았으므로 대표
PNG를 보존하지 않았다. 실제 앱 조작과 재시작·토큰 만료를 포함한 검증은 `P0-D`
통합 E2E에서 이어간다.
