# 음식점 주문 수신함 재시작·재연결 복구

- 기준일: 2026-07-28
- 대상: `RestaurantDeskApp`, 음식 주문 수신함 API
- 검증 성격: 별도 로컬 E2E DB, 실제 테스트 계정/API 폐쇄 루프, Windows MAUI 직접 확인

## 반영 결과

음식점 수신함의 기본 대상을 `전달완료`와 `취소` 전까지의 미처리 주문으로
명시했다. API는 로그인 claim의 음식점 범위를 유지하면서 처리상태,
`UpdatedAfterUtc`, page와 page size를 받아 최근 변경 순으로 반환한다.

앱은 시작할 때 서버 수신함을 먼저 읽고 SignalR에 연결한다. 실시간 수신,
일반 서버 재조회와 재연결 직후 재조회를 typed 복구 출처로 구분하되 모두 같은
`OrderNo` 항목에 upsert한다. 재연결되면 음식점 그룹에 다시 가입한 직후
30초를 기다리지 않고 서버 수신함을 확인한다.

수신함이 100건을 넘으면 다음 page까지 순서대로 읽고, 전체 snapshot을 받은
경우에만 로컬에서 사라진 주문을 정리한다. 동시에 발생한 주기 조회와 재연결
조회는 직렬화해 늦게 끝난 과거 응답이 최신 목록을 덮지 않도록 했다.

30초 조회 한 번이 실패해도 마지막 정상 목록을 유지하고 다음 주기에 다시
시도한다. 401은 로그인 복구, 403은 음식점 소유권·운영자 역할 오류로 분리해
업무를 잠근다. 서버가 401을 반환하면 refresh token으로 access token을 한 번
강제 갱신하고 원래 요청을 한 번만 다시 보낸다. 403은 재시도하지 않는다.

SignalR 주문 알림은 로컬 설정의 음식점 ID를 신뢰하지 않고, 인증된 음식점
상세 API에서 같은 주문을 확인한 뒤 수신함과 알림음에 반영한다. 따라서
운영자 계정의 서버 claim과 샘플 appsettings 값이 다르더라도 정당한 주문을
누락하지 않으며, 다른 음식점 주문은 서버 범위 조회에서 확인되지 않아
반영되지 않는다.

## 실제 앱 확인 범위

기존 개발 DB를 변경하지 않도록 별도 로컬 E2E DB를 만들고 주문자, 음식점
운영자, 음식 배달 기사 테스트 계정을 실제 인증 API로 등록했다. 음식점 101과
기사 역할·프로필은 해당 DB에만 로컬 fixture로 연결했다. 비밀번호와 token은
추적 파일 및 이 기록에 남기지 않았다.

테스트 주문 `FOOD-20260728075353260`은 음식점 앱이 실행되지 않은 상태에서
등록했다. 서버 수신함 복구, 음식점 수락, 기사 추천·수락, 픽업 완료, 전달 완료를
차례로 실행했고 최종적으로 음식 주문 `전달완료`, 배차 `배달완료`, 운송
`인수완료`, 기사 활성 업무 0건을 확인했다. 실행 모드는 `Simulation`이므로
추천 상태는 별도 E2E fixture로 만들었고 운영 자동 배차를 실행하지 않았다.

Windows용 `RestaurantDeskApp`에서 실제 음식점 계정으로 로그인한 뒤 업무
모드와 `신규 주문 수신함`을 열었다. 화면에는 인증된 음식점 이름, 실시간 연결,
서버 미처리 주문 복구와 30초 보완 조회가 표시됐으며 완료 주문만 남은 상태는
샘플 대체 없이 빈 수신함으로 렌더됐다.

Windows용 `FDriverApp`에서도 실제 기사 계정으로 지도 업무에 로그인했다.
로그인 기사와 역할, 실시간 연결, 30초 보완 조회, 대기·추천 0건, 진행 중인
배달 없음이 실제 서버 상태와 일치했다. 이 과정에서 공통
`기사운행Controller`의 운행 시작·위치 API가 실행 feature key 미분류로
차단되는 문제를 재현했다. 후속 보완에서는 공통 route를 국내 화물 경계로
분류하고, FDriverApp은 같은 운행 Command를 사용하는 음식 배달 전용 route로
전환했다. 음식 배달 자동 추천 표시도 국내 화물이 아니라
`FoodDeliveryWorkflow`를 확인한다.

실제 계정으로 운행 시작·종료 route를 다시 호출하면서 MySQL 재시도 전략과
충돌하던 사용자 트랜잭션도 확인했다. 관계형 변경은 `SaveChanges`의
트랜잭션을 사용하고, 별도 업무 큐·기사 상태 저장은 기존 멱등 갱신 경계를
유지하도록 잘못된 외형적 트랜잭션을 제거했다.

운행 시작 Command에는 기존 운송 실행 프로필의 음식 배달·화물 운송 유형을
전달한다. 음식 배달 시작은 공통 대기·위치 상태만 준비하고 Opinet과 화물
추천을 사용하는 즉시 화물 배차 효과는 실행하지 않는다. 음식 배달 기사의
대기는 앱 식별자가 포함된 위치 heartbeat 이후 음식 배달 정책에서 후보로
판정한다.

이번 후속 보완은 인증·복구·상태 동기화 연결을 수정한 작업이라 새로운 시각
디자인은 없다. 실제 Windows 렌더는 직접 확인했지만 저장소에 새 PNG를
보존하지 않았고, 위 Figma 이미지는 계속 설계 기준으로만 사용한다.
